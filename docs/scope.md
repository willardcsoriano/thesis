## Critical Path

Three tracks run in parallel. Two of them — Build and Ethics — must both finish before the **Pilot study** can run, and one of those sits behind a hard external gate. The third produces results without waiting on either.

- **Track A — Build** (paced by our own velocity, no external gate): LoRA fine-tuning script → Model export → Go Runtime complete (Session logger `[x]`, Confirmation gate `[x]`, Undo log in particular) → Ollama connectivity check passes → SynapseOS machine + other two machines provisioned → Screen capture software installed and tested.

- **Track C — Algorithm** (no external gate, and no dependency on Track B): A1 effect model + labelled corpus → A2 compositional recoverability classifier → A3 evaluation. Independence from IRB is the point rather than a side effect — D29 chose a contribution that evaluates against a corpus specifically so a results chapter exists whether or not ethics approval lands on time, and D32 makes it the manuscript's RQ1. **Convergence:** Track A ∧ Track B → Custom cross-platform task suite finalized + OSWorld benchmark setup verified → Pilot study → instrument/task revisions → Main study → Log parser / Metric computation / Anonymization / Statistical analysis → Qualitative coding → Final Thesis Compilation. ## Software — Go Runtime (SynapseOS)

These are features of the SynapseOS binary that the paper explicitly describes. All live in the Go runtime.

- `[x]` **CLI mode** — one-shot invocation (`synapse "<task>"` → proposed command → classify → auto-run or confirm → execute → exit), no persistent session; formalized as a permanent shipped mode rather than TUI scaffolding (D19). **Done and validated live 2026-07-12** — all three stages (propose, classify, execute) demonstrated against Ollama with real auto-run, block-and-cancel, and block-and-confirm-then-run paths (see `prototype/build-order.md` M1)
- `[x]` **Conversational TUI** — full-screen persistent chat interface (bubbletea + lipgloss); accepts NL input, renders responses and command output; wraps CLI mode's already-working intent parser, classifier, and executor rather than rebuilding them. **Done Session 28** (`synapse tui`, `internal/tui`) — the propose/classify/confirm/execute loop is injected and driven, never reimplemented, so safety gating is identical across modes; adds token streaming, terminal-native scrollback (inline, no alternate screen, D38), and the confirmation gate rendered as UI. See `prototype/build-order.md` M5. **Caveat kept visible:** a TUI needs a real TTY, so this is the one deliverable no automated test can exercise end-to-end — `prototype/manual-tests/m5-tui-mode.md` is the verification path.
- `[~]` **GUI-mode session launch** — the existing TUI launched fullscreen as an XFCE session, layered *over* the participant's ordinary desktop; this is Condition A as actually run in the study, rather than `synapse tui` at a terminal. **Rescoped by D27:** SynapseOS no longer replaces the desktop shell, session manager, or application launcher, so none of those is a deliverable — what remains is session plumbing (an `.xsession`/session-manager entry) on top of the runtime seams M5/M6 already established. **Built 2026-09-26:** `distro/synapseos.desktop`, `distro/synapseos-session`, `distro/install-session.sh`; not yet tried through a real login/logout cycle. See `prototype/build-order.md` M8, and D11/D12 for the study-condition and substrate reasoning this supersedes
- `[ ]` **GUI-mode XFCE fallback** — participant-accessible path back to the XFCE session running underneath, if SynapseOS becomes unresponsive or the participant wants to stop mid-task; every invocation logged (participant ID, task ID, timestamp) as its own telemetry event type, separate from the six events below (see D20). Under D27 the desktop beneath was never taken away, so this is ordinary window management rather than crash recovery — its telemetry requirement is unchanged, since fallback reliance is still a confound the study has to measure
- `[x]` **Intent parser client** — sends user utterance + session context to Ollama REST API; streams response tokens back to the TUI. **Done Session 28** — non-streaming `Generate` (M1) plus `GenerateStream` (M5 step 4, NDJSON token-by-token). Streaming is opt-in per mode: TUI streams, CLI/REPL deliberately do not (`docs/interface-modes.md`). A stream ending without a completion marker is rejected outright rather than returned short, so a truncated generation can never reach the classifier as a valid-but-different command.
- `[x]` **Bash execution engine** — dispatches shell commands as subprocesses via `os/exec`; captures stdout/stderr and surfaces the exit code. **Done 2026-07-12** (`internal/executor`), delivered via CLI mode first (`prototype/build-order.md` M1, previously scoped as a standalone M2); captures rather than streams for now — streaming to a live session is TUI-mode scope (M5), reusing this same package
- `[x]` **Confirmation gate** — classifies pending commands as reversible/irreversible before dispatch; blocks irreversible commands pending explicit user approval. **Done 2026-07-12** (`internal/classifier`), delivered via CLI mode first (`prototype/build-order.md` M1, previously scoped as a standalone M3), reused by the TUI. **Rule set substantially extended since** (F1: `sed -i`/`awk -i inplace`/`truncate`/unsafe `tee`; F3/D22: recursive `chmod`/`chown`, fetch-decode-exec, bare `eval`) — see `prototype/build-order.md` F1/F3 and `../docs/decisions.md` D22 for the current full rule set
- `[~]` **Undo log** — records reversible operations; exposes an undo command that restores prior system state. **Mechanical half done** (F2, `internal/undo`, `synapse undo`) and **extended to confirmed irreversible commands too** (F5: content-backup, hardlink-based trash, metadata backup, and git-reset-SHA capture — see `../docs/safety-model.md` for the full mechanism-per-shape taxonomy). **Telemetry half done Session 31** (M7): `synapse undo` emits an `undo_invoked` event on every outcome — applied, declined, and failed — since a participant who tried to recover and could not is a finding, not an absent record
- `[x]` **Session logger** — writes structured log entries for every event: task start, command issued, command output, undo events, confirmation gate triggers, task end. This is the source of all telemetry data the study depends on. **Done Session 31** (`internal/telemetry`, wired into `runLoop` via `withTelemetry` and into `synapse undo`). JSON Lines, one event per line, flushed per event so a crash loses at most the final line; a nil logger is a no-op so non-study runs are unaffected and no call site needs a branch. Enabled by `SYNAPSE_SESSION_LOG` + `SYNAPSE_PARTICIPANT`; a set log path with no participant code is a startup error rather than unattributable telemetry.
- `[x]` **Telemetry fields logged per event** — all six event types emitted end-to-end through the real loop and covered by `cmd/synapse/telemetry_loop_test.go`; `exit_code`, `latency_ms`, and `approved` are pointers so that a zero exit code, a zero latency, and a declined confirmation are recorded rather than omitted:
  - Timestamp (ms precision)
  - Event type (task_start / command_issued / command_result / confirmation_triggered / undo_invoked / task_end)
  - Command string (the bash command generated)
  - Execution latency (ms from dispatch to stdout/stderr capture)
  - Task ID (links events to the task prompt that caused them)
  - Participant ID (anonymized code, set at session start)
  - Condition (A = SynapseOS, B = native OS — always A for this logger)
  - Note: intent parsing accuracy is **not** its own logged field — it's a derived metric, computed offline by the Intent Parsing Accuracy Evaluator (Python Build Pipeline) by cross-referencing the logged command string + task ID against human-annotated ground truth. Section 1.1c's "system performance data... captured automatically" refers to this raw data, not a live accuracy score.
- `[x]` **Session context manager** — maintains in-memory conversation history; passes prior turns as prompt context to Ollama; rolling window when context approaches the budget; truncates verbose bash output before appending — never stores raw verbose output at full length (D10). **Done Session 29** (`internal/session`, wired into REPL and TUI via `withSessionContext`; one-shot CLI stays stateless by design, D19). Verified live: "rename it to renamed.txt" resolves *it* to the previous turn's file. Adds `context` and `clear` so a user can check what a pronoun would bind to before issuing a destructive follow-up, and announces evicted turns rather than forgetting silently.
- `[x]` **Ollama connectivity check** — verifies Ollama is running at `localhost:11434` on startup; fails gracefully with a user-readable error if not. **Done and validated live 2026-07-12** (`internal/ollama.Client.Ping`, unit-tested against an unreachable server) — see `prototype/build-order.md` M1

## Software — Algorithm Track (Recoverability Analysis)

The thesis's algorithmic contribution (D29; D32 makes it the manuscript's RQ1). These are graded and defended as the contribution, not as supporting tooling, and none of them is gated on IRB approval — the evaluation runs against a labelled command corpus, not against participants. The problem statement, the formal model, the argument for why the current pattern list cannot be extended into it, and the full evaluation design live in `algorithms.md`; milestone sequencing lives in `prototype/build-order.md`'s Algorithm Track (A1–A3). Only the deliverables are listed here.

- `[x]` **Shell AST parsing** (A1) — an *adopted* shell parser (`mvdan.cc/sh/v3`, bash dialect, with its word-expansion package), not a written one. Listed because something must produce the tree, and recorded in `algorithms.md`'s adoption ledger because writing a shell grammar is solved, tedious, and not the contribution
- `[x]` **Command effect model** (A1) — derives, per leaf command, the effects it would have resolved against a working directory: which paths are created, written, removed, or changed in metadata, with a `MovedTo` refinement for renames and moves. Argument-aware and existence-aware, because flags and state change effects (`rm -i`, `cp -n`, `chmod` with and without `-R`, `cp` onto an existing file). Composition rules propagate effects through `&&`/`||`/`;`, pipelines, subshells, conditionals, loops, redirects, command and process substitution, `sh -c`, `sudo` and its relatives, `xargs`, and `find -exec`, with an overlay so earlier parts of a line are visible to later ones. **Built 2026-09-20 as `internal/effects`, with unit tests; wired into the gate through `internal/gate`, on by default in strict mode (`SYNAPSE_ANALYSIS=strict|capture|off`; `off` restores the list alone).** Package and service state is modelled rather than left as a limitation: `internal/effects/pkgstate.go` asks the system's own tools (`apt-get -s`, `dpkg-query`, `apt-cache policy`, `dpkg-deb -f`, `systemctl is-active`/`is-enabled`) what a command would do and derives an inverse command (install to purge, remove or purge to a versioned install where a repository still offers the version, upgrade to downgrade, start and stop, enable and disable, mask to unmask). Maintainer scripts and service start-up side effects, network mutations, and other package managers (pip, npm, snap) are not modelled and stay unrecoverable unless plainly read-only. The per-command rule table is itself a list, and is stated as such (D34)
- `[~]` **Labelled recoverability corpus** (A1) — about 450 commands stratified by command shape and effect kind, with ground truth defined relative to a stated filesystem state per command (a fixture specification), ground-truth verdicts, and, where applicable, recovery plans; sourced from NL2Bash (Lin et al. 2018; partition N), templates covering each shell operator and shape (partition T), and an external partition (E) that is never executed and is labelled unrecoverable by construction; per-source partitions are kept separate rather than pooled. **Ground truth is automated, with no human labellers and no second annotator:** `internal/oracle` runs each command in a bubblewrap sandbox on its fixture and labels it from the tree diff (recoverable if nothing that existed was lost; removal, overwrite, replacement, retargeting, and re-moding count as loss; same-inode moves are not loss; mtimes and `.git` internals are ignored), and `cmd/corpusgen` builds the corpora sharing no code with `internal/effects`. Seed 20260922 gives the development corpus (`prototype/pilot/corpus4.jsonl`) and seed 20260923 the held-out one (`corpus5.jsonl`). A 74-command single-annotator hand-labelled pilot corpus also exists (`prototype/pilot/`). No inter-rater agreement figure is reported, because no human labels are compared; that is a stated consequence of the choice. Any chapter text that still promises two annotators must be brought into line
- `[~]` **Compositional recoverability analysis** (A2) — the contribution itself, as narrowed by D34: composition through wrappers and resolution of run-time targets by read-only dry runs, feeding a verdict and a capture plan, failing closed on anything not determined. Complements the pattern list rather than replacing it: the list is always consulted and the analysis can add a confirmation, never remove one. Package and service state is modelled by asking the system's own tools what a command would do (see the effect model above); process, account, and firewall state remain outside the model and always ask. **Built and wired into the confirmation gate, on by default in strict mode; not yet evaluated on the held-out corpus, so the deliverable is not complete**
- `[~]` **Minimal recovery-plan computation** (A2) — the problem statement's second output: for a recoverable-with-capture verdict, select the cheapest sufficient mechanism per effect and drop redundant captures, so "minimal" is something the evaluation can measure rather than a claim. The mechanisms themselves are adopted (hardlinks, git, XDG trash, file copies); this selects among them. **Built as part of `internal/effects` (plan and verdict), with `internal/gate` carrying the plan out through `internal/undo` at run time; package and service changes are captured as inverse commands (`undo.Entry.Inverses`), which `Apply` runs after trash and before content restore, with elevated privilege if the original had it, and prints the command if one fails**
- `[~]` **Recoverability evaluation harness** (A3) — runs the analysis and the baselines over the corpus (the shipped pattern-list classifier, a list flipped to fail closed, and a full pre-emptive working-directory snapshot as the trivial upper bound) and reports the metric set fixed in `algorithms.md` before any results existed, with silent loss reported on its own rather than folded into accuracy. Capture coverage is verified by executing in a sandbox and diffing, not asserted from the plan. **Partly built:** `cmd/listpilot` and `pilot/analyze.py` run and score three systems over a corpus; the sandboxed execute-and-diff (`internal/recoverycheck`) and the automated development corpus exist; the held-out result and the McNemar and Holm computations do not yet
- `[~]` **Depth pass on §3.1 of the manuscript** (A3) — the algorithm's methodology section was two pages against roughly thirty for the interface and user study. A primary contribution needs a methodology proportionate to the claim: corpus construction, labelling protocol, inter-rater procedure, baselines, and per-metric rationale. **Extended 2026-09-20** with corpus sizing, a state-relative labelling requirement, three baselines, capture coverage as a metric, and the statistics; the depth remains an outstanding deliverable until the results exist

## Software — Data Collection and Analysis

Scripts that process raw study data into results.

- `[ ]` **Task normalization** — standardizes task descriptions and expected outcomes across the OSWorld benchmark suite and the custom task suite into a consistent evaluation format (Section 2.2), so both suites can be scored the same way
- `[ ]` **Safety mechanism validation** — pre-study test pass verifying (a) every irreversible operation in the task set triggers the confirmation prompt and none execute without approval, and (b) a representative set of reversible operations can be undone with correct state restoration (Section 2.3); a build/test task, not just a chapter description
- `[ ]` **Log parser** — reads SynapseOS session logs; extracts per-task metrics: completion time (task_start → task_end delta), error events (typed: intent parsing error / execution error / recovery failure, per Section 3.3b), undo events, confirmation events, conversational turns per task (derived from command_issued event counts per task ID)
- `[ ]` **Metric computation script** — computes task completion time, error rate (Failed + Incorrect Outcomes / Total Task Attempts, per Section 3.3b), broken out by error type, SUS scores (standard formula: odd items: score−1; even items: 5−score; sum × 2.5), NASA-TLX composite (average of six subscales)
- `[ ]` **Anonymization step** — replaces all participant identifiers with participant ID codes before any analysis; runs before any output file is written
- `[ ]` **Statistical analysis script** — Shapiro-Wilk normality test; paired-samples t-test or Wilcoxon signed-rank (depending on normality result); Cohen's d effect size; descriptive statistics (mean, SD, 95% CI) per condition per group; **novice vs. power-user subgroup analysis and the condition × group interaction effect (primary analysis, per D5's dual-population design — not exploratory)**; subgroup analysis by OS type (Windows/macOS/Linux) as exploratory; correlation of prior AI exposure (frequency) with SynapseOS performance metrics, also exploratory (see D15)
- `[ ]` **Screen capture setup** — recording software configured on both the SynapseOS machine and the baseline machine before the study begins; output synced to participant session IDs

## Infrastructure — Hardware

Three physical machines required for the lab setup.

- `[ ]` **SynapseOS machine** — x86-64, 8 GB RAM recommended, 10 GB storage, XFCE desktop environment (X11 session) required as the host desktop SynapseOS layers onto; runs SynapseOS in GUI mode (fullscreen conversational interface) on a Debian 13 (Trixie) base (see decision D12). **Under D27 the XFCE session is not an invisible substrate** — it keeps running underneath, remains the participant's fallback target, and is not replaced. The Debian/XFCE choice is a methodological necessity rather than a finding: an agent layer that observes and acts on a desktop session needs a platform that permits it, and the proprietary platforms do not (D28)
- `[ ]` **Windows 11 / Linux (GNOME) dual-boot machine** — x86-64 hardware chosen for mainstream Linux driver support; Windows 11 and a mainstream distro (Ubuntu 24.04 LTS recommended) installed on separate partitions with boot-menu OS selection; standard user account on each OS, no custom software beyond what a typical user would have. Facilitator boots to the OS matching the participant's assignment before the session begins (see D9) — no runtime switching.
- `[ ]` **macOS machine** — Apple Silicon or Intel Mac; macOS (current release); standard user account. Kept as a dedicated machine rather than dual-boot or virtualized: Linux hardware support on Apple Silicon is unreliable, and macOS's license prohibits virtualizing macOS itself on non-Apple hardware.
