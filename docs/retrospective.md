## Overview

This is the project's process log — a chronological account of *how* work got done across working sessions with Claude Code, distinct from `session.md` (*what* changed, deliverables-oriented) and `decisions.md` (*why* an architecture choice was made). Its specific job is capturing friction: the blockers, wrong turns, and near-misses that came up mid-session, what actually resolved each one, and what the reusable lesson is — so the same mistake doesn't get rediscovered from scratch next time. Read `session.md` first for a changelog of results; come here when the question is "why did that take so long" or "what should I watch out for before doing something like this again." Organized by working session, newest first within each entry's own chronological narrative.

## Session 22 — Manual M2 Testing, Classifier Gap, Undo Log, Doc-Authority Shift

**Thread of thought, in order:**

1. Wanted to actually *use* the CLI-mode binary against real files rather than trust the prior session's live-run claims at face value. Set up a plain, ordinary test folder (`~/synapse-test/`) — had to correct a loose word choice ("sandboxed") that implied something more exotic than "kept out of the git repo."
2. Ran real move/delete/multi-step tasks successfully, which raised the sharper question: what does "it works" actually mean, in testable terms? That question is what eventually produced `testing-plan.md`.
3. A direct question — "should we limit the agent to just moving/opening files, not editing?" — prompted actually *testing* the classifier against `sed -i`/`tee`/`truncate`/`cp`-overwrite instead of reasoning about it abstractly. All four came back `Reversible` (auto-run, no confirmation) despite being as destructive as `rm`. This was the session's real finding, and it only surfaced because it was tested, not inspected.
4. That finding opened a much bigger conversation: should SynapseOS reimplement filesystem-MCP-style typed operations instead of raw bash? Re-derived the answer from scratch (product-first, not by citing D7) rather than treating the prior decision as settled — landed in the same place (hybrid, typed-ops gated on an unverified reliability question) but now for verified reasons, not inherited ones.
5. That, in turn, surfaced a real inconsistency in `build-order.md`: M8 (Undo log) was gated on M7 (Session logger) for a reason that only applied to *half* of what M8 was scoped to do. Split it once the actual dependency was traced through.
6. The user then explicitly challenged whether project docs should be treated as constraints at all, given the thesis is a living document, not the frozen submitted snapshot. This produced a real policy change (`CLAUDE.md`), not just a one-off answer — worth noting as the moment this repo's own "docs are revisable" culture got made explicit and binding rather than implicit.
7. Closed the loop by actually building what the analysis called for: classifier hardening (F1), a real disk-persisted undo mechanism (F2), and the test plan design (`testing-plan.md`, F3/F4 not yet built) — then verified F2 *live*, not just via unit tests, specifically because the earlier "it works" ambiguity was the whole reason this session started.
8. A late, unprompted tangent ("isn't Rust more suited for this?") got a real answer instead of a deflection — re-ran the language comparison per-component rather than pointing at D8 (which never actually compared Go to Rust in the first place).

**Blockers hit, worth flagging individually (see also the quick-reference table below):**

- **`os.Exit()` buried inside loop logic made it untestable.** `runAdHoc`'s core loop called `os.Exit()` at four points, which would kill the test process if exercised directly. Required extracting `runLoop` with injected I/O/confirmation/return-code before any test could be written — this was actually Session 21's work, but the same shape of problem (business logic entangled with process-exit or terminal I/O) is worth watching for early in any future package, since retrofitting it is a real, if small, refactor.
- **A destructive-then-confirm ordering bug in the undo command's own design.** First draft of `runUndo` popped the journal entry *before* asking whether to apply it — meaning declining would silently and permanently lose the undo record. Caught before shipping by asking "what happens on the 'no' path" explicitly, and fixed by adding a non-destructive `PeekLastJournal` separate from `PopLastJournal`. General lesson: any confirm-then-mutate flow needs its declined path designed on purpose, not left as "whatever the code happens to do."
- **Directory-diffing undo needed an explicit, honest scope boundary.** Correctly reconstructing a `mv` without parsing bash syntax (glob expansion isn't visible to Go code ahead of execution) could have turned into an open-ended parsing project. Scoped it deliberately: one level of recursion into newly created directories, pairing by basename, anything that doesn't cleanly pair left "unhandled" rather than guessed at. The discipline that mattered: decide and document the boundary *before* writing code, not discover it by shipping something subtly wrong.
- **Widening a core function's signature broke every existing test call site.** Adding `journalPath` to `runLoop` was a one-line design decision that touched 8 separate test functions. Mechanical but worth remembering: a shared internal API's tests are often the most expensive part of changing its signature, not the change itself.
- **A Markdown heading landed at the wrong nesting level.** Inserting a new `### Foundational Hardening` section into `build-order.md` first came out as `##`, breaking the document hierarchy (would have shown as a sibling of "Runtime Milestones" instead of a child). Caught by grepping the heading structure right after the edit rather than trusting the diff alone — worth doing that check by default whenever restructuring a doc with several nesting levels, since a misplaced heading doesn't produce an error, just a wrong document.

## Sessions 20–21 — .gitignore Privacy Rework, PR Shipping, Ollama Client/Loop Tests

**Thread of thought, in order:**

1. Started from a privacy request (keep `.gitignore`'s Claude-related entries out of the immediately-visible top of the file) and iterated twice — first just reordering within the custom section, then genuinely burying the entry mid-file once asked to go further.
2. Burying it mid-file collided with `/gitignore`'s own auto-managed block (a large fetched region that gets wholesale-replaced on every refresh) — the entry would have been silently deleted next time that command ran. Rather than accept the loss, extended the `/gitignore` command itself (a global, cross-project file) to recognize a "pinned custom" marker it preserves across refreshes.
3. Moved to shipping four unrelated pending concerns (tests, a doc update, the gitignore/session-untracking change, and pre-existing thesis content) as separate, purpose-scoped PRs, per this project's one-commit-per-concern convention.
4. Along the way, built the actual regression test suite for `internal/ollama` and `cmd/synapse`'s orchestration loop that this whole thread had been circling — closing the gap between "I ran it once live" and "there's reproducible evidence it works."

**Blockers hit:**

- **`git stash show -p` silently omits untracked files.** Needed to split eight unrelated pending changes (four tracked, three new/untracked) across four separate branches. `git stash push -u` stashes untracked files fine, but the standard way to inspect/reapply a stash (`git stash show -p`, or plain `git checkout <stash> -- <path>`) only reaches the *tracked*-file diff — untracked file content lives in a separate, less-discoverable parent commit of the stash (`stash@{0}^3`). Cost real time rediscovering this. **Lesson, concretely: `git checkout stash@{0} -- <path>` for tracked files; `git checkout stash@{0}^3 -- <path>` for files that were untracked when stashed.**
- **A branch that forked before an earlier PR merged can silently undo it.** The pre-existing `docs/thesis-ufo2-bifurcation` branch had forked before the PR that untracked `docs/session.md` was merged into `main`. Left as-is, merging it back would have resurrected `session.md` as tracked, quietly reversing already-shipped work — this isn't caught by a normal content diff, only by checking file-*tracking-state* consistency (`git ls-files <path>` on the stale branch) before merging. Had to add a small carry-along commit once noticed.
- **A sandbox flag (`go run -C <dir>`) triggered an unexpected directory reset, not a real error.** Using `-C` to point `go run` at a different directory printed a benign-looking "Shell cwd was reset to..." line that turned out to be the sandbox re-asserting its allowed root, not program output. It wasn't obvious at first that this was infrastructure noise rather than a bug. **Lesson: prefer `cd <dir> && ./binary` or an absolute-path binary invocation over directory-changing flags, inside this sandboxed environment specifically** — plain `cd` is respected; flag-based directory changes on external tools may not be.

## Blockers & Lessons — Quick Reference

| Blocker | Area | Root cause | Fix applied | Avoid next time by |
|---|---|---|---|---|
| Stashed untracked files invisible to `git stash show -p` | Git/tooling (PR shipping) | Untracked content lives in the stash's 3rd parent commit, not its main diff | `git checkout stash@{0}^3 -- <path>` | Default to this form whenever a stash mixes tracked + untracked changes |
| `/gitignore`'s managed block silently overwrites manual edits placed inside it | Git/tooling (.gitignore rework) | The command does a wholesale replace of everything between its markers on every refresh | Added a "pinned custom" marker the command now detects and preserves | Never hand-edit inside a tool-managed region without first checking whether the tool supports pinning/preserving it |
| A stale branch's merge can silently resurrect a file an already-merged PR untracked | Git/tooling (PR shipping) | The stale branch forked before that PR merged, so its tree still has the old tracked state | Small carry-along commit re-applying the untracking on the stale branch | Before merging any long-lived branch, diff its file *tracking state* (`git ls-files`) against current `main`, not just content |
| `go run -C <dir>` produced a confusing sandbox reset message | Sandbox/environment | The sandbox treats directory-changing flags differently from an actual `cd` | Built the binary once, invoked it by absolute path from within a `cd`'d directory | Prefer `cd && run`/absolute-path invocation over directory-changing CLI flags in this environment |
| `runAdHoc`'s loop called `os.Exit()` internally, making it untestable | Prototype — test suite (Session 21) | Process-control (`os.Exit`) was mixed into business logic instead of isolated at the outermost caller | Extracted `runLoop`, injected I/O/confirmation, returns an int instead of exiting | Keep `os.Exit`/direct terminal I/O out of any function that contains logic worth unit testing |
| First `synapse undo` design lost the journal entry on a declined confirmation | Prototype — F2 (undo log) | Popped (destructively removed) the entry before confirming the user wanted it applied | Added non-destructive `PeekLastJournal`, only `Pop` after confirmation | For any confirm-then-mutate flow, explicitly design the "declined" path before writing the "confirmed" path |
| A new Markdown section landed at the wrong heading level | Docs — Foundational Hardening track (`build-order.md`) | Manual heading-level entry, not caught by the diff view | Grepped the heading structure post-edit, fixed the level | Grep `^#+` after any edit that restructures a multi-level doc, don't trust the diff alone for hierarchy correctness |
