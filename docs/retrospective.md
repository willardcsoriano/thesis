## Overview

This is the project's process log — a chronological account of *how* work got done across working sessions with Claude Code, distinct from `session.md` (*what* changed, deliverables-oriented) and `decisions.md` (*why* an architecture choice was made). Its specific job is capturing friction: the blockers, wrong turns, and near-misses that came up mid-session, what actually resolved each one, and what the reusable lesson is — so the same mistake doesn't get rediscovered from scratch next time. This is the file to read for a start-to-finish, blockers-included audit of how a milestone actually got built, not just whether `build-order.md` currently marks it done. Read `session.md` first for a changelog of results; come here when the question is "why did that take so long" or "what should I watch out for before doing something like this again." Organized by working session, newest first within each entry's own chronological narrative — currently covers Sessions 17 through 31, i.e. the full history of the prototype from M1's first line of code onward. Session 29's entry was reconstructed after the fact from `build-order.md` and `decisions.md` rather than written at the time, and is marked as such. Sessions 1–16 predate the prototype (thesis-writing only) and aren't covered here.

## Session 33 — Measuring Before Rewriting, Twice, and Getting It Wrong Once

**Resolved from `open-problems.md`:** row 14 (no working-directory grounding). `loopSystemPrompt` never stated the cwd, so "here" and "this folder" resolved to nothing and the model emitted literal placeholders — `du -sh /path/to/folder`. Fixed by stating the directory in the step prompt and forbidding placeholder paths. Layer 7's plain tier moved 50.0% → 66.7% and clean termination 66.7% → 91.7%, measured on the same 12-task suite before and after.

**The measurement instrument was broken before the thing it measured.** Layer 7's first widened run reported 50% at the plain tier. Two scoring defects were found before that number was reported: the score required `verify() && exitCode == 0`, which charged loop-termination defects to the phrasing; and three verifiers substring-matched the whole transcript, so `step 2:` satisfied "did it report 2" and a latency's `4` satisfied "did it report 4". Those tasks passed at every tier regardless of what the model did. The two errors had been cancelling out — the headline stayed 50% while technical moved 91.7% → 100%. **Lesson: when a result has the shape you expected, that is when to check the instrument, not when to relax.**

**A fix that shipped its own regression.** Adding the working directory routed first steps through a prompt trailer they had never seen — one ending "Output DONE if the task is already fully accomplished." The technical tier fell 100% → 58.3%, every failure reading "model reported nothing needs to be done": a phrasing like `du -sh .` already looks finished, so the model agreed it was. Root cause was two rendering paths for the same prompt, one of which no test covered. Collapsed to one path; DONE is now offered only when something has actually run.

**Concluding from one unread field.** A probe asked whether the coding-agent architecture — tool-calling as the fork between talking and acting — is viable here. It read Ollama's `tool_calls` field, saw 0 calls in 69 attempts at 3B and 23 at 7B, and the conclusion recorded was that the architecture was unavailable on this stack. That was wrong twice. `prior-art.md` had already recorded 0/20 from Session 25 and was not read first. And the measurement was one layer too high: a direct `curl` to `/api/chat` shows the model emitting well-formed tool calls as JSON **in the content field**, which Ollama never parses. `ollama show` confirms the model declares a `tools` capability whose template renders the offered tools.

Writing the tolerant parser that reads the content field took the fork rate from **0% to 91.3%** on the same model, same prompts, same corpus — including 100% on the trap register, conversational openers wrapped around real work. **Lesson: a negative result from a single field is a result about that field. Check one layer lower before concluding anything about the system.** The corrected finding is in `prior-art.md`; the parser is `internal/toolcall`.

**Scope discipline under review pressure.** A second adviser review asked six questions about the algorithmic contribution. The response briefly widened D29 from one algorithm to four decision procedures, promoting two candidates — risk-tiered gating, termination policy — that this project had itself rejected as "too thin alone". The stated justification (neither is standalone once an effect set exists) was not wrong, but it was assembled after the fact; what actually drove it was that four procedures answer "what specific algorithm?" more impressively than one. Withdrawn the same day, with the rejections restored unchanged. **Lesson: a contribution that grows in response to a question, rather than in response to something learned, is growing for the wrong reason.** What survived is the part that was a real gap — the effect semantics is now named as a formal model rather than left implicit in an approach paragraph.

**"Hello" was never handled.** Live testing found that a greeting returned the visual-tasks `UNSUPPORTED` message — the first thing any user types, answered with a non-sequitur about editing images. D31 had already decided capability questions were answered locally; the handler was never written. Now local and deterministic, with exact-match normalisation so "hi" is a greeting and "hi, delete the logs" stays a task.

## Session 32 — The First Conversational Test

- **The product had never been tested as a conversation.** Every live run to this point was a single one-shot `synapse "task"` invocation. Multi-turn behaviour, pronoun resolution, and the M6 session memory — the features that make the system conversational rather than a command translator — had been built, unit-tested, and never once exercised end to end by a person or by an agent. The first three-turn REPL run was the first time any of it ran together. **Lesson:** a feature's tests pass in the shape the tests were written in; the shape the *product* is used in is a separate thing that has to be exercised deliberately. "Conversational" was the central claim and was the least-tested path in the system.

- **That first conversation found a defect in a feature shipped an hour earlier.** The natural-language answer layer (D31) worked on the task whose command produced substantial output, and degenerated to echoing on the two that did not: `mv` produces no stdout and was answered with a bare filename; a one-line `ls` was answered by repeating that line verbatim. The prompt said "answer their request directly, using the actual values from the output", and a 3B model satisfied that instruction by the shortest available path. **Lesson:** an instruction that a large model reads as intent, a small model reads as a specification — and satisfies literally. Prompts for small models need the *shape* of the wanted answer, not a description of it.

- **The fix was shape plus examples, not more instruction.** Requiring a complete sentence, explicitly forbidding a bare filename or a copy of the output, and giving four worked request/output/reply triplets — including one where the output is empty and one where it is an error — produced correct answers on all three turns. **Lesson:** few-shot examples are cheaper and more reliable than prose rules at this model size; the empty-output and error cases are the ones worth spending examples on, because they are where the degenerate answer appears.

- **The evidence layer held throughout.** The raw command, its output, and its exit code still print above every answer, as `vision.md`'s principle requires. **Lesson:** worth re-checking on every change to the answer path, because the failure mode is silent — an answer that looks good is exactly when nobody notices the evidence beneath it has gone.

- **The repeated-failing-command loop was two defects, not one, and only one of them was the model's.** The model re-proposed an identical failing command until the step cap. The first cause was that a small model reads a transcript of failures as *context* but not as an *instruction* — naming the failed commands explicitly and telling it they will fail again changed the behaviour immediately, and live it began varying its approach instead of repeating. The second cause was the loop's own: it had no reason to keep spending steps on a command it had already watched fail, and now stops at the first repeat. **Lesson:** when a model misbehaves in a loop, check whether the loop is also complicit. The prompt fix alone would have left five wasted steps whenever the guidance failed to take, and guidance at this model size is a reduction in probability rather than a guarantee.

- **Fixing it broke a test that encoded the old behaviour.** `TestFailedTaskIsAlsoAnswered` scripted five *identical* failing commands to reach the step cap; with the repeat guard in place it now stops at step two, so the test failed on a path it was not written to exercise. Corrected by scripting five *distinct* failures, which is what that test actually meant. **Lesson:** a test that reaches its target state through the behaviour being changed is a test that will fail for the right reason and look like a regression. The fix is to make the setup say what it means.

- **The live run then exposed an adjacent defect the tests could not see.** With repetition fixed, the model reached `UNSUPPORTED` — and the response told the user the request "isn't something a shell command can do… not visual tasks like editing images", when the actual situation was that the folder did not exist. `UNSUPPORTED` is carrying two meanings, *outside shell capability* and *impossible in this environment*, and the message only fits the first. **Lesson:** fixing one failure path routinely routes traffic onto another that was previously unreachable, and the second one has never been exercised. Re-run the original failing case after the fix, not just the test.

## Session 31 — M7 Shipped Logging Nothing, and the Shell Underneath Was Lying About Exit Codes

**Thread of thought, in order:**

1. Built M7 — the study's session logger — as a new `internal/telemetry` package, wired it into `runLoop` and `synapse undo`, covered it with tests, and marked the milestone done.
2. The user ran the binary. It logged nothing for tasks. `studyLogger` was being called from the `undo` subcommand and from nowhere else, so no task ever opened a log at all. Every automated test was green throughout.
3. Fixing that led into the executor, where two more defects were sitting under the same "tested, marked done" label — the interpreter was not the one the model's prompt assumes, and pipelines were reporting the wrong exit status.
4. Then five TUI defects, every one of them found by the user in live use and none by the test suite, plus a pre-existing data race found while reading that code.
5. Closed on the paper, where the errors were arithmetic rather than logical — and were also caught by the user rather than by the edits that introduced them.

**Blockers and findings:**

- **M7 was built, wired, tested, and logged nothing — and the test that was supposed to prove otherwise tested the wrong half of the seam.** The integration test called `runLoop` with `withTelemetry` itself, which verifies that the loop emits events when handed a logger, and says nothing about whether any entry point ever hands it one. It never did. This is the identical failure class as Session 30's TUI bugs: a test that constructs its own inputs exercises the callee and leaves the caller untested by construction. Worse, the failure had already been *named in writing* in this repo two sessions earlier — the `num_ctx` wire-level test in Session 29 exists because "a helper that builds the right map but is never wired in would pass a unit test and still leave every prompt truncated." The anticipation did not transfer to the next feature. **Lesson: writing a failure mode down does not defend against it; the only defence is at least one test that enters through the real entry point, for every feature that has to be switched on from somewhere else.**
- **The shell underneath was not the shell the prompt assumed, and the symptom looked like model error.** `/bin/sh` is dash on Debian, so bash-only syntax — which the system prompt explicitly asks the model to emit — was rejected by the interpreter. In the transcript that is indistinguishable from the model proposing a broken command, which is precisely the quantity this thesis exists to measure. Fixed by executing through `bash -o pipefail -c`. **Lesson: an environment failure and a model failure produce the same transcript. Before attributing a failure rate to the model, verify what interpreter, version, and flags its output is actually being run under.**
- **A pipeline reported success for a failed pipeline, and the bias ran in the flattering direction.** Without `pipefail`, `ls /missing | wc -l` exits 0 — only the last stage's status survives. The study's headline metrics include execution-error rate, so this was not a neutral defect: it silently moved the number in the direction that makes the system look good, which is the direction nobody audits. **Lesson: when a bug distorts a measurement, establish which way it distorts before ranking its severity — a defect that flatters the system is more dangerous than one that embarrasses it, because only the embarrassing one gets investigated.**
- **The fix needed its own escape hatch, and the escape hatch needed to stay auditable.** Under `pipefail`, an early-exit pipeline (`find … | head -1`) kills its producer and exits 141, so 141 is normalised to 0 — but the raw exit code and a `sigpipe` flag are both preserved in the telemetry record. **Lesson: when a measurement pipeline normalises a value, log the raw value beside it. A normalisation nobody can audit after the fact is indistinguishable from a fudge, and study data is exactly where that distinction has to hold.**
- **Five TUI defects, all found by a person, none by a heavily-covered test suite** — a duplicated command echo (`UNSUPPORTEDstep 1: UNSUPPORTED`), the CLI's timeout preamble leaking into the transcript, a blank gap above the prompt, a header truncating mid-sentence, and no scrolling at all. This is the second consecutive session where live use found everything and the tests found nothing, and the class is consistent: these are properties of what the screen *looks like*, and no assertion was ever written for them because layout is not what unit tests are pointed at. **Lesson: for an interface, "covered" and "correct" are close to unrelated — the manual suite is not a formality to be retired once coverage is high, it is the only instrument aimed at the thing being built.**
- **Mouse support fixed scrolling and silently took text selection away.** Enabling mouse reporting hands the terminal's pointer to the program, and drag-to-select goes with it. The trade was made without being flagged; it is now opt-in via a `mouse` command, default off. **Lesson: enabling a terminal capability removes a capability the terminal already provided. When a fix trades one affordance for another, the trade *is* the decision — surface it, rather than absorbing it into the fix.**
- **`tea.WithMouseCellMotion()` does not exist in bubbletea v2.** Mouse is view state (`v.MouseMode`), not a program option. A v1 API would have shipped unchecked. This is the third distinct Charm v2 drift finding in this repo, after the module path moving off `github.com/charmbracelet/…` to `charm.land/…` and the documented `Focus()`-inside-`Init()` example being wrong in context. **Lesson: for this dependency specifically, treat every remembered API as v1 until verified against the installed version — the v2 line changed enough that recall is a liability rather than a shortcut.**
- **A flaky test was written and then deleted rather than stabilised.** A program-level test waiting for task output in rendered terminal bytes failed roughly one run in ten under `-race`, because bubbletea v2 repaints differentially and the bytes are not guaranteed to contain the string on any given frame. The same path was already covered deterministically at the `Update` level. **Lesson: a flaky test that duplicates existing deterministic coverage is strictly worse than no test — it spends attention on every run and buys nothing that is not already guaranteed elsewhere.**
- **Three name collisions in a single test-writing pass** (`runProgram`, `step`, `streamingOllamaServer` all already existed). Small, but it cost a compile-fix cycle each time. **Lesson: grep the package for a helper's name before writing it; in a test file, the odds that the obvious name is taken are high precisely because the obvious name is obvious.**
- **A pre-existing data race, found by reading rather than by a failing test: the Ctrl+C interrupt watcher wrote to the same stream the running task was writing to.** Both now share a mutex. The watcher was added for an out-of-band concern and inherited none of the in-band path's discipline. **Lesson: a stream handed to two goroutines is shared state like any other. Any writer added for an out-of-band concern — signals, timeouts, progress reporting — needs the same synchronisation as the writer it is interrupting.**
- **The paper's numbers stopped adding up, and per-edit verification structurally could not have caught it.** Three separate instances, all caught by the user: keywords pushed to six against a guideline that caps them at five; the abstract pushed to 299 words against a 200-word limit; and, after the sample size changed, "40 participants" still sitting beside "Novice n=20 / Power users n=10." Every individual edit was correct — each verified the string it was replacing. None of them could have verified that the document still added up afterwards, because that is a property of the whole document and not of any edit. **Lesson: an edit-level assertion says nothing about document-level arithmetic. After any batch of edits that touches counts, limits, or sample sizes, run a numeric-consistency sweep as its own separate pass — it is the only thing that catches a figure that went stale three edits ago.**

## Session 30 — M5's First Real Terminal Run Found Two Bugs Every Automated Test Missed

**Thread of thought, in order:**

1. Handed `manual-tests/m5-tui-mode.md` to a human for the first time — the suite written precisely because a TUI cannot be driven by piped input and the build environment has no TTY.
2. Step 1 failed immediately. The pasted screen showed a streamed word split vertically (`UNS` above `UPPORTED`) and lines printed out of source order (`model reported…` above the `step 1:` line that precedes it). At that moment `internal/tui` was at 96.3% coverage across 27 tests, clean under `-race`, with several mutation-verified.
3. Diagnosed both, wrote failing tests first, then fixed; mutation-verified each fix by reintroducing the bug and confirming the new test fails.

**Blockers and findings:**

- **A test asserted the bug was correct behavior, and passed for years of sessions doing so.** `appendTranscript` treated every chunk of output as a complete line. That is true of the loop's own status writes (`step 1: …\n`) and false of streamed model tokens, which arrive as bare fragments. The test covering it appended newline-less strings like `"line 0"`, `"line 1"` and asserted each became its own transcript line — encoding exactly the wrong invariant. Coverage was high, the test was green, and it was green *because* it agreed with the defect. Replaced with `appendChunk(lines, open, chunk)`, which carries whether the last line is still being written to. **Lesson: coverage measures which lines ran, never whether the assertion describes the behavior you want. A test written from the implementation rather than from the requirement will ratify whatever the implementation does.**
- **A concurrency bug hid behind a decision made two sessions earlier for good reasons.** `startTask` returned `waitForEvent(m.events)` without having consumed an event, so a second goroutine began receiving from the same channel and delivery order to `Update` became undefined — and it compounded, since every task started added another receiver. Session 28's entry above records moving the TUI tests off the full program and onto direct `Update` calls to kill a race that made tests flaky (11s flaky → 0.05s deterministic). That was the right call for flakiness and the wrong one for coverage: it removed the only harness that could observe a *real* race. **Lesson: when you remove concurrency from a test to make it deterministic, you have also removed its ability to detect a concurrency defect. Something else must then cover the ordering property — a structural invariant asserted directly, or an integration test through the real path — or the coverage is silently gone.**
- **Neither bug needed a TTY, which invalidated the standing excuse for M5's weaker verification.** Session 28 recorded prominently that TUI mode is the first deliverable unverifiable without a human. True, but it became a blanket explanation covering things it did not actually cover: `appendChunk` is a pure function, and the listener-count invariant is a property of a returned value. Both were fully testable headlessly all along. **Lesson: a genuine environmental limitation will quietly absorb blame for gaps that have nothing to do with it. State precisely what the limitation blocks — rendering, color, flicker, human timing — and treat everything outside that boundary as normally testable.**
- **The missing test was of the path output actually takes.** Every existing test handed `Update` a message the test itself constructed; none went writer → `msgWriter` → events channel → `Update` → transcript. Added `TestTaskOutputReachesTheTranscriptInSourceOrder`, which drives that whole path under the runtime's own single-listener protocol and asserts both symptoms directly. Both bugs are mutation-verified against it. **Lesson: when every test synthesizes its own inputs, the seams between components are untested by construction — and the seams are where integration bugs live.**
- **Manual testing paid for itself on its first run.** The suite exists because of an environmental constraint, and it found two real defects in code marked complete, test-covered, and reviewed. Worth recording as evidence for keeping the `manual-tests/` convention rather than letting automated coverage stand in for it.

## Session 29 — A Silent 2048-Token Ceiling, and Milestone Numbers That Described a Plan Nobody Followed

*Reconstructed after the fact, and deliberately narrow.* This session was missed when the retrospective was last written up; the entry below is limited to what `build-order.md` (M6's build sequence, F6, V1, M8's first rescope), `decisions.md` (D10's amendment), and `scope.md` actually record. Anything that happened in this session and left no trace in those files is not recovered here rather than guessed at.

**Thread of thought, in order:**

1. M6 (session context) was next in the build order, and its first prerequisite turned out to be a live defect rather than new work: Ollama's default `num_ctx` is 2048 and it truncates prompts **silently**, so the effective context window was a quarter of what D10 had assumed and nothing in the system was reporting it.
2. Fixed that alone, as its own step, before building anything on top of it — then built `internal/session` as a pure, dependency-free type, wired it into `runLoop` via a variadic option, and only then into REPL and TUI with the `context`/`clear` affordances.
3. Turned the same scrutiny on `build-order.md` itself: renumbered the milestones to match the order things were actually built, added F6 and V1 as real items, and rescoped M8 downward.

**Blockers and findings:**

- **A dependency's default was silently destroying data the system depended on.** Nothing in the runtime set `num_ctx`, so every prompt was being clipped at 2048 tokens with no error, no warning, and no observable symptom other than the model behaving slightly worse than it should. Worst-case prompts were already around ~1.5K tokens, so it was close to biting before cross-task history existed at all. Verified by measurement through our own client against the live server — the same oversized prompt went from `prompt_eval_count` 2050 to 5532 — not by reading a configuration reference. **Lesson: a default that silently truncates is worse than one that fails, because failure is reported and truncation is not. Verify the *effective* value of any inference-time parameter against the live service, and route every call site through one options builder so a setting cannot be present on one path and quietly absent on another.**
- **The test written to guard that fix named, in advance, the bug the next feature shipped.** It is a wire-level assertion that `num_ctx` actually reaches the request body, written because "a helper that builds the right map but is never wired in would pass a unit test and still leave every prompt truncated." Two sessions later, `internal/telemetry` shipped exactly that: correct package, correct loop wiring, never switched on from the entry point. **Lesson: a failure mode written into a doc protects only the feature it was written for. Carrying it forward means a standing rule — every feature that must be switched on from somewhere else needs one test that enters through the real entry point — not a note in the file where it was first noticed.**
- **A prompt-design bug that every automated test passed and only a live run caught.** With cross-task history wired in, the follow-up "rename it to renamed.txt" returned `DONE` immediately, because `loopSystemPrompt` told the model that already-run commands indicate progress on the current task — so it read the *previous* task's steps as having finished the *current* one. The tests assert that history reaches the prompt; nothing asserts what the model concludes from it. Fixed by naming the two prompt sections explicitly and adding a rule that a task with no steps yet can never return `DONE`, then verified live against the file on disk. **Lesson: a test that checks the prompt was assembled correctly says nothing about whether the model reads it correctly — every prompt change needs a live check, because the prompt's consumer is not deterministic.**
- **The milestone numbers had been encoding an abandoned plan for months.** Execution and the confirmation gate were numbered as post-TUI milestones and were in fact built first, inside CLI mode, long before any TUI existed; reading the sequence top to bottom gave a plan that had been revised rather than a project that had been built. Renumbered, with a full old→new mapping table so every prior reference still decodes. **Lesson: when stable identifiers stop describing reality, the cost of renumbering is one mapping table written once; the cost of leaving them is every future reader silently decoding the wrong history. Accuracy of the record beats stability of the identifiers.**
- **An experiment's verdict had been sitting with no owner, which is how it would have lapsed.** F4 concluded "adopt typed operations for the bounded file-manipulation subset" and `internal/typedops` had existed and been tested since Session 25 — but it was never wired into `runLoop`, and the entry describing that gap called it "unscoped future work." F6 exists to force the call. **Lesson: a finding with no work item and no done-when is a note, not a decision — and the default outcome of a note is that nothing happens and nobody remembers choosing that.**
- **Four manual suites existed and two had never been run.** Every milestone verifies itself; nothing verified that the assembled system works for a person sitting in front of it — and the interactions between features (a task that streams, hits a confirmation, gets undone, then is referred back to) are exactly where a system like this breaks. V1 exists for that, and its first instalment paid out the very next session. **Lesson: per-milestone verification is structurally blind to interactions between milestones; the whole-system pass has to be its own scheduled item or it never happens.**

## Session 28 (second half) — M5 Built End to End (TUI Mode), and a Review That Found a Real Safety Defect

**Thread of thought, in order (second half of the session — M5 steps 3–5):**

1. Wired the real execution loop into the TUI (step 3). The architectural decision was the whole of this step: `runLoop` is synchronous and blocks mid-flight to ask a y/n question, while bubbletea's `Update` must never block. Reimplementing the loop as a TUI state machine would have been the idiomatic-looking answer and was rejected — it duplicates safety-critical gating, exactly what `interface-modes.md` forbids. Instead the identical `runLoop` is injected as a `TaskRunner` and driven on a goroutine, bridged by two channels. Net result worth stating plainly: every reversibility verdict, confirmation gate, and undo-journal write in TUI mode is literally the same code CLI and REPL run, so gating cannot drift between modes.
2. Added streaming (step 4) as a new `GenerateStream` on the Ollama client, opt-in per mode via a variadic `loopOption` — chosen specifically because this file's own earlier entry records that widening `runLoop`'s signature cost eight test call-site edits. The variadic form left every existing caller untouched.
3. Added viewport scrollback and lipgloss styling (step 5), which the plan had labelled the "purely cosmetic" step and which turned out not to be.
4. Closed with the milestone's manual test suite, per the convention established earlier in the session.

**Blockers and findings, M5 steps 3–5:**

- **The first TUI test pass was inherently racy, and the symptom was subtle rather than obvious.** Driving the whole program with scripted input bytes means the program consumes input as fast as it can parse it, which races the task goroutine publishing its confirmation request. The tell was two near-identical confirmation tests disagreeing — one passing, one failing — rather than an outright hang. Rewrote the confirmation and lifecycle tests to drive `Update` directly with constructed messages, keeping full-program tests only where real terminal input parsing is genuinely the thing under test. Runtime went from ~11s flaky to 0.05s deterministic. **Lesson: when a test's outcome depends on which of two concurrent producers wins, the fix is to remove the concurrency from the test, not to add sleeps to it.**
- **A test hung for the full timeout inside `httptest.Server.Close()`, not inside the code under test.** A handler blocked on `r.Context().Done()` deadlocks `Close()`, because a server that never finished writing a response does not reliably observe the client's disconnect. Fixed with an explicit release channel whose `defer` is registered *after* `defer server.Close()`, so LIFO ordering unblocks the handler first. **Lesson: when a hang appears after adding a test, check whether it is the test harness's teardown rather than assuming the new production code is at fault.**
- **A safety property emerged from streaming that was not in the plan.** A stream ending without a `done: true` marker is now rejected outright rather than returned as a short result — because the returned text becomes a shell command, and truncation does not merely shorten it, it can *change* it: a connection dropped partway through `rm -rf /home/user/tmp` yields the perfectly valid, catastrophically different `rm -rf /home`. Mutation-verified. **Lesson: when adding an incremental-delivery mechanism to something that produces executable output, "partial" is not a degraded version of "complete" — it is a different and possibly worse instruction.**
- **The step labelled "purely cosmetic" carried a real correctness property.** Scrollback is not just presentation: new output must auto-scroll only while the user is already at the bottom, never while they have scrolled up to read — and scroll keys must stay live during a pending confirmation, since scrolling back to check what a command actually proposes is precisely what someone needs before approving an irreversible step. **Thread of thought, in order:**

1. Refined M5's roadmap before writing code, verifying every technical claim it would rest on rather than planning from training data. **Blockers hit:**

- **`synapse undo` was gated behind an Ollama connectivity check — the safety net was unavailable exactly when it was most likely to be needed.** `main()` called `client.Ping()` unconditionally before dispatching *any* subcommand, so `undo` — a pure filesystem operation over the journal, trash, and content backups, with zero model involvement — refused to run whenever the model backend was down. The failure scenario is the exact one undo exists for: a destructive command has already run, and Ollama has since crashed, been stopped, or the machine rebooted. Verified concretely (`SYNAPSE_OLLAMA=http://localhost:9999 ./bin/synapse undo` → exit 1) rather than inferred from reading. This dated to M1/F2 and survived every prior session's testing because manual testing always had Ollama running — the failure mode only appears when it *isn't*. **Lesson: a safety mechanism's preconditions must be checked against the scenario it exists for, not the happy path it's usually exercised in. "Undo works" is not the same claim as "undo works when everything else is broken," and only the second one matters.** Fixed by dispatching model-free subcommands before the connectivity check.
- **M4's persistence turned a harmless behavior into a real one, silently.** No signal handling existed anywhere in the codebase — fine in one-shot CLI mode, where Ctrl+C killed a process that was about to exit anyway. But M4 made the process long-lived without revisiting that, so Ctrl+C during a task destroyed the entire session, precisely the thing M4 exists to keep alive; combined with the 120s step timeout, one hung command could hold a session hostage with no escape but killing everything. Not a failure against M4's stated done-when (which only promised clean exit on EOF/`exit`/`quit`) — a genuine scope gap that a lifecycle change introduced without anyone noticing. **Lesson: when a change alters a component's lifetime, re-audit behaviors that were previously safe *because* the lifetime was short.**
- **A test written to verify the interrupt fix was itself broken, and caught its own bug.** The first version fired the simulated interrupt the instant signal handling was installed — before the task's command had started — so cancellation landed on the preceding HTTP propose call instead, desynchronizing the scripted mock responses and hanging the run for the full 30s timeout. Fixed by delaying the interrupt until the command is genuinely running. **Lesson: a test for cancellation has to pin down *what* is being cancelled, not just that a cancel happened.**
- **The upstream framework's own documented example contained a bug for this use case.** Bubble Tea's docs put `textinput.Focus()` inside `Init()`. That compiles, but `Init` can only return a `Cmd` — it cannot mutate the model the runtime holds — so the focus lands on a discarded copy and the input silently ignores every keystroke. Caught by two failing tests showing an empty input value no matter what was typed. **Lesson: copying a documented example is not verification; the test that proves the example works in your context is.**
- **Two tests passed for the wrong reason and needed strengthening, found by mutation-testing rather than by reading them.** `TestQuitsOnCtrlC` did catch a broken quit binding, but only by hitting a 5-second watchdog and reporting `context deadline exceeded` — it asserted on an unrelated property, and its real signal was elapsed time, which nothing checked. Rewritten to assert explicitly that the program terminated on its own, failing in 2s with a clear message. **Lesson, reinforcing the standing norm: mutation-test every test that guards a behavior you actually care about; "it passes" and "it would fail if the behavior broke" are different claims.**
