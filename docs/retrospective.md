## Overview

This is the project's process log — a chronological account of *how* work got done across working sessions with Claude Code, distinct from `session.md` (*what* changed, deliverables-oriented) and `decisions.md` (*why* an architecture choice was made). Its specific job is capturing friction: the blockers, wrong turns, and near-misses that came up mid-session, what actually resolved each one, and what the reusable lesson is — so the same mistake doesn't get rediscovered from scratch next time. This is the file to read for a start-to-finish, blockers-included audit of how a milestone actually got built, not just whether `build-order.md` currently marks it done. Read `session.md` first for a changelog of results; come here when the question is "why did that take so long" or "what should I watch out for before doing something like this again." Organized by working session, newest first within each entry's own chronological narrative — currently covers Sessions 17 through 28, i.e. the full history of the prototype from M2's first line of code onward. Sessions 1–16 predate the prototype (thesis-writing only) and aren't covered here.

## Session 28 — M3b Built End to End (TUI Mode), and a Review That Found a Real Safety Defect

**Thread of thought, in order (second half of the session — M3b steps 3–5):**

1. Wired the real execution loop into the TUI (step 3). The architectural decision was the whole of this step: `runLoop` is synchronous and blocks mid-flight to ask a y/n question, while bubbletea's `Update` must never block. Reimplementing the loop as a TUI state machine would have been the idiomatic-looking answer and was rejected — it duplicates safety-critical gating, exactly what `interface-modes.md` forbids. Instead the identical `runLoop` is injected as a `TaskRunner` and driven on a goroutine, bridged by two channels. Net result worth stating plainly: every reversibility verdict, confirmation gate, and undo-journal write in TUI mode is literally the same code CLI and REPL run, so gating cannot drift between modes.
2. Added streaming (step 4) as a new `GenerateStream` on the Ollama client, opt-in per mode via a variadic `loopOption` — chosen specifically because this file's own earlier entry records that widening `runLoop`'s signature cost eight test call-site edits. The variadic form left every existing caller untouched.
3. Added viewport scrollback and lipgloss styling (step 5), which the plan had labelled the "purely cosmetic" step and which turned out not to be.
4. Closed with the milestone's manual test suite, per the convention established earlier in the session.

**Blockers and findings, M3b steps 3–5:**

- **The first TUI test pass was inherently racy, and the symptom was subtle rather than obvious.** Driving the whole program with scripted input bytes means the program consumes input as fast as it can parse it, which races the task goroutine publishing its confirmation request. The tell was two near-identical confirmation tests disagreeing — one passing, one failing — rather than an outright hang. Rewrote the confirmation and lifecycle tests to drive `Update` directly with constructed messages, keeping full-program tests only where real terminal input parsing is genuinely the thing under test. Runtime went from ~11s flaky to 0.05s deterministic. **Lesson: when a test's outcome depends on which of two concurrent producers wins, the fix is to remove the concurrency from the test, not to add sleeps to it.**
- **A test hung for the full timeout inside `httptest.Server.Close()`, not inside the code under test.** A handler blocked on `r.Context().Done()` deadlocks `Close()`, because a server that never finished writing a response does not reliably observe the client's disconnect. Fixed with an explicit release channel whose `defer` is registered *after* `defer server.Close()`, so LIFO ordering unblocks the handler first. **Lesson: when a hang appears after adding a test, check whether it is the test harness's teardown rather than assuming the new production code is at fault.**
- **A safety property emerged from streaming that was not in the plan.** A stream ending without a `done: true` marker is now rejected outright rather than returned as a short result — because the returned text becomes a shell command, and truncation does not merely shorten it, it can *change* it: a connection dropped partway through `rm -rf /home/user/tmp` yields the perfectly valid, catastrophically different `rm -rf /home`. Mutation-verified. **Lesson: when adding an incremental-delivery mechanism to something that produces executable output, "partial" is not a degraded version of "complete" — it is a different and possibly worse instruction.**
- **The step labelled "purely cosmetic" carried a real correctness property.** Scrollback is not just presentation: new output must auto-scroll only while the user is already at the bottom, never while they have scrolled up to read — and scroll keys must stay live during a pending confirmation, since scrolling back to check what a command actually proposes is precisely what someone needs before approving an irreversible step. Both mutation-verified. **Lesson: be suspicious of a plan step pre-labelled low-risk; the label suppresses the scrutiny that would find the risk.**
- **TUI mode is the first deliverable that cannot be verified end-to-end without a human**, because bubbletea requires a real attached TTY and the build environment has none. Every prior milestone could be smoke-tested by piping input to the compiled binary; this one cannot. Recorded prominently in `build-order.md`, `scope.md`, and the manual suite itself rather than left implicit, so the completeness claim is not read as stronger than it is.

## Session 28 (first half) — M3b Started (Toolchain + Skeleton), and a Review That Found a Real Safety Defect

**Thread of thought, in order:**

1. Refined M3b's roadmap before writing code, verifying every technical claim it would rest on rather than planning from training data. That check paid off immediately and repeatedly: Charm's TUI libraries have an actively-developed v2 line requiring Go ≥ 1.25, and — a fact no documentation surfaced — **their module path moved off `github.com/charmbracelet/…` to `charm.land/…` entirely**. `go get github.com/charmbracelet/bubbletea/v2` fails outright. That was only discovered by running the command and reading the error; Context7's own docs still show the old URLs.
2. Executed the roadmap's step 1 (toolchain bump alone, no feature code) and step 2 (bare framework skeleton, no backend wiring), each verified independently before moving on.
3. On a model switch mid-session, ran a deliberate review of the already-"done" M2, M3a, and M3b work rather than continuing forward. This is what the session is actually notable for: it found a genuine safety defect in code that had been marked complete, test-covered, and manually verified across multiple prior sessions.

**Blockers hit:**

- **`synapse undo` was gated behind an Ollama connectivity check — the safety net was unavailable exactly when it was most likely to be needed.** `main()` called `client.Ping()` unconditionally before dispatching *any* subcommand, so `undo` — a pure filesystem operation over the journal, trash, and content backups, with zero model involvement — refused to run whenever the model backend was down. The failure scenario is the exact one undo exists for: a destructive command has already run, and Ollama has since crashed, been stopped, or the machine rebooted. Verified concretely (`SYNAPSE_OLLAMA=http://localhost:9999 ./bin/synapse undo` → exit 1) rather than inferred from reading. This dated to M2/F2 and survived every prior session's testing because manual testing always had Ollama running — the failure mode only appears when it *isn't*. **Lesson: a safety mechanism's preconditions must be checked against the scenario it exists for, not the happy path it's usually exercised in. "Undo works" is not the same claim as "undo works when everything else is broken," and only the second one matters.** Fixed by dispatching model-free subcommands before the connectivity check.
- **M3a's persistence turned a harmless behavior into a real one, silently.** No signal handling existed anywhere in the codebase — fine in one-shot CLI mode, where Ctrl+C killed a process that was about to exit anyway. But M3a made the process long-lived without revisiting that, so Ctrl+C during a task destroyed the entire session, precisely the thing M3a exists to keep alive; combined with the 120s step timeout, one hung command could hold a session hostage with no escape but killing everything. Not a failure against M3a's stated done-when (which only promised clean exit on EOF/`exit`/`quit`) — a genuine scope gap that a lifecycle change introduced without anyone noticing. **Lesson: when a change alters a component's lifetime, re-audit behaviors that were previously safe *because* the lifetime was short.**
- **A test written to verify the interrupt fix was itself broken, and caught its own bug.** The first version fired the simulated interrupt the instant signal handling was installed — before the task's command had started — so cancellation landed on the preceding HTTP propose call instead, desynchronizing the scripted mock responses and hanging the run for the full 30s timeout. Fixed by delaying the interrupt until the command is genuinely running. **Lesson: a test for cancellation has to pin down *what* is being cancelled, not just that a cancel happened.**
- **The upstream framework's own documented example contained a bug for this use case.** Bubble Tea's docs put `textinput.Focus()` inside `Init()`. That compiles, but `Init` can only return a `Cmd` — it cannot mutate the model the runtime holds — so the focus lands on a discarded copy and the input silently ignores every keystroke. Caught by two failing tests showing an empty input value no matter what was typed. **Lesson: copying a documented example is not verification; the test that proves the example works in your context is.**
- **Two tests passed for the wrong reason and needed strengthening, found by mutation-testing rather than by reading them.** `TestQuitsOnCtrlC` did catch a broken quit binding, but only by hitting a 5-second watchdog and reporting `context deadline exceeded` — it asserted on an unrelated property, and its real signal was elapsed time, which nothing checked. Rewritten to assert explicitly that the program terminated on its own, failing in 2s with a clear message. **Lesson, reinforcing the standing norm: mutation-test every test that guards a behavior you actually care about; "it passes" and "it would fail if the behavior broke" are different claims.**

## Session 27 — M3a Persistent CLI Loop, try-it.md Iteration

**Thread of thought, in order:**

1. Manual hands-on testing (`try-it.md`, built the previous session) surfaced a real ergonomics complaint: re-invoking the full `synapse '<task>'` command for every single test step was tedious enough that the human tester explicitly asked whether finishing M3a (persistent CLI loop) — next in the build order anyway — would make testing meaningfully easier before doing more testing.
2. Answered that as an explicit trade-off rather than just building it: M3a removes the *re-typing* friction but changes nothing about what's actually being tested (classification/confirmation/undo all work identically) — it's ergonomics now, not new coverage. Framed as a recommendation, not a decision, since it was pulling a milestone forward ahead of its scheduled turn.
3. Given the go-ahead, implemented `runREPL`: a loop wrapping the already-tested `runLoop` in a `for` reading one stdin line at a time, exactly as `build-order.md` had already scoped M3a to do — genuinely small, reuse-driven, no new subsystem.
4. While designing it, spotted a risk the milestone's own text names directly ("no leaked confirmation state, state carried correctly between iterations") but doesn't spell out the mechanism of: a persistent loop needs to read both task lines *and* confirmation-prompt answers from the same stdin stream, and `bufio.Reader` reads ahead into its own private buffer. Two independent readers over one underlying stream — one for tasks, a fresh one per confirmation, matching the original one-shot `confirm`'s existing pattern — would let one silently steal input meant for the other. Recognized this before writing the naive version, not after debugging a flaky test.
5. Verified the fix wasn't just "looks right" but actually caught the failure mode: wrote `TestRunREPLSharesOneReaderBetweenTasksAndConfirmations` (interleaves a task, its "y" answer, and a second task on one scripted stream), then deliberately reverted the implementation to the naive two-reader version and confirmed the test failed exactly as predicted (the "y" got swallowed, read as a declined "no") before restoring the correct version. Mutation-testing the fix, not just the happy path.
6. Closed with the doc sync this project always does after a build push — but discovered `prototype/README.md`'s status table had drifted badly: it still said F3/F4 were "up next" despite being done since Session 26, a staleness that predates this session and wasn't caught by earlier sessions' doc-sync passes because README.md wasn't in their explicit sync list.

**Blockers hit:**

- **A silent, self-caught missing-flag bug in the testing doc itself.** After wrapping each `try-it.md` command in per-step `script -c "..."` calls (per an earlier round of user-directed edits), realized without `-a`/`--append` each call would *overwrite* the shared log file rather than accumulate — silently losing every step but the last. Caught by re-reading the design rather than by a user report; fixed with one `sed -i` pass across all wrapped lines.
- **Multiple rounds of user course-correction on exactly which lines to wrap in `script -c`**, converging only after "wrap only the actual command lines, not `cd`/`ls`/`cat` checks, and don't restructure anything" was stated precisely. The general lesson: when a user's instruction is ambiguous between "wrap everything" and "wrap only the substantive part," the narrower, more literal reading is usually right, and confirming scope narrowly before a big mechanical edit avoids a revert-and-redo cycle.
- **A go-build success looked like a failure to the human tester.** `go build` prints nothing on success, so `script -a -c "go build ..." | Script started.../Script done.` with zero lines in between read as "did nothing happen?" to someone not already fluent in Unix conventions. Not a code bug, but a real doc gap — fixed by adding an explicit "silence means success, here's how to verify the binary exists" note, since the walkthrough's whole audience is a non-expert manual tester.
- **`prototype/README.md` had drifted out of sync with `build-order.md` for at least two milestones (F3, F4) without anyone noticing**, because it wasn't on the explicit list of files a prior doc-sync pass touched. General lesson: a doc-sync pass needs an explicit, complete list of "files that describe milestone status" checked every time (`build-order.md`, `README.md`, `roadmap.md`, `session.md` at minimum) — updating only the ones already open in context lets others silently rot.

## Sessions 23–26 — Foundational Hardening: Adversarial Classifier Corpus, Live-Model Testing, Typed-Ops Experiment, Guiltless Undo Hardening

**Thread of thought, in order:**

1. Continuing directly from Session 22's finding (content-mutating commands slipping past the classifier) and its resulting test plan (`testing-plan.md`), built out the plan's six layers in order: a categorized adversarial classifier corpus (danger categories, not just today's known shapes), a live-model-facing harness that checks the model's *actual* output distribution rather than hand-picked strings, an executor chaos/edge-case suite, and the typed-operations reliability experiment the plan had flagged as a genuinely open empirical question rather than a foregone conclusion.
2. The live-model harness (Layer 3) found a real gap the same day it was built, not a clean pass: `wget url && bash setup.sh` (download-then-run, no pipe) slipped past the existing piped-only fetch-exec classifier rule — fixed the same session by requiring proper token boundaries on both sides of the pattern.
3. The typed-operations experiment (Layer 4/F4) went in assuming Ollama's native tool-calling API would be the natural way to dispatch typed operations — checked empirically instead of trusting that assumption, and found native `tool_calls` never populated across the full 20-call test matrix. Real finding, not a configuration mistake: fell back to hand-parsed freeform JSON, which worked, and the reliability comparison (typed-ops vs. raw-bash-plus-classifier) still produced a clean, actionable verdict despite the tooling surprise.
4. A tester question ("can we make deletes technically undoable?") reopened the undo mechanism itself mid-session (F5, unplanned — grew past F1–F4's original scope). Before building a hardlink-based trash for `rm`, tested by hand whether the same approach would be safe for `cp`-onto-existing-destination too: `stat -c %i` before/after a real `cp` overwrite showed `cp` mutates the destination's *same* inode in place, meaning a hardlink taken beforehand would share the very data about to be overwritten and protect nothing. Corrected course before writing any code, not after finding a broken test.
5. Closed the remaining four known undo gaps (git reset --hard, git clean -f, recursive chmod/chown, dd/mkfs onto a regular file) the same session, each verified against real command behavior (`git clean -n`'s actual dry-run output format, `syscall.Stat_t`'s actual field names) via `go doc` or a live throwaway repo rather than assumed from memory.

**Blockers hit:**

- **A sandboxed environment blocked live verification of `git reset --hard` mid-task.** Treated as a signal to fall back on well-established, unambiguous git semantics for that one piece rather than forcing a workaround — not every claim needs a live reproduction when the underlying behavior is uncontroversial and documented.
- **A test's assumption about Unix permissions was wrong, not the code under test.** A test chmod'd a *directory* to `0555` expecting that to block modifying a file inside it; Linux only requires directory write permission for creating/deleting/renaming directory entries, not for truncating an existing file's own content. Fixed by chmod'ing the file itself. Lesson: when a permissions-based test doesn't fail the way expected, suspect the test's model of Unix permission semantics before suspecting the implementation.
- **`os.MkdirAll` can't create its own parents once given a restrictive mode.** Tests simulating "the backup directory isn't writable" first tried `os.MkdirAll(dir, 0o555)` directly, which fails because `MkdirAll` needs write permission on the parents it creates along the way. Fixed by creating with `0o755` first, then `os.Chmod`-ing to the restrictive mode as a separate step.
- **A display-layer gap only surfaced by writing the test, not by writing the feature.** `runUndo`'s preview output had lines for `ContentBackups` and `Trashed` but silently omitted `GitReset` and `MetadataBackups` — added in an earlier pass but never wired into the one function a user actually sees output from. Caught only because a test asserted on the exact preview text, not because anyone re-read the display code end to end. Lesson: a "does it look right" gap like this survives code review easily; only an assertion on actual rendered output catches it.

## Session 22 — Manual M2 Testing, Classifier Gap, Undo Log, Doc-Authority Shift

**Thread of thought, in order:**

1. Wanted to actually *use* the CLI-mode binary against real files rather than trust the prior session's live-run claims at face value. Set up a plain, ordinary test folder (`~/synapse-test/`) — had to correct a loose word choice ("sandboxed") that implied something more exotic than "kept out of the git repo."
2. Ran real move/delete/multi-step tasks successfully, which raised the sharper question: what does "it works" actually mean, in testable terms? That question is what eventually produced `testing-plan.md`.
3. A direct question — "should we limit the agent to just moving/opening files, not editing?" — prompted actually *testing* the classifier against `sed -i`/`tee`/`truncate`/`cp`-overwrite instead of reasoning about it abstractly. All four came back `Reversible` (auto-run, no confirmation) despite being as destructive as `rm`. This was the session's real finding, and it only surfaced because it was tested, not inspected.
4. That finding opened a much bigger conversation: should SynapseOS reimplement filesystem-MCP-style typed operations instead of raw bash? Re-derived the answer from scratch (product-first, not by citing D7) rather than treating the prior decision as settled — landed in the same place (hybrid, typed-ops gated on an unverified reliability question) but now for verified reasons, not inherited ones.
5. That, in turn, surfaced a real inconsistency in `build-order.md`: M8 (Undo log) was gated on M7 (Session logger) for a reason that only applied to *half* of what M8 was scoped to do. Split it once the actual dependency was traced through.
6. The user then explicitly challenged whether project docs should be treated as constraints at all, given the thesis is a living document, not the frozen submitted snapshot. This produced a real policy change (`CLAUDE.md`), not just a one-off answer — worth noting as the moment this repo's own "docs are revisable" culture got made explicit and binding rather than implicit.
7. Closed the loop by actually building what the analysis called for: classifier hardening (F1), a real disk-persisted undo mechanism (F2), and the test plan design (`testing-plan.md`, F3/F4 not yet built) — then verified F2 *live*, not just via unit tests, specifically because the earlier "it works" ambiguity was the whole reason this session started.
8. A late, unprompted tangent ("isn't Rust more suited for this?") got a real answer instead of a deflection — re-ran the language comparison per-component rather than pointing at D8 (which never actually compared Go to Rust in the first place).

**Blockers hit, worth flagging individually (see also the quick-reference table below):**

- **`os.Exit()` buried inside loop logic made it untestable.** `runAdHoc`'s core loop called `os.Exit()` at four points, which would kill the test process if exercised directly. Required extracting `runLoop` with injected I/O/confirmation/return-code before any test could be written — this was actually Session 21's work, but the same shape of problem (business logic entangled with process-exit or terminal I/O) is worth watching for early in any future package, since retrofitting it is a real, if small, refactor.
- **A destructive-then-confirm ordering bug in the undo command's own design.** First draft of `runUndo` popped the journal entry *before* asking whether to apply it — meaning declining would silently and permanently lose the undo record. Caught before shipping by asking "what happens on the 'no' path" explicitly, and fixed by adding a non-destructive `PeekLastJournal` separate from `PopLastJournal`. General lesson: any confirm-then-mutate flow needs its declined path designed on purpose, not left as "whatever the code happens to do."
- **Directory-diffing undo needed an explicit, honest scope boundary.** Correctly reconstructing a `mv` without parsing bash syntax (glob expansion isn't visible to Go code ahead of execution) could have turned into an open-ended parsing project. Scoped it deliberately: one level of recursion into newly created directories, pairing by basename, anything that doesn't cleanly pair left "unhandled" rather than guessed at. The discipline that mattered: decide and document the boundary *before* writing code, not discover it by shipping something subtly wrong.
- **Widening a core function's signature broke every existing test call site.** Adding `journalPath` to `runLoop` was a one-line design decision that touched 8 separate test functions. Mechanical but worth remembering: a shared internal API's tests are often the most expensive part of changing its signature, not the change itself.
- **A Markdown heading landed at the wrong nesting level.** Inserting a new `### Foundational Hardening` section into `build-order.md` first came out as `##`, breaking the document hierarchy (would have shown as a sibling of "Runtime Milestones" instead of a child). Caught by grepping the heading structure right after the edit rather than trusting the diff alone — worth doing that check by default whenever restructuring a doc with several nesting levels, since a misplaced heading doesn't produce an error, just a wrong document.

## Sessions 20–21 — .gitignore Privacy Rework, PR Shipping, Ollama Client/Loop Tests

**Thread of thought, in order:**

1. Started from a privacy request (keep `.gitignore`'s Claude-related entries out of the immediately-visible top of the file) and iterated twice — first just reordering within the custom section, then genuinely burying the entry mid-file once asked to go further.
2. Burying it mid-file collided with `/gitignore`'s own auto-managed block (a large fetched region that gets wholesale-replaced on every refresh) — the entry would have been silently deleted next time that command ran. Rather than accept the loss, extended the `/gitignore` command itself (a global, cross-project file) to recognize a "pinned custom" marker it preserves across refreshes.
3. Moved to shipping four unrelated pending concerns (tests, a doc update, the gitignore/session-untracking change, and pre-existing thesis content) as separate, purpose-scoped PRs, per this project's one-commit-per-concern convention. `origin/main` had not been updated since Session 16, and shipping the first of those PRs as a squash-merge silently collapsed all 12 of Sessions 17–19's separate, already-real local commits into that one PR's single squashed commit on the remote — discovered only by comparing commit graphs, since file content matched (`git diff main origin/main` was empty) and nothing looked wrong on the surface.
4. Along the way, built the actual regression test suite for `internal/ollama` and `cmd/synapse`'s orchestration loop that this whole thread had been circling — closing the gap between "I ran it once live" and "there's reproducible evidence it works."

**Blockers hit:**

- **A squash-merge on a stale `origin/main` silently absorbed 12 unrelated local commits into one lump.** `origin/main` hadn't been pushed to since Session 16; the local branch was 12 commits ahead (all of Sessions 17–19's work). Squash-merging the first of four unrelated PRs collapsed that entire history into a single commit (`fbedc1c`) on the remote, instead of just that PR's own small change — an accident of the PR containing that stale base, not of the PR's own content. The two remaining PRs were rescued by branching fresh off `origin/main`'s actual current tip (verified content-identical to local `main` via an empty `git diff`) rather than off the divergent local history, avoiding the same trap a second time; the correct full fix (`git push --force-with-lease origin main` to restore local `main`'s real granular history) was left undone since it needs a human to run it directly, not this tool. **Lesson, concretely: before any squash-merge, check `git log origin/main..main` first** — if it's non-empty, the PR's squash will absorb everything in that range, not just the PR's own diff.
- **`git stash show -p` silently omits untracked files.** Needed to split eight unrelated pending changes (four tracked, three new/untracked) across four separate branches. `git stash push -u` stashes untracked files fine, but the standard way to inspect/reapply a stash (`git stash show -p`, or plain `git checkout <stash> -- <path>`) only reaches the *tracked*-file diff — untracked file content lives in a separate, less-discoverable parent commit of the stash (`stash@{0}^3`). Cost real time rediscovering this. **Lesson, concretely: `git checkout stash@{0} -- <path>` for tracked files; `git checkout stash@{0}^3 -- <path>` for files that were untracked when stashed.**
- **A branch that forked before an earlier PR merged can silently undo it.** The pre-existing `docs/thesis-ufo2-bifurcation` branch had forked before the PR that untracked `docs/session.md` was merged into `main`. Left as-is, merging it back would have resurrected `session.md` as tracked, quietly reversing already-shipped work — this isn't caught by a normal content diff, only by checking file-*tracking-state* consistency (`git ls-files <path>` on the stale branch) before merging. Had to add a small carry-along commit once noticed.
- **A sandbox flag (`go run -C <dir>`) triggered an unexpected directory reset, not a real error.** Using `-C` to point `go run` at a different directory printed a benign-looking "Shell cwd was reset to..." line that turned out to be the sandbox re-asserting its allowed root, not program output. It wasn't obvious at first that this was infrastructure noise rather than a bug. **Lesson: prefer `cd <dir> && ./binary` or an absolute-path binary invocation over directory-changing flags, inside this sandboxed environment specifically** — plain `cd` is respected; flag-based directory changes on external tools may not be.

## Sessions 17–19 — M2 Built From Scratch: First Live Validation, Classifier/Executor Wiring, D21's Bounded Loop

**Thread of thought, in order:**

1. Ran M2's walking skeleton against a live Ollama instance for the first time, closing the single largest empirical risk on the whole project: does a local 3B model turn plain-English intent into usable bash at all. Ollama was already running from a prior session but had the wrong model pulled, and the `ollama` CLI binary itself wasn't reachable from the shell despite the server process running — worked around it by pulling the correct model directly via the HTTP API (`POST /api/pull`) instead of troubleshooting the CLI.
2. That first live run surfaced two real findings, not hypothetical ones: `cleanCommand` only stripped triple-backtick fences, and 3 of 8 live outputs came back wrapped in single backticks instead — a formatting quirk that would have handed the (not-yet-built) execution engine a broken, non-executable string as-is. Separately, at least one proposed command was plausible but semantically wrong (`dpkg-query -Wf` piped through a `grep` pattern that only matches a different command's output format) — a model-accuracy limitation, explicitly distinguished from a code bug and left as-is, since measuring exactly this kind of failure is the eventual study's job, not something M2 itself should paper over.
3. Used that live run to redirect the build order rather than pressing ahead to M3 (TUI) as originally sequenced: decided CLI mode needed to be a fully complete interface (propose, classify, execute, confirm) before any TUI work started, absorbing the previously-separate M4 (execution)/M5 (confirmation gate) milestones into M2 outright. Propagated the same restructuring the same session across every file that described the milestone sequence (`build-order.md`, `README.md`, `roadmap.md`, `scope.md`) rather than letting them drift out of sync.
4. Session 18: fixed the backtick bug found in Session 17 (unit-tested for both fence styles), built `internal/classifier` (a short, explicitly-named pattern list, not a shell parser — deliberately, matching what the milestone had already committed to) and `internal/executor` from scratch, wired both into the ad-hoc single-task path, and live-validated all three resulting execution paths by hand: auto-run reversible, block-and-decline irreversible, block-and-confirm-then-run irreversible — file contents checked afterward with `cat`, not just trusted from the program's own printed output.
5. Session 19: reconsidered whether single-command execution was too limited, given that comparable agentic CLIs are loop-based rather than one-shot. Deliberately considered and rejected full autonomy (logged as **D21**) on two concrete grounds rather than a vague safety instinct: the model's already-observed accuracy limits from Sessions 17–18, and the thesis's own methodology chapter explicitly separating autonomous-agent benchmark evaluation from the human-in-the-loop evaluation this thesis targets — full autonomy would have silently recategorized the whole study. Built the bounded, gated loop instead (step cap, per-step re-gating, error feedback) and live-validated it against a synthetic scratch playground built for exactly this purpose, not against real files.

**Blockers hit:**

- **The `ollama` CLI was unreachable from the shell despite its server process already running, and the wrong model was pulled.** Rather than spending time debugging the CLI's own connectivity, pulled the model directly via the server's HTTP API (`POST /api/pull`) — the API was the actual dependency the prototype needed, not the CLI wrapper around it. Worth remembering generally: when a wrapper tool is misbehaving but the service underneath it is reachable, check whether the wrapper is even necessary before debugging it.
- **A hand-written model-output cleanup layer only handled the formatting quirk it was written for, not the one that actually showed up live.** `cleanCommand` stripped triple-backtick fences from day one, but the very first live run showed the model wraps output in single backticks more often (3 of 8 responses) — a reminder that this kind of defensive-parsing code needs real model output to find its failure modes, since the failure modes aren't something you can fully anticipate by reading the system prompt you wrote.
- **The model declared success despite visible evidence of failure in its own fed-back context, twice, in two different sessions.** Session 17's `dpkg-query`/`grep` mismatch produced silently wrong output; Session 19's `ls -lh | cat` pipeline exited 0 despite a visible `cat: ... No such file or directory` error (the shell's last-stage exit code masked the earlier failure), and the model still declared `DONE`. Neither was a defect in the loop mechanism itself — both were proposed, executed, and fed back correctly — the model's judgment on top of correct context was simply wrong. Logged as concrete, repeated supporting evidence for D21's decision against full autonomy, not dismissed as a one-off.
- **Nearly queued a full doc-propagation-then-paper-edit sequence before the D21 loop code itself existed.** Self-corrected mid-session (Session 19) to build first and document lightly instead, deferring the Ch.3 paper update rather than doing it ahead of validation — the same "don't worship documentation" discipline this project applies elsewhere.
