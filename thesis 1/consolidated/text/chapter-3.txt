                                       Chapter 3

                                 METHODOLOGY




         This chapter describes the methodology for designing, implementing, and
evaluating the recoverability analysis, and for deploying and validating it in SynapseOS,
the conversational interface layer that serves as its experimental platform and runs over

an ordinary Linux desktop session rather than replacing it.           The methodology is
organized into three sections: Dataset, which defines the data to be collected and how it
will be gathered; Procedure, which describes how the analysis and its platform are built
and how the validation study is conducted; and System Testing, which defines the

evaluation of the analysis on its corpus and the design, metrics, and statistical approach
of the validation study.
         This methodology answers the five research questions posed in Chapter 1, all of

which concern the analysis. RQ1 asks how a command’s effect on the system can be
represented formally so that recoverability is a predicate over it, with anything
undetermined treated as unrecoverable; RQ2, whether those effects can be derived from
the command’s structure before it runs, through composition and the read-only resolution

of run-time targets; RQ3, whether a minimum-cost recovery plan computed from them
restores the prior state; RQ4, whether the analysis loses less data silently, restores more,
and asks less often than a pattern list, a fail-closed list, and the command-safety checks of
open-source AI coding agents; and RQ5, how much composition and runtime-target

resolution each contribute beyond the per-command rule table. RQ1 is answered by the
effect model specified in Section 2.1(a), with the algorithm and the plan it supports
specified in (b) and (c); RQ2 through RQ4 are answered by the evaluation against

baselines in Section 3.1, and RQ5 by the ablations in Section 3.2.

          Two evaluations follow, of different standing.         The corpus evaluation in
Sections 3.1 and 3.2 is the study’s primary evidence: it answers the research questions
against a labeled corpus whose ground truth comes from sandboxed execution, without
reference to any participant. The validation study, defined in Section 1 and Sections 3.3

SynapseOS and has participants use it on matched tasks. It checks that the analysis’s
decisions carry through to real files and hold on commands people cause, which the
corpus does not contain, and it characterizes the platform through usability measures.

Neither evaluation depends on the other: the analysis takes a shell command as a string
and is indifferent to what produced it, so removing the interface would remove the
validation study but leave every research question, its corpus, its baselines, and its results

intact.



Conceptual Framework

          The conceptual framework places the recoverability analysis between a
generated shell command and its execution (Figure 3.1). Its input is a command and the
directory in which it will run. It derives the command’s effect set from its structure
(Objectives 1 and 2), learning targets known only at run time through dry runs it first

proves read-only and runs in a read-only sandbox; it decides whether the command can
be undone; and, where undoing it requires preparation, it computes the minimum-cost set
of pre-images to capture (Objective 3). Anything it cannot determine makes it ask. Its

verdict drives a confirmation gate, its plan’s captures are taken before the command runs
and recorded in an undo journal, and undo restores from them. SynapseOS supplies the
setting: the user issues a request in ordinary language through a persistent chat interface,
a locally hosted small language model translates it into a shell command, the command is

executed in a bash subprocess, and its output is rendered back in the interface. The
generated shell command is nonetheless displayed rather than hidden: the confirmation
gate requires the user to approve irreversible operations, and an approval given without
sight of what is being approved is not consent. Visibility also makes the system’s

──────── p. 50 ────────
                                                                                          50


translation of intent observable to the participant, which is what allows a user to notice a
misinterpretation before it executes rather than after. The confirmation gate consumes
the analysis’s verdict rather than a pattern match. The analyzer is specified in Section

2.1(a)–(c) of this chapter and evaluated in Sections 3.1 and 3.2, independently of the
validation study. This architecture is illustrated in Figure 3.1.
         The framework is evaluated in two parts of different standing.                 The

recoverability analyzer, the study’s research contribution, is evaluated on its own, on a
corpus of commands whose ground truth is obtained by sandboxed execution (Sections
3.1 and 3.2). The analyzer is then validated in use, deployed in the platform, through a
controlled study in which participants complete a fixed set of tasks under two conditions:

using SynapseOS as the interface, and using their own primary operating system —
Windows, macOS, or Linux — as the baseline. The study records the analyzer’s decision
on every command participants cause, so its behaviour in use can be compared with its
behaviour on the corpus, and its expert baseline design, which pits SynapseOS against

the environment each participant already knows and uses daily, characterizes the platform
through task completion time, error rate, and user satisfaction across the real-world OS
landscape [49].

Section 1: Dataset
        The study gathers two kinds of data. The primary dataset is a held-out corpus of
shell commands, each labeled by running it in a sandbox, on which the analysis is
evaluated against its baselines and its ablations (Objectives 4 and 5). The remaining data

serve the validation study, in which the analysis is deployed in SynapseOS and exercised
by participants, in three categories: benchmark task data used to exercise the platform in
a standardized environment, user study data collected from human participants in a

controlled setting, and system performance data, including the analysis’s decision on
every command, captured automatically through built-in telemetry during all sessions.



1.1 What to gather



a) Command Corpus
        The primary dataset is a corpus of shell commands. Each command is paired
with a fixture — the files and directories that exist when it runs — and with a ground-
truth label observed by running it on that fixture in a sandbox: whether it loses nothing,

loses something a captured pre-image could restore, or acts outside the filesystem. The
corpus is held as four partitions: human-written commands from NL2Bash [23],
templates covering each shell composition operator, commands whose effect lies outside
the filesystem, and commands the deployed model itself wrote. For every command,

each configuration compared in Section 3 records its decision: whether it would ask, and
what it would capture.      The configurations are the analysis, its baselines, and its
ablations. For every command the analysis would let run, the command is also executed,
undone, and the tree compared, which records whether the capture restored the prior

state.



b) Benchmark Task Suite

         The OSWorld task suite [49] provides standardized real-computer tasks across
shell operations, file management, web browsing, and application-level interactions, and
is used as a secondary check on the platform: only its tasks that can be expressed as shell

commands are adapted, since graphical-only tasks are outside SynapseOS’s scope
(Section 2.1(e)). OSWorld evaluates computer-using agents in real operating system
environments, which lets the platform’s results be related to the existing literature. Tasks
are presented as natural language instructions; agents interact with a real virtual machine

environment, and outcomes are evaluated by automated inspection of the resulting
system state — whether the goal was actually achieved — rather than by comparing
individual actions. In addition to OSWorld tasks, a custom cross-platform task suite is
developed for this study, covering file search and organization, system and process

monitoring, application and package management, and text and data processing — each
task defined as a human-level goal achievable via SynapseOS natural language
commands and via native OS tools on the comparison machine. Each task in both suites
is documented with a description, expected outcome, task category, and difficulty level.

1.2 How to gather



a) Command Corpus
         The corpus is generated by a program, not assembled by hand, and is held as

four partitions reported separately rather than pooled. The first is NL2Bash [23], which
supplies human-written commands and is the generalization set: candidates are drawn at
random from the dataset with a recorded seed, excluding any command used during
development. The second is a set of parameterized command templates covering each

shell composition operator — sequencing, conditional execution, pipelines, redirects,
command substitution, loops, find -exec, xargs, sh -c and other interpreters, and
wrappers such as sudo and env — which exists because naturally occurring corpora
under-represent compound commands, and compound commands are where the

algorithm’s contribution lies. The third is a set of commands whose effect lies outside
the filesystem, described under (b) below. A fourth partition holds commands the
deployed model itself wrote: the NL2Bash descriptions of a random sample of tasks are

given to the prototype’s model with the runtime’s own prompt, and the command it
returns is labeled by the same pipeline. It is reported apart, because a set drawn from this
prototype’s own output is biased toward the shapes it produces, and because the analysis
is about model-generated commands, which NL2Bash’s human-written ones are not.

Commands logged during the validation study are scored the same way (Section 3.5(e)).
         A second stratification is by the shape of the command, assigned by the
generator from the command’s syntax: a single named command; a chain; one whose
targets are computed while it runs; a redirect; one whose effect hides inside an interpreter

or a tool the rule table does not name; and one whose effect lies outside the filesystem.
The claims under test concern the composed, run-time, and hidden shapes, and a corpus
dominated by plain named commands would measure the strength of a list and not the
contribution of the analysis, so results are reported per shape as well as in aggregate.



b) Ground Truth by Sandboxed Execution

──────── p. 58 ────────
                                                                                         58


         Ground truth is observed, not judged. Each executable command is given a

fixture — the files and directories that exist when it runs — and is run once inside a
bubblewrap sandbox: the rest of the filesystem read-only, no network, empty standard
input, a hard time limit, and only the fixture writable. The tree is recorded before and

after, and the label follows from the difference. A command is recoverable when nothing
that existed was lost: paths may have been created, and a path that disappeared but whose
very same file now sits elsewhere was moved, not lost. It is recoverable only if a pre-
image is captured when something that existed was removed, overwritten, replaced by a

different kind of object, retargeted, or given different permission bits or an owner.
Modification times are ignored, since touching a file loses nothing a user could want
back. Commands that do not finish cleanly — a non-zero exit, a timeout, an attempt to
write outside the fixture — are excluded and counted, never labeled by guess.

         Commands whose effect the filesystem cannot show — on another machine, on
the mount table, on another process, on a device, on an account or the firewall — cannot
be labeled this way and are never executed. They form the external partition and are

labeled unrecoverable by construction.      The rule that assigns a command to it is
deliberately narrow, naming only tools that change such state, so that a read-only network
query is not counted as a loss the system failed to catch. It is a partition rule and not a
source of the other two labels.

         Ground truth is defined relative to a stated filesystem state. A command’s
effects depend on what exists: rm *.tmp deletes nothing where there are no such files, and
cp a b overwrites only if b is there. A label given with no state is a label about an
imagined directory, and an analysis that reads the real state cannot be scored against it.

Every corpus item therefore carries its fixture, and the analysis is run against that same
fixture. The fixture is built from the command’s text before the analysis is consulted: the
files and directories the command names are created, a glob becomes a few matching
files, and whether the destination of a copy, move, or redirect already exists is chosen by

the seed, with the other choice tried if the first does not run. Fixtures are never written
from the analysis’s output.

         The generator shares no code with the analysis and never consults it, so
agreement between the two is evidence and not circularity. It is deterministic for a given
seed, and it records the number of candidates drawn and the reasons for each exclusion

beside the corpus. There is no human labeler, and so no labeler disagreement to measure;
the threat that takes its place is the validity of the oracle itself, addressed in
Section 3.1(e).



c) Benchmark Tasks
         SynapseOS is deployed on Debian 13 (Trixie); OSWorld’s own environment is

an Ubuntu virtual machine [49], so its shell-expressible tasks are adapted to the Debian
evaluation machine.     Each benchmark task is executed through the conversational
interface, and results are captured programmatically through the built-in telemetry
system. Each task is supplied to SynapseOS as a natural language instruction, and the

resulting system state is compared against the expected outcome defined in the
benchmark. Because SynapseOS asks before every command its confirmation policy
does not let through unasked (Section 2.1(e)), benchmark runs are facilitator-attended
rather than unattended; the confirmation gate remains active throughout and every

confirmation is logged as part of the run record. OSWorld scores the resulting system
state rather than a human operator’s performance, so it applies only to the SynapseOS
condition. Condition B, which a human participant operates directly, has no equivalent

and is instead evaluated through the custom cross-platform task suite administered in the
user study (Section 1.2(d)).



d) User Study
         The user study is conducted in a controlled laboratory setting with two
machines: the SynapseOS evaluation machine (Debian 13, conversational interface) and
the baseline machine running the participant’s native OS — Windows 11, macOS, or

Linux with a GNOME desktop — as determined during screening. Each participant
completes a matched task set on both machines under a within-subjects design. Because

──────── p. 60 ────────
                                                                                        60


completing the identical task twice would measure recall rather than interface efficiency,
two parallel task forms — Set A and Set B — are constructed, matched item for item on

category, difficulty level, and number of required steps, differing only in the specific
targets involved. Form and condition order are crossed in a 2×2 counterbalance, yielding
four participant groups of ten: Set A first on SynapseOS, Set B first on SynapseOS, Set A
first on the native OS, and Set B first on the native OS. Task order within a form is

randomized per participant. Form equivalence is verified during the pilot study, and
condition order is retained as a between-subjects factor in the analysis so that residual
asymmetric transfer — carryover that is larger in one order than the other, which

counterbalancing redistributes but does not remove — is detectable rather than assumed
absent. Screen capture software records activity on both machines; the SynapseOS
session logger supplements the recording for the SynapseOS condition.
        The study involves 40 participants divided into two groups:

        Novice users (n = 20): participants with limited computing experience, capable
        only of basic tasks (web browsing, document editing) on any OS, and no prior
        command-line familiarity, recruited from the general university population
        Power users (n = 20): participants with demonstrated proficiency in computing

        on their primary OS — capable of performing file management, system
        monitoring, and process administration tasks efficiently — recruited from the
        university’s information technology and computer science programs

        Participants are recruited through university channels. Recruitment enforces a
minimum quota of four participants per primary OS background (Windows, macOS,
Linux), scaled with the sample so that the realized set cannot end up concentrated in a
single OS and leave the per-OS exploratory subgroup analysis (Section 3.4) without data

for the others. The binding constraint on this quota is the Linux-primary novice cell: a
daily Linux user with no command-line familiarity is uncommon, and if that cell cannot
be filled during recruitment the Linux quota is met from power users alone, with the
resulting imbalance reported rather than concealed. Informed consent is obtained from

all participants prior to the session.   Ethics approval is secured before recruitment

1.3 Why
          The analysis is evaluated against a labeled corpus of shell commands rather than
through participants, because its research questions concern what a command does,
which can be observed directly, and not what a person does. The separation is deliberate

and has a practical consequence worth stating: this evaluation depends on no ethics
approval, no recruitment, and no participant sessions, and can therefore be completed and
reported independently of the validation study’s schedule.

          The corpus is sized against the classes the analysis has to separate, not against a
single overall total. Commands are drawn until a fixed number carry each ground-truth
label, so that the label the false-negative test needs — a command that loses something
— is present in quantity whatever NL2Bash’s own composition, which is mostly read-

only. The target is on the order of 780 commands: about 450 from NL2Bash, of which
150 are losses; about 250 from templates; and about 80 external. This is a coverage-
based target rather than a power-computed one: a classical power analysis needs an
assumed effect size, and the quantity of interest, the false-negative rate, is expected to be

low for both the baseline and the algorithm, the regime in which an assumed effect size
would be a guess. What the corpus must give is enough losses that a Wilson interval on a
proportion near zero remains informative, and 150 does.

          The OSWorld benchmark is used as a secondary check on the platform for the
reason given in (b) above, its relation to the existing literature; the analysis itself is
evaluated on the command corpus, for the reasons given above.

         A custom cross-platform task suite is necessary because OSWorld’s task
coverage does not represent the human-goal-framed system tasks relevant to this study —
file organization, system monitoring, process management, and text processing —

achievable both through SynapseOS natural language commands and through
participants' native OS tools (Windows, macOS, or Linux graphical desktop). Tasks are
scoped to operations achievable via bash on SynapseOS and via native graphical or
terminal tools on the comparison machine.

         The evaluation follows a convergent (parallel) mixed-methods design: the
quantitative performance measures — task completion time, error rate, SUS, and NASA-
TLX — and the qualitative interview data are collected concurrently within each session
and integrated at the interpretation stage, so that the measured differences between

conditions and participants' accounts of why those differences arise inform one another
rather than being read in isolation.
         The within-subjects design is chosen because it allows each participant to serve

as their own control, producing a direct comparison between conditions while requiring a
smaller participant pool than a between-subjects design. Counterbalancing addresses the
primary threat to internal validity, the learning effect, by distributing it across conditions;
it does not remove asymmetric transfer, which is tested rather than assumed absent

(Section 3.7).
         The expert baseline design — using each participant’s primary OS as Condition
B rather than a fixed Linux graphical desktop — is chosen because a fixed Linux
baseline would confound interface quality with OS familiarity.            The overwhelming

majority of participants have never used a Linux desktop; performance under that
condition would reflect unfamiliarity with a foreign environment, not a meaningful
comparison of interface paradigms. Measuring the platform against what participants

already know and use daily characterizes it more honestly than measuring it against a
system they meet for the first time; these platform measures are characterizations, and the
validation outcome proper is the analysis’s behavior on the commands participants cause
(Section 3.5(e)).

                                                                                           63


         The dual-population design — novice and power users — lets the validation
study show whether the analysis’s decisions hold both for people who can read the

commands it judges and for people who cannot, and characterizes the platform across
both. The validation data serve two purposes. The system performance data, including
the analysis’s decision on every command participants cause, validate the analysis in use:
they show whether its verdicts and captures hold on commands the corpus does not

contain, and whether undo restores what participants’ commands changed. The user
study metrics and benchmark coverage characterize the platform on which it is deployed.
The research questions themselves are answered against the labeled command corpus

described in Section 3.1.



1.4 Participant screening criteria

         Participants are assigned to the novice or power user group based on a pre-study
screening questionnaire administered before the session begins.         The questionnaire
assesses the following dimensions:
         Years of general computer use

         Primary OS — the operating system used as the primary daily computing
         environment (Windows / macOS / Linux); must average four or more hours of
         use per day to qualify

         Self-reported proficiency on primary OS (basic / intermediate / advanced)
         Self-reported command-line familiarity (none / basic / intermediate / advanced)
         Prior exposure to conversational AI interfaces — frequency of use (never /
         occasionally / regularly / daily) and which tools (chatbots, voice assistants,

         code-completion or agentic coding assistants, other LLM-based tools)
         Self-reported proficiency is confirmed with a short behavioral screener: three
timed mini-tasks performed unaided on the participant’s primary OS using its native
tools, one from each of three of the four system-task categories used in the main study —

file organization (locate and relocate a set of recently modified files), process monitoring
(identify the application consuming the most memory via the OS’s native system

monitor), and application management (determine whether a named application is

installed and identify its version). Each task is scored pass/fail by the facilitator against a
fixed time limit and completion criterion. The behavioral screener exists because self-
reported proficiency alone is not a reliable classifier — a participant’s technical

capture.

           Participants are classified as novice users if they report basic proficiency on
their primary OS, computing use limited to web browsing and document editing, no prior
command-line experience on any platform, and fail the behavioral screener. Participants
are classified as power users if they report advanced proficiency on their primary OS —

capable of performing file management, process monitoring, and system administration
tasks efficiently using that OS’s native tools — regardless of which OS that is, and pass
all three behavioral screener tasks.       Participants whose self-report and behavioral
screener results disagree, or who do not clearly satisfy either classification, are excluded.

Primary OS is recorded for all participants as a grouping variable, and prior
conversational AI exposure as a covariate, in the analysis; prior AI exposure is analyzed
as an exploratory covariate only (see Section 3.4) rather than a primary grouping

variable, since splitting the sample along a third axis would leave subgroups too small to
support a hypothesis test.

2.1 System design and implementation

         The design comprises the recoverability analysis, specified in (a) to (c), one part

a) Effect-Semantics Model (Objective 1)
         The command-safety check SynapseOS began with, like those of the tools
surveyed in Chapter 2 and the execution pipeline’s own classification in (e) below, is an
enumerated list of named command shapes: a proposed command is matched against

patterns known to be destructive — rm, dd, mkfs, truncating redirects — and gated if it
matches. That mechanism is the baseline this study seeks to replace, and its limitations
are structural rather than incidental. It cannot enumerate its domain, because the space of

destructive commands is open-ended: extending the list to cover apt leaves snap, pip,
docker rm, and whatever ships next. It does not compose, because each rule matches a
command in isolation while a generated line routinely chains several operations with
differing recovery requirements. And it reasons about names rather than effects: cp a b is

harmless when b does not exist and destructive when it does, a distinction no name-
matching rule can draw.
         This study therefore proposes an algorithm that derives what a command would
do from its syntactic structure, and decides recoverability over that derivation.         It

produces two outputs: a verdict — recoverable, recoverable only with prior capture, or
unrecoverable — and, for the middle case, a recovery plan naming which pre-images
must be captured, and by which mechanism, before the command is allowed to run.

──────── p. 67 ────────
                                                                                          67


         The formal object. A command is represented by its effect set rather than by its

name. An individual effect on the filesystem is a triple: a kind, drawn from {read, create,
write, remove, metadata}; a target path, resolved against the working directory in which
the command would execute; and the pre-image that would have to be captured for that
effect to be reversed. A change to installed packages or running services is a sixth,

pathless kind, a state effect, recorded with the inverse command that would reverse it
(see Scope of the model below). A removal whose very bytes survive at another path, as
in a rename, is marked as a move: undo moves the data back, so it needs no capture. The

effect set of a command is the union of the effects of every leaf command within it, taken
over the whole of its operator structure.
         The verdict. The verdict is a predicate over the composed effect set: a command
is recoverable when every effect within it has an available mechanism capable of

restoring that effect’s pre-image. The verdict is not where the contribution lies: on silent
loss, the fail-closed list, which asks before every command it does not recognize as read-
only, reaches the same outcome on the commands studied. What the study contributes is
the derivation of the effect set, (b), and the plan computed from it, (c).

         Soundness. The analysis is deliberately one-sided. Any construct whose effects
cannot be resolved statically — a path arriving from command substitution, an
unexpanded variable, a glob that may match a block device — is treated as unrecoverable

rather than assumed benign. The two possible errors are not symmetric and are not
traded off against each other: over-approximating destructiveness costs the user an
unnecessary confirmation prompt, whereas under-approximating it destroys data that
cannot be recovered. This asymmetry is why the evaluation in Section 3.1 reports false-

negative rate separately rather than folding both directions into a single accuracy figure.
Two limits belong to the soundness claim itself. Resolution runs commands before the
user has consented, which is safe only because each is proven to have no effects; and the
interval between resolving a target and executing the command is a window in which

another process can change the filesystem, so a capture is of the state at resolution time
and not a guarantee about the state at execution time.

──────── p. 68 ────────
                                                                                             68


         Scope of the model. The effect domain is the filesystem, extended to two kinds
of state on the target system that have no pre-image to copy but do have an inverse:
installed packages and running or enabled services. For these the analysis does not re-

implement the package manager or the service manager. It asks the system’s own tools
what the command would do — the package manager’s simulation mode, the package
database, and the service manager’s state queries — and derives from the answer the
command that puts the state back: a purge for an install, a versioned install for a removal

or upgrade, a stop for a start, a disable for an enable. A change is recoverable only if that
inverse exists, so removing a package whose old version no repository still offers is
unrecoverable, and purging a package also captures its configuration files as removals.
Undo runs the inverse, with elevated privilege if the original had it, and prints the

command for the user to run if it fails. Not represented are what maintainer scripts and a
service’s own start-up do beyond the state change, which are arbitrary programs; network
mutations and anything on a remote host; and other package managers, which stay

unrecoverable unless plainly read-only. A command whose principal effect is one of
these is classified unrecoverable by the soundness rule above. This is safe but coarse,
and it is stated as a limitation of the model rather than deferred to the results.



b) Effect-Composition Algorithm (Objective 2)
         Extraction. For each leaf command, effects are derived from the command
together with its arguments. The derivation is argument-aware because flags change

effects and not merely behavior: rm -i differs from rm -f in whether removal is certain, cp
-n cannot overwrite where cp can, and chmod with and without -R differ in how many
paths acquire a metadata effect.

         Composition. Effects propagate upward through the operators that join
commands into a single line, and the propagation rule differs by operator. Sequencing
with ; accumulates effects unconditionally. Conjunction and disjunction — && and || —
make later effects conditional on an earlier exit status, so the effect set is a union over the

branches that may execute. A later part sees what an earlier one did as done only across

──────── p. 69 ────────
                                                                                           69


&&; after ;, ||, or a pipe it may run although the earlier part failed, so an earlier removal
is treated as possibly not having happened, and a later write to that path is captured, and

an earlier cd leaves the working directory unknown. An assignment or cd inside a branch
or loop outlives it, as in the shell, and a value on which the paths that may have run
disagree is unknown afterwards. A pipeline connects standard output to standard input
and contributes no filesystem effect of its own, but determines the exit status that gates

whatever follows it. Redirection introduces write effects that appear in no command in
the pipeline. Command substitution introduces effects whose targets are computable
only at runtime, and xargs and find -exec multiply a command across an argument set that
is not statically known. It is this propagation, rather than the per-command derivation,

that an enumerated pattern list has no means of expressing. Parts of a line are analyzed in
order against an overlay of what earlier parts created or removed, so that in mkdir out
&& cp a.txt out/ the copy lands in a directory that does not yet exist, and a path a line

creates and then deletes needs no capture because there was nothing there to lose. Loops
are analyzed once per resolved item with the loop variable bound; sh -c strings and
transparent wrappers such as sudo are analyzed as the command they run. Two parts of
composition are distinguished in what follows: propagation through the operators that

join commands (;, &&, ||, pipes, and redirects), which needs no lookup beyond the rule
table, and analysis through the commands that run other commands (wrappers, find -exec,
xargs, eval, sh -c strings, and loops). The composition ablation of Section 3.2 disables
the second and keeps the first; Algorithm 1 marks the lines each ablation switches off.

         Resolution. Some targets exist only while the command runs: rm $(ls *.log),
find -delete, xargs rm, git clean -f, tar -x. Rather than declaring these unknowable, the
analysis learns them by running a form of the command that cannot change anything —

find with each action replaced by a print of what the action would have touched, the read-
only command that feeds xargs, git clean -n, tar -t, rsync -n, the body of a command
substitution — and analyses the command again with the concrete targets in place. A
resolver is run only if the same analysis proves it has no effects, and it runs inside the

bubblewrap sandbox with the whole filesystem mounted read-only; without bubblewrap,

──────── p. 70 ────────
                                                                                          70


resolution is switched off and the command asks. If it cannot be proven read-only,

cannot run, or times out, the targets stay unresolved and the command asks. A resolver is
also refused when an earlier part of the same line creates, moves into, writes, or removes
anything under what it would read, because listing it beforehand would not show what
the command will meet. Resolution is what makes a capture possible for commands

whose targets a static reading cannot name.



c) Minimum-Cost Recovery-Plan Generation (Objective 3)
         The recovery plan is a minimum-cost cover of the same set — for each effect,
the cheapest mechanism sufficient to restore it, with redundant captures eliminated. Cost
is not uniform across mechanisms, which is what makes the selection non-trivial: a

hardlink capture is independent of file size where a content copy is proportional to it, a
single git object identifier covers an arbitrary number of tracked-file effects at once, and
two effects on overlapping paths need be captured only once.             The mechanisms
themselves — content backup, hardlink-based trash, git HEAD capture, permission-

metadata capture — are those of the execution pipeline described in (e); the algorithm
selects among them rather than introducing new ones. A rename or move is the one
removal that needs no capture, because the same data survives at the destination and

undo is moving it back; compression and archiving are not, because the bytes at the
destination are a transformation of the original and moving them back returns the wrong
content, so they are captured like any other deletion. Where a list can only refuse, the
plan adds a capture that restores.

         Why the plan is minimal. Cost is counted as the work and storage a capture
needs before the command runs: a hardlink, a permission record, a commit identifier, and
an inverse command each cost a constant, and a content copy costs the size of the file.
The capture a path needs is fixed by its effects: a removal alone is restored from a

hardlink; an overwrite needs a copy of the bytes, because a hardlink shares the very data
the write changes; and a change of mode or owner needs a record. The choices for
different paths are independent, with two exceptions, both shared captures that only

──────── p. 71 ────────
                                                                                         71


lower the total: a directory captured whole already covers every removal beneath it, and
one commit identifier restores the committed state of every tracked file a repository reset
touches, so it is chosen once per repository, and only files with uncommitted changes

need copies of their own. Choosing for each path the cheapest mechanism that suffices,
and dropping the removals a captured directory already covers, therefore gives the least
total cost: the total is a sum of per-path costs, each at its minimum, plus the shared
captures, and dropping a covered capture can only lower it. The claim is minimality

relative to these mechanisms and this cost model, not over every conceivable way of
restoring a system; on a copy-on-write filesystem, for instance, a whole-directory
snapshot could cost less than the plan’s copies.
           Parts (a) to (c) are stated formally together below, so that the analysis can be

checked directly rather than reconstructed from prose.

  Algorithm 1     Effect analysis and capture planning for a generated command

  Input:      command c, working directory wd, capture mechanisms M
  Output:     verdict in {RECOVERABLE, RECOVERABLE_WITH_CAPTURE, UNRECOVERABLE}
              plan, a set of (mechanism, target) pairs
  State:      scope S: the working directory (initially wd) and variables;
              overlay V of paths created or removed by earlier parts of c;
              V ⊕ E is V updated with the creations, removals, and moves in E;
              doubt(V) keeps V's creations but makes its removals possible
              only, so a later write to such a path is still captured
  Marks:      [C] is off in the composition ablation, which returns {UNKNOWN};
              [R] is off in the resolution ablation, where RESOLVE returns ⊥

  function EFFECTS(node, S, V)
    if node = (A && B) then                              // B runs only if A did
      EA ← EFFECTS(A, S, V)
      return EA ∪ EFFECTS(B, S after A, V ⊕ EA)
    else if node = (A ; B), (A || B), or (A | B) then
      EA ← EFFECTS(A, S, V)            // B may run although A failed
      S′ ← S after A, its directory unknown if A ran cd
      return EA ∪ EFFECTS(B, S′, doubt(V ⊕ EA))
    else if node = if, case, or while then
      analyze each branch or body from S; afterwards a variable or
      directory on which the paths that may have run disagree is unknown
    else if node has a redirect target t then
      return EFFECTS(strip_redirect(node), S, V) ∪ {write-or-create(t)}
    else if node = (for x in W; do body; done) then           // [C]
      return the union, over w in EXPAND(W) in order, of
             EFFECTS(body, S[x := w], V), S and V carried between items
    else if node runs another command: sh -c s, eval, a wrapper
         such as sudo, find, or xargs then                       // [C]
      if its targets are known only at run time then
        T ← RESOLVE(node, S, V)                                     // [R]

──────── p. 72 ────────
                                                                           72


       if T = ⊥ then return {UNRESOLVED}
    return EFFECTS(inner command, bound to T if resolved, S, V)
  else if node's targets are known only at run time then
    // $( ), tar -x, unzip, rsync, git clean
    T ← RESOLVE(node, S, V)                                       // [R]
    if T = ⊥ then return {UNRESOLVED}
    return EFFECTS(node with its run-time targets bound to T, S, V)
  else
    // a simple command; argument-aware; no rule gives {UNKNOWN}
    if S's directory is unknown then return {UNRESOLVED}
    return RULE(name, args, S, V)
  end if
end function

function RESOLVE(node, S, V)
  // learns run-time targets, changing nothing
  d ← DRYRUN(node)
  // find with actions replaced by prints; xargs' producer;
  // git clean -n, tar -t, rsync -n; command substitutions
  if an earlier part of c changed anything d reads then return ⊥
  if EFFECTS(d, S, V) has an effect other than a read
     or d cannot run, or does not finish in time then return ⊥
  run d in the read-only sandbox       // only a proven read-only d runs
  return the targets d prints
end function

function VERDICT(E, M)
  if UNRESOLVED ∈ E or UNKNOWN ∈ E
     or some effect has no mechanism in M that restores it
    then return UNRECOVERABLE
  if every effect in E is a read, a create, a move, or falls on a path
     created earlier in c then return RECOVERABLE
  return RECOVERABLE_WITH_CAPTURE
end function

function PLAN(E, M)
  P ← ∅
  if E resets a git repository then
    P ← P ∪ {(commit identifier, repository)}
  for each path p with a write, a metadata change, or a removal
      that is not a move, in path order do
    if p was created earlier in c then continue    // nothing to lose
    if p is tracked and unmodified in a repository whose commit
       identifier is in P then continue      // the commit restores it
    if p's only effect is a removal
       and p lies under a directory already hardlinked in P
      then continue
    m* ← the cheapest mechanism in M that restores p's effects
    // hardlink for a removal, copy for an overwrite, record for a mode
    P ← P ∪ {(m*, p)}
  end for
  for each package or service change in E do
    P ← P ∪ {(inverse, change)}
  end for
  return P
end function

d) Experimental Platform: Conversational Interface Layer
         The conversational surface is designed as a persistent, full-screen chat interface

that serves as the primary user-facing interface when SynapseOS is active, with the
XFCE session beneath it remaining available as a logged fallback. The CLI and TUI
interface modes implementing this surface are complete; the full-screen GUI mode is in
development, and the readiness checkpoint governing its use in the study is described in

the System Environment Specifications. The interface accepts natural language input,
displays system responses and command output, and maintains conversational context
across the session. An intent parsing pipeline translates each user utterance into a shell

command for execution.
         Conversational context is session-scoped: history is held in memory for the
duration of the login session and is cleared on logout or reboot, with no persistence layer
in the thesis prototype. When accumulated history exceeds a fixed token budget — set

well below the 8,192-token context window configured for the intent parsing model,
which itself supports up to 32,768 tokens — a rolling window discards the oldest turns to
keep the conversation within budget.       Verbose command output — such as a full
directory listing or search result — is truncated to a compact summary before being

appended to history, preventing a single command’s output from consuming a
disproportionate share of the available context.

──────── p. 74 ────────
                                                                                       74


        SynapseOS is designed around a locally-hosted small language model (SLM) as
the default, model-agnostic inference backend, with cloud inference available only as an
explicit opt-in. Because the system operates at the OS level — processing every natural

language command and observing terminal output, file paths, command history, and
interaction patterns — routing inference through a cloud API would give an external
provider continuous visibility into the user’s computing activity. On-device inference
eliminates this exposure by default; the architecture reserves the option for a user to

supply an API key for a supported cloud provider and substitute a hosted frontier model,
entirely at their discretion; this path is not implemented in the thesis prototype. The
default configuration requires no API key, no internet connection, and no per-query cost,
making SynapseOS fully operational in offline and air-gapped environments.

        The primary SLM is Qwen2.5-Coder-3B-Instruct, an open-weights5 code-
specialized model that demonstrated the strongest natural language-to-bash translation
accuracy among models below 7B parameters in controlled evaluation [46]. Among the
models directly compared in that evaluation, its code-specialized pretraining produced a

clear margin over general-purpose models of comparable or larger size — 58% NL2Bash
accuracy with prompt engineering, versus 49% for Llama 3.2-3B and 37% for a LoRA-
fine-tuned Llama 3.2-1B — attributable to Qwen2.5-Coder’s training corpus of 5.5

trillion code tokens against Llama 3.2's general-purpose pretraining.          At 4-bit
quantization6, the model requires approximately 1.8 GB of memory and runs on the
target Debian 13 (Trixie) hardware without a dedicated GPU. The model may be fine-
tuned via Low-Rank Adaptation (LoRA)7 on the NL2Bash corpus8 and a custom

SynapseOS task suite to improve intent parsing. If it is, every NL2Bash item in the
evaluation corpus, and every description used for the model-generated partition, is
excluded from the fine-tuning data, and the model-generated partition is regenerated with
the fine-tuned model, so that the analysis is never scored on commands the model was

trained to reproduce.

         Accuracy is measured using an execution-based scoring methodology rather

e) Execution Pipeline

         Once the intent parser produces a shell command, SynapseOS passes it through
a confirmation gate and an undo journal before execution, following the reversibility-
and-guardrail framing proposed for LLM-powered natural language shells [12] and asks
only where it must, since a command that takes longer than a caregiver would is among

the costs VoicePilot’s guidelines for LLM speech interfaces warn against [32]. The gate
acts on the analysis’s verdict under one of two policies. Under the strict policy, the
default and the policy used in the validation study, it asks before every command whose
verdict is not plainly recoverable, that is, before every command that is recoverable only

with capture or unrecoverable, and on approval takes the captures the plan names before
the command runs.       Under the capture policy it asks only before unrecoverable
commands, and takes the plan’s captures for the rest without asking. Under either policy

the enumerated-pattern list is still consulted, and a command it flags also asks, so the list
can add a confirmation but never remove one. With the analysis disabled, the gate falls
back to the list alone. Captures use five mechanisms — full content backup, hardlink-
based trash, git HEAD capture, permission-metadata capture, or, for package and service

state, an inverse command — and are recorded to a persistent undo journal before the
command runs, so that a command approved in error remains recoverable. Rollback is

──────── p. 76 ────────
                                                                                            76


invoked through a dedicated undo command rather than from within the conversation.

Once the gate has passed it, the command is dispatched to a bash subprocess. Standard
output and standard error are captured and rendered in the conversational surface as the
system’s response to the original natural language input.
         SynapseOS executes only shell-expressible operations. The system’s capability

boundary is the Linux command-line toolchain: file management, process control, text
processing, package management, network configuration, and any application that
exposes a command-line interface.         GUI-only interactions — clicking buttons in
graphical applications, navigating web page elements, or interacting with visual-only

interfaces — are explicitly outside scope, in deliberate contrast to broader desktop agent
frameworks that additionally orchestrate GUI automation atop the existing session [53].
This boundary is intentional: it constrains the research to a tractable, verifiable claim that

the system can be built, evaluated, and defended within the thesis timeline.

2.4 Study session procedure
         Each participant session follows a standardized procedure conducted in the

following order:
      1. Briefing: The session facilitator explains the study purpose, session structure,
         and participant rights. The participant reads and signs the informed consent
         form. The pre-study screening questionnaire is administered to confirm group

         classification.
      2. System familiarization: For the SynapseOS condition, the participant is given a
         five-minute orientation to the conversational interface and shown how to enter
         natural language commands. For the native OS condition, no familiarization is

         provided — participants use their own operating system as they normally
         would. No task-specific training is provided under either condition.
      3. Task completion: The participant completes the full task set under the assigned

         condition. Tasks are presented one at a time via a printed task prompt sheet.
         The session logger captures start and end times automatically. Screen recording
         captures all on-screen activity. Participants are not asked to verbalize while
         tasks are timed. Concurrent think-aloud reliably slows task performance, and

         here it would slow the two conditions unequally, since narrating while
         composing a natural-language instruction competes for the same linguistic

──────── p. 80 ────────
                                                                                        80


        resources far more than narrating while pointing and clicking. Verbal data is
        instead collected retrospectively, by replaying the screen recording with the
        participant during the post-study interview.
      4. Post-condition questionnaire: Immediately after completing all tasks under a

        condition, the participant completes the SUS and NASA-TLX questionnaires for
        that condition.
      5. Condition changeover: If the participant has not yet completed both conditions,

        a short break is offered, the participant moves to the other machine (SynapseOS
        or native OS), and the session returns to step 2.
      6. Post-study interview: After both conditions are completed, the facilitator
        conducts a semi-structured interview of approximately 10–15 minutes covering

        perceived ease of use, trust in the conversational interface, preference between
        conditions, and open-ended feedback.
      7. Debrief: The facilitator discloses the full study objectives, answers participant
        questions, and thanks the participant. Session data is pseudonymized under the

        participant’s ID code at session close; the ID-to-consent mapping is retained for
        the fourteen-day withdrawal window described in Section 2.5 and destroyed
        thereafter.
        Total estimated session duration per participant: 90–120 minutes.

3.1 Evaluation against baselines (Objective 4)

──────── p. 83 ────────
                                                                                        83

a) Baselines
         Three baselines bound the comparison. The first is the enumerated-pattern

classifier already implemented in the prototype, which matches commands against a
hand-maintained list of known destructive shapes; it is the honest comparison because it
is what the system does today, not a weakened construction. The second is the same list
turned around to fail closed: every command in the line, including those inside

substitutions, loops, and wrappers, must be a known read-only form or the line asks. It
resolves no targets and plans no capture, and it is the strongest simple alternative,
because it removes the enumerated list’s silent failures on commands nobody named.
The upper bound on safety is a full pre-emptive copy of the working directory before

every command, which recovers everything and is unusable in practice; it establishes
what the minimal-plan computation must justify itself against on cost. That cost is
measured, not asserted: on this study’s ext4 evaluation machine, the cheapest real version

of a pre-emptive snapshot — a Timeshift-style hardlink snapshot via rsync -a --
link-dest, what a filesystem with no native snapshot falls back to — was timed
against a working directory of 1,165 real files (580 MB). A snapshot taken when nothing
had changed since the last one, or when exactly one file had, took 60–250 ms, because

deciding what to hardlink means visiting every entry in the tree regardless of what
changed; the capture plan for a comparable single-file command took 0–20 ms, set by
what the command touches rather than by the size of the directory around it
(pilot/snapshot_bench.txt). A copy-on-write filesystem such as btrfs or XFS

would close most of this gap, since it would not need to visit every file either; on ext4,
the filesystem this study is conducted on, it does not.

c) Statistical Comparison Against Baseline
         The analysis and each baseline are scored against the same labeled corpus,
which makes every comparison paired rather than independent: for each command, each

system either lets it run silently or does not, and either covers a loss or does not, and two
systems’ outcomes on that one command are not independent of each other. Significance
is therefore tested with McNemar’s exact test on the resulting 2×2 table of discordant
pairs — commands one system handles correctly and the other does not — at α = 0.05,

rather than with a two-sample test that would treat the corpus as though two different sets
of commands had been drawn.
         Silent loss is the safety measure (Table 3.3) and is reported on its own rather
than folded into an accuracy figure: it is tested over the 405 commands that lose

something or act outside the filesystem, the only commands on which it is defined, with a
95% Wilson confidence interval on each system’s rate; capture coverage is tested over
the 325 executable losses. For the analysis, the false-negative rate of Table 3.3 coincides

with silent loss, because a command it judges recoverable runs without being asked

──────── p. 86 ────────
                                                                                           86


about. The Wilson interval is used rather than the normal approximation because silent
loss is expected to be low for the stronger systems, and the normal approximation is
unreliable near the boundary of a proportion — the exact regime this metric sits in.
         A significance test states only whether the two methods differ, not by how much,

so each comparison is paired with an effect size — the paired-data equivalent of the
Cohen’s d reported for the user study (§3.5(d)).        The primary measure is the risk
difference: the algorithm’s accuracy minus the baseline’s, with a Newcombe-adjusted
95% confidence interval built for paired proportions, reported for silent loss and for

capture coverage. The odds ratio from the same 2×2 discordant-pairs table is reported
alongside it, since it is the effect-size convention most directly tied to McNemar’s test
itself and lets the result be compared against other paired-classifier studies that report it

in preference to a risk difference.
         With three baselines and two primary metrics, the comparisons that carry a
claim are the analysis against each of the first two baselines on silent loss and on capture
coverage. Four tests share one family, so significance is judged with a Holm correction

at a family-wise α = 0.05, and the uncorrected values are reported beside the corrected
ones. The full-snapshot baseline is a bound on cost and safety, not a comparison of
accuracy, and is reported descriptively. The remaining metrics of Table 3.3 are reported
where they arise: needless confirmation in (d) and Section 3.2; recovery success as the

share of executed commands the undo restored exactly, in (d); storage overhead from the
recovery check, where the median capture over the 304 commands that captured anything
was 0% of a full copy of the fixture, because most captures are hardlinks; time overhead

against the snapshot baseline in (a); and the contribution of composition and resolution
through the ablations in Section 3.2. The open-source checks are compared with the
analysis on silent loss by McNemar’s exact test and reported with Wilson intervals,
outside the Holm family because they are a check on the first baseline rather than a

primary comparison. Needless confirmation is tested as a second family of its own: the
analysis against the pattern list and against the fail-closed list, under each policy, with
McNemar’s exact test and a Holm correction across the four.

e) Threats Specific to This Evaluation
         Four are anticipated. First, corpus bias is addressed by partitioning, as described

in Section 1.2(a). Second, oracle validity replaces label subjectivity: the labels are

observed, so they cannot be argued with, but they are facts about one command on one
small fixture, run for a few seconds, seeing the working tree and not repository internals.

A loss that appears only on a differently shaped tree, or after the time limit, is labeled by

what happened here. The oracle’s own behavior is pinned by unit tests over commands
whose outcome is known, its exclusions are reported, and the bias they introduce —

toward commands that run on a small fixture, which excludes most NL2Bash candidates

that name paths or hosts the fixture cannot supply — is stated and not corrected. Third,

──────── p. 92 ────────
                                                                                           92


the algorithm and the labels are produced by the same research team, which creates a risk

that the labels reflect the algorithm’s assumptions; the generator is independent of the

analysis by construction, and the corpus is fixed by a recorded seed and hash before the
analysis is run on it. A fourth threat follows from the same fact: the analysis rests on a

table of what each known command does, written by the same team, and a table written
with the corpus in view measures the cases its author anticipated. The corpus is therefore

generated from several seeds. Earlier ones are used to correct the analysis and the undo;

the primary result is reported on one drawn after both are frozen, with the analyzer’s hash
recorded beside the result. That result is a single draw, so variation from one corpus

draw to another is not estimated; the development rounds, drawn from different seeds

before the design was frozen, showed the same pattern (zero silent loss for the analysis
and capture coverage near 90%), but they were not independent of the design and are not

offered as replication. Nor does the corpus verify the package and service part of the

model: the oracle can write only inside a fixture, so no command in the corpus changes
installed packages or running services under observation, and the inverse plans for such

changes are checked by the prototype’s unit tests rather than by execution.



3.2 Ablation studies (Objective 5)
         Chapter 1, Section 1.5 states the analysis’s claim as what it adds on top of a table

of what each known command does, not that it has none — a distinction raised directly

by this study’s adviser: how much of the result above comes from the algorithm itself,
and how much from that table? The algorithm adds two things a table cannot do, and

RQ5 asks for the contribution of each. Composition analyses through the commands that

hide another command’s targets: wrappers (sudo, env, nohup, timeout, and similarly
transparent commands), find -exec/-execdir/-ok/-okdir, xargs, eval, shell -c strings, and

for-loops. Runtime-target resolution learns targets that exist only while a command runs,
by running a form of it first proven read-only: command substitution and the producer

feeding xargs, the rewritten find expression, and the dry runs of tar, unzip, rsync, rename,

git, and the package and service tools. Three further configurations of the analyzer are

──────── p. 93 ────────
                                                                                         93


run over the identical held-out corpus, each identical to the one scored above except for

what it disables: composition, routed straight to the unresolved verdict an unknown

command receives; resolution, with no runner, so that every target it would have learned
is unresolved; and both, which leaves the per-command rule table alone. Every other

dispatch path is untouched, including the &&/pipe/subshell traversal that requires no

lookup beyond the table. If the table is where the result comes from, disabling either
should cost little.

         Each costs a great deal (Table 3.5). Capture coverage, verified by the same

sandboxed recovery check as the primary result, falls from 291 of 325 executable losses
(89.5%) to 115 (35.4%) without composition, to 148 (45.5%) without resolution, and to

104 (32.0%) without both. McNemar’s exact test on the paired discordant items rejects
equality overwhelmingly in each case, and not one discordant item favors an ablated

configuration over the full one: 176 items without composition, 143 without resolution,

and 187 without both. Silent loss is unchanged at 0.0% in every configuration, because
the fail-closed default that the analysis falls back to for anything it cannot resolve

depends on neither — a command it can no longer see through, or whose targets it can no

longer learn, is treated exactly as an unknown command already is, which asks rather
than runs silently. Composition and resolution are therefore not what keep the analysis

safe; the table and the fail-closed default already do that, which is why Table 3.4 found
the analysis indistinguishable from the fail-closed list on silent loss. They are what make

the analysis useful — the difference between asking about nearly everything and actually

recovering what was lost — and that is the part a table, however complete, cannot supply
on its own.

table: composition without resolution reaches 45.5% and resolution without composition
35.4%, against 32.0% for the table, while the two together reach 89.5%. Of the 143

items lost when resolution is disabled, 126 involve find (58 with -exec, 47 feeding xargs,

12 with -delete, and 9 in substitutions or archive commands), 6 are other xargs pipelines,
5 are rsync, 4 are git, and 2 are plain command substitutions: composition can see that

3.3 Validation study: evaluation dataset

        Sections 3.3 to 3.7 define the validation study, in which the analysis is deployed
in SynapseOS and exercised by participants. It exercises the platform on two task

datasets: the OSWorld benchmark task suite [49] for direct comparison with results in the
existing literature, and the custom cross-platform task suite described in Sections 1.1 and

1.5. The user study evaluation involves 40 participants (20 novice, 20 power users); the

baseline condition is each participant’s primary operating system — Windows 11,
macOS, or Linux with GNOME desktop — on a dedicated baseline machine.



3.4 Validation study: evaluation profile

        The study employs a within-subjects design with two conditions:

        Condition A: SynapseOS (conversational interface layer on the Debian 13
        evaluation machine)

        Condition B: Participant’s primary operating system (Windows 11, macOS, or
        Linux with GNOME desktop, as determined by pre-study screening, on the

        dedicated baseline machine)

        All 40 participants complete both conditions.               Condition order is
counterbalanced: 20 participants complete Condition A first, and 20 participants complete

Condition B first. Condition order is crossed with the two task forms in a 2×2 design,

four groups of ten (Section 1.2(d)). This distributes order effects across conditions;
residual asymmetric transfer is tested through the condition × order term of the model in

Section 3.6 and discussed in Section 3.7.

        The two participant groups — novice users and power users — are analyzed
both in aggregate and separately to determine whether the effect of the interface

condition differs across experience levels. Additionally, primary OS (Windows, macOS,

──────── p. 96 ────────
                                                                                          96


Linux) is recorded as a secondary grouping variable to determine whether results vary

across participant backgrounds, and prior conversational AI exposure (frequency of use)
is recorded as a covariate to determine whether familiarity with LLM-based tools

correlates with SynapseOS performance independent of OS proficiency. For the platform
measures, the main analysis is the pooled within-subjects comparison across all 40

participants; per-OS subgroup analyses and AI-exposure correlations are treated as

exploratory given the smaller per-group sample sizes they entail.



3.5 Validation study: criteria and formula
         The following metrics and formulas are used in the validation study. Items (a)

to (d) characterize the platform against each participant’s baseline; item (e) validates the

analysis in use.



a) Task Completion Time

         Mean task completion time is computed per condition per participant group.

Inferential testing and effect size reporting follow the procedures described in Section
3.6.



b) Error Rate

         Error rate is computed as the proportion of task attempts resulting in failure or

incorrect outcome:

           Error Rate = (Failed Tasks + Incorrect Outcomes) / Tasks Presented

         Error events are further categorized by type: intent parsing errors (incorrect bash

command generated), execution errors (bash subprocess failure), and recovery failures
(an undo that does not restore the prior state). Retries are recorded separately as attempts

and do not change the rate, whose denominator is the number of tasks presented, not

attempted (Section 2.2).     The same paired statistical test is applied to error rate
differences between conditions.

──────── p. 97 ────────
                                                                                          97


c) User Satisfaction

            SUS scores are computed per the standard scoring procedure [4] to produce a
score on a 0–100 scale; a score above 68 is conventionally treated as above-average

usability, a benchmark drawn from scores across a large sample of studies [39]. NASA-

TLX scores are computed as the unweighted mean of the six subscale ratings [14] to
produce a composite workload score per participant per condition.               Because a

conversational interface is meant to widen access rather than only to save time, workload

and task success are weighted alongside completion time among the platform measures,
not treated as secondary to it.

            Qualitative interview data is analyzed using thematic analysis to identify
recurring themes in participant perceptions of both conditions.



d) Statistical Significance and Effect Size

            All platform comparisons between conditions are tested at α = 0.05. Effect size

is reported using Cohen’s d, with thresholds of 0.2 (small), 0.5 (medium), and 0.8
(large). Sample size is justified by an a priori power analysis for a paired-samples

comparison at α = 0.05, two-tailed, computed against the noncentral t distribution.

Detecting a medium effect (d = 0.5) at 80% power requires 34 participants; the 40-
participant sample provides approximately 87% power at that effect size and detects

effects down to d = 0.45, giving margin for attrition and for exclusions arising from the
screening rule in Section 1.4. Analyzed alone, each 20-participant subgroup detects

effects of d = 0.66 or larger. The condition × group interaction, which characterizes

whether the platform serves the two groups differently, remains the least-powered
comparison in the design, since an interaction of a given size requires substantially more

participants than a main effect of the same size; it is therefore reported with effect sizes

and confidence intervals as the main descriptive finding for the platform, and is not
treated as a confirmatory significance test. The sample size is set by these platform

comparisons; the analysis-in-use measures of (e) are descriptive and need no power

analysis.

──────── p. 98 ────────
                                                                                         98


e) Analysis Decisions in Use

         Every command executed during the SynapseOS condition is logged with the

analysis’s verdict and capture plan and with a snapshot of the task directory taken
immediately before it ran (Section 1.1(d)), replayed on a copy of that snapshot in the

sandbox, and labeled exactly as the corpus is (Section 1.2(b)). It is then scored with the
corpus measures: silent loss in use, the proportion of data-losing commands that ran

without confirmation and without a capture; restoration in use, the proportion of data-

losing commands whose capture, applied by undo, restored the fixture exactly; and
needless confirmation in use, the proportion of commands that lose nothing on which the

participant was nonetheless asked. Each undo a participant invokes is also checked

against the state before the command it reverts. A command that changes installed
packages or running services, which a directory snapshot cannot hold, is scored instead

by recording the affected packages’ versions and the services’ active and enabled states
before it runs and checking them after undo. These are the measures by which the

platform validates the analysis: a silent loss here would be a failure of the analysis on a

command people actually cause, which the corpus could not reveal.



f) Benchmark Task Success
         For the adapted OSWorld tasks, the platform’s task success rate is the proportion

of tasks whose resulting system state matches the benchmark’s expected outcome, of the

tasks attempted. The adapted subset, the OSWorld tasks expressible as shell commands,
is fixed before data collection and its size reported with the result.



3.6 Validation study: data analysis plan

         The analysis-in-use measures of Section 3.5(e) are reported descriptively, as
proportions with Wilson 95% intervals over the commands executed, and set beside the

corpus results of Section 3.1; they are not tested for significance, because the number and

kind of commands participants cause cannot be fixed in advance. Quantitative analysis
of the platform measures proceeds in three stages. First, descriptive statistics — means,

──────── p. 99 ────────
                                                                                            99


standard deviations, and 95% confidence intervals — are computed for all platform

measures (task completion time, error rate, SUS score, NASA-TLX score) per condition

and per participant group. Second, the Shapiro-Wilk test is applied to assess normality of
each distribution before selecting the appropriate inferential test: the paired-samples t-test

for normally distributed data, or the Wilcoxon signed-rank test for non-normally

distributed data. Third, effect size is computed for all primary comparisons regardless of
statistical significance: Cohen’s d where the paired-samples t-test is applied, and the

matched-pairs rank-biserial correlation where the Wilcoxon signed-rank test is applied.
          Subgroup analysis is conducted separately for the novice and power user groups

to determine whether the effect of the interface condition differs across populations. The

interaction between interface condition and user group is examined to assess whether
SynapseOS produces differential effects depending on technical background. Because

condition order and task form are crossed between subjects (Section 1.2(d)), each

platform measure is modeled with condition, group, order, and task form as fixed effects
and crossed random intercepts for participant and task: error, which is binary per task, by

a logistic mixed model; completion time by a linear mixed model on its logarithm; and

the SUS and NASA-TLX scores, which are taken once per condition, by a linear mixed
model with a random intercept for participant, from which the condition × group and

condition × order interactions are read; the paired tests above serve as the per-comparison
checks.

          The benchmark task success rate of Section 3.5(f) is reported descriptively, as a

proportion with its Wilson interval, as are the telemetry measures of Section 1.1(d) that
are not otherwise analyzed (command latency and conversational turns per task), as

means with confidence intervals per participant group.

          Qualitative data from post-study interviews is analyzed using reflexive thematic
analysis following the six-phase procedure described by Braun and Clarke [3]:

familiarization with the data, initial code generation, theme search, theme review, theme

definition, and write-up.    In keeping with the reflexive approach, which treats the
analyst’s interpretation as part of the method and does not compute inter-rater agreement,

──────── p. 100 ────────
                                                                                          100


one member of the research team develops the codes and themes; the codebook and the
excerpts that support each theme are retained so that the analysis can be audited. Themes

are reported alongside representative participant quotations.



3.7 Validation study: threats to validity
         The following threats to validity are identified and the mitigations applied in this

study are described.

         Internal validity:
         Learning effect and asymmetric transfer: Participants may perform better on

         the second condition through familiarity rather than interface quality, and

         counterbalancing alone does not resolve this: it redistributes carryover but only
         cancels it when transfer is symmetric, which cannot be assumed here, since

         having solved a task once confers a different advantage in each direction.
         Mitigation: parallel task forms matched on category, difficulty, and step count

         are crossed with condition order in a 2×2 design, so no participant meets the

         same task twice; task order within a form is randomized; and condition order is
         entered as a between-subjects factor in the analysis, with the condition × order

         interaction inspected so that residual transfer is measured rather than presumed

         absent.
         Demand characteristics: Participants may behave differently from natural use

         because they know they are being observed. Mitigation: participants are

         instructed to complete tasks as they naturally would; the specific hypotheses of
         the study are withheld until the post-study debrief to reduce social desirability

         bias.
         Fatigue: Completing the full task set twice in a single session may degrade

         performance in the second condition independent of interface quality.

         Mitigation: a short break is offered between conditions and total session length
         is bounded to approximately 120 minutes.

──────── p. 101 ────────
                                                                                   101


Fallback reliance: GUI mode provides a participant-accessible fallback to the
underlying XFCE session if SynapseOS becomes unresponsive or a participant

wishes to stop using it mid-task; unrestricted, this would let a participant’s own

choice substitute for the interface under evaluation, confounding the within-
subjects comparison. Mitigation: every fallback invocation is logged with

participant ID, task ID, and timestamp; any task during which it is invoked is

excluded from the primary completion-time and error-rate comparison for that
task rather than counted as a SynapseOS success, and fallback-invocation rate is

reported separately as an exploratory reliability metric.
Single scorer and analyst: task outcomes on the native-OS condition, and the

qualitative themes, are judged by one team member, so their reliability cannot be

checked against a second judgment. The rubric is fixed before data collection
and applied identically to both conditions, the SynapseOS condition is

additionally checked by script, and the codebook and supporting excerpts are

retained for audit, but a residual scorer effect remains and is not estimated.
Too few data-losing commands: participants may cause few commands that

destroy anything, which would leave the analysis-in-use measures of

Section 3.5(e) with small denominators. Mitigation: the task suite is reviewed
before the pilot to include tasks whose natural solutions delete, move, or

overwrite files, and every analysis-in-use proportion is reported with its
denominator and Wilson interval, however small.

Unscoped undo: the undo command reverts the most recent entry in the undo

log, even one recorded in another directory or an earlier session. The manual
verification (Section 2.3) showed that after a task whose only destructive step

was declined, undo proposed reverting an unrelated earlier change.               Undo

previews what it will revert and requires confirmation, but a participant who
confirms without reading the preview could revert the wrong change, which

would confound the undo measures the validation study reports. Mitigation:

──────── p. 102 ────────
                                                                                                          102


          before data collection, undo will either be restricted to the current directory and

          session or the log will be reset at the start of each session; every undo
          invocation, and the entry it reverted, is logged.

          External validity:
          Sample generalizability: The study uses a university-recruited sample of 40

          participants across three primary OS backgrounds (Windows, macOS, Linux),

          which limits direct generalization to the broader population of computer users.
          Findings should be interpreted as indicative rather than definitive; replication

          with larger and more diverse samples is recommended as a direction for future

          work.
          Task generalizability: The evaluation is bounded by OSWorld coverage and the

          custom task suite developed for this study. Computing workflows outside this

          coverage are not evaluated, and results may not extend to all possible use cases.
          Platform specificity: SynapseOS is evaluated on a single hardware and

          software configuration — a dedicated machine running SynapseOS in GUI
          mode (XFCE desktop environment, X11 session) on a Debian 13 (Trixie) base.

          Performance characteristics on different hardware, display configurations, or

          Linux distributions may differ from the reported results.
