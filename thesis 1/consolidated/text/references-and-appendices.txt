        The appendices begin with the algorithm and its evaluation: the per-command

effect rules the analysis builds on (Appendix A), worked examples traced through the
analysis (Appendix B), the evaluation corpus and protocol, with how each reported result

is reproduced (Appendix C), and the defects found after the evaluation (Appendix D).
The validation study’s instruments and procedure follow (Appendices E to K).

        Appendices E to K reproduce the instruments administered to participants and

the procedure governing their administration. Wording, difficulty calibration, and task-
form equivalence are validated during the pilot study described in Chapter 3, Section 2.3

and revised before the main study begins; the instruments are reproduced here in the form

submitted for ethics review.

                                     APPENDIX A

                              Per-Command Effect Rules

         This appendix lists every command the recoverability analysis knows and what
it does with each. It is the enumeration on which the analysis of Chapter 3, Section 2.1

and Algorithm 1 builds: the rules give the effects of a single command (create, write,

remove, metadata, or a change of package or service state), and the algorithm composes,
resolves, and decides over them. A command that is not listed here is unknown, and an

unknown command is treated as unrecoverable, so the system asks before running it. The

tables     are      generated       from      the      prototype’s      source      code
(prototype/internal/effects, by make rulemap), and an automated test

fails whenever the generated map and the code disagree, so the appendix describes the
analysis as built rather than as intended. In total the map holds 39 commands with a

mutating rule, 13 transparent wrappers, 31 package, service, and system-state tools (5 of

them modeled with inverses), 42 commands that are always unrecoverable (Table A.8
lists mkfs.* as a family beside them), 17 interpreters, and 172 commands that are read-

only in their usual forms; a few of these, such as date and hostname, also appear in

Table A.9 for the forms that change state.
         Table A.1 gives the constructs through which effects are composed. Tables A.2

to A.5 give the mutating rules, grouped by kind of command. Table A.6 lists the

resolvers, which are the only commands the analysis itself ever runs. Tables A.7 and A.8
cover package, service, and system state and the commands that are always

unrecoverable, and Table A.9 the commands that are read-only only in some forms.

         A target that is known only when the command runs is found by running a form

of the command that cannot change anything. Table A.6 lists every such resolver. Each
runs with an output cap and a timeout, under bubblewrap, and not at all without it;

resolution is refused, and the command is unresolved, when a privileged command’s file
targets would have to be resolved, the working directory is unknown, or a bound is hit.

The package and service queries are the exception: they read system-wide state that is the

same for every user, so a privileged apt or systemctl command is still resolved
through its own simulation.

         Package, service, and system state is not a path, so it is handled separately. The

read-only forms of these tools (listing, status, simulation) pass. Of the remaining forms,
five tools are modeled: the tool is asked what would change, and the change is recorded

with the commands that reverse it (the inverse). Every other tool asks, for the reason
given in Table A.7.

a) Step by Step: Deleting Temporary Files

         The request “delete the temporary files” becomes the following command. Two

files match, one of them inside a subfolder.


find . -name '*.tmp' -delete


      1. Parse. The line is one simple command, find, with no wrapper around it.
      2. Dispatch. find with -delete is a composition handler (Table A.1), so its

         targets must be resolved rather than read from its words.

      3. Resolve.     The expression is rewritten to find . -name '*.tmp' -
         printf '0\t%p\0', in which -delete has become a -printf that

         reports which action would fire on which path. The rewritten form contains no
         action token, so it is run read-only. It prints one.tmp and sub/two.tmp.

      4. Effects. Each match becomes a remove: remove one.tmp and remove

         sub/two.tmp.

──────── p. 129 ────────
                                                                                      129


      5. Verdict. The effects are removals of regular files, not moves, so the verdict is

         RECOVERABLE_WITH_CAPTURE.

      6. Plan.    Each removed file needs only its pre-image kept, so the cheapest
         mechanism is trash, a hardlink into the undo journal that costs no copy at any

         size: trash one.tmp and trash sub/two.tmp.

      7. Gate, capture, run, undo. Under the default strict policy the system asks first.
         On confirmation, both files are captured, the command runs, and synapse

         undo restores both from the journal.

         With composition switched off (the ablation of Chapter 3), find is not resolved
through, and the same command is UNRECOVERABLE: the user is asked, but nothing

is captured, which is the behavior of an enumerated pattern list. Under sudo, the
command is also UNRECOVERABLE (“runs with elevated privilege, so its targets

cannot be resolved as the current user”), because root may reach files that a resolution

run as the user would not list.

          C.5 Labeling by the oracle

          Every executable command is labeled from one run on its fixture, and the oracle
shares no code with the analysis.

──────── p. 142 ────────
                                                                                              142


         Fixture. Every fixture starts from the same base tree of twelve small files
(a.txt, b.txt, notes.txt, app.conf, report.docx, data.csv, big.log,

src/main.go,              logs/x.log,               logs/y.log,              build/out.o,
backup/old.txt) and an empty directory tmp. To it are added the relative names

the command mentions: a name with a trailing slash, a name others are nested under, or

the target of cd, find, or -C becomes a directory, and a glob becomes a few matching
files. Absolute paths and paths that climb out with .. are not created. Whether the paths

a command would create (its last operand and its redirect targets) already exist is a choice

made by a hash of the seed and the command’s source; if the command does not finish
cleanly with that choice, the other is tried. Template commands that act on a repository

first run a setup that creates and commits one.

         Run. The command runs under bubblewrap with the whole filesystem mounted
read-only except the fixture, every namespace unshared (so there is no network), standard

input empty, HOME inside the fixture, memory and file-size limits, and a limit of three
seconds. A shell function makes sudo and doas transparent, since the fixture belongs

to the user who runs the oracle and a privileged prefix changes nothing about what the

command does to it.
         Label. The tree is recorded before and after the run: for every path, its kind,

permission bits (including the set-user-ID, set-group-ID, and sticky bits), owner, inode,

content hash, and link target. A command is labeled a loss (C) if a path that existed has
disappeared, unless the same inode now sits at another path, which is a move; or if a

path’s content, kind, link target, permission bits, or owner changed. Otherwise it is

labeled as losing nothing (R); paths it created do not count. Modification times are not
recorded, and a repository’s internal directory is not walked, since it is not a user file.

         Exclusions. A run that exits non-zero, times out, writes outside the fixture or
needs privilege, names a program that is not installed (exit status 127), or fails in the

harness is excluded and counted by reason, never labeled.

                                                                                      143


        External rule. A command is external, and is labeled unrecoverable (U) without
being run, if any command in it, after skipping the wrappers sudo, doas, env, time,

nohup, nice, xargs, exec, command, timeout, and ionice and their options, is

one of ssh, scp, sftp, mount, umount, kill, killall, pkill, shutdown,
reboot, halt, poweroff, useradd, userdel, usermod, passwd, groupadd,

mkfs, fdisk, parted, losetup, chroot, swapon, swapoff, modprobe,

insmod, iptables, ip6tables, docker, kubectl, or su; is curl or wget
with an option that sends data or names a request method (unless the request is forced to

be a GET); is rsync or scp with a remote host operand; or if any word names a disk
device under /dev/sd, /dev/nvme, or /dev/hd. The last clause is the one that

labeled a read-only listing of disk devices as external in the model-generated partition

(Section C.8). The twenty fixed external templates are external by construction; they
include dd onto a disk, crontab -r, and nc sending a file.

         C.9 Differential test of composition
         The differential test aims the oracle at the shape the corpus barely samples: lines

in which a later part runs after an earlier part changed, moved, or failed to change

something. Each generated line joins two or three short commands on the base fixture
with ;, &&, ||, a pipe, !, if with or without else, for, while, a brace group, or a

subshell. The parts are drawn by weight from commands that destroy something that

existed, commands that create, read, or fail outright, changes to the shell’s own state (cd
and assignments), uses of an assigned variable, and commands that fail when a directory

is read-only; in two of every five lines, on average, tmp or logs is first made read-only
so that a part fails. Every line the analysis lets run is executed, undone with V3, and

compared, exactly as in the recovery check; a line that is not restored exactly is a loss that

was neither asked about nor undone.
         The first draw found the eighth defect of Appendix D: before it was fixed, undo

restored 1,512 of the 1,536 lines the analysis let run. After the fix, six draws were run

(Table C.8). The last draw was not seen until the fixes were complete; its first run
restored 6,150 of 6,151 lines, and its one failure, a second name a line left for a restored

file, was then fixed.

or branched. Round 7 is drawn from NL2Bash and from templates, which are mostly
single commands and && chains, and the oracle excludes every command that exits non-

zero, so lines in which a later part runs after an earlier one failed are almost absent. Re-
scoring round 7 after each fix changed none of its decisions under any system compared,

re-scoring the model-generated partition after the seventh changed none of its 720, and

no reported result changed. Since the defects concentrate where parts of a line interact,
the differential test of Appendix C.9 is the safeguard for that region: it uses the same

sandboxed ground truth, needs no labels, and runs as one command, make

composecheck. Because each new draw surfaced rarer cases than the one before,
rarer shapes may remain, and the zero silent loss of Chapter 3 is a result on the corpus,

not a proof over all of bash.

                                     APPENDIX G

                          Custom Cross-Platform Task Suite

        The suite comprises sixteen tasks in two parts. Twelve core tasks span the four
categories defined in Chapter 3, Section 1.5 at three difficulty levels, and constitute the

main platform comparison. Four boundary tasks deliberately fall outside what a shell-

mediated interface can express; they are administered and scored but reported separately
from the main comparison, because their purpose is to characterize the capability

boundary honestly rather than to contribute to the between-condition contrast. Omitting

them would leave the suite composed only of work the command line does well, which
would make any favourable result difficult to defend.

        Every task exists in two parallel forms, matched on category, difficulty, and
number of required steps, and differing only in target. No participant encounters the

same form twice; form and condition order are crossed as described in Chapter 3,

Section 1.2(d). All prompts are phrased as human goals in plain language, containing no
shell syntax, no command names, and no interface-specific vocabulary, so that they are

equally answerable through natural language on SynapseOS and through native tools on

the baseline machine.
        Tasks T7–T9 require identical provisioning on all study machines — the same

designated applications present or absent, and the two test applications (SampleApp,

DemoTool) installed — so that the prompt means the same thing under both conditions
and on all three baseline operating systems; this provisioning is part of the facilitator

checklist in Appendix K. Task T9 is classified irreversible and is included specifically to
exercise the confirmation gate; T11 mutates file content and is included to exercise the

undo journal. Difficulty is assigned by the number of distinct operations required and the

specificity of the target, and is validated during the pilot study described in Chapter 3,
Section 2.3.

           Who is running this study. This research is conducted by undergraduate

Science.    It will be carried out only after review and approval by the University’s

           Why we are doing this. Most of what a computer can do is reachable only by
people who know how to write commands for it. We have built a system that lets a

person say what they want in ordinary language — for example, “find the files I changed

last week and put them in one folder” — and carries it out. We want to find out whether
that is genuinely easier to use than the desktop you already use, and whether it makes

more difference for people who have never used a command line.

           What you would do. You would attend one session of about 90 to 120 minutes.
You would complete a set of everyday computer tasks twice: once using our system, and

once using the operating system you normally use, on a computer we provide. Which
one you start with is decided in advance and is not a test of you. Afterwards you would

fill in two short questionnaires about each interface and take part in a 10 to 15 minute

conversation about your experience, during which we may replay the screen recording
and ask what you were thinking at particular moments.

           What we record. We record what happens on the screen during the tasks, audio

of the closing conversation, your questionnaire answers, and the times and outcomes of
the tasks. We do not record your name against any of this. Everything is filed under a

code.
