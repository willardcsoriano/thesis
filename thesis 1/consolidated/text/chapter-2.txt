                  REVIEW OF RELATED LITERATURE




2.1 Introduction to the Review
         This chapter reviews two bodies of research. The first is the program-analysis
and command-safety work on which the study’s recoverability analysis builds; the second
is the work on conversational and language-model-mediated interfaces to personal

computing, in which SynapseOS, the platform where the analysis is deployed, is
situated. The review spans nearly four decades of work on natural-language interfaces to
computing systems, from the symbolic-artificial-intelligence consultants developed for
the Unix shell in the late 1980s [49] to the large language model (LLM) agents that now
operate shells, graphical applications, browsers, and mobile devices.         It has three
purposes: to establish the conceptual vocabulary and technical foundations on which the
present study builds, to characterize the current state of the field and its recurring
limitations, and to locate precisely the gaps that the proposed recoverability analysis, and
the system in which it is deployed, are designed to fill.
         Works were included in this review if they satisfy at least one of seven criteria:
they analyze or guard shell commands or scripts, reason statically about a program’s
effects, or restore a system’s state after a change; they translate natural language into
executable system actions; they operate graphical, web, or mobile interfaces through

LLM-based reasoning; they address speech- or accessibility-driven interaction with
computing systems; they provide an evaluation environment for such systems; they
report a controlled empirical comparison between a language-mediated interface and a
conventional graphical one; or they set out the interaction theory, and the critiques of
natural-language interaction, against which such an interface must be judged. Works

2.2 Theoretical Framework
         This review rests on two frameworks of different standing. The first is the
theoretical basis of the study’s contribution: the program-analysis tradition of which the
recoverability analysis is an instance. The second organizes the literature on language-

mediated interfaces, in which the platform that deploys the analysis is positioned.



Program analysis: abstract interpretation and effect systems
         The technique on which the study’s recoverability analysis relies — determining
what a piece of code will do without executing it — is not new. It has a decades-long
history in programming-language theory under two related names, neither of which the
natural-language shells and command guards surveyed in this chapter draw on. Abstract
interpretation, introduced by Cousot and Cousot [8], is the foundational technique for
computing sound, conservative approximations of a program’s runtime behavior by
evaluating it over an abstract domain rather than its concrete one. Type-and-effect

systems extend a program’s type judgment with an explicit account of the side effects an
expression may produce, so that a compiler or static checker can reason about those
effects instead of leaving them implicit in execution; their types and effects can be
inferred by the algebraic reconstruction of Jouvelot and Gifford [20], and Talpin and
Jouvelot [44] give them a full formal treatment. The recoverability algorithm this study
contributes (Chapter 3, Section 2.1(a)–(c)) is an instance of this discipline, applied to a
question to which no work in the surveyed corpus applies either tradition: whether the
effects of a generated command can be undone, and what must be captured beforehand so

──────── p. 17 ────────
                                                                                          17


that they can be. The algorithm treats a generated shell command as an expression whose
effect is derived from its syntax and composed across its operators — an effect on the
filesystem and on the system’s installed packages and running services, rather than on a
type system’s abstract state — and it computes the recoverability verdict over that effect
set, not over the command’s name. This connects the algorithm to an established formal
lineage rather than presenting it as a bespoke heuristic. It also grounds the algorithm’s
one-sided soundness property — over-approximating destructiveness under uncertainty
rather than under-approximating it — in the same requirement abstract interpretation
itself imposes: a sound abstraction may lose precision, but it may never assert a property
the concrete execution does not actually have.
         Two parts of the analysis go beyond a purely static reading. The first concerns

targets known only at run time: for these, the analysis runs a form of the command first,
which makes it a hybrid of static and dynamic analysis. Its soundness still rests on the
static part, because a form is run only when the static analysis proves it can change
nothing, and a target that cannot be resolved this way falls back to unrecoverable. The
second is the recovery plan, a cost-minimizing choice over that abstraction: for each

effect the abstraction admits, it selects the cheapest capture that restores it, so the plan
inherits the abstraction’s over-approximation, capturing more than strictly necessary

when the analysis is unsure, never less. Combining static and dynamic analysis is not

new in general; what is specific to this study is the combination it uses: dry runs run only
after the static analysis proves them read-only, feeding a recoverability verdict, and a

recovery plan chosen over that verdict’s effects.
         Three properties of the analysis follow from this framework and are carried

through the rest of the study. Its abstract domain is the effect set: what a command would
read, create, write, remove, or alter in metadata, or change in the system’s installed

packages and running services, not the command’s name alone.              Its semantics is
compositional: the effects of a line are built from the effects of its parts through the

operators that join them, which is what an enumerated list of command patterns cannot
express. And its soundness is one-sided: whatever cannot be determined is treated as

──────── p. 18 ────────
                                                                                            18


unrecoverable, so that the analysis may ask more often than necessary but may never

declare a destructive command safe, a guarantee that holds relative to the per-command
rule table and to the filesystem as it is when targets are resolved, shortly before the

command runs (Chapter 3, Section 2.1(a)).



The four-layer interaction pipeline

         The second framework organizes the interface literature. The heterogeneous
systems surveyed in this chapter — shell translators, web and mobile agents, desktop

automation frameworks, and accessibility interfaces — differ widely in platform, action
space, and evaluation method, yet they address a common problem: converting a user’s

expressed intent into effects on a computing system. To compare them on common

ground, this review adopts a four-layer interaction pipeline of Input, Reasoning, Action,
and Operating-System Integration. The framework is informed by the component view

of large language model (LLM)-brained graphical user interface (GUI) agents in the
survey of Zhang and colleagues [53]; its perception, planning, and action components are

recast here as four layers for language-mediated computing interfaces as a class, with an
added layer for the scope of an interface’s effect. Figure 2.1 depicts the pipeline and

situates the layers relative to one another.

         The Input layer concerns how a user expresses intent, whether by typed text,
speech, or structured shortcuts. The Reasoning layer concerns how that intent is parsed

into a plan and grounded into the affordances of the environment. The Action layer
concerns how a grounded plan is executed — through command translation, through

binding to native application programming interfaces (APIs), or through simulated
keyboard and mouse operations. The Operating-System Integration layer concerns the

scope of computing an approach can affect, from a single application to an entire
operating system.

         This framework suits that literature for three reasons. First, it is modality-
neutral: because it abstracts over whether intent arrives as text, speech, or gesture and

whether action is realized through shell commands, API calls, or simulated clicks, it

accommodates the full span of surveyed systems without privileging any one interaction
style, a necessary property for a review that spans command-line, graphical, and

accessibility work. Second, it is diagnostic: locating each system’s principal limitation at
a specific layer — visual grounding as a Reasoning-and-Action failure, or narrow

platform coverage as an Operating-System Integration limitation — turns an otherwise
flat catalogue of systems into a structured comparison, and the comparative synthesis of

§2.9 makes this layer-by-layer positioning explicit. Third, it is directly applicable to the
platform.   SynapseOS, in which the analysis is deployed (Chapter 3, Figure 3.1),

instantiates the same pipeline: it accepts natural-language intent at the Input layer, parses
it with a locally-hosted small language model at the Reasoning layer, translates it into

shell commands executed through the standard toolchain at the Action layer, and spans
the full graphical session rather than a single application at the Operating-System

Integration layer. The pipeline therefore serves both as the organizing lens for the

interface literature and as the vocabulary in which the platform is later positioned.
Within it, the analysis sits between the Reasoning and Action layers, where a generated

command is about to take effect.

2.3 Historical Foundations of Natural-Language Interfaces

        The aspiration to let users describe what they want in ordinary language and
have a computer carry it out is not new: an early system of this kind for an operating

system, the Berkeley Unix Consultant of Wilensky and colleagues [49], was already
operational by the late 1980s.    It was an intelligent natural-language interface that

allowed naive users to learn about the Unix operating system through conversation in

ordinary English, addressing both the natural-language-frontend problem and the
consultation problem, and so distinguishing itself from systems intended only as

command translators. Built on the KODIAK knowledge representation, it incorporated a
user-modeling component that represented the user’s knowledge state and a teaching

component through which users could extend its knowledge base in natural language.
The system demonstrated end-to-end natural-language consultation about Unix,

successfully answering "how do I," definitional, and problem-solving questions.
Critically, its authors identified knowledge acquisition as the principal bottleneck:

extending the system to a new domain required substantial hand-engineering, a concern
that directly foreshadows the contemporary problem of LLM-based agents requiring per-

application grounding data.
        The intervening decades saw natural-language interaction treated primarily as a

supervised-learning problem. Representative of this pre-LLM era, the work of Li and

colleagues on mapping natural-language instructions to mobile user-interface action
sequences [23] trained dedicated phrase-extraction and grounding transformers on hand-

annotated action sequences, achieving 70.59% accuracy on predicting complete ground-
truth action sequences on its benchmark but remaining bound to its purpose-built datasets

and architectures. The decisive shift came with the introduction of in-context reasoning
patterns for LLMs. ReAct, introduced by Yao and colleagues [51], collapsed the multi-

stage supervised pipeline into a prompting strategy: the language model is prompted to
alternate between free-text "Thought" steps that update its plan and "Action" steps that

interact with an external environment, with observations fed back into subsequent

──────── p. 21 ────────
                                                                                         21


reasoning.    Implemented purely as a prompting strategy without fine-tuning, ReAct
nonetheless outperformed imitation-learning and reinforcement-learning baselines that

required thousands of training trajectories.

         The historical significance of this transition is twofold, and it frames the
remainder of this review. First, it explains why progress in the field has been so rapid

since 2023: the methodological foundations became portable across modalities and
platforms in a way that the earlier dataset-bound approaches were not. Nearly every

system surveyed in the sections that follow inherits from ReAct the convention of
interleaving reasoning traces with environment-affecting actions. Second, this shared

inheritance underscores a corresponding fragility: these systems inherit the failure modes
of LLM reasoning — hallucinated actions, plan inconsistency, and brittleness on long-

horizon tasks — alongside their capabilities, a concern that the evaluation literature
reviewed in §2.8 quantifies.



Interface paradigms and the case against natural language

         The aspiration to a natural-language interface has a long-standing critique that
remains unanswered, and a review that omitted it would misrepresent the state of the

question.    Shneiderman’s account of direct manipulation [41] holds that interfaces
succeed when the objects of interest are continuously visible, when actions upon them are

rapid, incremental, and reversible, and when their effects are immediately apparent —
properties that let a user build and maintain an accurate model of system state. Norman

formalized what an interface does for a user as the bridging of two gulfs [31]: the gulf of
execution, between an intention and the actions a system makes available, and the gulf of

evaluation, between the system’s response and the user’s ability to interpret it. Hutchins,
Hollan, and Norman [18] argued that direct manipulation narrows both, by making an

interface feel like the object of interest itself rather than a description of it.

         A language interface sits awkwardly against nearly every one of those
properties. An utterance is not continuously visible, not incremental, and not reversible

by the same gesture that produced it; the set of available actions is not displayed, so the

──────── p. 22 ────────
                                                                                           22


user must guess at the system’s capabilities rather than see them. Shneiderman and Maes
debated precisely this trade-off between direct manipulation and interface agents [43],

and Shneiderman argued subsequently that speech and language interaction consume the
same cognitive resources a user needs in order to hold a task in mind, where pointing

does not [42]. Empirical work on modern conversational agents has largely borne the
concern out: Luger and Sellen documented a persistent gulf between what users expected

a conversational agent to understand and what it actually did [27], and Clark and
colleagues found that the properties people value in human conversation transfer poorly

to interaction with an agent [7].
         This critique is the strongest argument against the interface premise of the

platform, and it shapes the platform’s design rather than being set aside by it. Two of its

three concerns are addressed directly. The gulf of evaluation is narrowed by displaying
the generated command and its raw output rather than reporting an outcome in prose, so

that the user sees what was actually done rather than a description of it.              The
irreversibility of an utterance is answered by the confirmation gate and the undo journal,

which restore by mechanism the reversibility that direct manipulation obtains for free.
The third concern — that a user cannot see the boundary of what the system is able to do

— is not solved by this design and is carried forward as an acknowledged limitation.
         Beyond the critique lies the comparative question, which is older than the

current literature and considerably less settled than it is often assumed to be. It is widely
held that the command line’s power is inaccessible to most people in practice, yet the

best-known controlled comparison of command, menu, and iconic interfaces, conducted
by Whiteside and colleagues across seventy-six users and seven systems [48], concluded

that interface style itself predicted neither performance nor preference: careful design did,
and there was no necessary tradeoff between ease of use and ease of learning. That

finding is as much a caution for the present study as a motivation for it. It warns against

attributing to a conversational paradigm what may in fact belong to the quality of one

──────── p. 23 ────────
                                                                                         23


particular implementation, and it is a principal reason this study measures a specific

system against a specific baseline rather than claiming to measure one paradigm against
another.



2.4 Natural-Language-to-Shell Translation

           The thread of the literature most directly related to the platform concerns the
translation of natural language into shell commands. Because SynapseOS grounds user

intent into commands executed through the standard Linux command-line toolchain, the
accuracy, safety, and context-awareness of natural-language-to-Bash translation are of

central relevance to its design.
           The standard dataset for this task is NL2Bash, from Lin and colleagues [24]:

over nine thousand English descriptions paired with Bash commands, collected from
question-and-answer sites, tutorials, and course material. It supplies the human-written

commands of this study’s evaluation corpus (Chapter 3, Section 1.2(a)). Because its
commands were collected for translation rather than for safety, most of them are read-

only, and that corpus is therefore sized against the labels it must contain rather than
drawn as the dataset comes.

           Westenfelder and colleagues [47] address this translation problem directly.

Their work constructs a manually verified test set of 600 instruction–command pairs and
a training set of 40,939 pairs, and it introduces a functional-equivalence heuristic that

reaches 95% confidence in determining whether two Bash commands produce the same
effect, allowing automated evaluation to move beyond exact-string matching to a

measure of whether a generated command actually accomplishes the intended task. Their
fine-tuned models substantially outperform zero-shot baselines, demonstrating that fine-

tuning specifically on command-translation data is effective. The authors identify two
persistent limitations, ambiguity in user instructions and the absence of system context at

translation time — the contents of the current directory, the user’s command history, and

──────── p. 24 ────────
                                                                                             24


environment variables — and integrating context-aware retrieval is a direction their
findings point to, one that the persistent conversational session of SynapseOS is well

positioned to supply.

         The feasibility of deploying such a system without reliance on a hosted frontier
model is supported by the large-scale evaluation of Jacobs and colleagues [19], who

assess a broad range of locally deployable open-source LLMs on Bash command
generation. Their work provides an empirical anchor for the viability of running natural-

language-to-Bash translation on local, open-weights models of modest size, the
deployment posture adopted by SynapseOS for reasons of privacy and offline operation.

Taken together, the shell-and-command-line thread establishes that natural-language-to-
Bash translation is tractable, that safety and reversibility are central rather than incidental

concerns, and that local deployment is feasible. Yet no surveyed shell-level system has
been evaluated with users against the conventional workflow it would supplement. How

such systems guard the commands they generate, and what static analysis of shell
commands can establish, are taken up in §2.5.



2.5 Command Safety, Static Analysis, and Recovery

         The literature closest to the study’s algorithm concerns how shell commands are
checked before they run. It falls into three groups: guards, which decide whether a

generated command may run; analyses, which reason about what a shell program does;
and recovery mechanisms, which restore a system after the fact. Each supplies part of

what the study needs. None, as this section shows, determines before a command runs
whether its effects can be undone and captures exactly what undoing them requires.



Guards

         The most direct response to the risk of a generated command is a guard, which
decides whether the command may run at all. Where Westenfelder and colleagues study

translation accuracy (§2.4), Gyawali and colleagues study safety. Their NaSh system
[13], published under the operating-systems classification, proposes guardrails for an

──────── p. 25 ────────
                                                                                          25


LLM-powered natural-language shell for Linux: the model proposes a candidate
command, a guardrail layer between it and the user evaluates the command against

safety, reversibility, and confirmation criteria, and the user receives a structured preview
before execution.    Because LLM outputs may be unintended or unexplainable, the

authors note, guardrails are required for user error recovery; they leave two problems
open: recovery and rollback mechanisms for irreversible system operations, and

empirical user evaluation.     The study’s recoverability analysis addresses the first,
recovery from an operation already approved; its validation in use, the second.

         Shipped tools follow the same design. Coding agents guard the commands they
execute with lists of command patterns: the dangerous-command check of OpenAI’s

Codex CLI [32] and cc-safety-net [21], a pre-execution guard used with several agentic
coding tools, are representative open-source examples, and both are scored as baselines

in Chapter 3, Section 3.1(a). Both assume a version-controlled project, where deleting

project files is routine and version control, not the guard, makes a mistake recoverable.
Files on a personal computer, the setting of this study, have no such safeguard.

         Every shipped guard surveyed decides by permission: allow-and-deny lists over
command prefixes match the command against an enumerated set of patterns judged

dangerous, and the command is then allowed, refused, or escalated to the user. NaSh
[13] goes further as a proposal, adding summaries of what a command would affect and

selective undo, but leaves the mechanisms for both open. Permission answers whether a
command may run, not whether it can be undone once it has, and the two answers differ.

Refusal protects a user only until they approve, which, for any system that must let work
proceed, is most of the time. This gap, which the guards share, is the one the study’s

algorithmic contribution addresses.
         The distinction matters because enumeration does not compose. A pattern list

matches a command in isolation, but a generated line routinely chains operations with

different recovery requirements: a removal, a version-control reset, and an in-place edit
joined by &&, with redirects and command substitution changing what each actually

touches. No enumeration of command prefixes expresses that, and extending the list

──────── p. 26 ────────
                                                                                           26


does not converge: each newly named tool leaves the next one unnamed.                   The

comparison that matters, though, is not only with a list of dangerous commands. Turned
around to ask before every command it does not recognize as read-only, a list closes the

gap left by unnamed commands at the cost of asking about everything unfamiliar; this
fail-closed list is the strongest simple baseline. The analysis does not escape enumeration

either: its effects come from a table of what each known command does, and a command
the table does not name is treated exactly as the fail-closed list treats it, by asking. What

it adds is composition over the table, read-only resolution of run-time targets, and the

capture that lets a command run and still be undone. The study therefore claims what the
analysis adds to the fail-closed list, not the verdict alone: capturing what would be lost so

that undo restores it, and asking far less often, both made possible by composition and
resolution. Determining recoverability over a composed command, and computing the

minimal information needed to reverse it, is the open problem this study takes up (RQ1–
RQ3), and it separates the present work from the guardrail designs surveyed above.

         Risk in tool-executing agents has also been studied by evaluation rather than
guarding. ToolEmu emulates tool execution with a language model so that agents’

failures, including destructive actions, can be found before deployment [38]. It measures
how risky an agent is across many cases; it does not protect a user from the particular

command an agent is about to run.



Static analysis of shell programs
         Static analysis of shell scripts is comparatively little studied, and existing work

targets properties adjacent to recoverability rather than recoverability itself. ABash [28]
performs abstract interpretation over bash’s variable-expansion semantics to catch

common expansion bugs, with taint tracking, but it does not consider what a script’s
commands would do to the filesystem if executed correctly. Smoosh [12] gives the

POSIX shell a mechanized, executable small-step operational semantics which, run
against the POSIX and Modernish test suites and its authors’ own, proved more

conformant to the standard than seven widely used shells: exactly the kind of ground-

──────── p. 27 ────────
                                                                                         27


truth semantics against which a static effect analysis would need to be checked, though
Smoosh defines the semantics rather than analyzing programs written in it. Closest is

CoLiS [2], which applies symbolic execution to the more than twenty-seven thousand
POSIX-shell maintainer scripts in the Debian package archive, scripts that run as root

during install, upgrade, and removal, to find violations of properties Debian policy

requires, among them idempotence: running a script a second time causes no further
harm. Idempotence and recoverability are related but distinct. For example, rm -rf

/var/cache/pkg is idempotent, since a second run does no more damage, and destructive
on its first run, since nothing restores what it removes unless that was captured

beforehand; conversely, a command can be recoverable without being idempotent, if each
run produces a new, independently reversible effect. CoLiS, the nearest prior application

of static effect reasoning to shell scripts, therefore stops short of the present question:
verifying that re-execution is safe does not determine whether the first execution can be

undone. No work identified in this review derives a recoverability verdict for a shell
command from its statically computed effects; that is the specific gap the study’s

algorithmic contribution fills.



Recovery after the fact
         Guards and analyses act before a command runs. A separate literature restores a

system after something has gone wrong, asking not what a command will destroy but
how to recover what was destroyed. Three kinds of mechanism are relevant.

         Filesystem snapshots are the most widely deployed, and one shipped natural-
language shell relies on them: ANOLISA’s checkpoint tool snapshots an agent’s

workspace at file level before key operations or after each round of conversation, and
rolls back to any snapshot [1]. A copy-on-write filesystem such as btrfs snapshots a

whole subvolume cheaply, because a snapshot shares its blocks with the live filesystem
until they are modified [37], so snapshots can be taken on a schedule or before system

updates; without copy-on-write, as on the ext4 on which this study is conducted, a

snapshot must visit every file in the tree, a cost measured in Chapter 3, Section 3.1(a). A

──────── p. 28 ────────
                                                                                         28


snapshot needs no knowledge of the command it protects against, which is both its
strength and its limit: restoring one returns the whole subvolume to an earlier moment,

discarding every later change along with the unwanted one, and it cannot tell the user
beforehand whether a command will lose anything. Versioning file systems, the second

kind, keep old versions of individual files: the Elephant file system retains them under
per-file policies that decide when an old version may be forgotten [39]. Recovery is then

per file and needs no foresight, but storage is paid for on every change, mistaken or not,
and obtaining it means replacing the filesystem.

         The third kind, undo at the level of a service or the operating system, makes
recovery a property of the system’s design. Operator Undo intercepts and logs users’

interactions with an e-mail service before they reach it, so an operator can rewind the
service’s state, repair it, and replay what users did since [6].        Operating system

transactions let a program group system calls whose effects can be rolled back as a unit
before they commit [35]. Intrusion recovery systems such as Taser log system activity so

that an attack’s effects can be identified and reverted afterward while legitimate changes

are kept [11]. Each restores more completely than any list can, but each requires what
this study’s setting lacks: a service built to be undoable, a kernel and programs that use

transactions, or continuous logging of all system activity.
         A different route learns a command’s effects by running it where they are

contained. The try utility runs a command in a semisolate over the current environment,
built from Linux namespaces and a union filesystem, captures its effects on the

filesystem, and lets the user inspect them and apply, discard, or apply part of them [22].
Its authors motivate it with cases this study shares, among them a language-model-

suggested find -exec that deletes a user’s files. It is the closest prior work to the
analysis’s dry runs, but its knowledge comes from elsewhere. try executes the command

itself, shows its effects to a user who must judge them, and does not contain effects
outside the filesystem, such as network calls; the present study runs only commands it

has first proven read-only, decides from the command’s structure what it would destroy,

──────── p. 29 ────────
                                                                                        29


and captures exactly that beforehand. For the same reason, try is not scored as a baseline

in Chapter 3: it decides nothing about a command, since it runs every command and
leaves what to keep to the user.

         The present study takes a narrower path between these literatures. Like a guard,
it acts on one command before it runs, on an unmodified system and filesystem; like a

recovery mechanism, it restores. It captures only what that command would destroy, as
determined by analysis, so its cost follows what the command touches rather than the size

of the system, and it can say beforehand whether undo will be possible. Table 2.1
compares the surveyed approaches on these properties.

2.6 Graphical and Computer-Using Agents

        A parallel and larger body of work addresses computer-using agents1 — systems

that operate graphical environments by issuing actions and observing results. Although
SynapseOS operates at the command line rather than by simulating graphical interaction,

this literature is essential context: it establishes the dominant architectural patterns,
defines the recurring technical bottleneck of visual grounding2, and, through its platform

coverage, reveals a gap in the setting where the analysis is deployed. The work is
organized here by the platform each system targets — web, mobile, and desktop —

together with the vision-language foundation models on which many depend.



Web agents

        The web has been the most heavily studied environment for language-guided

agents. Mind2Web, introduced by Deng and colleagues [10], is the first dataset for
developing generalist web agents that follow language instructions across diverse real-

world websites, comprising over two thousand open-ended tasks collected from 137
websites across 31 domains; its accompanying two-stage model uses a small language

model to filter candidate elements from large documents before invoking a larger model
to choose among them. WebArena, introduced by Zhou and colleagues [57], provides a

fully self-hosted, reproducible web environment of functional website clones and
evaluates 812 long-horizon tasks for functional correctness rather than trajectory

similarity, establishing a challenging benchmark on which contemporary models
achieved completion rates far below human performance. Zheng and colleagues [56], in

their SeeAct framework, decouple visual understanding from action: the model observes
a screenshot, generates a textual plan, and a separate step grounds that plan onto page

elements. Their central finding is diagnostic for the entire field — with oracle grounding

provided, the model completes 51.1% of tasks on live websites, substantially
outperforming a text-only baseline at 13.3%, but performance degrades sharply when

grounding must itself be inferred, confirming visual grounding as the principal
bottleneck.

──────── p. 32 ────────
                                                                                        32


Mobile agents

        Mobile-device control has produced large-scale datasets and progressively more
autonomous agents. The pre-LLM work of Li and colleagues [23], discussed in §2.3,

established the grounding problem for mobile interfaces. Android in the Wild, from
Rawles and colleagues [36], contributes a dataset of 715,000 episodes spanning 30,000

unique instructions, in which actions are gestures at arbitrary screen coordinates rather
than operations on indexed interface elements, exposing the challenge that actions must

be inferred from visual appearance rather than from a structured model of the interface.
AppAgent, from Zhang and colleagues [55], operates Android applications through a

simplified action space of taps and swipes and learns to use new applications through
autonomous exploration or by observing human demonstrations, generating application-

specific documentation that matched or exceeded human-written documentation.

Mobile-Agent, from Wang and colleagues [46], adopts a purely vision-centric approach
that requires no system metadata, using optical-character-recognition and icon-detection

modules to locate interface elements — achieving broad applicability across mobile
environments at the cost of vision-grounding errors that require recovery mechanisms.



Desktop and cross-application agents
        Desktop agents are the most direct graphical analogue to the present work, and

their limitations are the most instructive. ScreenAgent, from Niu and colleagues [30], is
a vision-language-model-driven agent for cross-application desktop control that operates

in a plan–act–reflect cycle, specifying actions as coordinates and key sequences; its

authors acknowledge that vision-only grounding is less reliable than approaches with API
access. WinClick, from Hui and colleagues [17], targets Windows-desktop grounding

and observes that most existing GUI agents rely on structured data formats such as the
document object model or HyperText Markup Language, which are unavailable across

general desktop environments; it therefore performs visual grounding directly from
screenshots. UFO², the "Desktop AgentOS" of Zhang and colleagues [54], is the most

ambitious desktop system surveyed: it fuses the native Windows accessibility framework

──────── p. 33 ────────
                                                                                              33


with vision-based parsing in a hybrid action mechanism, dispatching subtasks from a
coordinating agent to application-specialized agents.       Its authors argue that existing

computer-using agents are hindered by shallow operating-system integration, fragile
screenshot-based interaction, and disruptive execution; they identify adaptation to other

desktop platforms, such as Linux and macOS, as future work, and frame cross-platform
deployment as groundwork for a unified ecosystem of desktop automation solutions.

UFO² acts on the user’s behalf, as an automation layer beside the user’s own Windows

session, whereas the platform built for this study is operated by a person, turn by turn.
AgentOS, from Liu and colleagues [25], goes further in ambition, proposing that a

natural-language portal replace application silos as the way a person uses the operating
system, but it is offered as a research direction, without a built system or an evaluation.



Contemporaneous commercial systems (as of October 2026)
         The systems surveyed above are research artifacts. Shipping systems move

faster than the peer-reviewed literature, and one is close enough to this study to warrant
explicit positioning; what follows describes it as of October 2026. Alibaba Cloud Linux

4 Agentic Edition, ANOLISA, is a Linux distribution for AI agents whose default shell

accepts ordinary language alongside shell commands and forces confirmation before
operations it treats as unrecoverable, such as restarting the machine [1]; its checkpoint

tool is described in §2.5. It is the nearest shipped system to the present work. It is built
to run AI agents on cloud servers, whereas the platform studied here runs a local model

under a person’s direction, but the difference that matters here lies in recovery: it
recovers by snapshot, restoring everything since a checkpoint, rather than by determining

what one command will destroy and capturing exactly that. That difference reflects the
question this study asks, which is not whether conversation is a better interface, but

whether what a generated command destroys can be determined and captured before it
runs; the platform’s interface is the setting in which the answer is validated.

──────── p. 34 ────────
                                                                                         34


Vision-language foundation models

         Underlying many of these agents are vision-language models trained specifically
for interface understanding. CogAgent, from Hong and colleagues [16], is an eighteen-

billion-parameter visual language model specialized for GUI understanding and

navigation, using both low- and high-resolution image encoders to recognize the small
icons and text typical of graphical interfaces. It supports the position that pure-vision

GUI agents are viable when the underlying model is trained appropriately — but at a
compute cost, and with the cross-platform generalization limitations common to the

entire graphical-agent literature.   Across web, mobile, and desktop, these systems
demonstrate broad capability within a single platform class, while consistently

identifying visual grounding as an unsolved bottleneck.



2.7 Accessibility and Speech-Driven Interaction

         A distinct thread of the literature approaches conversational computing from the

perspective of accessibility, targeting users with motor, speech, or cognitive needs. It is
relevant to the present study in two ways: it provides the most rigorous human-centered

evaluations in the field, and it exhibits a limitation that is the mirror image of the
mainstream agent literature, and so it bears on the setting of the platform rather than on

the analysis.
         VoicePilot, from Padmanabha and colleagues [33], is a framework for using

LLMs as speech interfaces to physically assistive robots for individuals with motor
impairments. Although its immediate target is robotic assistance rather than desktop

computing, it is included here because it is the most rigorous human-centered evaluation
in the LLM-speech-interface literature. The authors derive five design guidelines from

an iterative evaluation that ended in a study with 11 older adults at an independent living
facility. Among them is that a command should execute in about the time a caregiver

would take; the present study’s confirmation step adds to that time whenever it asks,

which is one reason the study measures what asking costs as well as what it protects.
DexAssist, from Mehendale and Walishetti [29], targets web navigation by users with

──────── p. 35 ────────
                                                                                             35


fine-motor impairments using two LLMs in tandem — one to interpret voice commands

and a second to map the interpretation onto interface elements with fallback strategies —
reducing the misinterpretation failures of single-model voice navigation on dense

layouts.     The architecture of van Dam [45] proposes retrofitting LLM-based
conversational interfaces onto existing single-application graphical interfaces, exposing

an application’s navigation graph through a tool protocol and handling voice input
through real-time speech recognition; its author observes that most production

applications were never designed with speech in mind, making such retrofitting an
ongoing challenge.

           More recent work continues to mature the components required for speech-
driven interface control. Han and colleagues, in GUIRoboTron-Speech [14], advance

automated GUI agents driven directly by speech instructions, while Park and colleagues,
in R-VLM [34], contribute region-aware visual grounding for more precise identification

of on-screen elements. What unites this thread is that it operates at the level of the

individual application or interaction technique rather than at the level of the session itself,
presupposing an underlying conversational surface on which to run. A conversational

interface layer over the whole session could provide one. Accessibility is accordingly
positioned not as a target of the present study, which scopes it out for recruitment and

ethics reasons, but as a possible later use of its platform.



2.8 Evaluation Environments and Benchmarks

           The rapid proliferation of computer-using agents has been accompanied by

increasingly rigorous evaluation environments, which establish both the current ceiling of
the field’s capability and the methods by which that capability is measured. The most

consequential is OSWorld, from Xie and colleagues [50], a benchmark of 369 real-world
computer tasks in a real-computer environment spanning Ubuntu, Windows, and macOS,

and directly relevant to the present study as the source of a real-task suite against which
benchmark comparability can be established. At its 2024 release the margin it measured

was stark: humans achieved 72.36% success where the best evaluated model reached

──────── p. 36 ────────
                                                                                         36


12.24%. Its successor, OSWorld 2.0 [52], evaluates 108 long-horizon workflows whose
median item requires roughly an hour and a half of skilled human operation, and there the

best frontier configuration completes only 20.6% of tasks outright. The reported failures
concentrate not in interface navigation but in tracking constraints across a long task,

absorbing information that arrives mid-way, and verifying a result before declaring
completion. The field’s ceiling has moved substantially; it has not been reached. Direct

comparisons between interfaces are rarer. AXIS, from Lu and colleagues [26], compares
an API-first agent with unaided manual operation by people in Microsoft Word, in a

within-subjects design with a cloud-hosted frontier model, and Zhou and colleagues

compare screen-only graphical agents with command-line agents across 440 matched
desktop tasks [58].

         Complementing the benchmark literature, the survey of LLM-brained GUI
agents by Zhang and colleagues [53] synthesizes the field through 2024, organizing it

around the components of perception, planning, action, and memory, and informing the
four-layer view adopted in §2.2 of this review. It enumerates the field’s open challenges

— accurate element localization, knowledge retrieval, long-horizon planning, and safety-
aware execution control; of these, safety-aware execution control is the one closest to the

present study.        What the evaluation literature reveals, however, is a specific
methodological limitation: rigorous as these benchmarks are, they measure the

autonomous task completion of agents acting on a user’s behalf, not the comparative
performance of a human user working through a conversational interface versus a

conventional graphical one. That distinction motivates the evaluation design reviewed in

§2.10.

          Six patterns emerge from the comparison.



Bifurcation by coverage scope
          The first pattern is a split by coverage scope. Shell-level work [13, 47] and

single-application work [33, 45] sit at the narrow end; cross-application desktop, web,

and mobile agents sit at the broad end, but each within one platform class. No system in
the surveyed corpus implements a working conversational layer over the full graphical

session that has been empirically validated against the conventional desktop workflow it
would supplement. The Unix Consultant [49] came closest in ambition four decades ago,

but its pre-LLM foundation kept it from scaling beyond demonstration, and the recent
systems nearest that ambition do not fill the gap either: AgentOS [25] is a research

direction without a built system, and UFO² [54] is an automation layer that acts on the
user’s behalf (§2.6).



Execution mechanism at the action layer

          The second concerns the execution mechanism at the Action layer: how a system
turns a decided intent into an effect, and what each choice costs. The literature divides

among command translation, API binding, and GUI simulation, trending toward hybrid

──────── p. 40 ────────
                                                                                         40


execution [54] that prefers structured access where available and falls back to vision.

Vision-only systems [30, 46] gain broad applicability at the cost of grounding fragility;
structured-access systems gain precision at the cost of per-environment integration. The

Unix Consultant, notably, worked purely at the consultation layer without executing
actions, reflecting an underappreciated principle that the confirmation-gated design of the

present study revisits: the agent that explains can be safer than the agent that acts.



Visual grounding as the principal bottleneck
         The third is that visual grounding is the field’s principal bottleneck, identified

explicitly by both SeeAct [56] and the GUI-agents survey [53]: GPT-4V reaches 51.1%
with oracle grounding, and its sharp degradation without the oracle is attributable in

significant part to grounding failure. The bottleneck belongs to the graphical-simulation
approach. A command-line approach, which grounds intent into shell commands rather

than on-screen pixel regions, sidesteps it, at the cost of being bounded by what the
command line can express.        Direct comparison qualifies that tradeoff. Across 440

matched desktop tasks, screen-only graphical agents pass 59.1% while command-line

agents reach only 48.2%, so the shell is not automatically the stronger substrate; but
command-line agents whose skills are augmented under the guidance of verifiers reach

69.3%, the highest of the three conditions, and the authors attribute most of the
command-line deficit to incomplete skill coverage rather than model capability [58]. The

shell, then, is bounded by what its tools cover, which is the platform’s concern; the
analysis is concerned with what happens once a command is produced.



Scarcity of comparative user evaluation
         The fourth concerns evaluation method: systems in this field are rarely tested

with people, and seldom against the interfaces those people already use. Most surveyed

systems are evaluated by architectural demonstration [13, 45] or curated task benchmarks

[10, 46, 50, 57]; user studies are rare, and the comparisons that exist are narrow:
VoicePilot [33] conducts a substantive human-centered evaluation of LLM-based

──────── p. 41 ────────
                                                                                        41


interaction, and AXIS [26] compares an API-first agent against unaided manual operation
in a within-subjects design, but within a single application, on a single platform, with a

cloud-hosted frontier model. No surveyed work compares a conversational interface
against the conventional graphical workflow across operating-system-level tasks on the
same population. That gap belongs to the setting of this study, and the validation study
addresses it in passing rather than as a research question.



The operating-system substrate
          The fifth concerns the operating-system substrate: the Linux desktop, as the

person using the machine meets it, is a platform the surveyed work leaves unserved.
Windows [17, 54], Android [36, 46, 55], and the web [10, 56, 57] are each heavily
represented, while the Linux work that exists is aimed elsewhere than the end user’s

desktop session: NaSh [13] addresses Linux at the shell level as a design proposal;
Alibaba Cloud’s ANOLISA ships a natural-language Linux terminal with approval gating
and rollback, but scoped to server and DevOps workloads; and OSWorld [50] includes
Ubuntu as an evaluation platform rather than a deployment target. No surveyed system

implements a conversational session layer for the Linux desktop addressed to the person
using the machine, despite Linux’s wide use for development and server work.



Shared lineage and its fragility
          The sixth is the field’s shared intellectual lineage and its fragility. As §2.3
established, nearly every post-2023 system inherits the ReAct [51] convention of

interleaving reasoning with action, which explains both the field’s rapid progress and the
pervasiveness of LLM-reasoning failure modes across it. That fragility makes safety and
recoverability mechanisms, rather than raw capability alone, decisive for any deployable
system.

          One related but distinct class needs explicit positioning: AI-assisted coding
agents, which translate natural-language intent into shell commands and execute them
under human oversight, the same basic mechanism this study adopts. They are excluded

──────── p. 42 ────────
                                                                                         42


from Table 2.2 not because they are industry rather than academic work (a substantial

share of the literature surveyed here is likewise unrefereed preprint) but because they
differ on every axis that matters here: they are built for software engineers working
within an existing code repository and powered by large models on remote infrastructure,
whereas SynapseOS is addressed to any user of the machine regardless of command-line

fluency and runs a locally hosted small language model. The mechanism is shared; the
population and the model’s location are not.
         These patterns converge on a fourfold research gap. First, the shipped systems
surveyed guard a generated command by permission, matching it against an enumerated

list of dangerous patterns, while recovery restores wholesale, needs a system built for it,
or, in try [22], runs the command for the user to judge; none determines before a
command runs what it would destroy and captures exactly that (§2.5). This is the gap the

study’s algorithmic contribution addresses. Second, no system in the surveyed corpus
provides a conversational interface as a general route to operating a personal computer:
addressed to the person using the machine, spanning the operating system rather than one
application, and evaluated as an interface rather than as an autonomous agent. Existing

systems are automation utilities that act on the user’s behalf, measured by how often they
complete a task unattended, not by whether a person directs them more effectively than
the interfaces they already have. Third, the work that exists on an open platform targets
servers, agents, and benchmarks rather than an end user’s desktop session. Linux is

chosen because its desktop session, toolchain, and command line are open to inspection
and modification, making it the condition of the experiment rather than its subject; the
missing end-user desktop work there is what the platform addresses. Fourth, controlled
comparison of a language-model-mediated interface with the conventional graphical

workflow, with people, exists only within a single application, on a single platform, with
a cloud-hosted frontier model [26]; no such comparison was found in the surveyed
corpus for operating-system-level tasks under a locally-hosted model and an explicit

safety gate.

──────── p. 43 ────────
                                                                                            43


         SynapseOS is positioned against the other three gaps, as the platform on which
the analysis addressing the first is validated. It is a conversational interface layer for the
Linux desktop that translates natural-language intent into shell commands under a
confirmation gate driven by the analysis, and it is evaluated against each participant’s

own operating system. The closest prior work, NaSh [13], proposes guardrails for an
LLM-powered natural-language shell (generated code that remains analyzable, selective
undo, and summaries of what a command would affect) as a design position, explicitly

leaving their mechanisms and evaluation as open work. The present study contributes a
mechanism for part of that position: an analysis that derives what a command would
affect from its structure, through composition and the read-only resolution of run-time
targets, and a plan that captures the least that undoing it requires, evaluated against

ground truth observed wherever a command acts on files.



2.10 Review of the Methodological Literature

         The methodological literature bears on the study’s two kinds of evidence in
turn. The primary one, the evaluation of the algorithm, follows established practice for
judging program analyses. A sound analysis is judged first by what it misses, its false

negatives, and only then by what its false alarms cost, since soundness is the property it
claims [8]; silent loss is therefore the primary measure and needless confirmation the
cost. Ground truth for every command that acts on files is observed by execution, not
assigned by judges, and the 80 commands whose effects lie outside the filesystem are

labeled from a fixed table. Execution is the standard by which executable semantics of
the shell are validated against what shells actually do [12], and it underlies the scoring of
generated Bash commands against what was intended [47]. Part of the corpus comes
from a public dataset, NL2Bash [24], so the evaluation does not rest only on commands

written by the analysis’s own authors.       Ablation, rerunning the analysis with each
component switched off, tests the claim that particular components produce the result.
Comparisons scoring every system on the same commands use the standard paired-
proportion tests: McNemar’s exact test on the commands two systems handle differently,

──────── p. 44 ────────
                                                                                          44


Wilson intervals for each proportion, Newcombe intervals for each difference, and
Holm’s correction across each family of tests. Chapter 3, Sections 1.2, 3.1, and 3.2 give
the design.

         The second kind of evidence comes from the validation study, in which people
use the analysis deployed in an interface, so its evidence turns on how a conversational
interface should be evaluated. The surveyed work evaluates in three ways, each with a

characteristic limitation. Architectural demonstrations [13, 45] establish feasibility but
give no performance evidence. Curated task benchmarks [10, 50, 57] give reproducible,
quantitative measures, but of agents completing tasks autonomously on a user’s behalf,
not of a human working through an interface. Human-centered user studies, exemplified

by VoicePilot [33] and AXIS [26], give the most direct evidence of an interface’s value to
real users, but they are rare in this literature and, where present, confined to a single
application rather than the operating system as a whole.
         These limitations motivate a design grounded in established human-computer-

interaction practice. It is within-subjects: each participant completes tasks under both
SynapseOS and their own operating system, serving as their own control so that between-
person variance is removed as a confound, with the order of conditions counterbalanced

to distribute learning effects evenly.    Its expert baseline is each participant’s most
familiar environment rather than a fixed, possibly unfamiliar alternative, so no participant
is measured on an environment they have not used. This strengthens the ecological
validity that the surveyed benchmark-only evaluations lack; because familiarity then

favors the baseline, however, the comparison characterizes the platform against each
participant’s practiced environment rather than isolating interface quality (Chapter 3,
Section 1.2(d)). The instruments are established rather than constructed for the study: the
System Usability Scale [5] for perceived usability, interpreted through subsequent large-

sample analysis [40], and the NASA Task Load Index [15] for perceived workload. A
convergent mixed-methods structure in the sense of Creswell and Plano Clark [9] collects
the quantitative measures of task completion time and error rate and the qualitative
evidence of user experience concurrently and integrates them at interpretation. The

──────── p. 45 ────────
                                                                                           45


qualitative data, from retrospective think-aloud over the screen recording and a semi-

structured interview, are analyzed with Braun and Clarke’s thematic analysis [3], a
widely adopted six-phase approach for identifying and reporting patterns in qualitative
data.   Finally, the reviewed systems shape what is measured: the reversibility-and-
guardrail framing of NaSh [13] and VoicePilot’s guideline that a command should take no

longer than a caregiver would [33] together motivate measuring both what the
confirmation gate and undo protect and what they cost the participant.

2.11 Summary
         This chapter reviewed two literatures. The first, on which the study’s algorithm
builds, is program analysis, with abstract interpretation and type-and-effect systems [8,
20, 44] as its formal basis. Around it, the command guards of natural-language shells and

coding agents [13, 21, 32] decide by permission rather than by effect; the static analyses
of shell programs [2, 12, 28] target properties adjacent to recoverability but not
recoverability itself; recovery mechanisms, from snapshots, including ANOLISA’s [1], to
operating system transactions [6, 11, 35, 37, 39], restore after the fact, but wholesale or

only on a system built for it; the try utility [22] previews a command by running it; and
ToolEmu [38] measures the risks of agents rather than guarding a given command. The
second literature, in which the platform is situated, covers nearly four decades of natural-

language and LLM-mediated interfaces to personal computing, organized along a four-
layer pipeline of Input, Reasoning, Action, and Operating-System Integration.             Its
foundations set the long-standing aspiration to a natural-language interface to a real
operating system [49] and the methodological shift, driven by in-context reasoning [51],

that made the current generation of systems possible. The critique of natural-language
interaction from direct manipulation [7, 18, 27, 31, 41–43], with the controlled
comparison of Whiteside and colleagues [48], cautions that a conversational interface

must earn its place, which shapes the platform’s design. The shell thread, most directly
related to the proposed design, showed that natural-language-to-Bash translation is
tractable [47], that safety and reversibility are central [13], and that local deployment is
feasible [19], leaving the extension from shell to session, and empirical user evaluation,

open. The graphical-agent literature across web, mobile, and desktop [10, 16, 17, 30, 36,
46, 54–57] set the field’s architectural patterns and its recurring bottleneck of visual
grounding, and the accessibility thread [14, 29, 33, 34, 45] revealed a complementary
limitation a general conversational interface layer could address. Finally, the evaluation

literature [50, 52, 53] traced a capability ceiling that remains low on long-horizon work
and a methodological gap: interfaces are seldom evaluated comparatively against the
conventional workflow with real users, and, in the surveyed corpus, not at the level of the

operating system itself.
         Taken together, the surveyed works reveal the fourfold gap set out in the
synthesis: no analysis of what a generated command would destroy, with every shipped
guard deciding by permission, every shipped recovery restoring by snapshot, and try [22]

leaving the judgment of a contained run to the user; no conversational interface over a
whole desktop session for the person using it; no coverage of the Linux desktop; and no
controlled comparison of a conversational interface against the conventional workflow at
the level of the operating system. The study’s research addresses the first through a

recoverability analysis of generated shell commands, evaluated against ground truth from
sandboxed execution wherever a command acts on files; the other three describe the
setting in which that gap arises. SynapseOS, the conversational interface layer for the

Linux desktop built as the analysis’s experimental platform, is where the analysis is
deployed and validated in use, in a controlled, within-subjects comparison against each
participant’s own operating system. Chapter 3 sets out that methodology.
