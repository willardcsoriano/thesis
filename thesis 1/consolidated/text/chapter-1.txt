                                  INTRODUCTION




1.1 Background of the Study
            Ask a person to gather every photo they took last June into a single folder and

they will do it — opening a file browser, sorting by date, selecting, dragging. Ask a
computer the same thing, in those same words, and for fifty years it could not. The
instruction has always had to be translated first into the machine’s own vocabulary: a

path, a menu, a sequence of clicks, or a command typed with exact syntax. The
graphical desktop made that translation visual rather than textual, but it did not remove

it. The person still adapts to the machine. This study asks whether that is now
optional.
            The dominant paradigm for personal computing has remained largely

unchanged since the early 1980s, when the graphical desktop — icons, menus, and
pointer-driven interaction — was established through the Xerox Star and Apple Lisa
lineage. Despite its longevity, a parallel research tradition has long explored whether

users should instead be able to describe what they want in natural language and have
the computer carry it out. The earliest serious system in this tradition, the Berkeley

UNIX Consultant, was already operational by the late 1980s [45]. Decades later, the
rise of large language models (LLMs) and multimodal foundation models1 has
reopened this thread with substantially greater technical capability.

            The field that has emerged sits at the intersection of human-computer
interaction, operating systems, natural language processing, computer vision, and

program analysis. On the shell side, recent work has demonstrated that LLMs can

embedded as a Unix primitive with appropriate safety guardrails [11, 43]. On the
graphical side, so-called computer-using agents2 now operate desktop and mobile

applications by combining native APIs with vision-based grounding [49, 50]. On the
web, language-guided agents complete tasks across realistic websites with measurable

but limited reliability [52, 53]. A converging research thread approaches the same
technical problem from an accessibility perspective: speech-driven GUI command
mapping for users with motor and speech impairments has progressed from voice-to-

text dictation toward voice-to-action agents, with recent work on speech-instructed
GUI agents [12] and region-aware visual grounding [31] demonstrating that the
underlying components are maturing rapidly. Yet the gap between demonstration and

deployable replacement remains substantial. Capability on short, self-contained tasks
has advanced quickly, but sustained computer work has not: on OSWorld 2.0, a

benchmark of long-horizon tasks whose median item takes a skilled human roughly an
hour and a half, the best frontier configuration completes only 20.6% of tasks outright
[48].

        This rapid progress has been uneven across platforms. Windows is heavily
represented in the desktop agent literature [15, 50], Android in the mobile agent

literature [33, 42, 51], and the browser in the web agent literature [8, 52, 53]. Linux
desktop coverage, by contrast, is conspicuously absent: existing work either addresses
Linux only at the shell level [11] or treats it as one of several evaluation platforms

rather than a primary target [46].      No surveyed system implements a working
conversational session layer3 for the Linux desktop, despite Linux serving as the
substrate for most developer and server-side workflows.

        Capability raises a question of safety, and it is the question this study takes as
its subject. A system that writes a shell command from a request and runs it acts on the

user’s own files, so the cost of a misunderstood or over-broad command is measured in
lost data. Shell commands are programs: their targets may be hidden inside other
commands or computed only while they run, so what a command will change cannot

1.2 Gap and Opportunity

         Capability brings a risk the field has not addressed. A system that turns a
request into a shell command and runs it acts on the user’s own files, and a command

generated from a misunderstood request, or one simply broader than intended, can
delete or overwrite them with no way back. Every surveyed system guards against this
by permission: the generated command is matched against a list of patterns judged

dangerous and is then allowed, refused, or put to the user [11]. A list of this kind
cannot see what a command will actually touch when its targets are hidden inside
another command, such as find -exec or xargs, or are computed while it runs,

and it cannot back up what it does not know will be lost. Whether a generated
command can be undone, and what must be saved beforehand so that it can be, is a

question of program analysis rather than of interface design, and no surveyed system
answers it.
         Four compounding gaps in the existing literature therefore motivate the

present research. First, no surveyed system determines, before a generated command
runs, what it would destroy, or captures exactly that so that the command can be

undone; this is the gap the study’s algorithmic contribution addresses. Second, no
implemented and empirically evaluated system places a conversational layer over the
conventional desktop session as a whole. The idea is no longer unclaimed — AgentOS

[22] proposes a natural-language portal in place of the graphical desktop — but it is
offered as a research direction, without a built system or an evaluation. The systems
that are built automate on top of the desktop rather than replacing it: UFO², for

instance, positions itself as a “Desktop AgentOS” but operates as an automation layer

atop the existing Windows shell, deliberately confining itself to a separate desktop so

that agent and user do not interfere [50]. Third, the Linux work that exists serves
servers and agents rather than the desktop session of an end user. NaSh addresses
Linux at the shell level as a design proposal without evaluation [11]; shipping natural-

language shells such as Alibaba Cloud’s ANOLISA pair intent translation with
approval gating and rollback, but scope themselves explicitly to server and DevOps

workloads; and OSWorld includes Ubuntu as an evaluation platform rather than a
deployment target [46].      Fourth, controlled comparison against the conventional
graphical workflow exists only for narrow slices of the problem. AXIS evaluates an

API-first agent against manual operation within a single application, Microsoft Word,
using a cloud-hosted frontier model [23], and the accessibility literature evaluates
assistance for specific populations [30]. No study compares a conversational interface

against the conventional workflow across operating-system-level tasks, on a Linux
desktop, driven by a locally-hosted small model, under an explicit safety gate. The first

of these gaps is the one this study’s research addresses. The other three describe the
setting in which it arises, and they are why the analysis is deployed and validated in a
conversational interface layer rather than studied on a corpus alone.

         Notably, the accessibility-focused thread of the field exhibits the inverse
limitation. Speech-to-GUI mapping research targets specific user populations — users
with motor impairments, speech disorders, or cognitive disabilities — with specialized

techniques such as speech-instructed GUI agents and resilient visual grounding [12,
31], but operates at the level of individual applications or interaction techniques rather

than at the level of the session layer itself. These approaches presuppose an underlying
conversational system surface on which to run, yet no such surface exists. This
complementarity sharpens the opportunity: a general-purpose conversational interface

layer would serve not only mainstream users but also provide the substrate that
accessibility-specific configurations require.

         These gaps present an opportunity that is algorithmic first.          Whether a
generated command can be undone, and what must be saved beforehand so that it can

be, can be decided by analysing the command itself: deriving what it would change
from its syntactic structure, resolving the targets it computes while it runs before it

runs, and capturing exactly what it would destroy. That analysis is independent of the
interface and the model that produced the command, and it is this study’s research
contribution. It needs a setting in which generated commands act on a real user’s files,

and the remaining gaps supply one.           SynapseOS, built for this study, adds a
conversational interface layer to a Linux desktop that continues running underneath it,
in the way a new interactive shell such as zsh sits over an unchanged kernel and core

utilities: the desktop shell, window manager, and application launcher are left in place,
as are the kernel, the core system utilities, and the existing application ecosystem, and a

user retains every route to the machine they already had and gains a third. It serves as
the experimental platform on which the analysis is deployed, demonstrated, and
validated in use, with people of differing technical fluency and with the conventional

desktop workflow as the baseline.



1.3 Statement of the Problem
         A system that turns a request in ordinary language into a shell command and
runs it acts directly on the user’s own files and system state. Language models have

made such systems practical: a person who cannot write a shell command can now

have one written for them, and conversational interfaces, coding assistants, and agentic
tools increasingly execute what a model writes. A generated command can be wrong,
or broader than the request intended, and whether what it destroys can be restored
depends entirely on what was saved before it ran. The tools that execute generated
commands today decide only whether to run them, by matching the command against a
list of patterns judged dangerous; they cannot determine what a command will touch

when its targets are hidden inside another command or computed while it runs, and

                                                                                          6


they save nothing. This study addresses that problem: determining, before a generated

shell command runs, what it would change, whether the change can be undone, and the
least that must be captured beforehand so that it can be. It is a problem of program
analysis rather than of interface design, and the surveyed systems leave it open. It is
studied in the setting where it is most acute — a conversational interface layer through
which a person who does not read shell syntax operates a Linux desktop — but the

analysis takes a command as a string and is independent of the interface and the model
that produced it.
         Specifically, the study seeks to answer the following questions:
      1. How can the effect of a shell command on a system be represented formally,
         so that whether the command can be undone is a predicate over that
         representation, and so that anything the representation cannot determine is

         treated as unrecoverable rather than safe?
      2. Can a command’s effects be derived from its syntactic structure before it runs
         — composed through the wrappers, find -exec, xargs, loops, and
         substitutions that hide its targets, with targets known only at run time resolved
         by commands first proven read-only — without executing anything that

         changes the system?
      3. Given those effects, can a minimum-cost set of pre-images be computed
         whose capture is sufficient to restore the prior state, and does restoring from it
         return the system to that state?
      4. Against an enumerated list of destructive patterns and a list that refuses every

         command it does not recognize, does the analysis lose less data silently,
         restore more of what is lost, and ask the user less often?
      5. How much of that result do composition and runtime-target resolution each
         contribute, beyond the per-command rule table on which both rest?
         A further question is answered by validation rather than posed as a research

question: whether the analysis’s decisions hold when it is deployed in a working
interface and exercised by people, whose commands the evaluation corpus does not

1.4 Objectives of the Study
        The general objective of this study is to design and evaluate a recoverability
analysis for shell commands generated by a language model: an algorithm that
determines, before a command runs, what it would change, and computes the
minimum-cost set of pre-images that must be captured for the command to be undone.

The algorithm is deployed in SynapseOS, a conversational interface layer for the Linux
desktop built for this study, which serves as the experimental platform on which the
algorithm is demonstrated and validated in use.
        Specifically, this study aims:
      1. To formalize an effect-semantics model for shell-command recoverability: the

        kinds of effect a command can have on the system, a recoverability verdict
        over them, and a one-sided soundness rule under which anything that cannot
        be determined is treated as unrecoverable (RQ1).
      2. To develop an effect-composition algorithm that derives a command’s effects
        from its syntactic structure rather than its name, composing them through

        wrappers, find -exec, xargs, loops, and substitutions, and resolving
        targets known only at run time through dry runs it first proves read-only
        (RQ2).
      3. To develop a minimum-cost recovery-plan generation algorithm that
        computes, from a command’s effects, the cheapest set of captures sufficient to
        restore the prior state, and to verify by sandboxed execution that restoring

        from that plan does so (RQ3).
      4. To evaluate the recoverability analysis against pattern-based and fail-closed
        baselines, and against the command-safety checks of open-source AI agents,
        on a held-out command corpus whose ground truth is obtained by sandboxed

──────── p. 8 ────────
                                                                                             8


         execution, measuring silent data loss, verified restoration, and needless
         confirmation, with statistical testing (RQ4).

      5. To quantify the contribution of composition and of runtime-target resolution
         through ablation studies that disable each, and both, while leaving the per-
         command rule table unchanged (RQ5).
         Each objective is algorithmic and measurable, and each would stand if the
interface were removed, because the analysis takes a shell command as a string.
SynapseOS is the means by which the algorithm is deployed, demonstrated, and

validated in use, not an objective in itself: the validation study (Chapter 3,
Sections 3.3–3.7) measures how the analysis’s decisions hold on commands
participants cause, and characterizes the platform through task success, time, error rate,
and workload against each participant’s own primary operating system.

       Against that, the study contributes the following.
    1. An algorithm for recoverability analysis of generated shell commands.
       Given a command produced by a language model, the algorithm finds what it
       would change and, where that can be reversed only with preparation,

       computes the minimal set of pre-images sufficient to restore the prior state. It
       makes two claims and no others: it sees through the wrappers a line hides its
       effects behind, and it resolves targets computed at run time before the
       command runs. Deciding whether a command is dangerous is not among
       them: a list that refuses every command it does not recognize reaches the same

       verdict on the commands studied here, and the contribution is the capture that
       follows. Its formal basis is an effect semantics: a command is represented not
       by its name but by the set of system effects its syntactic structure implies —
       which paths it would read, create, write, remove, or alter in metadata —

──────── p. 10 ────────
                                                                                 10


resolved against a working directory and propagated through the operators that
join commands into one line. The recovery plan is a minimum-cost cover of
that effect set, and the verdict a predicate over it. This is the study’s principal

technical contribution and the subject of RQ1. It is distinguished from the
permission models used by existing agentic tools, which decide whether a
command is allowed by matching it against enumerated patterns, and which
take no pre-images: a permission model can refuse a command, but it cannot
restore what an approved command destroyed. It is equally distinguished
from privilege mechanisms such as sudo and polkit, which gate on who is

acting rather than on what is about to happen. The algorithmic difficulty lies
in composition and in targets that exist only while the command runs — a
single generated line may chain several operations through &&, pipelines,
subshells, and redirects, and rm $(ls *.log) or find -delete names nothing until
it executes — which is what an enumerated pattern list cannot express.

Soundness is deliberately one-sided: anything the analysis cannot resolve is
treated as unrecoverable, because over-approximating destructiveness costs a
confirmation prompt whereas under-approximating it destroys data.             The
analysis is not free of lists: it rests on a table of what each known command
does, and a command absent from that table is unknown and asks. Its claim is

what it adds on top of a table, not that it has none. That claim is measured
directly in Chapter 3, Section 3.2, by ablations that leave the same per-
command table in place. Disabling composition — seeing through wrappers,
find -exec, xargs, eval, shell -c strings, and loops — drops capture coverage on
the held-out corpus from 89.5% to 35.4% (McNemar’s exact test, p =

2.1×10−53); disabling runtime-target resolution drops it to 45.5% (p =

1.8×10−43); and disabling both leaves the table alone at 32.0%. Silent loss is

0% in every configuration, so what composition and resolution add is
coverage, not safety.

1.6 Significance of the Study

          The findings of this study are expected to benefit the following groups:
        1. Developers of AI agents that run shell commands. Coding assistants and
          other agents that execute generated commands guard them with lists of
          dangerous patterns, which the evaluation in Section 3.1(a) of Chapter 3 shows
          let most file-destroying commands in its corpus run without confirmation.

          The recoverability analysis is independent of the interface and of the language
          model, and can be placed in front of any system that executes generated shell
          commands.

1.7 Scope and Limitations of the Study

         Two terms are used deliberately throughout and are not interchangeable.
Conversational interface layer names what the user experiences: the surface through
which intent is expressed and results are returned. Session layer names where that
surface sits in the system: the software a user meets immediately after login. The first
is where this study’s algorithmic contribution is deployed and evaluated; the second is

its architectural position, and the phrase “session layer” is used only when
SynapseOS’s position relative to it is specifically at issue. This study covers the design
and evaluation of a recoverability analysis for generated shell commands, which is its
research contribution, and the implementation of SynapseOS, the conversational
interface layer for the Linux desktop4 in which the analysis is deployed and validated.
SynapseOS runs as an agentic layer over an ordinary desktop session rather than in

place of one: the desktop shell, session manager, and application launcher continue to
run and remain available to the user, as do the kernel and the core system utilities
beneath them. The Linux kernel, the core system utilities, and the existing ecosystem
of Linux applications are not modified by this study; SynapseOS interacts with the
system by translating natural language into shell commands executed through the

standard command-line toolchain, rather than by rewriting applications or the utilities
they depend on.      The subject matter spans program analysis, natural language
processing,   LLM-based     reasoning,    command-line     automation,    Linux   system
integration, and human-computer interaction.
         The study examines cross-application desktop workflows on Linux, including

shell operations, file management, and application-level tasks representable in the
OSWorld benchmark task suite [46]. The validation study recruits novice computer

users and power users for a controlled study on the platform. The study is conducted in

a Linux desktop environment and is bounded by the duration of the thesis project. The
recoverability analysis covers commands in the bash dialect on a Debian system: their
effects on the filesystem, and the changes to package and service state they make
through apt, dpkg, and systemd. It is evaluated on a corpus of 777 commands drawn
from NL2Bash, from templates covering each composition operator, and from tools

whose effects lie outside the filesystem, and the contributions of composition and of
runtime-target resolution are measured by ablation on the same corpus.
         The following limitations are acknowledged. First, SynapseOS commits to a
locally-hosted, code-specialized small language model (Qwen2.5-Coder-3B-Instruct)
rather than a hosted frontier model, prioritizing privacy and offline operation over the

potentially higher capability of larger hosted alternatives5; this tradeoff may affect the
ceiling on intent parsing accuracy achievable within the study. Second, users with
motor accessibility needs — a highly relevant population — are excluded from the
initial evaluation due to ethics-review and recruitment constraints; accessibility-
specific configurations such as speech-instructed agent operation for atypical speech

patterns [12] are likewise out of scope for the initial implementation but represent a
natural extension of the SynapseOS substrate. Third, SynapseOS targets the Linux
desktop specifically, and the findings may not generalize directly to Windows or
macOS desktop environments. Fourth, the safety confirmation policy for irreversible
system operations is defined in principle but requires empirical calibration during
implementation. Fifth, evaluation is bounded by the task coverage of the OSWorld

benchmark and the custom task suite developed for this study; tasks outside this
coverage are not evaluated. Sixth, the recoverability analysis treats anything it cannot
determine as unrecoverable, and so protects such commands only by asking first: code
run by an interpreter, programs it does not model, and variables with no value are of
this kind.    Its per-command rules are a hand-written enumeration, which its

Notes
        1. Foundation models are large neural networks trained on broad, general-purpose data and
           adaptable to many tasks. Multimodal variants accept multiple input types — typically text
           and images — enabling the model to interpret visual interfaces and screenshots alongside
           natural language.
        2. Computer-using agents are AI systems that interact with a computer’s graphical environment
           — clicking, typing, reading the screen — to complete tasks on behalf of a user. Unlike shell-
           level automation, they operate through the same visual interface a human would use.
        3. The session layer (or simply, the session) is the software the user directly interacts with
           immediately after login — the desktop shell, window manager, session manager, and
           application launcher on a graphical system, or the login shell on a text terminal. It is distinct
           from the userland (or user space): the core system libraries and command-line tools (e.g.,
           glibc, coreutils, bash, apt) that run outside the kernel and that the session layer itself depends
           on and invokes. SynapseOS sits above the session layer and does not replace it; the
           underlying userland is unchanged.
        4. A Linux session manager is the program that starts after user login and establishes the
           graphical environment — launching the window manager, desktop shell, and background
           services. SynapseOS does not replace this component: it launches over the session that the
           component establishes and becomes the surface the user works in.
        5. Open-weights models make their trained parameters publicly available for local download and
           use. Users run inference on their own hardware without routing queries to an external service
           provider, enabling offline operation and preventing user data from being transmitted to third
           parties.
