Chapter 1
Introduction

1.1 Background of the Study

Ask a person to gather every photo they took last June into a single folder and they will do it — opening a file browser, sorting by date, selecting, dragging.  Ask a computer the same thing, in those same words, and for most of the history of personal computing it could not.  The instruction has had to be translated first into the machine’s own vocabulary: a path, a menu, a sequence of clicks, or a command typed with exact syntax.  Language models now do that translation: they write the command for a person who could not.  That moves the risk.  The person no longer has to know the command, but neither can they check it, and when a command they did not write and cannot read is wrong, it is their files that are lost.

The aspiration to instruct a computer in ordinary language is old; an early system for conversing with an operating system, the Berkeley UNIX Consultant, was operational by the late 1980s [49].  Large language models (LLMs) and multimodal foundation models1 have reopened it with far greater capability.  They translate natural language into Bash commands with usable accuracy [13, 47], and computer-using agents2 built on them operate desktop, mobile, and web applications [53, 54, 56, 57].  More and more of these systems act by running commands on a real machine, and so on a person’s own files.

A command can delete or overwrite files, and whether that can be undone depends on what was saved before it ran.  Shell commands are programs: their targets may be hidden inside other commands, as in sudo rm, find -exec, or xargs, or computed only while they run, as in rm $(ls *.log), so what a command will change cannot be read from its name.  Determining that before it runs, and saving beforehand exactly what it would destroy, is a problem of program analysis rather than of interface design.  This study addresses it, and uses a conversational interface layer for the Linux desktop as the setting in which the analysis is deployed and validated.

1.2 Gap and Opportunity

The systems surveyed in Chapter 2 that run generated commands guard them in one of two ways, and neither looks at what a particular command will do.  Most guard by permission: the command is matched against a list of patterns judged dangerous and is then allowed, refused, or put to the user, as in the dangerous-command check of OpenAI’s Codex CLI [32] and cc-safety-net, a guard used with several AI coding agents [21].  A few that ship add coarse recovery: Alibaba Cloud’s ANOLISA, a Linux distribution for AI agents, snapshots an agent’s workspace before key operations or after each round of conversation and can roll back to any snapshot [1], which restores everything since the snapshot rather than what one command destroyed.  A list judges a command by its name and arguments, so it misses what the command touches through another command or a target computed at run time, and neither a list nor a snapshot can say, before a command runs, whether it will lose anything.  NaSh, a design for a natural-language shell, proposes summaries of what a command would affect and selective undo, but leaves their mechanism open [13], and no system in the surveyed literature, nor any shipping tool examined, determines before a generated command runs what it would destroy, or captures exactly that so that the command can be undone.  That is the gap this study’s research addresses.

The setting in which the gap arises has gaps of its own, surveyed in Chapter 2, Section 2.9: no surveyed system, implemented and evaluated, places a conversational layer over a whole desktop session for the person using the machine [25, 54], the Linux work that exists serves servers and agents rather than an end user’s desktop [1, 13], and controlled comparisons with the conventional graphical workflow cover narrow slices such as a single application [26].  They are not what this study contributes; they are why the analysis is deployed in a working interface and validated with people, rather than only evaluated on a corpus.

The opportunity is algorithmic.  A command’s effect on a system can often be derived from the command itself, before it runs, and what that effect would destroy can be saved first; where it cannot be derived, the analysis can say so and ask.  This study builds that analysis, and its terms are used throughout.  An effect is one thing a command does to one path — reading, creating, writing, or removing it, or changing its permissions — or to the system’s installed packages and running services.  A pre-image is the data an effect would destroy, and capturing it means saving it before the command runs by the cheapest means that suffices — a hardlink, a copy, or a record — so that undo can restore it.  Composition follows effects through the operators that join commands into one line (;, &&, ||, pipes, and redirection) and through the commands that run other commands (wrappers such as sudo, find -exec, xargs, sh -c strings, eval, and loops), and resolution learns targets known only at run time by running a form of the command first proven to change nothing.  The analysis’s verdict on a command is one of three: recoverable, if undoing it needs nothing saved because it only creates or moves files; recoverable with capture, if undoing it needs pre-images saved first; and unrecoverable, if no capture would restore what it does, or the analysis cannot tell.  It fails closed: anything it cannot determine is unrecoverable, so the user is asked.  A confirmation policy decides which verdicts the user is asked about: the strict policy asks before every command that is not plainly recoverable, and the capture policy asks only before unrecoverable ones, capturing the rest silently.  The analysis takes a command as a string, so it is independent of the interface and of the model that wrote the command.  SynapseOS, a conversational interface layer built for this study over a Linux desktop that keeps running underneath it, is the experimental platform on which the analysis is deployed and validated with people, against each participant’s own primary operating system.

1.3 Statement of the Problem

Language models have made it practical to turn a request in ordinary language into a shell command and run it on the user’s own system, and conversational interfaces, coding assistants, and agentic tools increasingly execute what a model writes.  A generated command can be wrong, or broader than the request intended, and whether what it destroys can be restored depends on what was saved before it ran, which the tools that run such commands today do not determine (Section 1.2).  This study addresses that problem: determining, before a generated shell command runs, what it would change, whether the change can be undone, and the least that must be captured beforehand so that it can be.  It is studied where it is most acute, a person who does not read shell syntax operating a Linux desktop through conversation, but the analysis applies wherever generated bash commands run on a system like the one studied.

Specifically, the study seeks to answer the following questions:

  1. How can the effect of a shell command on a system be represented formally, so that whether the command can be undone is a predicate over that representation, and so that anything the representation cannot determine is treated as unrecoverable rather than safe?
  2. Can a command’s effects be derived from its syntactic structure before it runs — composed through the operators that join commands and the commands that run other commands, with targets known only at run time (command substitutions, find matches, xargs input, archive members) resolved by commands first proven read-only — without executing anything that changes the system?
  3. Given those effects, can a minimum-cost set of pre-images be computed whose capture is sufficient to restore the prior state, and does restoring from it return the system to that state?
  4. Against an enumerated list of destructive patterns, a fail-closed list that asks before every command it does not recognize as read-only, and the command-safety checks of open-source AI coding agents, does the analysis lose less data silently, restore more of what is lost, and ask the user less often?
  5. How much of that result do composition and runtime-target resolution each contribute, beyond the per-command rule table on which both rest?

A further question is answered by validation rather than posed as a research question: whether the analysis’s decisions hold when it is deployed in a working interface and exercised by people, whose commands the evaluation corpus does not contain (Chapter 3, Sections 3.3–3.7).

1.4 Objectives of the Study

The general objective of this study is to design and evaluate a recoverability analysis for shell commands generated by a language model: an algorithm that determines, before a command runs, what it would change, and computes the minimum-cost set of pre-images that must be captured for the command to be undone.  The algorithm is deployed in SynapseOS, the experimental platform on which it is demonstrated and validated in use.

Specifically, this study aims:

  1. To formalize an effect-semantics model for shell-command recoverability: the kinds of effect a command can have on the system, a recoverability verdict over them, and a one-sided soundness rule under which anything that cannot be determined is treated as unrecoverable (RQ1).
  2. To develop an effect-composition algorithm that derives a command’s effects from its syntactic structure rather than its name, composing them through the commands that run other commands and resolving targets known only at run time through dry runs it first proves read-only (RQ2).
  3. To develop a minimum-cost recovery-plan generation algorithm that computes, from a command’s effects, the cheapest set of captures sufficient to restore the prior state, and to verify by sandboxed execution that restoring from that plan does so (RQ3).
  4. To evaluate the recoverability analysis against pattern-based and fail-closed baselines and the command-safety checks of open-source AI coding agents, on a held-out command corpus whose ground truth is obtained by sandboxed execution, measuring silent data loss, verified restoration, and needless confirmation, with statistical testing (RQ4).
  5. To quantify the contribution of composition and of runtime-target resolution through ablation studies that disable each, and both, while leaving the per-command rule table unchanged (RQ5).

Each objective is algorithmic and measurable, and each would stand if the interface were removed, because the analysis takes a shell command as a string.  SynapseOS is the platform, not an objective in itself: the validation study (Chapter 3, Sections 3.3–3.7) measures how the analysis’s decisions hold on commands participants cause, and characterizes the platform through task success, time, error rate, and workload.

Against that, the study makes one research contribution and builds two supporting artifacts that serve it.  The research contribution is the following.

  1. An algorithm for recoverability analysis of generated shell commands. Given a command, the algorithm derives its effects from its structure, through composition and the read-only resolution of run-time targets; decides whether the command can be undone; and computes the minimum-cost set of pre-images to capture before it runs.  Its formal basis is an effect semantics in the tradition of abstract interpretation, which reasons soundly about what a program could do without running it, and type-and-effect systems, which track what a program changes and not only what it computes [8, 20, 44]: a command is represented not by its name but by the set of effects its syntax implies, resolved against a working directory and propagated through the operators that join commands into one line, and the verdict is a predicate over that set.  Soundness is one-sided, because over-approximating what a command destroys costs a confirmation, whereas under-approximating it destroys data.  The analysis rests on a table of what each known command does, and a command absent from that table is unknown and asks; its claim is what it adds on top of a table, not that it has none.  It is distinguished from permission models, which can refuse a command but cannot restore what an approved one destroyed, and from privilege mechanisms such as sudo and polkit, which gate on who is acting rather than on what is about to happen.  It was evaluated on a held-out corpus of 777 commands, drawn after the analysis was frozen from NL2Bash, a public dataset of English descriptions paired with Bash commands, and from templates and commands written for the purpose.  For the 697 commands that act on files, the ground truth was observed by running each in a sandbox; the 80 whose effects lie outside the filesystem, such as on another machine, were labeled from a fixed table of state-changing tools.  Of the 405 that destroy data or act outside the filesystem, it let none run without either asking or capturing first, where an enumerated pattern list let 41.2% through.  Of the 325 that destroy files, the pattern list let 31% through and the checks of Codex CLI and cc-safety-net let 73% to 97% through, though those checks ask about fewer harmless commands than the analysis does (1 to 15 of the 372 that lose nothing).  Its capture coverage, the share of those 325 it captured beforehand and that undo then restored exactly, was 89.5%, where a fail-closed list, which asks before every command it does not recognize as read-only, restored none; and of the 372 commands that lose nothing, it asked about 32 to 45 (9% to 12%, depending on the policy), against that list’s 101 (27%).  On silent loss it ties the fail-closed list, both at zero, so its contribution is what it restores, and that it asks far less often than the fail-closed list and not significantly more often than the pattern list (32 to 45 against 30 of 372), not the verdict itself.  Ablations, which rerun the analysis with one part switched off and the same table kept, show where the result comes from: without composition, capture coverage falls to 35.4%; without resolution, to 45.5%; and without both, to 32.0%, each drop significant under McNemar’s exact test, which compares two systems on the same commands (each p < 10−42), with silent loss at zero throughout (Chapter 3, Sections 3.1–3.2).  This is the study’s principal technical contribution and the subject of RQ1 through RQ5.

The two supporting artifacts are not research contributions; they are how the contribution is deployed and validated in use.

  1. SynapseOS, the experimental platform. A working conversational interface layer for a Linux desktop in which the analysis is deployed: it grounds natural-language intent in shell commands, gates each command on the analysis’s verdict, captures what the analysis’s plan names before the command runs, and records a recovery journal from which the command can be undone, implemented as a single binary running over an unmodified desktop session.
  2. A validation of the analysis in use. A controlled study in which participants operate the platform on matched tasks, measuring how the analysis’s decisions hold on commands people cause — silent loss, verified restoration, and needless confirmation in live use — and, as characterizations of the platform, task success, time, error rate, and workload against each participant’s own primary operating system, for users fluent in neither existing interface and users fluent in both.

The research contribution is evaluated against a labeled command corpus, independently of any participant; the platform and its validation are reported separately for that reason, and a negative result on any of them is reported as such.

1.6 Significance of the Study

The findings of this study are expected to benefit the following groups:

  1. Developers of AI agents that run shell commands. Coding assistants and other agents that execute generated commands guard them with lists of dangerous patterns: on this study’s corpus the shipped checks of Codex CLI and cc-safety-net let 73% to 97% of the file-destroying commands run with neither a confirmation nor a capture, across their presets, and even a pattern list built for this study as a baseline let 31% through (Section 1.5) [21, 32].  The recoverability analysis can be placed in front of any system that runs generated Bash commands on a Debian-like Linux system, the setting studied here (Section 1.7), and it adds what a list cannot: a capture, taken before the command runs, from which the command can be undone.
  2. The research community. The study contributes a static analysis of shell commands for recoverability, a property the surveyed analyses of shell programs do not address (Chapter 2, Section 2.5), together with an evaluation against ground truth observed by sandboxed execution for every command that acts on files, rather than assigned by human labelers, and ablations that separate what composition and runtime-target resolution each contribute from the rule table beneath them.
  3. People who direct a computer through conversation. A person who cannot read a shell command cannot judge one a model wrote for them, so letting a model act on their behalf is safe only if what it destroys can be restored; the analysis supplies that for the commands it can determine, and asks first about the rest.  The validation study also characterizes the platform for novice and power users, and the platform could later host accessibility-specific configurations, such as speech-driven operation for users with motor impairments [14, 33, 34], which are outside the scope of this study.

1.7 Scope and Limitations of the Study

This study covers the design and evaluation of a recoverability analysis for generated shell commands, which is its research contribution.  The analysis covers commands in the bash dialect on a Debian system: their effects on the filesystem, and the changes to package and service state they make through apt, dpkg, and systemd.  It is evaluated on a corpus of 777 commands drawn from NL2Bash, from templates covering each composition operator, and from tools whose effects lie outside the filesystem, and the contributions of composition and of runtime-target resolution are measured by ablation on the same corpus.  The subject matter is program analysis applied to shell commands, drawing on natural language processing, LLM-based reasoning, Linux system integration, and human-computer interaction for the setting in which it is deployed.

The study also covers the implementation of the platform in which the analysis is deployed.  SynapseOS is a conversational interface layer, the surface through which intent is expressed and results are returned, and it sits above the session layer3 of the Linux desktop4; it runs as an agentic layer over an ordinary desktop session rather than in place of one: the desktop shell, session manager, and application launcher continue to run and remain available to the user, as do the kernel and the core system utilities beneath them.  The Linux kernel, the core system utilities, and the existing ecosystem of Linux applications are not modified by this study; SynapseOS interacts with the system by translating natural language into shell commands executed through the standard command-line toolchain.  The validation study recruits novice computer users and power users for a controlled study on the platform, on cross-application desktop workflows that include shell operations, file management, and tasks representable in the OSWorld benchmark task suite [50], and it is bounded by the duration of the thesis project.

The following limitations are acknowledged, those of the analysis first.  First, the recoverability analysis treats anything it cannot determine as unrecoverable, and so protects such commands only by asking first: code run by an interpreter, programs it does not model, and variables with no value are of this kind.  Of the 325 file-destroying commands in the corpus, 34 (10.5%) are protected only this way (Chapter 3, Section 3.1(d), lists them by cause), and undo restored 630 of the 631 commands executed in the recovery check, the one failure being reported in Chapter 3.  Second, its per-command rules are a hand-written enumeration, which its composition builds on rather than replaces, and it resolves a command’s targets shortly before the command runs, so a file changed by another process in the interval is captured as it was when resolved; and testing after the evaluation found seven defects in the analysis, all fixed, none triggered by any command in the corpus, so that re-running it changed no decision (Chapter 3, Section 3.1(d)).  Third, it is evaluated on a corpus of human-written commands from NL2Bash, templates written by the same team that wrote its rule table and the pattern-list baseline, and commands whose effects lie outside the filesystem; each label describes what a command did on its fixture, the files and directories prepared for it to run on, not on every possible filesystem, and the labels of the 80 external commands, a fifth of the 405 behind the silent-loss result, are assigned from a table rather than observed, so they are weaker evidence than the 697 observed in the sandbox.  Nor does it ask less often than the pattern list, which it does not significantly exceed (32 to 45 against 30 of 372), or than the coding-agent checks (1 to 15); and the deployed gate, which also consults the pattern list, asks about 58 to 67 (16% to 18%), still well below the fail-closed list’s 27%.  Its corpus was written by people, not by the model: a smaller partition of commands the deployed model wrote pointed the same way, but there the analysis let one loss through, on a command that partition’s own labeling rule mislabeled, and its advantage in capture coverage over the pattern list was not significant; it rests on 19 losses (Chapter 3, Section 3.1(d)).  These threats and their mitigations are stated in Chapter 3, Section 3.1(e).  Fourth, the recovery plan is minimum-cost relative to the capture mechanisms and cost model stated in Chapter 3, Section 2.1(c), not over every conceivable way of restoring a system.  Fifth, the platform offers two confirmation policies over the analysis’s verdict, a strict policy, the default, which asks before every command that is not plainly recoverable, and a capture policy, which asks only before unrecoverable commands (Chapter 3, Section 2.1(e)); which serves users better is a question the validation study informs rather than settles.  Sixth, the platform commits to a locally hosted, open-weights, code-specialized small language model (Qwen2.5-Coder-3B-Instruct) rather than a hosted frontier model, prioritizing privacy and offline operation over the potentially higher capability of larger hosted alternatives5; this may limit how often a request is translated correctly, which bounds the validation study but not the analysis, which takes whatever command it is given.  Seventh, the platform targets the Linux desktop, and the validation study’s findings may not generalize to Windows or macOS; it is bounded by the task coverage of the OSWorld benchmark and the custom task suite, and users with motor accessibility needs are excluded from it for ethics-review and recruitment reasons, so accessibility-specific configurations such as speech-instructed operation for atypical speech [14] are out of scope.

Chapter 2
Review of Related Literature

2.1 Introduction to the Review

This chapter reviews two bodies of research: the program-analysis and command-safety work on which the study’s recoverability analysis builds, and the work on conversational and language-model-mediated interfaces to personal computing in which SynapseOS, the platform where the analysis is deployed, is situated.  The review spans nearly four decades of work on natural-language interfaces to computing systems, from the symbolic-artificial-intelligence consultants developed for the Unix shell in the late 1980s [49] to the large language model (LLM) agents that now operate shells, graphical applications, browsers, and mobile devices.  Its purpose is threefold: to establish the conceptual vocabulary and technical foundations on which the present study builds, to characterize the current state of the field and its recurring limitations, and to locate precisely the gaps that the proposed recoverability analysis, and SynapseOS, the system in which it is deployed, are designed to fill.

Works were included in this review if they satisfy at least one of seven criteria: they analyze or guard shell commands or scripts, reason statically about a program’s effects, or restore a system’s state after a change; they translate natural language into executable system actions; they operate graphical, web, or mobile interfaces through LLM-based reasoning; they address speech- or accessibility-driven interaction with computing systems; they provide an evaluation environment for such systems; they report a controlled empirical comparison between a language-mediated interface and a conventional graphical one; or they set out the interaction theory, and the critiques of natural-language interaction, against which such an interface must be judged.  The comparison criterion is stated explicitly because the fourth gap this chapter identifies concerns the scarcity of exactly such comparisons: a corpus admitting only the other criteria could not contain a comparative interface study by construction, and an absence argument drawn from it would be circular rather than evidential.  Works concerned solely with model architecture or training, without a computing-interaction target, and general-purpose conversational systems without a system-control capability, were excluded unless they bear on that interaction theory.

Candidate works were identified through language-model-assisted search across arXiv, the ACM Digital Library, IEEE Xplore, and the ACL Anthology, extended by backward and forward citation chaining from each work that met the criteria above.  Shipped systems that guard or recover from agents’ commands are documented outside those databases, so vendor documentation and open-source repositories were also searched directly for command guards and recovery mechanisms, as of October 2026; ANOLISA, Codex CLI, and cc-safety-net were found this way.  This review is therefore a narrative review rather than a systematic one, and the search is not claimed to be exhaustive.  Because assisted search can surface plausible but non-existent references, and can attribute to a source a claim that source does not make, every work cited in this chapter was subsequently verified by hand against its primary record — author list, venue, and year — and, where a specific claim is attributed to a work, against the presence of that claim in the work’s own text.  That verification pass corrected errors of both attribution and currency introduced by the initial search, and it is reported here because the reliability of this chapter rests on it rather than on the discovery method.  The limitation this leaves is one of recall rather than accuracy: assisted search favors well-indexed and heavily cited work, so the corpus may under-represent less visible literature.  The absence claims in §2.9 are accordingly scoped to the surveyed corpus and stated as such, rather than as claims about the literature as a whole.  The chapter first sets out the theoretical frameworks (§2.2), then proceeds thematically — historical foundations and the case against natural-language interaction (§2.3), natural-language-to-shell translation (§2.4), command safety, static analysis of shell commands, and recovery mechanisms, the literature closest to the study’s algorithm (§2.5), graphical and computer-using agents (§2.6), accessibility and speech-driven interaction (§2.7), and evaluation environments (§2.8) — before synthesizing the surveyed works into a statement of the research gap and a comparative analysis (§2.9).  It closes with a review of the methodological literature that informs the validation study (§2.10) and a summary that motivates the methodology detailed in Chapter 3 (§2.11).

2.2 Theoretical Framework

This review rests on two frameworks of different standing.  The first is the theoretical basis of the study’s contribution: the program-analysis tradition in which the recoverability analysis is an instance.  The second organizes the literature on language-mediated interfaces, in which the platform that deploys the analysis is positioned.

Program analysis: abstract interpretation and effect systems

The technique the study’s recoverability analysis relies on — determining what a piece of code will do without executing it — is not new; it has a decades-long history in programming-language theory under two related names, neither of which the natural-language shells and command guards surveyed in this chapter draw on.  Abstract interpretation, introduced by Cousot and Cousot [8], is the foundational technique for computing sound, conservative approximations of a program’s runtime behavior by evaluating it over an abstract domain rather than its concrete one.  Type-and-effect systems, whose types and effects can be inferred by the algebraic reconstruction of Jouvelot and Gifford [20] and are given a full formal treatment by Talpin and Jouvelot [44], extend a program’s type judgment with an explicit account of the side effects an expression may produce, so that a compiler or static checker can reason about those effects instead of leaving them implicit in execution.  The recoverability algorithm this study contributes (Chapter 3, Section 2.1(a)–(c)) is an instance of this discipline applied to a question that no work in the surveyed corpus applies either tradition to: whether the effects of a generated command can be undone, and what must be captured beforehand so that they can be.  A generated shell command is treated as an expression whose effect — on the filesystem and on the system’s installed packages and running services, rather than on a type system’s abstract state — is derived from its syntax and composed across its operators, and it is that effect set, not the command’s name, that the recoverability verdict is computed over.  This connects the algorithm to an established formal lineage rather than presenting it as a bespoke heuristic, and it grounds the algorithm’s one-sided soundness property — over-approximating destructiveness under uncertainty rather than under-approximating it — in the same requirement abstract interpretation itself imposes: a sound abstraction may lose precision, but it may never assert a property the concrete execution does not actually have.

Two parts of the analysis go beyond a purely static reading.  Combining static and dynamic analysis is not new in general; what is specific to this study is the combination it uses, dry runs run only after the static analysis proves them read-only, feeding a recoverability verdict, and a recovery plan chosen over that verdict’s effects.  Where a target is known only at run time, the analysis runs a form of the command first, which makes it a hybrid of static and dynamic analysis; its soundness still rests on the static part, because a form is run only when the static analysis proves it can change nothing, and a target that cannot be resolved this way falls back to unrecoverable.  And the recovery plan is a cost-minimizing choice over that abstraction: for each effect the abstraction admits, it selects the cheapest capture that restores it, so the plan inherits the abstraction’s over-approximation, capturing more than strictly necessary when the analysis is unsure, never less.

Three properties of the analysis follow from this framework and are carried through the rest of the study.  Its abstract domain is the effect set: what a command would read, create, write, remove, or alter in metadata, or change in the system’s installed packages and running services, rather than the command’s name.  Its semantics is compositional: the effects of a line are built from the effects of its parts through the operators that join them, which is what an enumerated list of command patterns cannot express.  And its soundness is one-sided: whatever cannot be determined is treated as unrecoverable, so that the analysis may ask more often than necessary but may never declare a destructive command safe.  That guarantee is relative to the per-command rule table and to the filesystem as it is when targets are resolved, shortly before the command runs (Chapter 3, Section 2.1(a)).

The four-layer interaction pipeline

The heterogeneous systems surveyed in this chapter — shell translators, web and mobile agents, desktop automation frameworks, and accessibility interfaces — differ widely in platform, action space, and evaluation method, yet they address a common problem: converting a user’s expressed intent into effects on a computing system.  To compare them on common ground, this review adopts a four-layer interaction pipeline — Input, Reasoning, Action, and Operating-System Integration — as its framework for the interface literature.  The framework is informed by the component view of large language model (LLM)-brained graphical user interface (GUI) agents in the survey of Zhang and colleagues [53], whose perception, planning, and action components are recast here, with an added layer for the scope of an interface’s effect, as four layers for language-mediated computing interfaces as a class.  Figure 2.1 depicts the pipeline and situates the layers relative to one another.

Figure 2.1. The four-layer interaction pipeline for language-mediated computing interfaces, adapted from the LLM-brained GUI-agent survey of Zhang and colleagues [53].  A user’s intent enters at the Input layer, is parsed and grounded at the Reasoning layer, executed at the Action layer, and takes effect within a scope defined at the Operating-System Integration layer.

The Input layer concerns how a user expresses intent, whether by typed text, speech, or structured shortcuts.  The Reasoning layer concerns how that intent is parsed into a plan and grounded into the affordances of the environment.  The Action layer concerns how a grounded plan is executed — through command translation, through binding to native application programming interfaces (APIs), or through simulated keyboard and mouse operations.  The Operating-System Integration layer concerns the scope of computing an approach can affect, from a single application to an entire operating system.

This framework is appropriate to that literature for three reasons.  First, it is modality-neutral: because it abstracts over whether intent arrives as text, speech, or gesture and whether action is realized through shell commands, API calls, or simulated clicks, it accommodates the full span of surveyed systems without privileging any one interaction style — a necessary property for a review that spans command-line, graphical, and accessibility work.  Second, it is diagnostic: locating each system’s principal limitation at a specific layer — visual grounding as a Reasoning-and-Action failure, or narrow platform coverage as an Operating-System Integration limitation — turns an otherwise flat catalogue of systems into a structured comparison, and it is this layer-by-layer positioning that the comparative synthesis of §2.9 makes explicit.  Third, it is directly applicable to the platform: SynapseOS, in which the analysis is deployed (Chapter 3, Figure 3.1), instantiates this same pipeline — accepting natural-language intent at the Input layer, parsing it with a locally-hosted small language model at the Reasoning layer, translating it into shell commands executed through the standard toolchain at the Action layer, and spanning the full graphical session rather than a single application at the Operating-System Integration layer.  The pipeline therefore serves both as the organizing lens for the interface literature and as the vocabulary in which the platform is later positioned; the analysis sits between its Reasoning and Action layers, where a generated command is about to take effect.

2.3 Historical Foundations of Natural-Language Interfaces

The aspiration to let users describe what they want in ordinary language and have a computer carry it out is not new.  An early system of this kind for an operating system, the Berkeley Unix Consultant of Wilensky and colleagues [49], was already operational by the late 1980s.  The Unix Consultant was an intelligent natural-language interface that allowed naive users to learn about the Unix operating system through conversation in ordinary English, addressing both the natural-language-frontend problem and the consultation problem, and thereby distinguishing itself from systems intended only as command translators.  It was built on the KODIAK knowledge representation and incorporated a user-modeling component that represented the user’s knowledge state and a teaching component through which users could extend its knowledge base in natural language.  The system demonstrated end-to-end natural-language consultation about Unix, successfully answering "how do I," definitional, and problem-solving questions.  Critically, its authors identified knowledge acquisition as the principal bottleneck: extending the system to a new domain required substantial hand-engineering — a concern that directly foreshadows the contemporary problem of LLM-based agents requiring per-application grounding data.

The intervening decades saw natural-language interaction treated primarily as a supervised-learning problem.  Representative of this pre-LLM era, the work of Li and colleagues on mapping natural-language instructions to mobile user-interface action sequences [23] trained dedicated phrase-extraction and grounding transformers on hand-annotated action sequences, achieving 70.59% accuracy on predicting complete ground-truth action sequences on its benchmark but remaining bound to its purpose-built datasets and architectures.  The decisive shift came with the introduction of in-context reasoning patterns for LLMs.  ReAct, introduced by Yao and colleagues [51], collapsed the multi-stage supervised pipeline into a prompting strategy: the language model is prompted to alternate between free-text "Thought" steps that update its plan and "Action" steps that interact with an external environment, with observations fed back into subsequent reasoning.  Implemented purely as a prompting strategy without fine-tuning, ReAct nonetheless outperformed imitation-learning and reinforcement-learning baselines that required thousands of training trajectories.

The historical significance of this transition is twofold, and it frames the remainder of this review.  First, it explains why progress in the field has been so rapid since 2023: the methodological foundations became portable across modalities and platforms in a way that the earlier dataset-bound approaches were not.  Nearly every system surveyed in the sections that follow inherits from ReAct the convention of interleaving reasoning traces with environment-affecting actions.  Second, this shared inheritance underscores a corresponding fragility: these systems inherit the failure modes of LLM reasoning — hallucinated actions, plan inconsistency, and brittleness on long-horizon tasks — alongside their capabilities, a concern that the evaluation literature reviewed in §2.8 quantifies.

Interface paradigms and the case against natural language

The aspiration to a natural-language interface has a long-standing critique that remains unanswered, and a review that omitted it would misrepresent the state of the question.  Shneiderman’s account of direct manipulation [41] holds that interfaces succeed when the objects of interest are continuously visible, when actions upon them are rapid, incremental, and reversible, and when their effects are immediately apparent — properties that let a user build and maintain an accurate model of system state.  Norman formalized what an interface does for a user as the bridging of two gulfs [31]: the gulf of execution, between an intention and the actions a system makes available, and the gulf of evaluation, between the system’s response and the user’s ability to interpret it.  Hutchins, Hollan, and Norman [18] argued that direct manipulation narrows both, by making an interface feel like the object of interest itself rather than a description of it.

A language interface sits awkwardly against nearly every one of those properties.  An utterance is not continuously visible, not incremental, and not reversible by the same gesture that produced it; the set of available actions is not displayed, so the user must guess at the system’s capabilities rather than see them.  Shneiderman and Maes debated precisely this trade-off between direct manipulation and interface agents [43], and Shneiderman argued subsequently that speech and language interaction consume the same cognitive resources a user needs in order to hold a task in mind, where pointing does not [42].  Empirical work on modern conversational agents has largely borne the concern out: Luger and Sellen documented a persistent gulf between what users expected a conversational agent to understand and what it actually did [27], and Clark and colleagues found that the properties people value in human conversation transfer poorly to interaction with an agent [7].

This critique is the strongest argument against the interface premise of the platform, and it shapes the platform’s design rather than being set aside by it.  Two of its three concerns are addressed directly.  The gulf of evaluation is narrowed by displaying the generated command and its raw output rather than reporting an outcome in prose, so that the user sees what was actually done rather than a description of it.  The irreversibility of an utterance is answered by the confirmation gate and the undo journal, which restore by mechanism the reversibility that direct manipulation obtains for free.  The third concern — that a user cannot see the boundary of what the system is able to do — is not solved by this design and is carried forward as an acknowledged limitation.

The comparative question is older than the current literature and considerably less settled than it is often assumed to be.  It is widely held that the command line’s power is inaccessible to most people in practice.  But the best-known controlled comparison of command, menu, and iconic interfaces, conducted by Whiteside and colleagues across seventy-six users and seven systems [48], concluded that interface style itself did not predict either performance or preference: careful design did, and the system that served novices best also served experts best.  That finding is as much a caution for the present study as a motivation for it.  It warns against attributing to a conversational paradigm what may in fact belong to the quality of one particular implementation, and it is a principal reason this study measures a specific system against a specific baseline rather than claiming to measure one paradigm against another.

2.4 Natural-Language-to-Shell Translation

The thread of the literature most directly related to the platform concerns the translation of natural language into shell commands.  Because SynapseOS grounds user intent into commands executed through the standard Linux command-line toolchain, the accuracy, safety, and context-awareness of natural-language-to-Bash translation are of central relevance to its design.

The standard dataset for this task is NL2Bash, from Lin and colleagues [24]: over nine thousand English descriptions paired with Bash commands, collected from question-and-answer sites, tutorials, and course material.  It supplies the human-written commands of this study’s evaluation corpus (Chapter 3, Section 1.2(a)).  Its commands were collected for translation rather than for safety, so most of them are read-only, which is why that corpus is sized against the labels it must contain rather than drawn as the dataset comes.

Westenfelder and colleagues [47] address this translation problem directly.  Their work constructs a manually verified test set of 600 instruction–command pairs and a training set of 40,939 pairs, and introduces a functional-equivalence heuristic that reaches 95% confidence in determining whether two Bash commands produce the same effect — allowing automated evaluation to move beyond exact-string matching to a measure of whether a generated command actually accomplishes the intended task.  Their fine-tuned models substantially outperform zero-shot baselines, demonstrating that fine-tuning specifically on command-translation data is effective.  The authors identify two persistent limitations: ambiguity in user instructions, and the absence of system context — the contents of the current directory, the user’s command history, and environment variables — at translation time.  Integrating context-aware retrieval is identified as a direction, one that the persistent conversational session of SynapseOS is well positioned to supply.

The feasibility of deploying such a system without reliance on a hosted frontier model is supported by the large-scale evaluation of Jacobs and colleagues [19], who assess a broad range of locally deployable open-source LLMs on Bash command generation.  Their work provides an empirical anchor for the viability of running natural-language-to-Bash translation on local, open-weights models of modest size — the deployment posture adopted by SynapseOS for reasons of privacy and offline operation.  Taken together, the shell-and-command-line thread establishes that natural-language-to-Bash translation is tractable, that safety and reversibility are central rather than incidental concerns, and that local deployment is feasible; yet no surveyed shell-level system has been evaluated with users against the conventional workflow it would supplement.  How such systems guard the commands they generate, and what static analysis of shell commands can establish, are taken up in §2.5.

2.5 Command Safety, Static Analysis, and Recovery

The literature closest to the study’s algorithm concerns how shell commands are checked before they run.  It falls into three groups: guards, which decide whether a generated command may run; analyses, which reason about what a shell program does; and recovery mechanisms, which restore a system after the fact.  Each establishes part of what the study needs, and none, as this section shows, determines before a command runs whether its effects can be undone and captures exactly what undoing them requires.

Guards

Where translation accuracy is the concern of Westenfelder and colleagues (§2.4), safety is the concern of Gyawali and colleagues, whose NaSh system [13] proposes guardrails for an LLM-powered natural-language shell for Linux.  Published under the operating-systems classification, NaSh interposes a guardrail layer between the user’s natural-language input and the LLM-generated command: the model proposes a candidate command, the guardrail layer evaluates it against safety, reversibility, and confirmation criteria, and the user receives a structured preview before execution.  The authors note that LLM outputs may be unintended or unexplainable, requiring guardrails for user error recovery, and they leave as open work both the design of recovery and rollback mechanisms for irreversible system operations and the empirical user evaluation of the approach.  The first of these open problems, recovery from an operation already approved, is the one the present study’s recoverability analysis addresses; the second is taken up by its validation in use.

The same design is what ships.  Coding agents that execute generated commands guard them with lists of command patterns: the dangerous-command check of OpenAI’s Codex CLI [32] and cc-safety-net [21], a pre-execution guard used with several agentic coding tools, are representative open-source examples, and both are scored as baselines in Chapter 3, Section 3.1(a).  Both are designed for agents working inside a version-controlled project, where deleting project files is routine and version control, rather than the guard, is what makes a mistake recoverable.  A personal computer’s files have no such safeguard, which is the setting of this study.

The gap these guards share is the one this study’s algorithmic contribution addresses.  Every shipped guard surveyed decides by permission: the command is matched against an enumerated set of patterns judged dangerous, and is then allowed, refused, or escalated to the user, through allow-and-deny lists over command prefixes.  NaSh [13] goes further as a proposal, adding summaries of what a command would affect and selective undo to its guardrails, but leaves the mechanisms for both open.  A permission model answers whether a command may run.  It does not answer whether, having run, the command can be undone — and those are different questions with different answers.  Refusing a command protects a user only until they approve it, which for any system that must let work proceed is most of the time.

The distinction matters because enumeration does not compose.  A pattern list matches a command in isolation, whereas a generated line routinely chains several operations whose recovery requirements differ — a removal, a version-control reset, and an in-place edit may appear in one invocation joined by &&, with redirects and command substitution altering what each actually touches.  No enumeration of command prefixes expresses that, and extending the list does not converge: each newly named tool leaves the next one unnamed.  Determining recoverability over a composed command, and computing the minimal information needed to reverse it, is the open problem this study takes up (RQ1–RQ3), and it is what separates the present work from the guardrail designs surveyed above.  The comparison that matters is not only against an enumerated list of dangerous commands.  A list can be turned around so that it asks before every command it does not recognize as read-only, which removes the first weakness above at the cost of asking about everything unfamiliar; that fail-closed list is the strongest simple baseline, and the study therefore claims what the analysis adds to it — capturing what would be lost so that undo restores it, and asking far less often, both of which composition and resolution make possible — and not the verdict alone.

Risk in agents that execute tools has also been studied by evaluation rather than by guarding.  ToolEmu emulates tool execution with a language model so that the failures of language-model agents, including destructive actions, can be found before the agents are deployed [38].  It measures how risky an agent is across many cases; it does not protect a user from the particular command an agent is about to run.

Static analysis of shell programs

Static analysis of shell scripts specifically is comparatively little studied, and the existing work targets properties adjacent to recoverability rather than recoverability itself.  ABash [28] performs abstract interpretation over bash’s variable-expansion semantics to catch common expansion bugs and includes taint tracking, but is not concerned with what a script’s commands would do to the filesystem if executed correctly.  Smoosh [12] gives the POSIX shell a mechanized, executable small-step operational semantics, validated against other shells' conformance test suites — exactly the kind of ground-truth semantics a static effect analysis would need to be checked against — but stops at defining that semantics rather than analyzing programs written in it.  Closest of the three is CoLiS [2], which applies symbolic execution to the more than twenty-seven thousand POSIX-shell maintainer scripts in the Debian package archive to find violations of the properties Debian policy requires of these scripts, which run with root privileges during install, upgrade, and removal; among those properties is idempotence, that running a script a second time causes no further harm.  Idempotence and recoverability are related but distinct: a script can be idempotent while still being destructive on its first run — rm -rf /var/cache/pkg is idempotent, since running it twice does no more damage than once, and destructive: nothing restores it unless what it removes was captured before the first run — and a command can be recoverable without being idempotent, if each run produces a new, independently-reversible effect.  CoLiS is therefore the nearest prior application of static effect reasoning to shell scripts specifically, and it stops short of the present study’s question for exactly this reason: verifying that re-execution is safe does not determine whether the first execution can be undone.  No work identified in this review derives a recoverability verdict for a shell command from its statically-computed effects; that is the specific gap the present study’s algorithmic contribution fills.

Recovery after the fact

Guards and analyses act before a command runs.  A separate literature restores a system after something has gone wrong, and it approaches the study’s question from the other side: not what a command will destroy, but how to recover what was destroyed.  Three kinds of mechanism are relevant.

Filesystem snapshots are the most widely deployed, and one shipped natural-language shell already relies on them: ANOLISA’s checkpoint tool snapshots an agent’s workspace at file level before key operations or after each round of conversation, and rolls back to any snapshot [1].  A copy-on-write filesystem such as btrfs can snapshot a whole subvolume at little cost, because a snapshot shares its blocks with the live filesystem until they are modified [37], so snapshots can be taken on a schedule or before system updates.  A snapshot needs no knowledge of the command it protects against, which is both its strength and its limit.  Restoring one returns the whole subvolume to an earlier moment and discards every later change along with the unwanted one, and nothing about a snapshot can tell the user, before a command runs, whether that command will lose anything.  On a filesystem without copy-on-write, such as the ext4 on which this study is conducted, a snapshot must visit every file in the tree, a cost measured in Chapter 3, Section 3.1(a).  Versioning file systems instead keep old versions of individual files: the Elephant file system retains versions under per-file policies that decide when an old version may be forgotten [39].  Recovery is then per file and needs no foresight, but its storage cost is paid on every change, mistaken or not, and obtaining it means replacing the filesystem.

Undo at the level of a service or the operating system makes recovery a property of the system’s design.  Operator Undo intercepts and logs the user interactions with an e-mail service before they reach it, so that an operator can rewind the service’s state, repair it, and replay what users did since [6].  Operating system transactions let a program group system calls so that their effects can be rolled back as a unit before they commit [35].  Intrusion recovery systems such as Taser log system activity so that the effects of an attack can be identified and reverted afterward while legitimate changes are kept [11].  Each restores more completely than any list can, but each requires something the setting of this study does not have: a service built to be undoable, a kernel and programs that use transactions, or continuous logging of all system activity.

A different route learns a command’s effects by running it where they can be contained.  The try utility runs a command in a semisolate over the current environment, built from Linux namespaces and a union filesystem, captures its effects on the filesystem, and lets the user inspect them and then apply, discard, or apply part of them [22].  Its authors motivate it with cases this study shares, a find -exec suggested by a language model that deletes a user’s files among them.  It is the closest prior work to the analysis’s dry runs, and the two differ in where the knowledge comes from: try executes the command itself and shows its effects to a user who must judge them, and it does not contain effects outside the filesystem, such as network calls; the present study runs only commands it has first proven read-only, decides from the command’s structure what it would destroy, and captures exactly that before the command runs.  For the same reason try is not scored as a baseline in Chapter 3: it decides nothing about a command, since it runs every command and leaves what to keep to the user.

The present study takes a narrower path between these literatures.  Like a guard, it acts on one command before the command runs, on an unmodified system and filesystem.  Like a recovery mechanism, it restores.  It captures only what that one command would destroy, which it determines by analysis, so its cost follows from what the command touches rather than from the size of the system, and it can say before the command runs whether undo will be possible.  Table 2.1 compares the approaches surveyed in this section on these properties.

2.6 Graphical and Computer-Using Agents

A parallel and larger body of work addresses computer-using agents1 — systems that operate graphical environments by issuing actions and observing results.  Although SynapseOS operates at the command line rather than by simulating graphical interaction, this literature is essential context: it establishes the dominant architectural patterns, defines the recurring technical bottleneck of visual grounding2, and, through its platform coverage, reveals a gap in the setting where the analysis is deployed.  The work is organized here by the platform each system targets — web, mobile, and desktop — together with the vision-language foundation models on which many depend.

Web agents

The web has been the most heavily studied environment for language-guided agents.  Mind2Web, introduced by Deng and colleagues [10], is the first dataset for developing generalist web agents that follow language instructions across diverse real-world websites, comprising over two thousand open-ended tasks collected from 137 websites across 31 domains; its accompanying two-stage model uses a small language model to filter candidate elements from large documents before invoking a larger model to choose among them.  WebArena, introduced by Zhou and colleagues [57], provides a fully self-hosted, reproducible web environment of functional website clones and evaluates 812 long-horizon tasks for functional correctness rather than trajectory similarity, establishing a challenging benchmark on which contemporary models achieved completion rates far below human performance.  Zheng and colleagues [56], in their SeeAct framework, decouple visual understanding from action: the model observes a screenshot, generates a textual plan, and a separate step grounds that plan onto page elements.  Their central finding is diagnostic for the entire field — with oracle grounding provided, the model completes 51.1% of tasks on live websites, substantially outperforming a text-only baseline at 13.3%, but performance degrades sharply when grounding must itself be inferred, confirming visual grounding as the principal bottleneck.

Mobile agents

Mobile-device control has produced large-scale datasets and progressively more autonomous agents.  The pre-LLM work of Li and colleagues [23], discussed in §2.3, established the grounding problem for mobile interfaces.  Android in the Wild, from Rawles and colleagues [36], contributes a dataset of 715,000 episodes spanning 30,000 unique instructions, in which actions are gestures at arbitrary screen coordinates rather than operations on indexed interface elements, exposing the challenge that actions must be inferred from visual appearance rather than from a structured model of the interface.  AppAgent, from Zhang and colleagues [55], operates Android applications through a simplified action space of taps and swipes and learns to use new applications through autonomous exploration or by observing human demonstrations, generating application-specific documentation that matched or exceeded human-written documentation.  Mobile-Agent, from Wang and colleagues [46], adopts a purely vision-centric approach that requires no system metadata, using optical-character-recognition and icon-detection modules to locate interface elements — achieving broad applicability across mobile environments at the cost of vision-grounding errors that require recovery mechanisms.

Desktop and cross-application agents

Desktop agents are the most direct graphical analogue to the present work, and their limitations are the most instructive.  ScreenAgent, from Niu and colleagues [30], is a vision-language-model-driven agent for cross-application desktop control that operates in a plan–act–reflect cycle, specifying actions as coordinates and key sequences; its authors acknowledge that vision-only grounding is less reliable than approaches with API access.  WinClick, from Hui and colleagues [17], targets Windows-desktop grounding and observes that most existing GUI agents rely on structured data formats such as the document object model or HyperText Markup Language, which are unavailable across general desktop environments; it therefore performs visual grounding directly from screenshots.  UFO², the "Desktop AgentOS" of Zhang and colleagues [54], is the most ambitious desktop system surveyed: it fuses the native Windows accessibility framework with vision-based parsing in a hybrid action mechanism, dispatching subtasks from a coordinating agent to application-specialized agents.  Its authors argue that existing computer-using agents are hindered by shallow operating-system integration, fragile screenshot-based interaction, and disruptive execution, and they identify adaptation to other desktop platforms, such as Linux and macOS, as future work.  UFO² acts on the user’s behalf, as an automation layer beside the user’s own Windows session, and its authors frame cross-platform deployment as groundwork for a unified ecosystem of desktop automation solutions; the platform built for this study is instead operated by a person, turn by turn.  AgentOS, from Liu and colleagues [25], goes further in ambition, proposing that a natural-language portal replace application silos as the way a person uses the operating system, but it is offered as a research direction, without a built system or an evaluation.

Contemporaneous commercial systems (as of October 2026)

The systems surveyed above are research artifacts.  Shipping systems move faster than the peer-reviewed literature, and one is close enough to this study to warrant explicit positioning; what follows describes it as of October 2026.  Alibaba Cloud Linux 4 Agentic Edition, ANOLISA, is a Linux distribution for AI agents whose default shell accepts ordinary language alongside shell commands and forces confirmation before operations it treats as unrecoverable, such as restarting the machine [1]; its checkpoint tool is described in §2.5.  It is the nearest shipped system to the present work, and it differs in the respect that matters here: it recovers by snapshot, restoring everything since a checkpoint, rather than by determining what one command will destroy and capturing exactly that.  It is also built to run AI agents on cloud servers, whereas the platform studied here runs a local model under a person’s direction.  The question this study asks is not whether conversation is a better interface, but whether what a generated command destroys can be determined and captured before it runs; the platform’s interface is the setting in which the answer is validated.

Vision-language foundation models

Underlying many of these agents are vision-language models trained specifically for interface understanding.  CogAgent, from Hong and colleagues [16], is an eighteen-billion-parameter visual language model specialized for GUI understanding and navigation, using both low- and high-resolution image encoders to recognize the small icons and text typical of graphical interfaces.  It supports the position that pure-vision GUI agents are viable when the underlying model is trained appropriately — but at a compute cost, and with the cross-platform generalization limitations common to the entire graphical-agent literature.  Across web, mobile, and desktop, these systems demonstrate broad capability within a single platform class, while consistently identifying visual grounding as an unsolved bottleneck.

2.7 Accessibility and Speech-Driven Interaction

A distinct thread of the literature approaches conversational computing from the perspective of accessibility, targeting users with motor, speech, or cognitive needs.  This thread is relevant to the present study in two ways: it provides the most rigorous human-centered evaluations in the field, and it exhibits a limitation that is the mirror image of the mainstream agent literature, and so bears on the setting of the platform rather than on the analysis.

VoicePilot, from Padmanabha and colleagues [33], is a framework for using LLMs as speech interfaces to physically assistive robots for individuals with motor impairments.  Although its immediate target is robotic assistance rather than desktop computing, it is included here because it is the most rigorous human-centered evaluation in the LLM-speech-interface literature.  The authors derive five design guidelines from an iterative evaluation that ended in a study with 11 older adults at an independent living facility, among them that a command should execute in about the time a caregiver would take, a cost the present study’s confirmation step adds to whenever it asks, and a reason it asks only where a command is not shown to be recoverable.  DexAssist, from Mehendale and Walishetti [29], targets web navigation by users with fine-motor impairments using two LLMs in tandem — one to interpret voice commands and a second to map the interpretation onto interface elements with fallback strategies — reducing the misinterpretation failures of single-model voice navigation on dense layouts.  The architecture of van Dam [45] proposes retrofitting LLM-based conversational interfaces onto existing single-application graphical interfaces, exposing an application’s navigation graph through a tool protocol and handling voice input through real-time speech recognition; its author observes that most production applications were never designed with speech in mind, making such retrofitting an ongoing challenge.

More recent work continues to mature the components required for speech-driven interface control.  Han and colleagues, in GUIRoboTron-Speech [14], advance automated GUI agents driven directly by speech instructions, while Park and colleagues, in R-VLM [34], contribute region-aware visual grounding for more precise identification of on-screen elements.  What unites this thread is that it operates at the level of the individual application or interaction technique rather than at the level of the session itself.  These approaches presuppose an underlying conversational surface on which to run.  A conversational interface layer over the whole session could provide one, which positions accessibility not as a target of the present study, which scopes it out for recruitment and ethics reasons, but as a possible later use of its platform.

2.8 Evaluation Environments and Benchmarks

The rapid proliferation of computer-using agents has been accompanied by increasingly rigorous evaluation environments, and these establish both the current ceiling of the field’s capability and the methods by which that capability is measured.  The most consequential is OSWorld, from Xie and colleagues [50], a benchmark of 369 real-world computer tasks in a real-computer environment spanning Ubuntu, Windows, and macOS.  At its 2024 release the margin it measured was stark: humans achieved 72.36% success where the best evaluated model reached 12.24%.  Its successor, OSWorld 2.0 [52], evaluates 108 long-horizon workflows whose median item requires roughly an hour and a half of skilled human operation; there the best frontier configuration completes only 20.6% of tasks outright.  The reported failures concentrate not in interface navigation but in tracking constraints across a long task, absorbing information that arrives mid-way, and verifying a result before declaring completion.  The field’s ceiling has moved substantially; it has not been reached.  OSWorld is also directly relevant to the present study as the source of a real-task suite against which benchmark comparability can be established.  Direct comparisons between interfaces are rarer.  AXIS, from Lu and colleagues [26], compares an API-first agent with unaided manual operation by people in Microsoft Word, in a within-subjects design with a cloud-hosted frontier model, and Zhou and colleagues compare screen-only graphical agents with command-line agents across 440 matched desktop tasks [58].

Complementing the benchmark literature, the survey of LLM-brained GUI agents by Zhang and colleagues [53] synthesizes the field through 2024, organizing it around the components of perception, planning, action, and memory, and informing the four-layer view adopted in §2.2 of this review.  It enumerates the field’s open challenges — accurate element localization, knowledge retrieval, long-horizon planning, and safety-aware execution control; of these, safety-aware execution control is the one closest to the present study.  What the evaluation literature reveals, however, is a specific methodological limitation: rigorous as these benchmarks are, they measure the autonomous task completion of agents acting on a user’s behalf, not the comparative performance of a human user working through a conversational interface versus a conventional graphical one.  That distinction motivates the evaluation design reviewed in §2.10.

2.9 Synthesis: Comparative Analysis and Research Gap

The synthesis has two parts.  The first concerns the study’s algorithm and is stated briefly because §2.5 has established it: every guard surveyed decides whether a command may run by matching it against a list of patterns or, like ToolEmu [38], measures risk across many runs; every analysis of shell programs targets a property other than recoverability; every recovery mechanism either restores wholesale, as ANOLISA’s snapshots do [1], or needs a system built for it; try [22] previews a command only by running it and leaving its effects for the user to judge; and none derives from a command’s structure what it would destroy or captures what is needed to undo it.  That is the research gap.  The second part concerns the setting in which the gap arises.

Six patterns emerge from this comparison, each surfacing a recurring theme in the literature.

Bifurcation by coverage scope

The field is bifurcated by coverage scope.  Shell-level work [13, 47] and single-application work [33, 45] sit at the narrow end; cross-application desktop, web, and mobile agents sit at the broad end but each within a single platform class.  No system in the surveyed corpus implements a working conversational layer over the full graphical session that has been empirically validated against the conventional desktop workflow it would supplement.  The Unix Consultant [49] came closest in ambition four decades ago, but its pre-LLM foundation prevented it from scaling beyond demonstration.  Neither AgentOS [25], a research direction without a built system, nor UFO² [54], an automation layer that acts on the user’s behalf (§2.6), fills it.

Execution mechanism at the action layer

A second pattern concerns the execution mechanism at the Action layer.  The literature divides among command translation, API binding, and GUI simulation, with a trend toward hybrid execution [54] that prefers structured access where available and falls back to vision.  Vision-only systems [30, 46] achieve broad applicability at the cost of grounding fragility, while structured-access systems achieve precision at the cost of per-environment integration.  Notably, the Unix Consultant operated purely at the consultation layer without executing actions — an approach that reflects an underappreciated design principle, that the agent that explains can be safer than the agent that acts, which the confirmation-gated design of the present study revisits.

Visual grounding as the principal bottleneck

A third pattern is that visual grounding is the field’s principal bottleneck, identified explicitly by both SeeAct [56] and the GUI-agents survey [53].  The 51.1% ceiling of GPT-4V with oracle grounding and its sharp degradation without are attributable in significant part to grounding failure.  This bottleneck is a property of the graphical-simulation approach specifically; a command-line approach that grounds intent into shell commands rather than into on-screen pixel regions sidesteps it, at the cost of being bounded by what is expressible on the command line.  Direct comparison qualifies that tradeoff usefully.  Across 440 matched desktop tasks, screen-only graphical agents pass 59.1% while command-line agents reach only 48.2% — the shell is not automatically the stronger substrate — but command-line agents whose skills are augmented under the guidance of verifiers reach 69.3%, the highest of the three conditions, and the authors attribute most of the command-line deficit to incomplete skill coverage rather than to model capability [58].  The shell is bounded, then, by what its tools cover, which is the platform’s concern; the analysis is concerned with what happens once a command is produced.

Scarcity of comparative user evaluation

A fourth pattern concerns evaluation method.  Most surveyed systems are evaluated either through architectural demonstration [13, 45] or through curated task benchmarks [10, 46, 50, 57].  User studies are rare, and the comparisons that do exist are narrow.  VoicePilot [33] conducts a substantive human-centered evaluation of LLM-based interaction, and AXIS [26] compares an API-first agent against unaided manual operation in a within-subjects design — but within a single application, on a single platform, with a cloud-hosted frontier model.  No surveyed work compares a conversational interface against the conventional graphical workflow across operating-system-level tasks on the same population.  That gap belongs to the setting of this study, and the validation study addresses it in passing rather than as a research question.

The operating-system substrate

A fifth pattern concerns the operating-system substrate.  Windows [17, 54], Android [36, 46, 55], and the web [10, 56, 57] are each heavily represented; the Linux work that exists is aimed elsewhere than the end user’s desktop session.  NaSh [13] addresses Linux at the shell level as a design proposal; Alibaba Cloud’s ANOLISA ships a natural-language Linux terminal with approval gating and rollback, but scoped to server and DevOps workloads; and OSWorld [50] includes Ubuntu as an evaluation platform rather than a deployment target.  No surveyed system implements a conversational session layer for the Linux desktop addressed to the person using the machine, despite Linux’s wide use for development and server work.

Shared lineage and its fragility

A sixth pattern is the field’s shared intellectual lineage and its attendant fragility.  As established in §2.3, nearly every post-2023 system inherits the ReAct [51] convention of interleaving reasoning with action, which explains both the field’s rapid progress and the pervasiveness of LLM-reasoning failure modes across it — a fragility that makes safety and recoverability mechanisms, rather than raw capability alone, decisive for any deployable system.

A related but distinct class of contemporary systems warrants explicit positioning here: AI-assisted coding agents, which translate natural-language intent into shell commands and execute them under human oversight — the same basic mechanism the present study adopts.  These tools are excluded from Table 2.2 not on the grounds of being industry rather than academic work — a substantial share of the literature surveyed here is likewise unrefereed preprint — but because they occupy a different position on every axis that matters to this study.  They are built for software engineers operating within an existing code repository and are powered by large models hosted on remote infrastructure.  SynapseOS differs on both axes: any user of the machine regardless of command-line fluency, and a locally hosted small language model rather than a cloud dependency.  The mechanism is shared; the population and the model’s location are not.

These patterns converge on a fourfold research gap.  First, the surveyed systems guard a generated command by permission, matching it against an enumerated list of dangerous patterns, or recover by snapshot, and none determines before a command runs what it would destroy and captures exactly that (§2.5); this is the gap the study’s algorithmic contribution addresses.  Second, no system in the surveyed corpus provides a conversational interface as a general route to operating a personal computer — one addressed to the person using the machine, spanning the operating system rather than a single application, and evaluated as an interface rather than as an autonomous agent.  Existing systems are automation utilities: they act on the user’s behalf, and they are measured by how often they complete a task unattended rather than by whether a person directs them more effectively than they direct the interfaces they already have.  Third, the work that exists on an open platform targets servers, agents, and benchmarks rather than the desktop session of an end user.  Linux is chosen because its desktop session, toolchain, and command line are open to inspection and modification, which makes it the condition of the experiment rather than its subject; the absence of end-user desktop work there is what the platform addresses.  Fourth, controlled comparison of a language-model-mediated interface with the conventional graphical workflow, with people, exists only within a single application, on a single platform, with a cloud-hosted frontier model [26]; no such comparison was found in the surveyed corpus for operating-system-level tasks under a locally-hosted model and an explicit safety gate.  SynapseOS — a conversational interface layer for the Linux desktop that translates natural-language intent into shell commands under a confirmation gate driven by the analysis, evaluated against each participant’s own operating system — is positioned against the other three gaps, as the platform on which the analysis addressing the first is validated.  Its relationship to the closest prior work is worth stating directly.  NaSh [13] proposes guardrails for an LLM-powered natural language shell — generated code that remains analyzable, selective undo, summaries of what a command would affect — as a design position, and explicitly leaves their mechanisms and their evaluation as open work.  The present study contributes a mechanism for part of that position, which NaSh does not specify: an analysis that derives what a command would affect from its structure, through composition and the read-only resolution of run-time targets, and a plan that captures the least that undoing it requires, evaluated against observed ground truth.

2.10 Review of the Methodological Literature

The evaluation of the algorithm, which is the study’s primary evidence, follows from what the algorithm claims, and its methods are stated first.  Its 450 human-written commands are drawn from a public dataset of natural-language descriptions paired with Bash commands, NL2Bash [24], so that part of it is not written by the people who wrote the analysis; the rest are templates written for the study and commands that act outside the filesystem (Chapter 3, Section 1.2(a)); and it is stratified by the label each command must carry so that the rare destructive commands are present in number.  Of its 777 commands, the 697 that act on files have ground truth observed rather than judged, by executing each in a sandbox and comparing the filesystem before and after, in the way that executable semantics of the shell are validated against what shells actually do [12] and that Westenfelder and colleagues judge whether a generated Bash command does what was intended [47]; the 80 that act outside the filesystem are labeled from a fixed table of state-changing tools.  Its comparisons are paired, because every system is scored on the same commands, and use the standard tests for paired proportions: McNemar’s exact test on the commands two systems handle differently, Wilson intervals for each proportion and Newcombe intervals for each difference, and Holm’s correction across each family of tests.  And its claim that composition and resolution, rather than the rule table, produce the result is tested by ablation: the analysis is rerun with each part switched off and the table kept.  Chapter 3, Sections 3.1 and 3.2 give the details.

The methodological literature reviewed here shapes the validation study, in which the analysis is deployed in an interface and exercised by people, and so concerns how a conversational interface should be evaluated.  The evaluation practices of the surveyed work fall into three categories, each with a characteristic limitation.  Architectural demonstrations [13, 45] establish feasibility but provide no performance evidence.  Curated task benchmarks [10, 50, 57] provide reproducible, quantitative measures but assess the autonomous task completion of agents acting on a user’s behalf rather than the performance of a human working through an interface.  Human-centered user studies, exemplified by VoicePilot [33] and AXIS [26], provide the most direct evidence of an interface’s value to real users but remain rare in this literature and, where present, are confined to a single application rather than the operating system as a whole.  The instruments this study adopts are drawn from established practice rather than constructed for it: the System Usability Scale [5] for perceived usability, with its interpretation grounded in subsequent large-sample analysis [40], and the NASA Task Load Index [15] for perceived workload.

These limitations motivate the methodological posture of the present study, which is grounded in established human-computer-interaction evaluation practice.  The study adopts a within-subjects design, in which each participant completes tasks under both the SynapseOS condition and the condition of their own operating system, so that each participant serves as their own control and between-person variance is removed as a confound; the order of conditions is counterbalanced to distribute learning effects evenly.  It further adopts an expert-baseline comparison — using each participant’s most familiar environment as the comparison condition rather than a fixed alternative that may be unfamiliar — so that no participant is measured on an environment they have not used; familiarity then favors the baseline, so the comparison characterizes the platform against each participant’s practiced environment rather than isolating interface quality (Chapter 3, Section 1.2(d)), while strengthening the ecological validity that the benchmark-only evaluations in the surveyed literature lack.  To integrate the quantitative measures of task completion time and error rate with qualitative evidence of user experience, the study employs a convergent mixed-methods structure in the sense set out by Creswell and Plano Clark [9], collecting both strands concurrently and integrating them at the interpretation stage; the qualitative data, gathered through retrospective think-aloud over the screen recording and a semi-structured interview, are analyzed using the thematic-analysis method of Braun and Clarke [3], a widely adopted six-phase approach for identifying and reporting patterns in qualitative data.  Design considerations surfaced by the reviewed systems inform the evaluation directly: the reversibility-and-guardrail framing of NaSh [13], and VoicePilot’s guideline that a command should take no longer than a caregiver would [33], together motivate measuring both what the confirmation gate and undo protect and what they cost the participant.

The specific instantiation of this methodology — the composition of the benchmark and custom task suite, the participant profile and screening criteria, the session procedure, the metrics and their computation, and the statistical and qualitative analysis plan — is presented in detail in Chapter 3.

2.11 Summary

This chapter reviewed two literatures.  The first, on which the study’s algorithm builds, is program analysis: abstract interpretation and type-and-effect systems [8, 20, 44] supply its formal basis, the command guards of natural-language shells and coding agents [13, 21, 32] decide by permission rather than by effect, the static analyses of shell programs [2, 12, 28] target properties adjacent to recoverability but not recoverability itself, recovery mechanisms from snapshots, including ANOLISA’s [1], to operating system transactions [6, 11, 35, 37, 39] restore after the fact, but wholesale or only on a system built for it, try [22] previews a command by running it, and ToolEmu [38] measures the risks of agents rather than guarding a given command.  The second, in which the platform is situated, is the literature on natural-language and LLM-mediated interfaces to personal computing across nearly four decades, organized along a four-layer pipeline of Input, Reasoning, Action, and Operating-System Integration.  The historical foundations established the long-standing aspiration to a natural-language interface to a real operating system [49] and the methodological shift, driven by in-context reasoning [51], that made the current generation of systems possible, and the critique of natural-language interaction from direct manipulation [7, 18, 27, 31, 41–43], together with the controlled comparison of Whiteside and colleagues [48], cautions that a conversational interface must earn its place, which shapes the platform’s design.  The shell-and-command-line thread most directly related to the proposed design demonstrated that natural-language-to-Bash translation is tractable [47], that safety and reversibility are central concerns [13], and that local deployment is feasible [19], while leaving the extension from shell to session, and empirical user evaluation, as open work.  The graphical-agent literature across web, mobile, and desktop [10, 16, 17, 30, 36, 46, 54–57] established the field’s architectural patterns and its recurring bottleneck of visual grounding, while the accessibility thread [14, 29, 33, 34, 45] revealed a complementary limitation that a general conversational interface layer could address.  The evaluation literature [50, 52, 53] traced a capability ceiling that remains low on long-horizon work, and exposed a methodological gap: interfaces are seldom evaluated comparatively against the conventional workflow with real users, and, in the surveyed corpus, not at the level of the operating system itself.

Synthesized, the surveyed works reveal a fourfold gap: no analysis of what a generated command would destroy, every shipped guard deciding by permission and every shipped recovery restoring by snapshot, with try [22] instead leaving the judgment of a contained run to the user; no conversational interface over a whole desktop session addressed to the person using it; no coverage of the Linux desktop; and no controlled comparison of a conversational interface against the conventional workflow at the level of the operating system.  The first is the gap the present study’s research addresses, through a recoverability analysis of generated shell commands evaluated against ground truth obtained by sandboxed execution wherever a command acts on files.  The other three describe the setting in which that gap arises, and SynapseOS, the conversational interface layer for the Linux desktop built as the analysis’s experimental platform, is where the analysis is deployed and validated in use, through a controlled, within-subjects comparison against each participant’s own operating system.  The methodology through which this evaluation is conducted is the subject of Chapter 3.

Chapter 3
Methodology

This chapter describes the methodology for designing, implementing, and evaluating the recoverability analysis, and for deploying and validating it in SynapseOS, the conversational interface layer that serves as its experimental platform and runs over an ordinary Linux desktop session rather than replacing it.  The methodology is organized into three sections: Dataset, which defines the data to be collected and how it will be gathered; Procedure, which describes how the analysis and its platform are built and how the validation study is conducted; and System Testing, which defines the evaluation of the analysis on its corpus and the design, metrics, and statistical approach of the validation study.

This methodology answers the five research questions posed in Chapter 1, all of which concern the analysis.  RQ1 asks how a command’s effect on the system can be represented formally so that recoverability is a predicate over it, with anything undetermined treated as unrecoverable; RQ2, whether those effects can be derived from the command’s structure before it runs, through composition and the read-only resolution of run-time targets; RQ3, whether a minimum-cost recovery plan computed from them restores the prior state; RQ4, whether the analysis loses less data silently, restores more, and asks less often than a pattern list, a fail-closed list, and the command-safety checks of open-source AI coding agents; and RQ5, how much composition and runtime-target resolution each contribute beyond the per-command rule table.  RQ1 is answered by the effect model specified in Section 2.1(a), with the algorithm and the plan it supports specified in (b) and (c); RQ2 through RQ4 are answered by the evaluation against baselines in Section 3.1, and RQ5 by the ablations in Section 3.2.

Two evaluations follow, of different standing.  The corpus evaluation in Sections 3.1 and 3.2 is the study’s primary evidence: it answers the research questions against a labeled corpus whose ground truth comes from sandboxed execution, without reference to any participant.  The validation study, defined in Section 1 and Sections 3.3 onward and run on the platform described in Section 2, deploys the analysis in SynapseOS and has participants use it on matched tasks.  It checks that the analysis’s decisions carry through to real files and hold on commands people cause, which the corpus does not contain, and it characterizes the platform through usability measures.  Neither evaluation depends on the other: the analysis takes a shell command as a string and is indifferent to what produced it, so removing the interface would remove the validation study but leave every research question, its corpus, its baselines, and its results intact.

Conceptual Framework

The conceptual framework places the recoverability analysis between a generated shell command and its execution (Figure 3.1).  Its input is a command and the directory in which it will run.  It derives the command’s effect set from its structure (Objectives 1 and 2), learning targets known only at run time through dry runs it first proves read-only and runs in a read-only sandbox; it decides whether the command can be undone; and, where undoing it requires preparation, it computes the minimum-cost set of pre-images to capture (Objective 3).  Anything it cannot determine makes it ask.  Its verdict drives a confirmation gate, its plan’s captures are taken before the command runs and recorded in an undo journal, and undo restores from them.  SynapseOS supplies the setting: the user issues a request in ordinary language through a persistent chat interface, a locally hosted small language model translates it into a shell command, the command is executed in a bash subprocess, and its output is rendered back in the interface.  The generated shell command is nonetheless displayed rather than hidden: the confirmation gate requires the user to approve irreversible operations, and an approval given without sight of what is being approved is not consent.  Visibility also makes the system’s translation of intent observable to the participant, which is what allows a user to notice a misinterpretation before it executes rather than after.  The confirmation gate consumes the analysis’s verdict rather than a pattern match.  The analyzer is specified in Section 2.1(a)–(c) of this chapter and evaluated in Sections 3.1 and 3.2, independently of the validation study.  This architecture is illustrated in Figure 3.1.

The framework is evaluated in two parts of different standing.  The recoverability analyzer, the study’s research contribution, is evaluated on its own, on a corpus of commands whose ground truth is obtained by sandboxed execution (Sections 3.1 and 3.2).  The analyzer is then validated in use, deployed in the platform, through a controlled study in which participants complete a fixed set of tasks under two conditions: using SynapseOS as the interface, and using their own primary operating system — Windows, macOS, or Linux — as the baseline.  The study records the analyzer’s decision on every command participants cause, so its behaviour in use can be compared with its behaviour on the corpus, and its expert baseline design, which pits SynapseOS against the environment each participant already knows and uses daily, characterizes the platform through task completion time, error rate, and user satisfaction across the real-world OS landscape [50].

Section 1: Dataset

The study gathers two kinds of data.  The primary dataset is a held-out corpus of shell commands, each labeled by running it in a sandbox, on which the analysis is evaluated against its baselines and its ablations (Objectives 4 and 5).  The remaining data serve the validation study, in which the analysis is deployed in SynapseOS and exercised by participants, in three categories: benchmark task data used to exercise the platform in a standardized environment, user study data collected from human participants in a controlled setting, and system performance data, including the analysis’s decision on every command, captured automatically through built-in telemetry during all sessions.

1.1 What to gather

a) Command Corpus

The primary dataset is a corpus of shell commands.  Each command is paired with a fixture — the files and directories that exist when it runs — and with a ground-truth label observed by running it on that fixture in a sandbox: whether it loses nothing, loses something a captured pre-image could restore, or acts outside the filesystem.  The corpus is held as four partitions: human-written commands from NL2Bash [24], templates covering each shell composition operator, commands whose effect lies outside the filesystem, and commands the deployed model itself wrote.  For every command, each configuration compared in Section 3 records its decision: whether it would ask, and what it would capture.  The configurations are the analysis, its baselines, and its ablations.  For every command the analysis would let run, the command is also executed, undone, and the tree compared, which records whether the capture restored the prior state.

b) Benchmark Task Suite

The OSWorld task suite [50] provides standardized real-computer tasks across shell operations, file management, web browsing, and application-level interactions, and is used as a secondary check on the platform: only its tasks that can be expressed as shell commands are adapted, since graphical-only tasks are outside SynapseOS’s scope (Section 2.1(e)).  OSWorld evaluates computer-using agents in real operating system environments, which lets the platform’s results be related to the existing literature.  Tasks are presented as natural language instructions; agents interact with a real virtual machine environment, and outcomes are evaluated by automated inspection of the resulting system state — whether the goal was actually achieved — rather than by comparing individual actions.  In addition to OSWorld tasks, a custom cross-platform task suite is developed for this study, covering file search and organization, system and process monitoring, application and package management, and text and data processing — each task defined as a human-level goal achievable via SynapseOS natural language commands and via native OS tools on the comparison machine.  Each task in both suites is documented with a description, expected outcome, task category, and difficulty level.

c) User Study Data

The following data types are collected from each participant during the user study:

  • Task completion time: the elapsed time from when the task prompt is presented to when the participant signals task completion or the session logs a terminal event
  • Error rate: the proportion of tasks presented that end in failure or an incorrect outcome, per participant per condition; recovery attempts are recorded separately as an error category rather than counted in the rate
  • User satisfaction scores: responses to the System Usability Scale (SUS) [5] and the NASA Task Load Index (NASA-TLX) [15], collected immediately after each condition; both are validated instruments for measuring perceived usability and cognitive workload respectively
  • Qualitative feedback: responses gathered through a semi-structured post-study interview covering perceived ease of use, trust in the system, and comparison between the two conditions

d) System Performance Data

The following telemetry data is captured automatically by SynapseOS throughout all sessions:

  • Command execution latency: time elapsed from utterance submission to bash subprocess completion
  • Undo log events: count and type of operations logged to the undo stack
  • Confirmation prompts triggered: count of irreversible operations that required user confirmation
  • Analysis decisions: for every command executed, the analysis’s verdict and capture plan, whether the participant was asked, and the task fixture it ran against, and a snapshot of the task directory taken immediately before the command ran, so that the command can be replayed on the state it actually met and scored as the corpus is (Section 3.5(e))
  • Conversational turns per task: the number of utterances required to complete each task
  • Intent parsing accuracy: whether the system correctly identified the user’s intent on the first attempt

1.2 How to gather

a) Command Corpus

The corpus is generated by a program, not assembled by hand, and is held as four partitions reported separately rather than pooled.  The first is NL2Bash [24], which supplies human-written commands and is the generalization set: candidates are drawn at random from the dataset with a recorded seed, excluding any command used during development.  The second is a set of parameterized command templates covering each shell composition operator — sequencing, conditional execution, pipelines, redirects, command substitution, loops, find -exec, xargs, sh -c and other interpreters, and wrappers such as sudo and env — which exists because naturally occurring corpora under-represent compound commands, and compound commands are where the algorithm’s contribution lies.  The third is a set of commands whose effect lies outside the filesystem, described under (b) below.  A fourth partition holds commands the deployed model itself wrote: the NL2Bash descriptions of a random sample of tasks are given to the prototype’s model with the runtime’s own prompt, and the command it returns is labeled by the same pipeline.  It is reported apart, because a set drawn from this prototype’s own output is biased toward the shapes it produces, and because the analysis is about model-generated commands, which NL2Bash’s human-written ones are not.  Commands logged during the validation study are scored the same way (Section 3.5(e)).

A second stratification is by the shape of the command, assigned by the generator from the command’s syntax: a single named command; a chain; one whose targets are computed while it runs; a redirect; one whose effect hides inside a shell, interpreter, or wrapper it names, such as sh -c, awk, or env; and one whose effect lies outside the filesystem.  A command that fits several is given the first that applies, in the order hidden, run-time, chain, redirect, single; and the shape follows the syntax alone, so a program the rule table does not model is classed by how it is written, not by why the analysis asks about it, which is why the 34 losses the analysis asked about are counted differently by cause and by shape in Section 3.1(d).  The claims under test concern the composed, run-time, and hidden shapes, and a corpus dominated by plain named commands would measure the strength of a list and not the contribution of the analysis, so results are reported per shape as well as in aggregate.

b) Ground Truth by Sandboxed Execution

Ground truth is observed, not judged.  Each executable command is given a fixture — the files and directories that exist when it runs — and is run once inside a bubblewrap sandbox: the rest of the filesystem read-only, no network, empty standard input, a hard time limit, and only the fixture writable.  The tree is recorded before and after, and the label follows from the difference.  A command is recoverable when nothing that existed was lost: paths may have been created, and a path that disappeared but whose very same file now sits elsewhere was moved, not lost.  It is recoverable only if a pre-image is captured when something that existed was removed, overwritten, replaced by a different kind of object, retargeted, or given different permission bits or an owner.  Modification times are ignored, since touching a file loses nothing a user could want back.  Commands that do not finish cleanly — a non-zero exit, a timeout, an attempt to write outside the fixture — are excluded and counted, never labeled by guess.

Commands whose effect the filesystem cannot show — on another machine, on the mount table, on another process, on a device, on an account or the firewall — cannot be labeled this way and are never executed.  They form the external partition and are labeled unrecoverable by construction.  The rule that assigns a command to it is deliberately narrow, naming only tools that change such state, so that a read-only network query is not counted as a loss the system failed to catch.  It is a partition rule and not a source of the other two labels.

Ground truth is defined relative to a stated filesystem state.  A command’s effects depend on what exists: rm *.tmp deletes nothing where there are no such files, and cp a b overwrites only if b is there.  A label given with no state is a label about an imagined directory, and an analysis that reads the real state cannot be scored against it.  Every corpus item therefore carries its fixture, and the analysis is run against that same fixture.  The fixture is built from the command’s text before the analysis is consulted: the files and directories the command names are created, a glob becomes a few matching files, and whether the destination of a copy, move, or redirect already exists is chosen by the seed, with the other choice tried if the first does not run.  Fixtures are never written from the analysis’s output.

The generator shares no code with the analysis and never consults it, so agreement between the two is evidence and not circularity.  It is deterministic for a given seed, and it records the number of candidates drawn and the reasons for each exclusion beside the corpus.  There is no human labeler, and so no labeler disagreement to measure; the threat that takes its place is the validity of the oracle itself, addressed in Section 3.1(e).

c) Benchmark Tasks

SynapseOS is deployed on Debian 13 (Trixie); OSWorld’s own environment is an Ubuntu virtual machine [50], so its shell-expressible tasks are adapted to the Debian evaluation machine.  Each benchmark task is executed through the conversational interface, and results are captured programmatically through the built-in telemetry system.  Each task is supplied to SynapseOS as a natural language instruction, and the resulting system state is compared against the expected outcome defined in the benchmark.  Because SynapseOS asks before every command its confirmation policy does not let through unasked (Section 2.1(e)), benchmark runs are facilitator-attended rather than unattended; the confirmation gate remains active throughout and every confirmation is logged as part of the run record.  OSWorld scores the resulting system state rather than a human operator’s performance, so it applies only to the SynapseOS condition.  Condition B, which a human participant operates directly, has no equivalent and is instead evaluated through the custom cross-platform task suite administered in the user study (Section 1.2(d)).

d) User Study

The user study is conducted in a controlled laboratory setting with two machines: the SynapseOS evaluation machine (Debian 13, conversational interface) and the baseline machine running the participant’s native OS — Windows 11, macOS, or Linux with a GNOME desktop — as determined during screening.  Each participant completes a matched task set on both machines under a within-subjects design.  Because completing the identical task twice would measure recall rather than interface efficiency, two parallel task forms — Set A and Set B — are constructed, matched item for item on category, difficulty level, and number of required steps, differing only in the specific targets involved.  Form and condition order are crossed in a 2×2 counterbalance, yielding four participant groups of ten: Set A first on SynapseOS, Set B first on SynapseOS, Set A first on the native OS, and Set B first on the native OS.  Task order within a form is randomized per participant.  Form equivalence is verified during the pilot study, and condition order is retained as a between-subjects factor in the analysis so that residual asymmetric transfer — carryover that is larger in one order than the other, which counterbalancing redistributes but does not remove — is detectable rather than assumed absent.  Screen capture software records activity on both machines; the SynapseOS session logger supplements the recording for the SynapseOS condition.

The study involves 40 participants divided into two groups:

  • Novice users (n = 20): participants with limited computing experience, capable only of basic tasks (web browsing, document editing) on any OS, and no prior command-line familiarity, recruited from the general university population
  • Power users (n = 20): participants with demonstrated proficiency in computing on their primary OS — capable of performing file management, system monitoring, and process administration tasks efficiently — recruited from the university’s information technology and computer science programs

Participants are recruited through university channels.  Recruitment enforces a minimum quota of four participants per primary OS background (Windows, macOS, Linux), scaled with the sample so that the realized set cannot end up concentrated in a single OS and leave the per-OS exploratory subgroup analysis (Section 3.4) without data for the others.  The binding constraint on this quota is the Linux-primary novice cell: a daily Linux user with no command-line familiarity is uncommon, and if that cell cannot be filled during recruitment the Linux quota is met from power users alone, with the resulting imbalance reported rather than concealed.  Informed consent is obtained from all participants prior to the session.  Ethics approval is secured before recruitment begins.  Participant data is pseudonymized at the point of collection under the participant ID scheme described in Section 2.5; recordings, which cannot be anonymized at collection, are governed by the retention and destruction rule stated there.

After completing each condition, participants fill out the SUS and NASA-TLX questionnaires.  After completing both conditions, a brief semi-structured interview is conducted to gather qualitative feedback.

1.3 Why

The analysis is evaluated against a labeled corpus of shell commands rather than through participants, because its research questions concern what a command does, which can be observed directly, and not what a person does.  The separation is deliberate and has a practical consequence worth stating: this evaluation depends on no ethics approval, no recruitment, and no participant sessions, and can therefore be completed and reported independently of the validation study’s schedule.

The corpus is sized against the classes the analysis has to separate, not against a single overall total.  Commands are drawn until a fixed number carry each ground-truth label, so that the label the false-negative test needs — a command that loses something — is present in quantity whatever NL2Bash’s own composition, which is mostly read-only.  The target is on the order of 780 commands: about 450 from NL2Bash, of which 150 are losses; about 250 from templates; and about 80 external.  This is a coverage-based target rather than a power-computed one: a classical power analysis needs an assumed effect size, and the quantity of interest, the false-negative rate, is expected to be low for both the baseline and the algorithm, the regime in which an assumed effect size would be a guess.  What the corpus must give is enough losses that a Wilson interval on a proportion near zero remains informative, and 150 does.

The OSWorld benchmark is used as a secondary check on the platform for the reason given in (b) above, its relation to the existing literature; the analysis itself is evaluated on the command corpus, for the reasons given above.

A custom cross-platform task suite is necessary because OSWorld’s task coverage does not represent the human-goal-framed system tasks relevant to this study — file organization, system monitoring, process management, and text processing — achievable both through SynapseOS natural language commands and through participants' native OS tools (Windows, macOS, or Linux graphical desktop).  Tasks are scoped to operations achievable via bash on SynapseOS and via native graphical or terminal tools on the comparison machine.

The evaluation follows a convergent (parallel) mixed-methods design: the quantitative performance measures — task completion time, error rate, SUS, and NASA-TLX — and the qualitative interview data are collected concurrently within each session and integrated at the interpretation stage, so that the measured differences between conditions and participants' accounts of why those differences arise inform one another rather than being read in isolation.

The within-subjects design is chosen because it allows each participant to serve as their own control, producing a direct comparison between conditions while requiring a smaller participant pool than a between-subjects design.  Counterbalancing addresses the primary threat to internal validity, the learning effect, by distributing it across conditions; it does not remove asymmetric transfer, which is tested rather than assumed absent (Section 3.7).

The expert baseline design — using each participant’s primary OS as Condition B rather than a fixed Linux graphical desktop — is chosen because a fixed Linux baseline would confound interface quality with OS familiarity.  The overwhelming majority of participants have never used a Linux desktop; performance under that condition would reflect unfamiliarity with a foreign environment, not a meaningful comparison of interface paradigms.  Measuring the platform against what participants already know and use daily characterizes it more honestly than measuring it against a system they meet for the first time; these platform measures are characterizations, and the validation outcome proper is the analysis’s behavior on the commands participants cause (Section 3.5(e)).

The dual-population design — novice and power users — lets the validation study show whether the analysis’s decisions hold both for people who can read the commands it judges and for people who cannot, and characterizes the platform across both.  The validation data serve two purposes.  The system performance data, including the analysis’s decision on every command participants cause, validate the analysis in use: they show whether its verdicts and captures hold on commands the corpus does not contain, and whether undo restores what participants’ commands changed.  The user study metrics and benchmark coverage characterize the platform on which it is deployed.  The research questions themselves are answered against the labeled command corpus described in Section 3.1.

1.4 Participant screening criteria

Participants are assigned to the novice or power user group based on a pre-study screening questionnaire administered before the session begins.  The questionnaire assesses the following dimensions:

  • Years of general computer use
  • Primary OS — the operating system used as the primary daily computing environment (Windows / macOS / Linux); must average four or more hours of use per day to qualify
  • Self-reported proficiency on primary OS (basic / intermediate / advanced)
  • Self-reported command-line familiarity (none / basic / intermediate / advanced)
  • Prior exposure to conversational AI interfaces — frequency of use (never / occasionally / regularly / daily) and which tools (chatbots, voice assistants, code-completion or agentic coding assistants, other LLM-based tools)

Self-reported proficiency is confirmed with a short behavioral screener: three timed mini-tasks performed unaided on the participant’s primary OS using its native tools, one from each of three of the four system-task categories used in the main study — file organization (locate and relocate a set of recently modified files), process monitoring (identify the application consuming the most memory via the OS’s native system monitor), and application management (determine whether a named application is installed and identify its version).  Each task is scored pass/fail by the facilitator against a fixed time limit and completion criterion.  The behavioral screener exists because self-reported proficiency alone is not a reliable classifier — a participant’s technical background in one domain (e.g., software development) does not guarantee fluency with a given OS’s native file management, process monitoring, and system administration tools, which is the specific competency this study’s novice/power-user split is intended to capture.

Participants are classified as novice users if they report basic proficiency on their primary OS, computing use limited to web browsing and document editing, no prior command-line experience on any platform, and fail the behavioral screener.  Participants are classified as power users if they report advanced proficiency on their primary OS — capable of performing file management, process monitoring, and system administration tasks efficiently using that OS’s native tools — regardless of which OS that is, and pass all three behavioral screener tasks.  Participants whose self-report and behavioral screener results disagree, or who do not clearly satisfy either classification, are excluded.  Primary OS is recorded for all participants as a grouping variable, and prior conversational AI exposure as a covariate, in the analysis; prior AI exposure is analyzed as an exploratory covariate only (see Section 3.4) rather than a primary grouping variable, since splitting the sample along a third axis would leave subgroups too small to support a hypothesis test.

1.5 Task design

The custom cross-platform task suite is designed to cover human-level system tasks achievable both through SynapseOS natural language commands and through native tools on the participant’s primary OS.  Task design follows four principles:

  1. Ecological validity — tasks reflect actions a real user would perform in their everyday computing environment: finding and organizing files, monitoring system resources, managing processes, and handling text data
  2. Cross-platform equivalence — all tasks are defined as human-level goals achievable both through SynapseOS natural language commands (mapped to bash) and through native tools on the participant’s primary OS (File Explorer, Task Manager, Finder, Activity Monitor, GNOME, or equivalent).  The method of achievement differs by platform; the human goal does not
  3. Difficulty stratification — tasks are rated at three difficulty levels (simple, moderate, complex) based on the number of steps required and the specificity of the target operation
  4. Population appropriateness — both participant groups receive the same task set, with task wording written in plain language accessible to novice users and free of OS-specific or CLI-specific terminology

The custom task suite comprises tasks organized into four categories: file search and organization, system and process monitoring, application and package management, and text and data processing.  All tasks are defined at the human-goal level — achievable via SynapseOS natural language on the evaluation machine and via native graphical or terminal tools on the comparison machine.  Each task is documented with a unique identifier, a natural language prompt as presented to the participant, the expected outcome, and the assigned difficulty level.  The full suite — twelve core tasks in two parallel forms, plus four boundary tasks lying outside shell expressibility that are scored and reported separately — is given in Appendix C.  Difficulty calibration and form equivalence are validated during the pilot study and revised as necessary before the main study begins.

Section 2: Procedure / Experiment

The procedure has two parts.  The recoverability analysis, the study’s contribution, is designed and specified first, in the order of the objectives it serves: its effect-semantics model, its effect-composition algorithm, and its recovery-plan generation.  SynapseOS, the experimental platform in which it is deployed, follows, together with the scaffolding that makes the validation study trustworthy: collected data is processed and pseudonymized, the system and instruments are validated, each participant session follows a standardized procedure, and participant welfare is protected throughout.

2.1 System design and implementation

The design comprises the recoverability analysis, specified in (a) to (c), one part per objective, and the experimental platform in which it is deployed, in (d) and (e): a conversational interface layer and an execution pipeline, integrated into a unified session manager that launches over the conventional Linux graphical desktop session rather than replacing it.

a) Effect-Semantics Model (Objective 1)

The command-safety check SynapseOS began with, like those of the tools surveyed in Chapter 2 and the execution pipeline’s own classification in (e) below, is an enumerated list of named command shapes: a proposed command is matched against patterns known to be destructive — rm, dd, mkfs, truncating redirects — and gated if it matches.  That mechanism is the baseline this study seeks to replace, and its limitations are structural rather than incidental.  It cannot enumerate its domain, because the space of destructive commands is open-ended: extending the list to cover apt leaves snap, pip, docker rm, and whatever ships next.  It does not compose, because each rule matches a command in isolation while a generated line routinely chains several operations with differing recovery requirements.  And it reasons about names rather than effects: cp a b is harmless when b does not exist and destructive when it does, a distinction no name-matching rule can draw.

This study therefore proposes an algorithm that derives what a command would do from its syntactic structure, and decides recoverability over that derivation.  It produces two outputs: a verdict — recoverable, recoverable only with prior capture, or unrecoverable — and, for the middle case, a recovery plan naming which pre-images must be captured, and by which mechanism, before the command is allowed to run.

The formal object. A command is represented by its effect set rather than by its name.  An individual effect on the filesystem is a triple: a kind, drawn from {read, create, write, remove, metadata}; a target path, resolved against the working directory in which the command would execute; and the pre-image that would have to be captured for that effect to be reversed.  A change to installed packages or running services is a sixth, pathless kind, a state effect, recorded with the inverse command that would reverse it (see Scope of the model below).  A removal whose very bytes survive at another path, as in a rename, is marked as a move: undo moves the data back, so it needs no capture.  The effect set of a command is the union of the effects of every leaf command within it, taken over the whole of its operator structure.

The verdict. The verdict is a predicate over the composed effect set: a command is recoverable when every effect within it has an available mechanism capable of restoring that effect’s pre-image.  The verdict is not where the contribution lies: on silent loss, the fail-closed list, which asks before every command it does not recognize as read-only, reaches the same outcome on the commands studied.  What the study contributes is the derivation of the effect set, (b), and the plan computed from it, (c).

Soundness. The analysis is deliberately one-sided.  Any construct whose effects cannot be resolved statically — a path arriving from command substitution, an unexpanded variable, a glob that may match a block device — is treated as unrecoverable rather than assumed benign.  The two possible errors are not symmetric and are not traded off against each other: over-approximating destructiveness costs the user an unnecessary confirmation prompt, whereas under-approximating it destroys data that cannot be recovered.  This asymmetry is why the evaluation in Section 3.1 reports false-negative rate separately rather than folding both directions into a single accuracy figure.  Two limits belong to the soundness claim itself.  Resolution runs commands before the user has consented, which is safe only because each is proven to have no effects; and the interval between resolving a target and executing the command is a window in which another process can change the filesystem, so a capture is of the state at resolution time and not a guarantee about the state at execution time.

Scope of the model. The effect domain is the filesystem, extended to two kinds of state on the target system that have no pre-image to copy but do have an inverse: installed packages and running or enabled services.  For these the analysis does not re-implement the package manager or the service manager.  It asks the system’s own tools what the command would do — the package manager’s simulation mode, the package database, and the service manager’s state queries — and derives from the answer the command that puts the state back: a purge for an install, a versioned install for a removal or upgrade, a stop for a start, a disable for an enable.  A change is recoverable only if that inverse exists, so removing a package whose old version no repository still offers is unrecoverable, and purging a package also captures its configuration files as removals.  Undo runs the inverse, with elevated privilege if the original had it, and prints the command for the user to run if it fails.  Not represented are what maintainer scripts and a service’s own start-up do beyond the state change, which are arbitrary programs; network mutations and anything on a remote host; and other package managers, which stay unrecoverable unless plainly read-only.  A command whose principal effect is one of these is classified unrecoverable by the soundness rule above.  This is safe but coarse, and it is stated as a limitation of the model rather than deferred to the results.

b) Effect-Composition Algorithm (Objective 2)

Extraction. For each leaf command, effects are derived from the command together with its arguments.  The derivation is argument-aware because flags change effects and not merely behavior: rm -i differs from rm -f in whether removal is certain, cp -n cannot overwrite where cp can, and chmod with and without -R differ in how many paths acquire a metadata effect.

Composition. Effects propagate upward through the operators that join commands into a single line, and the propagation rule differs by operator.  Sequencing with ; accumulates effects whether or not the earlier part succeeded.  Conjunction and disjunction — && and || — make later effects conditional on an earlier exit status, so the effect set is a union over the branches that may execute.  A later part sees what an earlier one did as done only across &&; after ;, ||, or a pipe it may run although the earlier part failed, so an earlier removal is treated as possibly not having happened, and a later write to that path is captured, and an earlier cd leaves the working directory unknown.  An assignment or cd inside a branch or loop outlives it, as in the shell, and a value on which the paths that may have run disagree is unknown afterwards.  A pipeline connects standard output to standard input and contributes no filesystem effect of its own, but determines the exit status that gates whatever follows it.  Redirection introduces write effects that appear in no command in the pipeline.  Command substitution introduces effects whose targets are computable only at runtime, and xargs and find -exec multiply a command across an argument set that is not statically known.  It is this propagation, rather than the per-command derivation, that an enumerated pattern list has no means of expressing.  Parts of a line are analyzed in order against an overlay of what earlier parts created or removed, so that in mkdir out && cp a.txt out/ the copy lands in a directory that does not yet exist, and a path a line creates and then deletes needs no capture because there was nothing there to lose.  Loops are analyzed once per resolved item with the loop variable bound; sh -c strings and transparent wrappers such as sudo are analyzed as the command they run.  Two parts of composition are distinguished in what follows: propagation through the operators that join commands (;, &&, ||, pipes, and redirects), which needs no lookup beyond the rule table, and analysis through the commands that run other commands (wrappers, find -exec, xargs, eval, sh -c strings, and loops).  The composition ablation of Section 3.2 disables the second and keeps the first; Algorithm 1 marks the lines each ablation switches off.

Resolution. Some targets exist only while the command runs: rm $(ls *.log), find -delete, xargs rm, git clean -f, tar -x.  Rather than declaring these unknowable, the analysis learns them by running a form of the command that cannot change anything — find with each action replaced by a print of what the action would have touched, the read-only command that feeds xargs, git clean -n, tar -t, rsync -n, the body of a command substitution — and analyses the command again with the concrete targets in place.  A resolver is run only if the same analysis proves it has no effects, and it runs inside the bubblewrap sandbox with the whole filesystem mounted read-only; without bubblewrap, resolution is switched off and the command asks.  If it cannot be proven read-only, cannot run, or times out, the targets stay unresolved and the command asks.  A resolver is also refused when an earlier part of the same line creates, moves into, writes, or removes anything under what it would read, because listing it beforehand would not show what the command will meet.  Resolution is what makes a capture possible for commands whose targets a static reading cannot name.

c) Minimum-Cost Recovery-Plan Generation (Objective 3)

The recovery plan is a minimum-cost cover of the same set — for each effect, the cheapest mechanism sufficient to restore it, with redundant captures eliminated.  Cost is not uniform across mechanisms, which is what makes the selection non-trivial: a hardlink capture is independent of file size where a content copy is proportional to it, a single git object identifier covers an arbitrary number of tracked-file effects at once, and two effects on overlapping paths need be captured only once.  The mechanisms themselves — content backup, hardlink-based trash, git HEAD capture, permission-metadata capture — are those of the execution pipeline described in (e); the algorithm selects among them rather than introducing new ones.  A rename or move is the one removal that needs no capture, because the same data survives at the destination and undo is moving it back; compression and archiving are not, because the bytes at the destination are a transformation of the original and moving them back returns the wrong content, so they are captured like any other deletion.  Where a list can only refuse, the plan adds a capture that restores.

Why the plan is minimal. Cost is counted as the work and storage a capture needs before the command runs: a hardlink, a permission record, a commit identifier, and an inverse command each cost a constant, and a content copy costs the size of the file.  The capture a path needs is fixed by its effects: a removal alone is restored from a hardlink; an overwrite needs a copy of the bytes, because a hardlink shares the very data the write changes; and a change of mode or owner needs a record.  The choices for different paths are independent, with two exceptions, both shared captures that only lower the total: a directory captured whole already covers every removal beneath it, and one commit identifier restores the committed state of every tracked file a repository reset touches, so it is chosen once per repository, and only files with uncommitted changes need copies of their own.  Choosing for each path the cheapest mechanism that suffices, and dropping the removals a captured directory already covers, therefore gives the least total cost: the total is a sum of per-path costs, each at its minimum, plus the shared captures, and dropping a covered capture can only lower it.  The claim is minimality relative to these mechanisms and this cost model, not over every conceivable way of restoring a system; on a copy-on-write filesystem, for instance, a whole-directory snapshot could cost less than the plan’s copies.

d) Experimental Platform: Conversational Interface Layer

The conversational surface is designed as a persistent, full-screen chat interface that serves as the primary user-facing interface when SynapseOS is active, with the XFCE session beneath it remaining available as a logged fallback.  The CLI and TUI interface modes implementing this surface are complete; the full-screen GUI mode is in development, and the readiness checkpoint governing its use in the study is described in the System Environment Specifications.  The interface accepts natural language input, displays system responses and command output, and maintains conversational context across the session.  An intent parsing pipeline translates each user utterance into a shell command for execution.

Conversational context is session-scoped: history is held in memory for the duration of the login session and is cleared on logout or reboot, with no persistence layer in the thesis prototype.  When accumulated history exceeds a fixed token budget — set well below the 8,192-token context window configured for the intent parsing model, which itself supports up to 32,768 tokens — a rolling window discards the oldest turns to keep the conversation within budget.  Verbose command output — such as a full directory listing or search result — is truncated to a compact summary before being appended to history, preventing a single command’s output from consuming a disproportionate share of the available context.

SynapseOS is designed around a locally-hosted small language model (SLM) as the default, model-agnostic inference backend, with cloud inference available only as an explicit opt-in.  Because the system operates at the OS level — processing every natural language command and observing terminal output, file paths, command history, and interaction patterns — routing inference through a cloud API would give an external provider continuous visibility into the user’s computing activity.  On-device inference eliminates this exposure by default; the architecture reserves the option for a user to supply an API key for a supported cloud provider and substitute a hosted frontier model, entirely at their discretion; this path is not implemented in the thesis prototype.  The default configuration requires no API key, no internet connection, and no per-query cost, making SynapseOS fully operational in offline and air-gapped environments.

The primary SLM is Qwen2.5-Coder-3B-Instruct, an open-weights5 code-specialized model that demonstrated the strongest natural language-to-bash translation accuracy among models below 7B parameters in controlled evaluation [47].  Among the models directly compared in that evaluation, its code-specialized pretraining produced a clear margin over general-purpose models of comparable or larger size — 58% NL2Bash accuracy with prompt engineering, versus 49% for Llama 3.2-3B and 37% for a LoRA-fine-tuned Llama 3.2-1B — attributable to Qwen2.5-Coder’s training corpus of 5.5 trillion code tokens against Llama 3.2's general-purpose pretraining.  At 4-bit quantization6, the model requires approximately 1.8 GB of memory and runs on the target Debian 13 (Trixie) hardware without a dedicated GPU.  The model may be fine-tuned via Low-Rank Adaptation (LoRA)7 on the NL2Bash corpus8 and a custom SynapseOS task suite to improve intent parsing.  If it is, every NL2Bash item in the evaluation corpus, and every description used for the model-generated partition, is excluded from the fine-tuning data, and the model-generated partition is regenerated with the fine-tuned model, so that the analysis is never scored on commands the model was trained to reproduce.

Accuracy is measured using an execution-based scoring methodology rather than syntax-level string matching, following Westenfelder et al. [47] — see Section 2.3 for the full evaluation procedure.

This selection was reconfirmed against models released after the initial literature review, to guard against the fast-moving small-model landscape becoming stale before study execution; no smaller alternative offered comparable shell-generation evidence within the same CPU-only hardware budget [19].  Newer mixture-of-experts variants require all experts resident in memory regardless of active parameters per token, which is incompatible with this study’s memory budget, and newer general-purpose small models report reasoning benchmarks but no shell-command generation evidence.

e) Execution Pipeline

Once the intent parser produces a shell command, SynapseOS passes it through a confirmation gate and an undo journal before execution, following the reversibility-and-guardrail framing proposed for LLM-powered natural language shells [13] and asks only where it must, since a command that takes longer than a caregiver would is among the costs VoicePilot’s guidelines for LLM speech interfaces warn against [33].  The gate acts on the analysis’s verdict under one of two policies.  Under the strict policy, the default and the policy used in the validation study, it asks before every command whose verdict is not plainly recoverable, that is, before every command that is recoverable only with capture or unrecoverable, and on approval takes the captures the plan names before the command runs.  Under the capture policy it asks only before unrecoverable commands, and takes the plan’s captures for the rest without asking.  Under either policy the enumerated-pattern list is still consulted, and a command it flags also asks, so the list can add a confirmation but never remove one.  With the analysis disabled, the gate falls back to the list alone.  Captures use five mechanisms — full content backup, hardlink-based trash, git HEAD capture, permission-metadata capture, or, for package and service state, an inverse command — and are recorded to a persistent undo journal before the command runs, so that a command approved in error remains recoverable.  Rollback is invoked through a dedicated undo command rather than from within the conversation.  Once the gate has passed it, the command is dispatched to a bash subprocess.  Standard output and standard error are captured and rendered in the conversational surface as the system’s response to the original natural language input.

SynapseOS executes only shell-expressible operations.  The system’s capability boundary is the Linux command-line toolchain: file management, process control, text processing, package management, network configuration, and any application that exposes a command-line interface.  GUI-only interactions — clicking buttons in graphical applications, navigating web page elements, or interacting with visual-only interfaces — are explicitly outside scope, in deliberate contrast to broader desktop agent frameworks that additionally orchestrate GUI automation atop the existing session [54].  This boundary is intentional: it constrains the research to a tractable, verifiable claim that the system can be built, evaluated, and defended within the thesis timeline.

2.2 Data pre-processing

Prior to statistical analysis, the command corpus and all data collected during the benchmark evaluation and user study — not the system itself — undergo the following processing steps:

  • Command corpus: each candidate command is given a fixture built from its own text before the analysis is consulted; commands that do not finish cleanly on their fixture are excluded and counted with the reason, never labeled by guess (Section 1.2(b)); and the corpus is fixed by a recorded seed and hash before the analysis is run on it (Section 3.1(e))
  • Task normalization: task descriptions and expected outcomes are standardized across both the OSWorld benchmark and the custom task suite to ensure consistent evaluation criteria
  • Log parsing and event extraction: raw session logs from SynapseOS telemetry are parsed to extract per-task metrics — completion time, error events, and undo events
  • Metric computation: task completion time is computed as the elapsed time between task prompt presentation and task completion event; error rate is computed as the ratio of failed or incorrect outcomes to the number of tasks presented — the denominator is the task count rather than the attempt count, so that retrying cannot lower a participant’s error rate; each task is scored against a written rubric specifying the observable end state that counts as success, with partial completion, abandonment at the time limit, and facilitator intervention coded as distinct outcomes; and because SynapseOS outcomes are captured by the session logger while native-OS outcomes must be judged from screen recording, all tasks in both conditions are scored by one procedure: the rubric, fixed before any session is run, is applied to the screen recording by a single research team member, and for the SynapseOS condition a script additionally checks the end state the rubric names (a file, a package, a service) from the session log, so that the scoring of that condition does not rest on the scorer’s judgment alone; SUS and NASA-TLX scores are computed according to their respective standard scoring formulas
  • Participant data pseudonymization: all participant records are pseudonymized at the point of extraction, replacing identifying information with participant ID codes prior to any analysis

2.3 Validation

The following validation procedures are applied to ensure the reliability and accuracy of the system and the study instruments:

  • Pilot study: conducted with five participants prior to the main study to validate the task set difficulty, the questionnaire instruments, and the session procedure; findings from the pilot study are used to revise instruments and procedures before the main data collection begins
  • Intent parsing accuracy: evaluated using an execution-based scoring methodology [47] — each generated command is executed in a controlled environment and its resulting system state compared against a human-annotated expected outcome for each task utterance, rather than syntax-level string matching, with ambiguous cases, where the resulting state differs from the expected one only in ways the task did not ask about, decided by a written equivalence rubric fixed before data collection and applied by two members of the team independently, disagreements settled by discussion and the number of cases decided this way reported; accuracy is computed as the proportion of first-attempt matches
  • Confirmation policy effectiveness: evaluated by verifying that every command in the task set that the analysis judges unrecoverable, and under the strict policy every command it judges recoverable only with capture, triggers the confirmation prompt, and that no such command executes without user approval
  • Undo success rate: evaluated by executing a representative set of reversible operations and verifying that the undo log correctly restores the prior system state in each case

The last two procedures have been carried out once on the prototype as a manual verification of ten test cases, recorded as terminal logs and provided as supplementary material.  In seven, a request is sent to the deployed system, where the language model writes the command, and the run is repeated with the analysis disabled, each from a freshly created test directory of ordinary files; both configurations include the same undo log, so the analysis changes only what is captured before a command runs; the affected files are listed in the initial state, after execution, and after undo, and in every case the model wrote the same command in both runs.  Requests name the kind of command under test, and some spell it out, because with loose phrasing the model produced a usable command of the intended shape in only two of seven cases, a limitation of translation rather than of the analysis.  One further case examines the analysis alone, one uses an everyday request, and one examines the scope of undo.  All ten behaved as expected.  Without the analysis, two data-destroying commands ran with no confirmation at all; where a command’s targets were indirect, undo restored the affected files in every case with the analysis enabled and in none with it disabled; and where targets were named directly, the two configurations behaved identically.  The verification is illustrative rather than evidential.  Its cases were chosen to exhibit specific behaviours, so it supports no claim about rates; the claims of RQ2 through RQ5 rest on the corpus evaluation in Section 3.1.  What it adds is confirmation that the analysis’s decisions carry through to the files themselves in the deployed system, which the corpus evaluation, presenting commands directly to the analysis, does not exercise.  It also surfaced two defects, recorded in docs/open-problems.md; the one that bears on the study is described under threats to validity (Section 3.7).

2.4 Study session procedure

Each participant session follows a standardized procedure conducted in the following order:

  1. Briefing: The session facilitator explains the study purpose, session structure, and participant rights.  The participant reads and signs the informed consent form.  The pre-study screening questionnaire is administered to confirm group classification.
  2. System familiarization: For the SynapseOS condition, the participant is given a five-minute orientation to the conversational interface and shown how to enter natural language commands.  For the native OS condition, no familiarization is provided — participants use their own operating system as they normally would.  No task-specific training is provided under either condition.
  3. Task completion: The participant completes the full task set under the assigned condition.  Tasks are presented one at a time via a printed task prompt sheet.  The session logger captures start and end times automatically.  Screen recording captures all on-screen activity.  Participants are not asked to verbalize while tasks are timed.  Concurrent think-aloud reliably slows task performance, and here it would slow the two conditions unequally, since narrating while composing a natural-language instruction competes for the same linguistic resources far more than narrating while pointing and clicking.  Verbal data is instead collected retrospectively, by replaying the screen recording with the participant during the post-study interview.
  4. Post-condition questionnaire: Immediately after completing all tasks under a condition, the participant completes the SUS and NASA-TLX questionnaires for that condition.
  5. Condition changeover: If the participant has not yet completed both conditions, a short break is offered, the participant moves to the other machine (SynapseOS or native OS), and the session returns to step 2.
  6. Post-study interview: After both conditions are completed, the facilitator conducts a semi-structured interview of approximately 10–15 minutes covering perceived ease of use, trust in the conversational interface, preference between conditions, and open-ended feedback.
  7. Debrief: The facilitator discloses the full study objectives, answers participant questions, and thanks the participant.  Session data is pseudonymized under the participant’s ID code at session close; the ID-to-consent mapping is retained for the fourteen-day withdrawal window described in Section 2.5 and destroyed thereafter.

Total estimated session duration per participant: 90–120 minutes.

2.5 Ethical considerations

This study involves human participants and is subject to ethics review and approval by the Institutional Review Board (IRB) or equivalent ethics committee of Mapúa University – Makati prior to the commencement of participant recruitment.  The following ethical principles are observed throughout the study:

  • Informed consent: All participants receive a written information sheet describing the study purpose, procedures, data collected, and their rights.  Participation is entirely voluntary; participants may withdraw at any time without penalty or consequence.
  • Pseudonymization: Each participant is assigned an ID code at enrollment, and all session logs, questionnaire responses, and transcripts are stored and analyzed under that code alone.  Recordings are pseudonymous rather than anonymous: voice is inherently identifying and screen video may capture file names visible on screen, so they cannot be anonymized at the point of collection and are instead governed by the retention rule below.
  • Data minimization: Only the data types specified in Section 1.1 are collected.  No identifying metadata — names, email addresses, or device identifiers — is retained beyond the consent confirmation step.
  • Data security: All collected data is stored on password-protected institutional infrastructure accessible only to the research team.  Interview recordings are deleted after transcription and verification.
  • Confidentiality: Study findings are reported in aggregate.  No individual participant’s data is disclosed in any form that could enable identification.
  • Risks and protections: Participants issue natural-language instructions that cause real commands to execute, including commands capable of deleting or modifying files.  That risk is contained by the study environment rather than by restricting what participants may attempt.  Both conditions run on dedicated laboratory machines provisioned for the study, holding only synthetic task data and no personal or institutional files; no participant uses a personal device or signs into a personal account at any point; and each machine is restored to a clean baseline image between participants.  Participants are informed before consenting that the commands they trigger execute for real on the study machine and that nothing belonging to them is exposed.  The foreseeable discomfort is frustration or a sense of failure while working under observation and timing; participants are told in advance that the interface rather than their competence is under evaluation, and that they may pause or stop without giving a reason.
  • Legal basis and retention: Personal data in this study is processed under Republic Act No. 10173, the Data Privacy Act of 2012, on the basis of the participant’s written consent.  Screen recordings and audio are retained only as long as coding requires: both are destroyed once transcription and coding are verified complete, and in no case later than ninety days after the final session.  The mapping between ID codes and signed consent forms is stored separately from study data, accessible only to the principal researcher, and destroyed when the withdrawal window below closes, fourteen days after the last session.
  • Right to withdraw: Participants may discontinue the session at any point, and may request withdrawal of their data for up to fourteen days after their session — the ID-to-consent mapping is retained through that window specifically so that withdrawal remains possible.  After it closes the mapping is destroyed and individual records can no longer be located.  This limit is stated on the consent form so that it is understood before participation rather than discovered after.

Section 3: System Testing

System testing evaluates the analysis and then validates it in use.  Section 3.1 evaluates it against baselines on the command corpus (Objective 4), which answers RQ2 through RQ4, and Section 3.2 measures what composition and runtime-target resolution contribute, by ablation (Objective 5), which answers RQ5.  Sections 3.3 to 3.7 define the validation study on the platform: its evaluation dataset, evaluation profile, criteria and formulas, data analysis plan, and threats to validity.

3.1 Evaluation against baselines (Objective 4)

The analysis is evaluated on the command corpus of Section 1.1(a) and 1.2(a)–(b), against the baselines in (a), by the metrics in (b) and the statistics in (c); (d) reports the results, and (e) the threats specific to this evaluation.  The evaluation answers RQ4 directly, and it supplies the evidence for RQ2 and RQ3: whether a command’s effects can be derived before it runs shows in silent loss and capture coverage, overall and for each command shape, and whether the plan restores, in capture coverage verified by sandboxed undo.

a) Baselines

Three baselines bound the comparison.  The first is the enumerated-pattern classifier already implemented in the prototype, which matches commands against a hand-maintained list of known destructive shapes; it is the honest comparison because it is what the system does today, not a weakened construction.  The second is the same list turned around to fail closed: every command in the line, including those inside substitutions, loops, and wrappers, must be a known read-only form or the line asks.  It resolves no targets and plans no capture, and it is the strongest simple alternative, because it removes the enumerated list’s silent failures on commands nobody named.  The upper bound on safety is a full pre-emptive copy of the working directory before every command, which recovers everything and is unusable in practice; it establishes what the minimal-plan computation must justify itself against on cost.  That cost is measured, not asserted: on this study’s ext4 evaluation machine, the cheapest real version of a pre-emptive snapshot — a Timeshift-style hardlink snapshot via rsync -a --link-dest, what a filesystem with no native snapshot falls back to — was timed against a working directory of 1,165 real files (580 MB).  A snapshot taken when nothing had changed since the last one, or when exactly one file had, took 60–250 ms, because deciding what to hardlink means visiting every entry in the tree regardless of what changed; the capture plan for a comparable single-file command took 0–20 ms, set by what the command touches rather than by the size of the directory around it (pilot/snapshot_bench.txt).  A copy-on-write filesystem such as btrfs or XFS would close most of this gap, since it would not need to visit every file either; on ext4, the filesystem this study is conducted on, it does not.

Because the first baseline was written by the same team, it was checked against command-safety checks that others ship.  Two open-source checks were scored on the same held-out corpus and labels reported in (d) below: the dangerous-command check of OpenAI’s Codex CLI [32], ported from its source and verified against that source’s own unit tests, and cc-safety-net [21], a pre-execution guard used with several agentic coding tools, run unmodified under each of its three presets, all three reported in (d).  On the 325 commands that destroy files, they let between 73% and 97% run with no confirmation and no capture, against 31% for the enumerated-pattern classifier, and neither makes any provision for recovery.  Both are designed for coding agents working inside a version-controlled project, where deleting project files is routine and version control is the safeguard, so these figures describe how they would serve a person’s own files, not how well they serve their intended purpose.  The first baseline is therefore the strictest enumerated list tested, and comparisons against it understate rather than overstate the analysis’s advantage over lists in current use.  No shipping tool was found that determines a command’s effects before it runs in order to capture what it would destroy; on recovery there is no external counterpart, which is the gap identified in Chapter 2, Section 2.5.  Their results are reported in (d) beside the others.

c) Statistical Comparison Against Baseline

The analysis and each baseline are scored against the same labeled corpus, which makes every comparison paired rather than independent: for each command, each system either lets it run silently or does not, and either covers a loss or does not, and two systems’ outcomes on that one command are not independent of each other.  Significance is therefore tested with McNemar’s exact test on the resulting 2×2 table of discordant pairs — commands one system handles correctly and the other does not — at α = 0.05, rather than with a two-sample test that would treat the corpus as though two different sets of commands had been drawn.

Silent loss is the safety measure (Table 3.3) and is reported on its own rather than folded into an accuracy figure: it is tested over the 405 commands that lose something or act outside the filesystem, the only commands on which it is defined, with a 95% Wilson confidence interval on each system’s rate; capture coverage is tested over the 325 executable losses.  For the analysis, the false-negative rate of Table 3.3 coincides with silent loss, because a command it judges recoverable runs without being asked about.  The Wilson interval is used rather than the normal approximation because silent loss is expected to be low for the stronger systems, and the normal approximation is unreliable near the boundary of a proportion — the exact regime this metric sits in.

A significance test states only whether the two methods differ, not by how much, so each comparison is paired with an effect size — the paired-data equivalent of the Cohen’s d reported for the user study (§3.5(d)).  The primary measure is the risk difference: the algorithm’s accuracy minus the baseline’s, with a Newcombe-adjusted 95% confidence interval built for paired proportions, reported for silent loss and for capture coverage.  The odds ratio from the same 2×2 discordant-pairs table is reported alongside it, since it is the effect-size convention most directly tied to McNemar’s test itself and lets the result be compared against other paired-classifier studies that report it in preference to a risk difference.

With three baselines and two primary metrics, the comparisons that carry a claim are the analysis against each of the first two baselines on silent loss and on capture coverage.  Four tests share one family, so significance is judged with a Holm correction at a family-wise α = 0.05, and the uncorrected values are reported beside the corrected ones.  The full-snapshot baseline is a bound on cost and safety, not a comparison of accuracy, and is reported descriptively.  The remaining metrics of Table 3.3 are reported where they arise: needless confirmation in (d) and Section 3.2; recovery success as the share of executed commands the undo restored exactly, in (d); storage overhead from the recovery check, where the median capture over the 304 commands that captured anything was 0% of a full copy of the fixture, because most captures are hardlinks; time overhead against the snapshot baseline in (a); and the contribution of composition and resolution through the ablations in Section 3.2.  The open-source checks are compared with the analysis on silent loss by McNemar’s exact test and reported with Wilson intervals, outside the Holm family because they are a check on the first baseline rather than a primary comparison.  Needless confirmation is tested as a second family of its own: the analysis against the pattern list and against the fail-closed list, under each policy, with McNemar’s exact test and a Holm correction across the four.

d) Results on the Held-Out Corpus

The procedure above has been run on the prototype, so that the proposal rests on a measurement and not only on a design.  Four corpora were generated from different seeds, numbered rounds 4 to 7 after the prototype’s earlier evaluation rounds, each drawn after fixing what the recovery check on the one before it exposed: development (round 4: 778 commands, seed 20260922), a round that drove the recovery check and led to fixing two undo defects (round 5: 772 commands, seed 20260923), a round whose recovery check found five further undo defects — a hard link left in place after it should have been removed, the backup files sed and mv make with a suffix option, cp --parents, and a resolver for Perl’s rename that this was the first corpus to exercise — and fixing them (round 6: 776 commands, seed 20260924), and the corpus reported below (round 7: 777 commands, seed 20260925: 450 from NL2Bash, 247 from templates, 80 external; 325 executable losses), drawn after the analysis and the undo were both frozen, with the analyzer’s hash and the corpus’s hash recorded, and run once.  The figures below are from that corpus; the earlier three are development corpora.  Testing after this run, by rule-by-rule unit tests, a property test, and two rounds of mutation testing, found five further defects in the analyzer, and the review of this chapter found a sixth and a seventh: a find or a directory removal after an earlier change to the same tree on one line, and a line read as if every part succeeded, so that a part that runs only after an earlier one failed, as on the right of ||, was analyzed as if it had not.  No command in this corpus met the conditions that trigger them; all have been fixed, and re-running the corpus with the fixed analyzer changed none of its decisions under any configuration compared.

On it the enumerated-pattern classifier let 167 of the 405 commands that lose something or act outside the filesystem run with no confirmation and no capture (41.2%, 95% Wilson interval 36.5–46.1%).  Neither the fail-closed list nor the effect analysis let any through (0.0%, interval 0.0–0.9%).  The fail-closed list asked on every one of the 325 executable losses and captured nothing for any of them, and asked on 101 of the 372 commands that lose nothing (27%).  The analysis asked on 45 of those 372 under the strict policy (12%) and 32 under the capture policy (9%); the pattern list asked on 30 (8%).  Capture coverage below is the same under both policies, which differ only in whether the user is asked; the ablations in Section 3.2 are read under the capture policy.  On needless confirmation the analysis asks far less than the fail-closed list under either policy (McNemar’s exact test, Holm-adjusted p = 2.3×10−18 under the capture policy and 9.5×10−15 under the strict one), but not less than the pattern list: under the capture policy it asks about 32 commands to the list’s 30 (adjusted p = 0.89), and under the strict policy 45 (adjusted p = 0.13).  RQ4’s third part is therefore answered yes against the fail-closed list and no against the pattern list: the analysis is not shown to ask more often than the list, and in exchange lets nothing run silently that the list lets through.  These figures score the analysis alone.  The deployed gate also consults the pattern list and asks when either does (Section 2.1(e)); scored that way, it asks about 58 of the 372 harmless commands under the capture policy (15.6%) and 67 under the strict policy (18.0%), still well below the fail-closed list’s 101, and still lets no destructive command run silently.  The analysis-in-use measures of Section 3.5(e) score the deployed gate.

The two open-source checks were scored on the 325 commands that destroy files and the 372 that lose nothing.  Codex CLI’s check let 314 of the 325 run without asking (96.6%, Wilson interval 94.0–98.1%) and asked about 1 of the 372 harmless commands (0.3%); cc-safety-net let 262 through under its standard preset (80.6%, 76.0–84.5%), 257 under its strict preset (79.1%, 74.3–83.1%), and 236 under its paranoid preset (72.6%, 67.5–77.2%), asking about 7, 12, and 15 harmless commands (1.9%, 3.2%, and 4.0%).  Neither makes any capture, so their capture coverage is zero.  Against each, the analysis’s advantage on silent loss is significant beyond any reasonable correction (McNemar’s exact test, p < 10−70, since every discordant command favors the analysis).  On needless confirmation the answer to RQ4 against these checks is no: the analysis asks about 32 to 45 harmless commands to their 1 to 15, which is the cost of letting no destructive command through where they let 73% to 97% through.

Capture coverage, the second primary measure, counts a command as covered only if the analysis planned a capture and the undo then restored the tree exactly, checked by executing the command in the sandbox, applying the undo the runtime would apply, and comparing the tree.  By that measure the analysis covered 291 of the 325 executable losses (89.5%, interval 85.7–92.4%), the pattern list 135 (41.5%, 36.3–47.0%), and the fail-closed list none.  The pattern list’s captures were not executed, so its 135 counts every loss it planned a capture for as restored, an upper bound that makes the comparison in Table 3.4 conservative toward the list.  The 34 losses the analysis did not cover it asked about: 9 run code in an interpreter or through awk’s system(), 8 run a program it does not model, 5 depend on a variable with no value, 4 are shred, 4 feed xargs from a here-string, 2 are a find -exec gzip writing inside the tree it searches, 1 removes its own working directory, and 1 is rsync over ssh.  Across all 631 commands that were executed and that the analysis did not refuse, the undo restored 630 exactly (99.8%).  The one that failed is rsync -ur dir_a dir_b && rsync -ur dir_b dir_a: the second call copies a directory the first call’s own output had just nested inside it, one level deeper than the analysis re-resolves; it is reported, not fixed (docs/open-problems.md).

The pooled figures hold within each partition.  On the 150 losses among the human-written NL2Bash commands the analysis let none through silently and covered 133 (88.7%); on the 175 among the templates, written by the same team as its rule table, it let none through and covered 158 (90.3%).  The pattern list let 40% of the NL2Bash losses, 23% of the template losses, and 84% of the 80 external commands run silently.  Under the capture policy the analysis asked needlessly on 8% of the harmless NL2Bash commands and 10% of the harmless templates.  By command shape, of the 405 commands that lose something or act outside the filesystem, the pattern list let through silently 4 of the 34 compound lines, 5 of the 29 hidden effects, 53 of the 164 commands with run-time targets, 37 of the 85 plain commands, 1 of the 13 redirections, and 67 of the 80 external commands; the analysis let none through in any shape, and the 34 file-destroying commands it asked about without a capture are 6 compound lines, 8 hidden effects, 15 with run-time targets, and 5 plain commands.  The same figures for every system are provided as supplementary material.

Four limits apply.  The remaining commands the analysis asked on without capturing are mostly ones it cannot see into — an interpreter or an unknown program, a variable with no value in the fixture, a privileged command whose targets it declines to resolve, and shred — and it asks on these by construction.  A large share of NL2Bash candidates are excluded because they name paths or programs the fixture cannot supply, which biases that partition toward commands that run on a small tree.  The external partition is assigned by a table of state-changing tools and not observed, so its labels are only as good as the table, as the model-generated partition’s one error shows.  And the model-generated partition’s commands were generated in round 6, before the analyzer was frozen; re-scoring them with the final analyzer changed no decision, but they were not drawn after the freeze.

e) Threats Specific to This Evaluation

Four are anticipated.  First, corpus bias is addressed by partitioning, as described in Section 1.2(a).  Second, oracle validity replaces label subjectivity: the labels are observed, so they cannot be argued with, but they are facts about one command on one small fixture, run for a few seconds, seeing the working tree and not repository internals.  A loss that appears only on a differently shaped tree, or after the time limit, is labeled by what happened here.  The oracle’s own behavior is pinned by unit tests over commands whose outcome is known, its exclusions are reported, and the bias they introduce — toward commands that run on a small fixture, which excludes most NL2Bash candidates that name paths or hosts the fixture cannot supply — is stated and not corrected.  Third, the algorithm and the labels are produced by the same research team, which creates a risk that the labels reflect the algorithm’s assumptions; the generator is independent of the analysis by construction, and the corpus is fixed by a recorded seed and hash before the analysis is run on it.  A fourth threat follows from the same fact: the analysis rests on a table of what each known command does, written by the same team, and a table written with the corpus in view measures the cases its author anticipated.  The corpus is therefore generated from several seeds.  Earlier ones are used to correct the analysis and the undo; the primary result is reported on one drawn after both are frozen, with the analyzer’s hash recorded beside the result.  That result is a single draw, so variation from one corpus draw to another is not estimated; the development rounds, drawn from different seeds before the design was frozen, showed the same pattern (zero silent loss for the analysis and capture coverage near 90%), but they were not independent of the design and are not offered as replication.  Nor does the corpus verify the package and service part of the model: the oracle can write only inside a fixture, so no command in the corpus changes installed packages or running services under observation, and the inverse plans for such changes are checked by the prototype’s unit tests rather than by execution.

3.2 Ablation studies (Objective 5)

Chapter 1, Section 1.5 states the analysis’s claim as what it adds on top of a table of what each known command does, not that it has none — a distinction raised directly by this study’s adviser: how much of the result above comes from the algorithm itself, and how much from that table?  The algorithm adds two things a table cannot do, and RQ5 asks for the contribution of each.  Composition analyses through the commands that hide another command’s targets: wrappers (sudo, env, nohup, timeout, and similarly transparent commands), find -exec/-execdir/-ok/-okdir, xargs, eval, shell -c strings, and for-loops.  Runtime-target resolution learns targets that exist only while a command runs, by running a form of it first proven read-only: command substitution and the producer feeding xargs, the rewritten find expression, and the dry runs of tar, unzip, rsync, rename, git, and the package and service tools.  Three further configurations of the analyzer are run over the identical held-out corpus, each identical to the one scored above except for what it disables: composition, routed straight to the unresolved verdict an unknown command receives; resolution, with no runner, so that every target it would have learned is unresolved; and both, which leaves the per-command rule table alone.  Every other dispatch path is untouched, including the &&/pipe/subshell traversal that requires no lookup beyond the table.  If the table is where the result comes from, disabling either should cost little.

Each costs a great deal (Table 3.5).  Capture coverage, verified by the same sandboxed recovery check as the primary result, falls from 291 of 325 executable losses (89.5%) to 115 (35.4%) without composition, to 148 (45.5%) without resolution, and to 104 (32.0%) without both.  McNemar’s exact test on the paired discordant items rejects equality overwhelmingly in each case, and not one discordant item favors an ablated configuration over the full one: 176 items without composition, 143 without resolution, and 187 without both.  Silent loss is unchanged at 0.0% in every configuration, because the fail-closed default that the analysis falls back to for anything it cannot resolve depends on neither — a command it can no longer see through, or whose targets it can no longer learn, is treated exactly as an unknown command already is, which asks rather than runs silently.  Composition and resolution are therefore not what keep the analysis safe; the table and the fail-closed default already do that, which is why Table 3.4 found the analysis indistinguishable from the fail-closed list on silent loss.  They are what make the analysis useful — the difference between asking about nearly everything and actually recovering what was lost — and that is the part a table, however complete, cannot supply on its own.

The two depend on each other.  Neither alone recovers much more than the table: composition without resolution reaches 45.5% and resolution without composition 35.4%, against 32.0% for the table, while the two together reach 89.5%.  Of the 143 items lost when resolution is disabled, 126 involve find (58 with -exec, 47 feeding xargs, 12 with -delete, and 9 in substitutions or archive commands), 6 are other xargs pipelines, 5 are rsync, 4 are git, and 2 are plain command substitutions: composition can see that find -exec rm removes each match, but only resolution can say which files match.  The two also differ in what they cost the user.  Without composition the analysis asks needlessly about 246 of the 372 commands that lose nothing (66%), because every wrapper and find becomes an unknown command; without resolution it asks about 70 (19%), because it still sees what kind of command it faces and only the targets are unknown; the full analysis asks about 32 (9%).

3.3 Validation study: evaluation dataset

Sections 3.3 to 3.7 define the validation study, in which the analysis is deployed in SynapseOS and exercised by participants.  It exercises the platform on two task datasets: the OSWorld benchmark task suite [50] for direct comparison with results in the existing literature, and the custom cross-platform task suite described in Sections 1.1 and 1.5.  The user study evaluation involves 40 participants (20 novice, 20 power users); the baseline condition is each participant’s primary operating system — Windows 11, macOS, or Linux with GNOME desktop — on a dedicated baseline machine.

3.4 Validation study: evaluation profile

The study employs a within-subjects design with two conditions:

  • Condition A: SynapseOS (conversational interface layer on the Debian 13 evaluation machine)
  • Condition B: Participant’s primary operating system (Windows 11, macOS, or Linux with GNOME desktop, as determined by pre-study screening, on the dedicated baseline machine)

All 40 participants complete both conditions.  Condition order is counterbalanced: 20 participants complete Condition A first, and 20 participants complete Condition B first.  Condition order is crossed with the two task forms in a 2×2 design, four groups of ten (Section 1.2(d)).  This distributes order effects across conditions; residual asymmetric transfer is tested through the condition × order term of the model in Section 3.6 and discussed in Section 3.7.

The two participant groups — novice users and power users — are analyzed both in aggregate and separately to determine whether the effect of the interface condition differs across experience levels.  Additionally, primary OS (Windows, macOS, Linux) is recorded as a secondary grouping variable to determine whether results vary across participant backgrounds, and prior conversational AI exposure (frequency of use) is recorded as a covariate to determine whether familiarity with LLM-based tools correlates with SynapseOS performance independent of OS proficiency.  For the platform measures, the main analysis is the pooled within-subjects comparison across all 40 participants; per-OS subgroup analyses and AI-exposure correlations are treated as exploratory given the smaller per-group sample sizes they entail.

3.5 Validation study: criteria and formula

The following metrics and formulas are used in the validation study.  Items (a) to (d) characterize the platform against each participant’s baseline; item (e) validates the analysis in use.

a) Task Completion Time

Mean task completion time is computed per condition per participant group.  Inferential testing and effect size reporting follow the procedures described in Section 3.6.

b) Error Rate

Error rate is computed as the proportion of tasks presented that end in failure or an incorrect outcome:

Error Rate = (Failed Tasks + Incorrect Outcomes) / Tasks Presented

Error events are further categorized by type: intent parsing errors (incorrect bash command generated), execution errors (bash subprocess failure), and recovery failures (an undo that does not restore the prior state).  Retries are recorded separately as attempts and do not change the rate, whose denominator is the number of tasks presented, not attempted (Section 2.2).  Its difference between conditions is tested by the logistic mixed model of Section 3.6.

c) User Satisfaction

SUS scores are computed per the standard scoring procedure [5] to produce a score on a 0–100 scale; a score above 68 is conventionally treated as above-average usability, a benchmark drawn from scores across a large sample of studies [40].  NASA-TLX scores are computed as the unweighted mean of the six subscale ratings [15] to produce a composite workload score per participant per condition.  Because a conversational interface is meant to widen access rather than only to save time, workload and task success are weighted alongside completion time among the platform measures, not treated as secondary to it.

Qualitative interview data is analyzed using thematic analysis to identify recurring themes in participant perceptions of both conditions.

d) Statistical Significance and Effect Size

All platform comparisons between conditions are tested at α = 0.05.  Effect size is reported using Cohen’s d, with thresholds of 0.2 (small), 0.5 (medium), and 0.8 (large).  Sample size is justified by an a priori power analysis for a paired-samples comparison at α = 0.05, two-tailed, computed against the noncentral t distribution.  Detecting a medium effect (d = 0.5) at 80% power requires 34 participants; the 40-participant sample provides approximately 87% power at that effect size and detects effects down to d = 0.45, giving margin for attrition and for exclusions arising from the screening rule in Section 1.4.  Analyzed alone, each 20-participant subgroup detects effects of d = 0.66 or larger.  The condition × group interaction, which characterizes whether the platform serves the two groups differently, remains the least-powered comparison in the design, since an interaction of a given size requires substantially more participants than a main effect of the same size; it is therefore reported with effect sizes and confidence intervals as the main descriptive finding for the platform, and is not treated as a confirmatory significance test.  The sample size is set by these platform comparisons; the analysis-in-use measures of (e) are descriptive and need no power analysis.

e) Analysis Decisions in Use

Every command executed during the SynapseOS condition is logged with the analysis’s verdict and capture plan and with a snapshot of the task directory taken immediately before it ran (Section 1.1(d)), replayed on a copy of that snapshot in the sandbox, and labeled exactly as the corpus is (Section 1.2(b)).  It is then scored with the corpus measures: silent loss in use, the proportion of data-losing commands that ran without confirmation and without a capture; restoration in use, the proportion of data-losing commands whose capture, applied by undo, restored the fixture exactly; and needless confirmation in use, the proportion of commands that lose nothing on which the participant was nonetheless asked.  Each undo a participant invokes is also checked against the state before the command it reverts.  A command that changes installed packages or running services, which a directory snapshot cannot hold, is scored instead by recording the affected packages’ versions and the services’ active and enabled states before it runs and checking them after undo.  These are the measures by which the platform validates the analysis: a silent loss here would be a failure of the analysis on a command people actually cause, which the corpus could not reveal.

f) Benchmark Task Success

For the adapted OSWorld tasks, the platform’s task success rate is the proportion of tasks whose resulting system state matches the benchmark’s expected outcome, of the tasks attempted.  The adapted subset, the OSWorld tasks expressible as shell commands, is fixed before data collection and its size reported with the result.

3.6 Validation study: data analysis plan

The analysis-in-use measures of Section 3.5(e) are reported descriptively, as proportions with Wilson 95% intervals over the commands executed, and set beside the corpus results of Section 3.1; they are not tested for significance, because the number and kind of commands participants cause cannot be fixed in advance.  Quantitative analysis of the platform measures proceeds in three stages.  First, descriptive statistics — means, standard deviations, and 95% confidence intervals — are computed for all platform measures (task completion time, error rate, SUS score, NASA-TLX score) per condition and per participant group.  Second, the Shapiro-Wilk test is applied to assess normality of each distribution before selecting the appropriate inferential test: the paired-samples t-test for normally distributed data, or the Wilcoxon signed-rank test for non-normally distributed data.  Third, effect size is computed for all primary comparisons regardless of statistical significance: Cohen’s d where the paired-samples t-test is applied, and the matched-pairs rank-biserial correlation where the Wilcoxon signed-rank test is applied.

Subgroup analysis is conducted separately for the novice and power user groups to determine whether the effect of the interface condition differs across populations.  The interaction between interface condition and user group is examined to assess whether SynapseOS produces differential effects depending on technical background.  Because condition order and task form are crossed between subjects (Section 1.2(d)), each platform measure is modeled with condition, group, order, and task form as fixed effects and crossed random intercepts for participant and task: error, which is binary per task, by a logistic mixed model; completion time by a linear mixed model on its logarithm; and the SUS and NASA-TLX scores, which are taken once per condition, by a linear mixed model with a random intercept for participant, from which the condition × group and condition × order interactions are read.  The condition term of each of these models is the confirmatory test for its measure, with Holm’s correction across the four; the paired tests above are sensitivity checks, and the power analysis, computed for a paired t-test, approximates the power of the condition term.

The benchmark task success rate of Section 3.5(f) is reported descriptively, as a proportion with its Wilson interval, as are the telemetry measures of Section 1.1(d) that are not otherwise analyzed (command latency and conversational turns per task), as means with confidence intervals per participant group.

Qualitative data from post-study interviews is analyzed using reflexive thematic analysis following the six-phase procedure described by Braun and Clarke [3]: familiarization with the data, initial code generation, theme search, theme review, theme definition, and write-up.  In keeping with the reflexive approach, which treats the analyst’s interpretation as part of the method and does not compute inter-rater agreement, one member of the research team develops the codes and themes; the codebook and the excerpts that support each theme are retained so that the analysis can be audited.  Themes are reported alongside representative participant quotations.

3.7 Validation study: threats to validity

The following threats to validity are identified and the mitigations applied in this study are described.

Internal validity:

  • Learning effect and asymmetric transfer: Participants may perform better on the second condition through familiarity rather than interface quality, and counterbalancing alone does not resolve this: it redistributes carryover but only cancels it when transfer is symmetric, which cannot be assumed here, since having solved a task once confers a different advantage in each direction. Mitigation: parallel task forms matched on category, difficulty, and step count are crossed with condition order in a 2×2 design, so no participant meets the same task twice; task order within a form is randomized; and condition order is entered as a between-subjects factor in the analysis, with the condition × order interaction inspected so that residual transfer is measured rather than presumed absent.
  • Demand characteristics: Participants may behave differently from natural use because they know they are being observed. Mitigation: participants are instructed to complete tasks as they naturally would; the specific hypotheses of the study are withheld until the post-study debrief to reduce social desirability bias.
  • Fatigue: Completing the full task set twice in a single session may degrade performance in the second condition independent of interface quality. Mitigation: a short break is offered between conditions and total session length is bounded to approximately 120 minutes.
  • Fallback reliance: GUI mode provides a participant-accessible fallback to the underlying XFCE session if SynapseOS becomes unresponsive or a participant wishes to stop using it mid-task; unrestricted, this would let a participant’s own choice substitute for the interface under evaluation, confounding the within-subjects comparison. Mitigation: every fallback invocation is logged with participant ID, task ID, and timestamp; any task during which it is invoked is excluded from the primary completion-time and error-rate comparison for that task rather than counted as a SynapseOS success, and fallback-invocation rate is reported separately as an exploratory reliability metric.
  • Single scorer and analyst: task outcomes on the native-OS condition, and the qualitative themes, are judged by one team member, so their reliability cannot be checked against a second judgment.  The rubric is fixed before data collection and applied identically to both conditions, the SynapseOS condition is additionally checked by script, and the codebook and supporting excerpts are retained for audit, but a residual scorer effect remains and is not estimated.
  • Too few data-losing commands: participants may cause few commands that destroy anything, which would leave the analysis-in-use measures of Section 3.5(e) with small denominators. Mitigation: the task suite is reviewed before the pilot to include tasks whose natural solutions delete, move, or overwrite files, and every analysis-in-use proportion is reported with its denominator and Wilson interval, however small.
  • Unscoped undo: the undo command reverts the most recent entry in the undo log, even one recorded in another directory or an earlier session.  The manual verification (Section 2.3) showed that after a task whose only destructive step was declined, undo proposed reverting an unrelated earlier change.  Undo previews what it will revert and requires confirmation, but a participant who confirms without reading the preview could revert the wrong change, which would confound the undo measures the validation study reports.  Mitigation: before data collection, undo will either be restricted to the current directory and session or the log will be reset at the start of each session; every undo invocation, and the entry it reverted, is logged.

External validity:

  • Sample generalizability: The study uses a university-recruited sample of 40 participants across three primary OS backgrounds (Windows, macOS, Linux), which limits direct generalization to the broader population of computer users.  Findings should be interpreted as indicative rather than definitive; replication with larger and more diverse samples is recommended as a direction for future work.
  • Task generalizability: The evaluation is bounded by OSWorld coverage and the custom task suite developed for this study.  Computing workflows outside this coverage are not evaluated, and results may not extend to all possible use cases.
  • Platform specificity: SynapseOS is evaluated on a single hardware and software configuration — a dedicated machine running SynapseOS in GUI mode (XFCE desktop environment, X11 session) on a Debian 13 (Trixie) base.  Performance characteristics on different hardware, display configurations, or Linux distributions may differ from the reported results.

APPENDIX B

APPENDIX C
Custom Cross-Platform Task Suite

The suite comprises sixteen tasks in two parts.  Twelve core tasks span the four categories defined in Section 1.5 at three difficulty levels, and constitute the main platform comparison.  Four boundary tasks deliberately fall outside what a shell-mediated interface can express; they are administered and scored but reported separately from the main comparison, because their purpose is to characterize the capability boundary honestly rather than to contribute to the between-condition contrast.  Omitting them would leave the suite composed only of work the command line does well, which would make any favourable result difficult to defend.

Every task exists in two parallel forms, matched on category, difficulty, and number of required steps, and differing only in target.  No participant encounters the same form twice; form and condition order are crossed as described in Section 2.4.  All prompts are phrased as human goals in plain language, containing no shell syntax, no command names, and no interface-specific vocabulary, so that they are equally answerable through natural language on SynapseOS and through native tools on the baseline machine.

Tasks T7–T9 require identical provisioning on all study machines — the same designated applications present or absent, and the two test applications (SampleApp, DemoTool) installed — so that the prompt means the same thing under both conditions and on all three baseline operating systems; this provisioning is part of the facilitator checklist in Appendix G.  Task T9 is classified irreversible and is included specifically to exercise the confirmation gate; T11 mutates file content and is included to exercise the undo journal.  Difficulty is assigned by the number of distinct operations required and the specificity of the target, and is validated during the pilot study described in Section 2.3.

Participant Information Sheet

Study title. Recoverability Analysis of Language-Model-Generated Shell Commands, Deployed in the SynapseOS Conversational Interface

Who is running this study. This research is conducted by undergraduate researchers in the Department of Computer Science, Mapúa University – Makati, in partial fulfilment of the requirements for the degree of Bachelor of Science in Computer Science.  It will be carried out only after review and approval by the University’s Institutional Review Board.  Contact details for the research team and for the ethics committee are given at the end of this sheet.

Why we are doing this. Most of what a computer can do is reachable only by people who know how to write commands for it.  We have built a system that lets a person say what they want in ordinary language — for example, “find the files I changed last week and put them in one folder” — and carries it out.  We want to find out whether that is genuinely easier to use than the desktop you already use, and whether it makes more difference for people who have never used a command line.

What you would do. You would attend one session of about 90 to 120 minutes.  You would complete a set of everyday computer tasks twice: once using our system, and once using the operating system you normally use, on a computer we provide.  Which one you start with is decided in advance and is not a test of you.  Afterwards you would fill in two short questionnaires about each interface and take part in a 10 to 15 minute conversation about your experience, during which we may replay the screen recording and ask what you were thinking at particular moments.

What we record. We record what happens on the screen during the tasks, audio of the closing conversation, your questionnaire answers, and the times and outcomes of the tasks.  We do not record your name against any of this.  Everything is filed under a code.

What could go wrong, and what protects you. The instructions you give will cause real commands to run, and some commands can delete or change files.  You will be working on a laboratory computer prepared for this study, holding only made-up practice files.  You will not use your own device and will not sign in to any of your own accounts, so none of your own data is involved at any point.  Each machine is reset to a clean state between participants.  Some people find working under observation and a timer uncomfortable, or feel frustrated when a task does not go well.  We are evaluating the interface, not you, and you may pause or stop at any moment without giving a reason.

Benefits. There is no direct benefit to you.  The findings are intended to inform how conversational interfaces to computers are designed, particularly for people without technical training.

How your information is handled. Your data is processed under Republic Act No. 10173, the Data Privacy Act of 2012, on the basis of your written consent.  It is stored under a code rather than your name, on password-protected university infrastructure that only the research team can reach.  Screen recordings and audio cannot be made fully anonymous — a voice identifies a person, and a screen can show file names — so we keep them only as long as we need them for analysis.  They are destroyed once transcription and coding are complete, and in any case no later than ninety days after the last session.  The list linking your code to your signed consent form is kept separately and destroyed when the withdrawal window below closes, fourteen days after your last session.

Withdrawing. You may stop the session at any point, without explanation and without any consequence.  You may also ask us to delete your data for up to fourteen days afterwards; we keep the code-to-consent list for exactly that period so that we can find and remove your records if you ask.  After fourteen days that list is destroyed and we can no longer identify which records are yours, so withdrawal is not possible beyond that point.

How the results are used. Results are reported in aggregate in a thesis and possibly in academic publications.  We may quote short remarks you make in the closing conversation.  Quotations are attributed only to a participant code and a group label, never to your name, and you can decline to be quoted while still taking part in everything else.

APPENDIX G
Session Facilitator Checklist

Followed identically for every participant so that session conduct does not vary across the sample.  Items marked † must be completed before the participant arrives.

Before the session †

  1. Restore both machines to the clean baseline image; confirm no data remains from the previous participant.
  2. Boot the baseline machine into the operating system matching the participant’s screening record (Windows, macOS, or Linux with GNOME).
  3. Provision the task environment identically on both machines: practice file set in place, the applications referenced by tasks T7–T9 present or absent as specified, and the test applications SampleApp and DemoTool installed.
  4. On the SynapseOS machine, confirm the inference server is running and the model is loaded, and run one throwaway task to confirm the system responds.
  5. Confirm screen recording works on both machines and has free storage for the full session.
  6. Lay out the printed task prompt sheet for the assigned form, the two questionnaire sets, the information sheet, and the consent form.
  7. Record which interface mode SynapseOS is running in for this session, per the readiness checkpoint in the System Environment Specifications.

During the session

  1. Give the information sheet, answer questions, obtain signed consent.  File the consent form separately from all study materials.
  2. Give the five-minute orientation to the assigned first condition.  Use the same wording for every participant; do not demonstrate any task from the task set.
  3. Start screen recording.  Present tasks one at a time in the randomized order for this participant.  Do not prompt, hint, or answer questions about how to accomplish a task.
  4. Do not ask the participant to think aloud during timed tasks.
  5. Record the outcome of each task and note any facilitator intervention, with the reason.
  6. Administer SUS and NASA-TLX immediately on completing the condition, before any discussion of it.
  7. Offer a short break.  Move to the second machine and repeat from step 3 with the other task form.
  8. Conduct the closing conversation, replaying portions of the screen recording to prompt recall.  Ask what the participant was thinking, not whether they liked the system.
  9. Debrief: explain the study’s expectations in full, answer questions, and thank the participant.

After the session

  1. Transfer all recordings and logs to protected storage under the participant code; delete local copies from both machines.
  2. Log any fallback invocation, with participant code, task, and timestamp.
  3. Note any deviation from this checklist, however small, for reporting with the results.
  4. Restore both machines to the clean baseline image.
  5. Diarise the participant’s fourteen-day withdrawal deadline.
