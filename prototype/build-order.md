## Overview

This is the authoritative build sequence for the SynapseOS prototype: the order in which runtime features are built, what each milestone depends on, and the concrete condition that marks it done. It is the *gating* layer that the other docs do not provide — `../docs/scope.md` lists everything that must exist but not in what order, and `../docs/decisions.md` explains why each piece is shaped the way it is. Each milestone is an independently runnable vertical slice, not a horizontal layer, so the prototype works end-to-end at every step rather than only at the end. Milestones are sequenced risk-first: the least certain assumptions are tested earliest, and the highest-effort deferrable work (LoRA fine-tuning) is last, because earlier milestones tell us how much of it is actually needed. The `README.md` status table is the at-a-glance view; this file is the detail behind it.

## Sequencing Principles

- **Vertical slices.** Every milestone runs end-to-end. No milestone is a layer that only pays off later.
- **Risk-first.** The most uncertain assumption is retired earliest (M1: does a 3B model produce usable bash at all?).
- **Runtime before pipeline.** The Go runtime is built against the *stock* model first. Fine-tuning is deferred until its payoff is measurable.
- **Telemetry is not an afterthought.** The session logger (M7) is treated as load-bearing — it is the study's entire dataset — not bolted on before the study.
- **Foundations before features (added Session 22).** Safety/correctness infrastructure — classifier coverage, the undo safety net, the test suite that verifies both — is cheapest to build while the execution surface is still small (CLI mode alone) and gets *more* expensive every layer built on top of it. Extending the "telemetry is not an afterthought" principle: neither is safety hardening. The Foundational Hardening track (F1–F5, below) was pulled forward ahead of M4 for this reason, not sequenced by milestone number — which is also why this file is ordered by what happened rather than numerically.
- **Done means testable.** A milestone is done only when its definition-of-done can be demonstrated, not when the code exists.
- **Every milestone ends with a manual test suite (added Session 28).** `manual-tests/` holds one hands-on walkthrough per milestone — created as that milestone's final step, after the automated tests pass, so the person who actually has to trust the milestone can verify it themselves in a terminal rather than take a status write-up on faith. Scoped to golden path plus human-only edge cases — never exhaustive, that's the automated suite's job — and opens with a short summary of what's already machine-verified. One file per milestone (`m1-cli-mode-and-undo-safety-net.md` — M1 + Foundational Hardening F1–F5; `m4-persistent-loop.md` — M4; `m5-tui-mode.md` — M5; `m6-session-context.md` — M6), not one giant combined doc, so a suite stays scoped to what its milestone actually added.

### M1 — CLI mode: propose, classify, execute ✅

- **Goal:** Prove the riskiest assumption before building anything around it — can a local 3B model turn plain-English intent into usable bash? Then make CLI mode a genuinely complete, useful interface on its own (D19), not just a proof-of-concept that TUI later supersedes: propose a command, classify it as reversible/irreversible, auto-run it if safe, ask for confirmation if not. **Revised 2026-07-12:** this milestone absorbed the core logic originally scoped as separate M2/M3 milestones (whose entries follow immediately, placed beside the work that absorbed them rather than at their numeric position) — execution and the confirmation gate don't need a TUI to exist, and CLI mode isn't a real interface mode until it can actually do things, not just print suggestions. M3 (TUI) now depends on this being fully done, not just the walking-skeleton half of it. **Reopened 2026-07-12 (D21):** single-command execution left tasks that inherently need several distinct actions unaddressed; the ad-hoc path now runs a bounded, gated multi-step loop instead of exactly one command — see D21 for the full reasoning, including why full autonomy was considered and rejected.
- **Delivers:**
  - `internal/ollama` client (non-streaming generate + connectivity check) — **done, validated live and covered by automated tests** (`client_test.go`, 9 tests against `httptest`, 90.6% coverage — request shape, response decoding, non-200/malformed-body/unreachable-server/cancelled-context error paths, Session 21)
  - `cmd/synapse` harness: sample task suite (propose-only, for quality-eyeballing — deliberately does not auto-execute against the real filesystem) and an ad-hoc single-task path (`synapse "<task>"`) that proposes, classifies, confirms, and executes — **done, validated live and covered by automated tests** (`loop_test.go`, 9 tests, orchestration core `runLoop` at 88.2% coverage — multi-step reversible execution, irreversible block/decline/confirm, per-step re-gating, step-cap reporting, `UNSUPPORTED`/`DONE` handling, propose-time errors, Session 21)
  - `internal/classifier`: reversibility classifier that pattern-matches a proposed command against known-irreversible shapes (`rm`, `dd`, `mkfs`, `shred`, `git reset --hard`, `git clean -f`, truncating redirects); reversible commands auto-run, irreversible ones print the command and reason and block on an explicit y/n before running — **done, 100% test coverage**
  - `internal/executor`: `os/exec` subprocess dispatch (`sh -c`) with stdout/stderr capture and exit-code surfacing — **done, 100% test coverage**
  - Bounded multi-step loop (D21): after each executed command, its result (stdout/stderr/exit code) is fed back to the model, which proposes the next command toward the same task or signals completion; every step is independently classified and gated, no batch approval; a hard step cap prevents runaway iteration — **done, validated live and covered by automated tests** (see `loop_test.go` above, in particular the per-step re-gating case verifying a reversible first step never exempts a later irreversible step from confirmation)
- **Closes (`../docs/scope.md`):** *Ollama connectivity check*; *Intent parser client* (non-streaming); *CLI mode*; *Bash execution engine*; *Confirmation gate*.
- **Depends on:** Ollama installed, `qwen2.5-coder:3b` pulled.
- **Done when:** `go run ./cmd/synapse` prints a proposed command for all sample tasks (✅ demonstrated); `synapse "<task>"` proposes a command, classifies it, auto-runs reversible commands and shows their output, and blocks irreversible commands on confirmation before running them (✅ demonstrated live, all three paths, and regression-tested against a scripted mock server, Session 21); a downed server prints an actionable error instead of a stack trace (✅, via `client.Ping`, unit-tested); a genuinely multi-step task (requiring more than one command) completes correctly through the bounded loop, with every step individually gated and a step-limit case reported honestly rather than silently truncated (✅ demonstrated live 2026-07-12, and unit-tested Session 21).
- **Status:** Complete, including the bounded multi-step loop (D21), validated live 2026-07-12 and backed by automated regression tests as of Session 21 (`go test ./...`: `classifier` 100%, `executor` 100%, `ollama` 90.6%, `cmd/synapse` 63.0% overall / 88.2% on the orchestration core). Model-output quality (does the 3B model propose *correct* commands) remains a live-eyeball/future-accuracy-evaluator concern, not something unit tests can or should assert — see the "Risk retired" notes below.
- **Risk retired:** Model viability at the 3B budget — the single largest empirical unknown in the whole runtime. **Retired 2026-07-12**, confirmed live against `qwen2.5-coder:3b`. Two findings from the first live run: (1) `cleanCommand` only stripped triple-backtick fences, not inline single backticks — 3 of 8 outputs came back wrapped in single backticks; **fixed** the same day (handles both fence styles, unit-tested). (2) At least one command was plausible but semantically wrong (`dpkg-query -Wf` piped through a `grep` pattern that only matches `dpkg -l`'s different output format) — a model-accuracy limitation, not a code bug, and exactly the kind of failure the eventual study is designed to measure; left as-is, not something M1's scope fixes.
- **Risk retired:** Whether the reversibility classifier's pattern-matching approach and one-shot CLI confirmation (print + block on stdin) are workable. **Retired 2026-07-12** — the three live runs above exercised auto-run, block-and-cancel, and block-and-confirm-then-run, all behaving as designed. The classifier's pattern list is intentionally small and named explicitly (see `internal/classifier`) rather than attempting full shell parsing; expanding it as new failure modes surface is expected, ordinary maintenance, not a reopened risk.
- **Risk retired (D21):** Whether the loop mechanism itself (propose → classify → confirm → execute → feed back → repeat) works. **Retired 2026-07-12** — a genuine multi-part task (create a folder, move matching files into it) completed correctly, with per-step gating firing on a chained `rm && ls` mid-loop, not just on the first proposal.
- **Risk not retired, and not expected to be by this milestone:** Whether the model reliably recognizes its own step failed. The same live session surfaced a case where a broken pipeline (`ls -lh` output piped into `cat`) still exited 0 — the shell's last-stage exit code masked the earlier failure — and the model declared `DONE` despite visible `cat: ... No such file or directory` lines in its own fed-back stderr. The loop mechanism behaved correctly (proposed, executed, fed back exactly what happened); the model's judgment on top of that context was wrong. This is a model-accuracy limitation in the same family as the `dpkg-query` finding above, not a defect in the loop — and further evidence for D21's case against full autonomy: if the model can't reliably tell its own step failed even when told, giving it more unsupervised steps compounds the risk rather than reducing it.
- **Process log:** `../docs/retrospective.md#sessions-1719-m2-built-from-scratch-first-live-validation-classifierexecutor-wiring-d21s-bounded-loop` — the actual build-from-zero story (first live Ollama run, the backtick-stripping and `dpkg-query` findings, D21's bounded-loop decision); `../docs/retrospective.md#sessions-2021-gitignore-privacy-rework-pr-shipping-ollama-clientloop-tests` for the regression-test build-out that got M1 to "test-covered," not just "run once live," afterward.

### F1 — Classifier content-mutation coverage ✅

- **Goal:** Close the gap between "known-deletion-shaped commands" (the original rule set) and "known-content-mutating commands" — both destroy data with no built-in undo, only the first kind was flagged.
- **Delivers:** New `internal/classifier` rules for `sed -i`/`--in-place`, `awk -i inplace`, `truncate`, and a dedicated `tee`-without-`-a`/`--append` check; 18 new test cases (destructive shapes correctly flagged, lookalikes like `grep -i` and `sed` without `-i` correctly left alone). **Done, 100% package coverage.**
- **Deliberately not closed:** `cp` onto an existing destination. Unlike the shapes above (destructive essentially every time they're invoked), `cp`'s destructiveness is conditional on the destination already existing, which a text-pattern classifier can't know. Blanket-flagging every `cp` would cost a confirmation keypress on the common, safe case far more often than it would catch real danger — documented in `internal/classifier/classifier.go` as a known, tracked gap rather than silently dropped. Properly closing it needs the classifier to consult filesystem state (see F4).
- **Closes:** Hardens *Confirmation gate* (`../docs/scope.md`) — no new scope item, a correctness fix to an existing one.
- **Process log:** `../docs/retrospective.md#session-22-manual-m2-testing-classifier-gap-undo-log-doc-authority-shift` — the manual filesystem testing session that found this gap in the first place, and the "is this even tested, or just inspected" question it raised.

### F2 — Mechanical undo log (CLI mode) ✅

- **Goal:** Build undo as early as possible, while the execution surface is still just CLI mode's `runLoop` — cheaper now than after TUI/GUI/session-context add more execution paths it would need to hook into. Decouples the *mechanism* (works today, on M1 alone) from the *study telemetry integration* (still genuinely needs M7 — see the narrowed M7 below).
- **Delivers:** `internal/undo` — snapshots the working directory before/after each auto-run reversible step, diffs what appeared vs. disappeared, and pairs paths by basename to reconstruct moves (handles the flagship `mkdir dest && mv *.log dest` shape correctly, including one level of recursion into newly created directories). Pure creations (`touch`, `mkdir`, `cp`-to-new-path) are undone by removal; disappearances with no matching arrival are left unhandled rather than guessed at, since this package keeps no content backup and irreversible-classified commands (already gated separately) are out of scope by design. Journal persisted to `~/.synapse/undo.log` (JSON lines) so it survives CLI mode's one-shot, cold-process lifecycle. New `synapse undo` subcommand: peeks the last entry, shows what it would do, confirms, then applies — declining leaves the entry in place for a later attempt. **Done** — 10 unit tests in `internal/undo` plus a `cmd/synapse` integration test confirming `runLoop` wires it correctly.
- **Known limitation:** shallow, one-level-deep snapshot — a command that moves files more than one directory level away from where they started won't be correctly paired, and is recorded as unhandled rather than mishandled.
- **Closes:** The mechanical half of *Undo log* (`../docs/scope.md`) — restoring prior state for a reversible operation now works. The telemetry half (logging `undo_invoked` events) is M7, unchanged, still gated on M7.
- **Defect found and fixed after this item was marked done (Session 28 review):** `synapse undo` was gated behind `main()`'s unconditional Ollama connectivity check, so the entire undo mechanism — pure filesystem state, no model involvement — refused to run whenever the model backend was unreachable. That is precisely backwards for a safety net: the scenario undo exists for (a destructive command already ran) is highly likely to coincide with a crashed/stopped Ollama or a rebooted machine. Verified concretely, not inferred. Fixed by dispatching model-free subcommands ahead of the connectivity check. It survived every earlier session's testing because manual testing always had Ollama running.
- **Process log:** `../docs/retrospective.md#session-22-manual-m2-testing-classifier-gap-undo-log-doc-authority-shift` — includes the destructive-then-confirm ordering bug caught before shipping (`PeekLastJournal` vs. `PopLastJournal`) and the deliberate scope boundary drawn around directory-diffing before it turned into an open-ended parsing project. `../docs/retrospective.md#session-28-m3b-started-toolchain-skeleton-and-a-review-that-found-a-real-safety-defect` for the connectivity-gating defect above.

### F3 — Rigorous engine test suite ✅

- **Goal:** Answer "is the engine foolproof" with more than a fixed example list — see the testing-plan write-up (Session 22) for the full design: an adversarial classifier corpus organized by danger category (not just today's known shapes), a live task-corpus harness that checks the *model's actual output distribution* against the classifier rather than hand-picked examples, and executor edge-case coverage (timeouts, huge/binary output, hung processes). Must be **model-parameterized** — the same corpus runs against any `SYNAPSE_MODEL` value, not hardcoded to `qwen2.5-coder:3b`, specifically so reliability findings can be checked against 5B/7B variants and separated from "is this a 3B-only problem."

- **Depends on:** F1 (the corpus includes everything F1 found, generalized into categories) — satisfied.

### F4 — Typed-operation reliability experiment ✅

- **Goal:** The empirical question behind "should SynapseOS reimplement filesystem-MCP-style typed operations instead of raw bash for file tasks" — does `qwen2.5-coder:3b` (and, per F3, other sizes) reliably emit structured tool calls via Ollama's native tool-calling API? Unverified, not assumed either way.
- **Delivers, done (Session 25):** `internal/typedops` (5 typed file operations — `find_files`/`move_files`/`delete_files`/`rename_files`/`copy_file` — dispatched via Go's own `os`/`io`, no MCP/Node) and `cmd/synapse/layer4_test.go` (`-tags live`), comparing the raw-bash path against the typed-op path on the same file-manipulation task set. **Real result, not assumed:** Ollama's native `tool_calls` field never populated for `qwen2.5-coder`, 3B or 7B (0/20 across the full matrix) — confirmed via `internal/ollama.Chat`, not inferred from docs — so the typed path relies on a hand-parsed freeform-JSON fallback. Typed-op path hit 100%/100% call-validity/task-success on both models; raw-bash hit 100%/100% on 7B but 80%/60% on 3B, including one real missing-system-dependency failure (`rename` not installed) the typed path structurally can't have.
- **Verdict (per this item's own "not decided in advance" framing):** adopt typed operations for the bounded, high-value file-manipulation subset — not a full rewrite of `internal/classifier`/`internal/executor`, and not "not worth it." `internal/typedops` exists but is **not wired into `runLoop`** — this experiment answered the architecture question; actually switching the runtime's default file-task path onto it is unscoped future work, not part of F4's done-when.
- **Depends on:** F3's harness (reused its model-parameterization and scoring) — satisfied.
- **Scope note:** even with a "yes, for file manipulation" verdict, this only ever covers the file-manipulation subset of D7's committed scope (package management, process control, arbitrary CLI tools stay on the raw-bash path) — additive hardening for the highest-value subset, not a replacement for the general execution path.
- **Process log:** `../docs/retrospective.md#sessions-2326-foundational-hardening-adversarial-classifier-corpus-live-model-testing-typed-ops-experiment-guiltless-undo-hardening` — includes the verified-not-assumed finding that Ollama's native tool-calling API never populated `tool_calls` for this model.

### F5 — Guiltless undo hardening: content-backup, trash, and beyond ✅

**Added 2026-08-26 (Session 24), not originally scoped as its own item** — grew out of a user-driven design principle set mid-F3/F4 ("accurate and guiltless": the classifier should minimize real mistakes *and* make even a wrongly confirmed "yes" as recoverable as possible), then kept expanding as each new mechanism made the next gap in the undo taxonomy obvious. Numbered F5 rather than folded into F3/F4 since it's a distinct capability (a third leg alongside "is the classifier accurate" and "is the typed path viable"), not a test-coverage exercise.

- **Goal:** F2's directory-diff undo only ever covered Reversible commands. Extend undo coverage to confirmed Irreversible commands wherever a bounded, nameable target exists to protect — closing the gap between "the classifier correctly blocked this" and "the user can recover from having said yes anyway."
- **Delivers, all done (Sessions 24–26), four mechanisms matched to what each command shape actually changes:**
  - **Content backup** (`undo.BackupContent`, D23) — full copy of a file about to be mutated in place: `sed -i`, `awk -i inplace`, `truncate`, a truncating redirect, `tee` w/o `-a`, `cp` onto an existing destination, and `dd`/`mkfs` onto an existing regular file (D25). `cp`'s in-place-overwrite behavior was verified empirically (inode number unchanged after overwrite), not assumed.
  - **Trash** (`undo.TrashPreserve`, D24) — a hardlink into `~/.synapse/trash` for pure deletions (`rm`), extended to `git clean -f` via a `git clean -n` dry-run (D25). Cost independent of file size, unlike a content copy, since removing a directory entry never touches the underlying data.
  - **Metadata backup** (`undo.BackupMetadata`, D25) — mode/uid/gid per file for a confirmed recursive `chmod`/`chown`.
  - **Git-reset undo** (`undo.CaptureGitHead`, D25) — the pre-reset commit SHA for a confirmed `git reset --hard`; no file-level backup at all.
  - `internal/executor` gained `RunIn(ctx, dir, cmd)` (Session 26) so `internal/undo` could invoke `git` in a specific repository directory regardless of the calling process's cwd — its first subprocess dependency.
  - `docs/safety-model.md` (new) is the taxonomy reference this item produced: every classified shape mapped to its undo mechanism (or documented lack of one) and why.
- **Depends on:** F1 (the classifier rules each mechanism hooks into).
- **Scope boundary, deliberate:** `dd`/`mkfs` onto a raw block device, `shred`, `eval`, process-kill (`pkill`/`fuser -k`/dynamic kill), and fetch/decode-exec remain undoable by none of the four mechanisms — each fails structurally (no bounded target, or a target that isn't filesystem state at all), not because building their undo was skipped. See `docs/safety-model.md` for the full reasoning per shape.
- **Process log:** `../docs/retrospective.md#sessions-2326-foundational-hardening-adversarial-classifier-corpus-live-model-testing-typed-ops-experiment-guiltless-undo-hardening` — includes the empirical `cp`-overwrite inode test that ruled out hardlinking as unsafe for that shape before any trash code was written, plus the permissions/`MkdirAll`/missing-display-line blockers hit while building the four mechanisms.

### M4 — Persistent CLI loop (interim) ✅

**Added 2026-08-21 (split from the original single TUI milestone, numbered M3 at the time):** the TUI milestone as originally scoped bundled two independent risks into one — whether a *persistent, multi-turn session* actually works, and whether the *bubbletea/lipgloss rendering layer* is worth the investment. Jumping straight from M1's one-shot `synapse "<task>"` (a fresh process per command, no memory) to a full-screen streaming TUI is a large leap to take in one step, and a failure in either risk would be hard to attribute to the right cause. M4 retires the session-lifecycle risk alone, cheaply: `runLoop` (Session 21's testable extraction of the M1 loop core) already takes its I/O and confirmation prompt as parameters, so wrapping it in a `for` loop that reads one line of stdin at a time — instead of exiting after one task — is a small, almost entirely reuse-driven change, not a new subsystem. **This is not a fourth interface mode and does not touch the paper** — decision D19 already commits the thesis to exactly three modes (CLI/TUI/GUI); M4 is an internal build checkpoint on the way to TUI mode (M5), not something `interface-modes.md` or the submitted proposal needs to describe separately. If M5 slips, M4 is not a fallback deliverable to ship in its place. **Done as of Session 27** (2026-08-28) — brought forward ahead of its numbered turn at the human tester's request, since it directly lowers the friction of every manual test pass described in `manual-tests/m1-cli-mode-and-undo-safety-net.md`. Manually testable via its own dedicated suite, `manual-tests/m4-persistent-loop.md` — created as this milestone's final step, per the same one-suite-per-milestone convention that file started.

- **Goal:** Prove that a persistent, multi-turn session — plain stdin/stdout, no rendering — actually works before spending effort on the TUI framework itself.
- **Delivers:** `runREPL` (`cmd/synapse/main.go`) — a loop, invoked via the new `synapse repl` subcommand, that reads one line of input at a time and runs each through the existing `runLoop(ctx, client, model, task, confirmFn, out, errOut, journalPath)` in the same long-running process, instead of one process per invocation. Plain `fmt.Println` output — no bubbletea, no styling, no scrollback, no token streaming. Exits cleanly on EOF (Ctrl+D) or an explicit `exit`/`quit`, including the edge case of a final task typed with no trailing newline before EOF. A task that fails (propose error, `UNSUPPORTED`, step limit, declined confirmation) does not end the session — the whole point of the persistent loop is that one bad task doesn't force a restart to try another. **Done, 100% coverage on `runREPL`** (`cmd/synapse/repl_test.go`, 8 tests).
- **The actual risk, retired and verified, not assumed:** a persistent loop reads task lines from stdin *and* every confirmation prompt a task's irreversible step raises must read from that same stream — two independent `bufio.Reader`s wrapping one `io.Reader` would let one silently steal input meant for the other (`bufio.Reader` reads ahead into its own buffer on first use). Fixed by threading one shared reader through both the task-read loop and `confirm` (which now takes `r *bufio.Reader, out io.Writer` instead of reaching for `os.Stdin`/`os.Stdout` directly — the same testable-parameters pattern as `runLoop`). Verified two ways: `TestRunREPLSharesOneReaderBetweenTasksAndConfirmations`/`TestRunREPLDeclinedConfirmationDoesNotLeakIntoNextTask` interleave a task, its y/n answer, and a second task on one scripted input stream exactly as a real terminal session would produce them; and, per this project's verify-before-trusting-your-own-fix norm, the fix was mutation-tested by hand — swapping the shared reader back out for a fresh `bufio.NewReader(in)` per confirmation call reliably failed the interleaving test (the "y" gets swallowed into the throwaway reader's buffer and is never seen), confirming the test actually catches the regression it claims to, not just a coincidental pass.
- **Closes:** Nothing in `../docs/scope.md` on its own — *Conversational TUI* and the streaming half of *Intent parser client* remain M5's to close. This milestone exists purely to de-risk M5, not to satisfy a deliverable.
- **Depends on:** M1 fully complete (unchanged from the original TUI-milestone dependency) — and, per the sequencing principle above, Foundational Hardening F1–F5 complete as of Session 26.
- **Done when:** A user can issue several distinct tasks in a row without the process restarting, each one still going through the same classify/confirm/execute path already unit-tested in Session 21, and can exit cleanly. **Met** — see `TestRunREPLProcessesMultipleTasksInOneProcess`, `TestRunREPLExitsCleanlyOnExitCommand`, `TestRunREPLExitsCleanlyOnEOF`.
- **Risk retired:** Persistent-session lifecycle — does multi-turn interaction in one process actually behave correctly (state carried correctly between iterations, no leaked confirmation state, clean exit) — isolated from any rendering or streaming concern.
- **Scope gap found and closed after this item was marked done (Session 28 review):** no signal handling existed anywhere, which was harmless while CLI mode was one-shot (Ctrl+C killed a process that was exiting anyway) but became a real defect the moment M4 made the process long-lived — Ctrl+C during a task destroyed the whole session, exactly what this milestone exists to preserve, and with `stepExecutionTimeout` at 120s a single hung command could hold a session with no escape short of killing everything. Closed by `runTaskInterruptibly`: per-task `signal.Notify`/`Stop` with a watcher goroutine cancelling only that task's context, so Ctrl+C mid-task returns to the prompt with the session intact, while Ctrl+C at an idle prompt keeps default terminate-the-process behavior (handlers are installed per task and torn down immediately after, deliberately, so the idle case doesn't get silently swallowed). Mutation-verified: disabling the watcher makes `TestRunREPLInterruptCancelsTaskButKeepsSessionAlive` hang and fail rather than pass. One limitation accepted and documented in code rather than hidden — an interrupt arriving while a `[y/N]` confirmation is blocked on stdin cancels the context but cannot interrupt the pending read, so nothing visible happens until the next Enter, which the gate then treats as "no" and fails closed (correct and safe, just not instant); fixing it properly would require moving the stdin read off the main goroutine, reintroducing the two-readers-over-one-stream hazard this milestone was built to eliminate.
- **Process log:** `../docs/retrospective.md#session-27-m4-persistent-cli-loop-then-numbered-m3a-try-itmd-iteration` — the shared-reader risk and its mutation-tested fix, plus the `try-it.md` iteration blockers (missing `-a` flag, `go build`'s silent-success confusion, `README.md` drift caught mid-pass).

### M5 — TUI rendering (bubbletea/lipgloss) ✅

- **Goal:** Layer the actual terminal UI onto M4's already-proven persistent loop, rather than building session lifecycle and rendering at the same time.
- **Delivers (all done, Session 28):** Full-screen bubbletea/lipgloss/bubbles interface — input box, a scrollable viewport for output, streamed token rendering — wired to the same `internal/ollama` client, reversibility classifier, and executor M1 delivers, wrapping M4's loop instead of reimplementing it. Upgrades the Ollama client to streaming. Nothing about classification, confirmation semantics, execution, or undo changes — M5 is presentation-layer only, decoupled from every safety-relevant decision, which is why it was sequenced after (not alongside) the milestones that actually retired those risks.
- **Verified technical baseline (Session 28, checked against Context7 + the real Go module proxy before and during implementation, not assumed from training data):** Charm has moved bubbletea, lipgloss, and bubbles to an actively-developed v2 line, currently at v2.0.9 / v2.0.6 / v2.2.1 respectively, well past beta/rc, not a preview. **The import path itself changed, not just the version** — `go get github.com/charmbracelet/bubbletea/v2` fails outright (`module declares its path as: charm.land/bubbletea/v2`); all three now live under `charm.land/{bubbletea,lipgloss,bubbles}/v2`. This wasn't visible in Context7's docs (which still show `github.com/charmbracelet/...` URLs) — only surfaced by actually running `go get` and reading the error, confirmed against the module proxy directly (`go list -m -json`). A real example of why "verify via the actual tool, not just the docs" matters even after a first documentation check. **v2 requires Go ≥ 1.25.0** (confirmed directly from the real v2 modules' own `go.mod`, not docs prose) — this repo's `prototype/go.mod` currently pins `go 1.24`, so adopting v2 means a one-line bump. Low-friction: `GOTOOLCHAIN=auto` (confirmed set) means `go build`/`go test` will fetch a compatible newer toolchain automatically the first time it's needed, no manual reinstall. **Decision: build against v2**, not the legacy v1 line (bubbletea v1.3.10 / lipgloss v1.1.0, still resolvable but no longer where Charm's active development is) — this is a from-scratch integration with no existing v1 code to migrate, so there's no cost to starting on the current major version, and it avoids inheriting a soon-to-be-legacy API on day one. Real breaking changes from the v1 API this repo's earlier docs (`stack.md`, this file) implicitly assumed: `Model.View()` now returns a `tea.View` struct, not a plain `string`; key messages are `tea.KeyPressMsg`, not `tea.KeyMsg`; `lipgloss.Style` is now a plain value type (`NewStyle()` returns `Style{}` directly) — the old `Renderer`/`NewRenderer()`/`ColorProfile()`/`SetColorProfile()` machinery is removed, color downsampling is handled by Bubble Tea v2 itself.
- **Build sequence — risk-isolated, same principle as F1–F5/M4 (retire the cheapest, most independent risk first):**
  1. **Toolchain bump alone, no feature code. ✅ Done (Session 28).** Bumped `prototype/go.mod` to `go 1.25`; `GOTOOLCHAIN=auto` fetched `go1.25.0` automatically on the next build, exactly as predicted. `go build ./... && go vet ./... && go test ./...` all passed with zero other changes.
  2. **Framework skeleton, no real logic wired in. ✅ Done (Session 28).** `internal/tui` — a bubbletea `Model` wrapping a `bubbles/v2/textinput`, no Ollama/classifier/executor wiring. Quits on `ctrl+c` only, **not** bare `q` (deliberately deviates from this plan's original "ctrl+c/q" wording — `q` needs to be regular typed text once a real task input is wired in, so binding it to quit would have been a live bug baked in from the start). `synapse tui` wired into `cmd/synapse/main.go` alongside `repl`/`undo`. 4 tests, using bubbletea's own documented `tea.WithInput`/`tea.WithOutput` pattern (bytes.Buffer, no real terminal) — confirmed as a real, current, working pattern by actually running it, not just citing the docs. **Two real findings, not a clean pass:** (a) `Model.Init()` returning `m.input.Focus()` compiled fine but was a genuine bug — `Init()` can only return a `Cmd`, never mutate the model the runtime actually holds, so focusing inside `Init()` silently discarded itself and every keystroke was ignored; caught by two failing tests (`TestBareQDoesNotQuit`, `TestTypedTextAccumulatesInInput` both showed an empty input value no matter what was typed), fixed by focusing at construction time in `NewModel()` instead, on the addressable local `textinput.Model` before it's ever wrapped. (b) The real compiled binary (`./bin/synapse tui`) cannot be smoke-tested by piping input the way `repl` was in M4 — a full-screen TUI genuinely needs a real attached TTY (`bubbletea: could not open TTY: open /dev/tty: no such device or address` when piped), confirmed as a real environment constraint, not a bug (`/dev/tty` exists on this machine; this sandboxed execution context just has no controlling terminal attached to it). This means the `manual-tests/` suite for M5, unlike M4's, cannot be supplemented with a live non-interactive run — genuine human-in-a-real-terminal testing is the only way to verify this end-to-end.
  3. **Wire in the existing loop, non-streaming first. ✅ Done (Session 28).** The confirmation gate is now UI state (block reason rendered inline, resolved by a keypress) instead of a blocking stdin read, and the whole flow runs on the existing blocking `client.Generate` with no streaming yet.
     - **Architecture, and the one decision that mattered here:** `runLoop` is synchronous and blocks mid-flight to ask a question; bubbletea's `Update` must never block. The obvious resolution — reimplement the loop as a TUI state machine — was rejected, because it would duplicate the safety-critical gating and is exactly what `../docs/interface-modes.md` warns against ("the moment mode-specific code starts reimplementing classification or execution, that's a sign the logic belongs back in the shared core"). Instead the *identical* `runLoop` is injected as a `tui.TaskRunner` and driven on its own goroutine, bridged by two channels: output flows in as messages via an `io.Writer` adapter, and its `confirmFn` publishes a confirmation request then blocks until `Update` — having rendered the prompt and taken a keypress — sends the verdict back. **Net effect: every reversibility verdict, confirmation gate, and undo-journal write in TUI mode is the same code CLI and REPL mode run, so gating cannot drift between interface modes.** `internal/tui` also stays free of any Ollama or filesystem dependency, which is what makes the whole UI testable with no model and no real commands.
     - **Deliberate divergence from the REPL, documented rather than papered over:** a `y` typed *before* the confirmation prompt renders is discarded, where the REPL's line-buffered stdin would have consumed it. That is the safer behavior and is kept on purpose — a pre-typed keystroke must never auto-approve a destructive command the user has not yet seen described — and is pinned by its own test so a future "fix" can't silently reintroduce type-ahead approval.
     - **Testing, and a real methodology finding:** the first test pass drove the whole program with scripted input bytes and was **inherently racy** — a running program consumes its input as fast as it can parse it, which races the task goroutine publishing the confirmation request, so the same tests passed and failed on timing rather than behavior (one confirmation test failed while its near-identical sibling passed). Rewritten to drive `Update` directly with constructed messages for the confirmation bridge and lifecycle, keeping full-program tests only where real terminal input parsing is genuinely the thing under test. Runtime dropped from ~11s of flaky to 0.05s deterministic. 20 tests, **95.2% coverage** (the remainder is `Run`, the real-terminal entrypoint, untestable without a TTY — see step 2's finding). Clean under `-race`, which matters here specifically because of the new goroutine/channel bridge. The fail-closed gate is mutation-verified: flipping the non-`y` branch to approve makes all four `TestConfirmationFailsClosed` subtests fail.
     - **Also fixed here:** `synapse tui` no longer prints the `model: …` banner into a screen the TUI is about to take over, and deliberately launches without an Ollama precheck — an unreachable backend surfaces as an ordinary error line inside the session, so a transient blip doesn't dump the user back to a bare shell.
  4. **Add streaming. ✅ Done (Session 28).** `internal/ollama.GenerateStream` — same endpoint and request shape as `Generate` (`POST /api/generate`) with `Stream: true`, invoking an `onToken` callback per fragment and returning the same `*GenerateResponse` type, so it is a drop-in substitute. The verified NDJSON wire format held up exactly as planned: a `json.Decoder` reads the object sequence natively, and the existing `GenerateResponse` struct decodes every chunk as-is, so no new type was needed.
     - **A safety property fell out of this that was not in the original plan.** A stream that ends without ever reporting `done: true` is rejected outright rather than returned as a short result. This is not strictness for its own sake: the returned text becomes a shell command, and truncation does not merely shorten it, it can *change* it into something far worse — a connection dropped partway through `rm -rf /home/user/tmp` yields the perfectly valid, catastrophically different `rm -rf /home`. Refusing to return partial text means a truncated generation can never reach the classifier or executor at all. Mutation-verified: removing the guard makes the truncation test report exactly that `rm -rf /home/user/tmp` fragment being handed back to the caller.
     - **Streaming is opt-in per mode, not global.** `runLoop` gained a variadic `loopOption` parameter (`withTokenStreaming(w)`) rather than a widened signature — chosen deliberately because a prior session's retrospective recorded that widening `runLoop`'s signature touched eight test call sites and was the expensive part of that change; the variadic form left every existing caller untouched. TUI mode passes the option; CLI and REPL do not, preserving the behavior `../docs/interface-modes.md` documents (CLI renders "once generation finishes"). A dedicated test pins that default so streaming can't silently become global.
     - **The command is still parsed from the fully assembled response, never from streamed fragments** — streaming changes only *when* text appears on screen, never what gets classified or executed.
     - 8 new client tests (progressive delivery verified with a real flushing `httptest` server, not a single buffered write; plus non-200, malformed chunk, empty stream, nil callback, and context cancellation) and 2 loop-level integration tests. `internal/ollama` at 89.4% coverage.
     - **Blocker worth recording:** the first cancellation test hung for the full test timeout — not in the code under test, but inside `httptest.Server.Close()`. A handler blocked on `r.Context().Done()` deadlocks `Close()`, because a server that never finished writing a response does not reliably observe the client's disconnect. Fixed with an explicit release channel whose `defer` is registered *after* `defer server.Close()`, so LIFO ordering unblocks the handler before `Close()` runs.
  5. **Scrollback and styling polish. ✅ Done (Session 28).** `bubbles/v2/viewport` for scrollable output, `lipgloss/v2` styling, alt-screen rendering, and the input width bound to the terminal.
     - **It was not purely cosmetic, which this step's own plan had assumed.** Scrollback carries a real correctness property: new output auto-scrolls only while the user is already at the bottom, and never while they have scrolled up to read. Yanking the view back mid-read would be worst exactly when it matters most — when someone has scrolled back to check what a command actually proposes before answering `y/N` on an irreversible step. For the same reason scroll keys stay live *during* a pending confirmation, and are explicitly proven not to count as an answer. Both properties are mutation-verified.
     - Styling is used to carry meaning rather than decoration: the confirmation prompt is the only bordered, colored element in the interface, so an irreversible-command gate can never be mistaken for ordinary output.
     - Sizing is driven by `WindowSizeMsg` with a `ready` guard, so nothing renders through a viewport sized from a guess before the real terminal dimensions arrive; viewport height is floored at 1 so a very short terminal cannot produce a zero or negative height.
     - 7 new tests. `internal/tui` at **96.3% coverage** (remainder is `Run`, the real-terminal entrypoint, untestable without a TTY), clean under `-race`.
- **Closes:** *Conversational TUI*; completes *Intent parser client* (streaming).
- **Depends on:** M4 done. (M1 fully complete is inherited transitively — M4 already depends on it.)
- **Done when:** A user types natural language, sees the proposed command render in-session, approved/auto-run commands execute with output shown in-session, can issue several turns in a row, and quits cleanly. **Met in code and covered by automated tests as of Session 28** — but note the honest caveat this milestone carries and the earlier ones did not: a full-screen TUI needs a real attached TTY, so no automated test and no assistant-run smoke test has ever exercised the compiled binary against an actual terminal. `manual-tests/m5-tui-mode.md` is therefore load-bearing here rather than confirmatory; the first real end-to-end run is a human's.
- **Risk retired:** Token-streaming feasibility and the bubbletea v2 interaction model specifically — with session-lifecycle risk already retired by M4, a problem found here is legible as a rendering problem, not a "did the loop even work" problem.

### M6 — Session context ✅

- **Goal:** Multi-turn memory, so a follow-up resolves against what just happened — "move it to Downloads" knows what *it* is. This is the milestone that turns the persistent session from a sequence of independent one-shots into an actual conversation.
- **Scope boundary:** REPL and TUI only. One-shot CLI mode stays stateless by design (D19) — that is what makes it scriptable, not a limitation to fix.

**What already exists, so M6 doesn't rebuild it:** `runLoop` already threads a `[]loopStep` history *within* a single task, and already truncates step output at `stepOutputChars`. The gap is only *across* tasks — each `runLoop` call starts with an empty history, so the previous task is invisible. M6 is therefore mostly about carrying and bounding that history between calls, not inventing a memory system.

**Prerequisite, and it is a live defect rather than new work (Session 29):** Ollama's default `num_ctx` is 2048 and it truncates prompts **silently** — measured, see D10's amendment. Nothing in the runtime sets `num_ctx` today, so the effective window is a quarter of what D10 assumed, and overflow raises no error at all. Current worst-case prompts (system prompt + task + 5 steps at `stepOutputChars`) land around ~1.5K tokens, so this is close to biting already; adding cross-task history would blow past it immediately and invisibly. **Step 1 below fixes this regardless of the rest of M6.**

- **Build sequence — risk-isolated, same principle as F1–F5/M4/M5:**
  1. **Set `num_ctx` explicitly, no other change. ✅ Done (Session 29).** `generationOptions()` is now the single place every model call gets its options, so `num_ctx` cannot be set on one path and silently omitted from another — which is exactly how the defect would come back. Default 8192 (4× the silent default, well short of the model's 32768 because the KV cache grows with it and the target is CPU-only), overridable via `SYNAPSE_NUM_CTX`, with an invalid value warning and falling back rather than failing the run. **Verified against the live server through our own client, not a mock:** the same oversized prompt went from `prompt_eval_count` 2050 to 5532. Three tests, including a wire-level one asserting `num_ctx` actually reaches the request body — a helper that builds the right map but is never wired in would pass a unit test and still leave every prompt truncated.
  2. **`internal/session` — the context type, pure and dependency-free. ✅ Done (Session 29).** `Context` holds completed turns (task text, commands, compact result notes) with `Append`, `Render`, `Summary`, `Clear`, and the rolling-window trim. No Ollama, no filesystem, no bubbletea — 98.1% coverage with no live anything.
     - **Token budgeting is measured, not guessed.** A 4-chars-per-token heuristic decides *before* sending; `Calibrate(promptChars, promptTokens)` then corrects the ratio from Ollama's own `prompt_eval_count`. That keeps the budget honest without shipping a tokenizer that would have to track the model, and implausible measurements are ignored rather than allowed to poison later estimates.
     - **Two invariants that carry real UX weight, both mutation-verified.** The newest turn is never evicted even if it alone busts the budget — a follow-up almost always refers to the turn immediately before it, so dropping that one would pay the full cost of keeping history while destroying its only reliable use. And evictions are *counted and reportable* (`TakeDropped`), because a rolling window that forgets invisibly is the worst failure mode available here: it looks exactly like the system working, right up until it inexplicably doesn't, with nothing to explain why.
     - Results are truncated harder than the in-task limit (200 vs 500 chars) on purpose: within a task, output is what the model reasons over; across tasks it only has to carry a referent, and every character spent is one unavailable to an older turn that might hold the actual one.
  3. **Wire into `runLoop` via a variadic `loopOption`. ✅ Done (Session 29).** `withSessionContext(*session.Context)`, the pattern `withTokenStreaming` established, for the same reason: no existing call site needed editing. Prior turns render ahead of the current task so the task reads as the most recent thing said, which is what lets a pronoun bind to the turn immediately above rather than something further back. Calibration feeds `prompt_eval_count` back after every generation.
     - **The turn is recorded on a `defer`, so every exit path is covered** — `DONE`, `UNSUPPORTED`, a declined confirmation, the step cap, a propose error, a cancelled context. A task that failed halfway still *did* whatever it did, and a follow-up ("undo that", "try again with sudo") needs to see it: a partial turn is memory, a missing one misrepresents what happened.
  4. **Wire into REPL and TUI, with the user-facing affordances. ✅ Done (Session 29).** Both modes get a session; one-shot CLI deliberately does not. `context` and `clear` are intercepted locally and never sent to the model — a user asking what is remembered needs the actual contents rather than a plausible-sounding generated answer, and `clear` must be reliable precisely because its job is being the escape hatch when memory has gone wrong. Both are also the deterministic reset points the manual suite needs.
     - **A real prompt-design bug that only the live run caught.** With history wired in, the follow-up "rename it to renamed.txt" returned `DONE` immediately: `loopSystemPrompt` told the model that already-run commands mean progress on the current task, so it read the *previous* task's steps as having already finished the *current* one. Every automated test passed — they assert the history reaches the prompt, not what the model concludes from it. Fixed by making the prompt name its two sections explicitly ("Earlier in this session" is background from finished tasks, usable only to resolve references and never as progress; "Steps already run" is the current task) plus an explicit rule that a task with no steps yet must never return `DONE`. Verified live afterward: the same follow-up now produces `mv notes.txt renamed.txt`, confirmed against the file on disk. **Lesson: a test that checks the prompt was assembled correctly says nothing about whether the model reads it correctly — prompt changes need a live check.**
  5. **Manual test suite. ✅ Done (Session 29).** `manual-tests/m6-session-context.md` — six steps centred on the one thing automation cannot check: whether the model actually *resolves* a reference, as opposed to whether the history was assembled into the prompt correctly. Also covers eviction being announced, `context`/`clear`, memory surviving a failed task, and one-shot CLI staying stateless.

- **Token budgeting — measure, don't estimate.** `GenerateResponse.PromptEvalCount` already reports exactly how many tokens the last prompt consumed, and is already decoded. That is a free, exact signal — no Go tokenizer needed, and strictly better than a chars-per-token heuristic. Use a cheap character estimate to decide *before* sending, then the measured count to correct the estimate's calibration afterward. Trim oldest turns first, per D10.

- **The UX decisions that make this "simplest yet most effective":**
  - **Dropping context must be visible.** A rolling window that silently forgets produces the worst possible failure mode — the system appears to work, then inexplicably doesn't remember something, and the user cannot tell why. One quiet line when turns are dropped costs nothing and converts a mystery into an explanation. This is the same principle as the silent-truncation defect above: the problem was never the truncation, it was the silence.
  - **The user needs a way to clear context.** If a follow-up resolves "it" against a stale turn, there must be an escape hatch that isn't "restart the session". A typed `clear` in both REPL and TUI, cheap to build, and it also gives a manual test a deterministic reset point.
  - **The user needs to see what is remembered.** A typed `context` that prints the retained turns compactly. Not a debug feature — the whole premise of pronoun resolution is that the user and the system agree on what "it" refers to, and this is the only way to check that agreement before issuing a destructive follow-up.
  - **Compact result notes, not raw output.** D10 already requires this; the point worth restating is *why* it is a UX decision and not just a budget one: a single `find /` dump would crowd out the earlier turns that actually carry the referent.

- **Explicitly not building** (all rejected in D10, restated so they don't creep back in): conversational summarization (a second inference call per compression event), persistence across sessions (storage, deletion UX, privacy surface), and any embedding/retrieval layer. The rolling window is sufficient at this scale, and simpler.

- **Closes:** *Session context manager* (`../docs/scope.md`).
- **Depends on:** M4 for session mechanics (not M5's rendering — the split exists precisely so M6 only needs the loop), and M1 for real command output to compress.
- **Done when:** "move it to Downloads" resolves *it* from the previous turn in both REPL and TUI; verbose output is never stored at full length; a long session stays under the configured ceiling with dropped turns reported rather than silent; `clear` and `context` both behave as described; and `prompt_eval_count` is confirmed to stay within the configured `num_ctx` across a long session rather than being silently clipped.
- **Risk retired:** Context overflow and pronoun/reference resolution — the two things that decide whether multi-turn actually works or merely appears to.

### F6 — Act on F4's typed-operation verdict ⬜

**Decision made 2026-09-20 — D33 (`../docs/decisions.md`): typed operations for file manipulation, generated bash for the rest. Implementation and the Chapter 3 statement are still open, so this stays ⬜. Nothing in `cmd/synapse` yet dispatches file manipulation through `internal/typedops`, and the confirmation gate and undo journal do not yet apply to typed calls.** The text below is the original framing and is kept as written.

**Added 2026-09-03 (Session 29), because a verdict with no owner is not a decision, it is a note.** F4 concluded "adopt typed operations for the bounded, high-value file-manipulation subset," and `internal/typedops` has existed and been tested since Session 25 — but it is not wired into `runLoop`, and the entry describing that gap called it "unscoped future work," which is where work goes to be forgotten. This item exists to force the choice rather than let it lapse by default.

- **Goal:** Decide, deliberately and on the record, whether the runtime's file-manipulation path runs on typed operations or stays on raw bash — then implement whichever is chosen.
- **This is a research-design decision before it is a build task, and that is why it needs its own item.** F4 measured raw bash at **80%/60%** call-validity/task-success on the 3B model against typed ops at **100%/100%**. The thesis measures task completion. Wiring typed ops would therefore improve the headline numbers — which is exactly why the choice has to be made openly rather than absorbed as an implementation detail. The honest framing is that these are two different systems being evaluated, not an optimisation:
  - *Raw bash* is the general system the thesis actually describes (D7: arbitrary CLI capability). Its failure modes — a missing system dependency, a wrong flag — are real properties of the approach, and measuring them is a legitimate finding rather than a defect to engineer around.
  - *Typed ops* is a narrower, more reliable system for one task category. Reporting its numbers as the system's numbers, without saying that file tasks took a different path, would misdescribe what was measured.
- **Whichever way it goes, it needs a decision entry** (`../docs/decisions.md`) recording the choice and the reasoning, and — if adopted — the paper must state plainly that file-manipulation tasks are dispatched through typed operations while other categories use generated bash. A silent split would be the worst outcome: better results with no account of why.
- **Deliberately not pre-decided here.** F4 was built specifically to answer this with evidence, and the evidence is in; what is missing is the call. Flagging the honest lean: the measured gap is large enough that ignoring it is hard to justify, and the transparency cost is a paragraph in Ch.3.
- **Depends on:** F4 (done — supplies the evidence).
- **Done when:** a decision entry exists, the runtime matches it, and Ch.3 describes whichever execution path the study actually runs on.

### M7 — Session logger ✅

- **Goal:** Capture the study's entire dataset — get it right well before the study, not the week before.
- **Delivers:** Structured per-event log emitting every telemetry field in `../docs/scope.md`: timestamp (ms), event type, command string, execution latency, task ID, participant ID, condition.
- **Also delivers (absorbed from the former M8, Session 29):** `synapse undo` emits an `undo_invoked` event through this logger on every application — successful, declined, or failed. A declined or failed undo is still a data point: "the participant tried to recover and could not" is precisely the kind of event the study needs to capture, and logging only successes would bias the record toward the system working.
- **Closes:** *Session logger*; *Telemetry fields logged per event*; the telemetry half of *Undo log* (the mechanical half is already closed by F2/F5).
- **Depends on:** M1 (there must be execution and confirmation-gate events to log), F2 (the undo mechanism whose invocations are logged).
- **Done when:** Every event type — `task_start`, `command_issued`, `command_result`, `confirmation_triggered`, `undo_invoked`, `task_end` — is written with all fields, and the output is parseable by the Python log parser.
- **Status:** Complete as of Session 31. `internal/telemetry` (83.3% coverage) plus `withTelemetry` wiring in `runLoop` and `runUndo`; all six event types verified end-to-end through the real loop, not by calling the logger directly, because the failure that matters is an emission site nobody wired.
- **Design notes:** JSON Lines rather than a JSON array, so a crash mid-session leaves every complete line parseable instead of one unclosed document. Every event is flushed as written — the study's data is irreplaceable and no interactive session needs the throughput that buffering would buy. A nil `*telemetry.Logger` is a valid no-op, which is what lets every emission site be unconditional; a branch at each call site is how an event eventually goes unlogged. `exit_code`, `latency_ms`, and `approved` are pointers because their zero values are all meaningful — a successful command exits 0, and `omitempty` on a plain int would have silently dropped the exit code of every success. Mutation-tested: reverting the pointer, dropping the confirmation emission, and logging only successful undos each fail a specific test.
- **Risk retired:** Data-completeness — a missing field means re-running 40 irreproducible participant sessions. **Retired Session 31**, subject to the pilot confirming the offline parser reads the format.

### M8 — GUI mode ⬜

- **Goal:** The study-facing interface for novice users (decision D11).
- **Delivers:** The existing TUI, launched fullscreen as the XFCE session, plus the participant-accessible fallback to the desktop beneath it.
- **Rescoped again 2026-09-12 (Session 31), and this is the larger of the two rescopes — D27.** SynapseOS is now an agentic layer *over* an ordinary XFCE desktop rather than a replacement for the desktop shell, session manager, and application launcher. That removes this milestone's remaining bespoke work entirely: there is no new rendering layer to build, because the TUI *is* the interface. What is left is session plumbing — an `.xsession`/session-manager entry that starts the TUI fullscreen, and the fallback that returns the participant to the XFCE session already running underneath. The user's desktop is not displaced, so the fallback stops being a crash-recovery mechanism and becomes ordinary window management. Estimated in days rather than the weeks the original entry implied.
- **Rescoped 2026-09-03 (Session 29) — this milestone got materially cheaper, and its entry did not know it.** It was written assuming GUI mode would wrap "the runtime built in M1, M4, M5, M6–M7," implying it inherits a pile of milestones and rebuilds a rendering layer on top. M5 changed that: TUI mode drives the execution loop through an injected `TaskRunner` (D26) rather than reimplementing it, and `internal/session` (M6) is an injectable value with no UI coupling. GUI mode therefore inherits the *same two seams* — inject a runner, inject a session — and the only genuinely new work is the window, the fullscreen X11 session plumbing, and the XFCE fallback. The safety gating, execution loop, undo mechanisms, streaming, and conversation memory all arrive for free and, more importantly, arrive *identically*, so a GUI-mode participant is running the same gated path a CLI user is. What remains is presentation and session plumbing, which is a smaller and much better-understood problem than the original entry implied. Also delivers the participant-accessible XFCE fallback (D20): logs every invocation as its own telemetry event type, separate from the six events M7 defines. TUI and CLI modes remain the server/remote and scripting targets respectively.
- **Closes:** *SynapseOS machine — GUI mode* (infrastructure); *GUI-mode XFCE fallback*.
- **Depends on:** M7 (the fallback must emit its own telemetry event, so the logger has to exist first) and the runtime seams M5/M6 established — the injected `TaskRunner` and the injectable session context. Corrected Session 29: the old list named M1/F2/M4/M5/M6–M7 as if each were a separate integration, which overstated the coupling. GUI mode consumes two interfaces, not seven milestones.
- **Done when:** The runtime runs fullscreen within an XFCE X11 session (not Wayland — XFCE's Wayland session remains experimental per D12) and is usable by a novice without terminal knowledge; TUI and CLI modes still work; the fallback reliably returns the participant to the XFCE session running beneath, and every invocation is captured in the session log.
- **Risk retired:** The novice-familiarity threat to study validity (a bare-terminal study would conflate terminal unfamiliarity with interface quality). The fallback's reliability is materially less risky under D27 than it was under D20's replacement framing — the desktop it falls back to was never taken away.

## Algorithm Track (A1–A3)
**Added 2026-09-12 (Session 31), in response to adviser feedback that the project has no identified algorithmic contribution.** `decisions.md` D29 records why recoverability analysis was chosen over the alternatives considered, and D34 (2026-09-20) narrows it to composition through wrappers and target resolution after a pilot showed the verdict alone was not what distinguished the approach; `../docs/algorithms.md` holds the full specification, including the evaluation design and the pilot. This track runs in parallel with Track B (ethics) and does not depend on IRB approval — which is the point of choosing a contribution that evaluates against a corpus rather than against participants.

**Briefly expanded to A1–A6 on 2026-09-14 and reverted the same day.** The expansion added milestones for risk-tiered gating and completion detection, following a revision to D29 that was itself withdrawn — see D29's revision note for why. The track is unchanged from its original scope.

### A1 — Command effect model and labelled corpus 🚧

**Scope narrowed 2026-09-20 (`decisions.md` D34):** the model has to support composition through wrappers and resolution of run-time targets, not verdicts for every command.

- **Goal:** Establish the formal object, and ground truth about it, before building anything that claims to compute it.
- **Delivers:** An **adopted** shell parser (`mvdan.cc/sh/v3`, bash dialect, with its word-expansion package; see `algorithms.md`'s adoption ledger); the effect model itself (kind, absolute target, `MovedTo` for renames and lossless compression, a `git-head` hint) with composition through `&&`/`||`/`;`, pipelines, subshells, blocks, conditionals, loops, redirects, command and process substitution, `sh -c`, `sudo` and its relatives, `xargs`, and `find -exec`/`-delete`, plus an overlay so earlier parts of a line are visible to later ones; a per-command rule table; and a labelled corpus of about 450 commands, stratified by command shape and effect kind, with **ground truth defined relative to a stated filesystem state for each command** (a fixture specification), a floor of unrecoverable-labelled commands per source, and recovery plans where they apply. Sources: NL2Bash (partition N), templates covering each shell operator and shape (partition T), and an external partition (E) that is never executed and is labelled unrecoverable by construction. From round 4 the labels are automated rather than hand-assigned: `internal/oracle` runs each command in a bubblewrap sandbox on its fixture and labels it from the tree diff (recoverable if nothing that existed was lost; otherwise not, where removed, overwritten, replaced, retargeted, and re-moded all count as loss, same-inode moves do not, and mtimes and `.git` internals are ignored), and `cmd/corpusgen` builds the corpora sharing no code with `internal/effects`.
- **Exists in code:** `internal/effects` (types, walker, expansion, rule table, wrappers, dry-run adapters, verdict and plan, the fail-closed baseline, a read-only resolver runner) with unit tests, all passing. A 74-command pilot corpus (`pilot/corpus.jsonl`, and `pilot/corpus2.jsonl` with per-command fixtures) exists, labelled by one annotator, and is the pilot in `algorithms.md`. The automated pipeline exists as `internal/oracle` and `cmd/corpusgen`, with `cmd/effexplain` for inspecting a disagreement; seed 20260922 gives the development corpus (`pilot/corpus4.jsonl`, `make corpus4`, `make round4`) and seed 20260923 is the held-out draw (`pilot/corpus5.jsonl`).
- **Does not exist:** the held-out result. There is no second annotator and none is needed: the hand-labelled corpus was the critical path, and replacing human labels with sandboxed execution removed it, at the cost of the inter-rater agreement statistic.
- **Done when:** the development and held-out corpora exist with per-command fixtures, and per-source partitions are preserved, since a corpus drawn partly from this prototype's own output is biased toward the shapes this model produces and must not be pooled with the generalisation set.
- **Risk retired:** that "recoverable" cannot be defined operationally. A defined, executable oracle answers it by construction; what it cannot show is that people agree with the definition, which is a scoped limitation rather than a retired risk. A second risk, found by the pilot: a state-aware analysis cannot be scored against state-free labels, so every command carries a fixture that fixes its state.

### A2 — Compositional recoverability analysis 🚧

- **Goal:** The contribution, and what RQ1 asks (D32), as narrowed by D34: composition through wrappers and resolution of run-time targets feeding a minimal capture plan. Not a verdict for every command; unknown commands fail closed.
- **Delivers:** Effect extraction per leaf command; propagation through the structure of the line; resolution of computed targets by read-only dry runs, each proven read-only by the analysis and run under a read-only sandbox where available; a verdict over the composed effect set; and a minimal capture plan mapped to the existing `internal/undo` mechanisms. Unknowns fail closed.
- **Exists in code:** all of the above in `internal/effects`, joined to the undo mechanisms by `internal/gate` and wired into `runLoop` in `cmd/synapse/analysis.go`. It is **on by default in strict mode**: `SYNAPSE_ANALYSIS=strict|capture|off` selects the policy, and `off` restores the pattern list alone. It was opt-in until 2026-09-20. The wiring is a union with the list (prompt if either would), so the analysis can add a confirmation and never remove one. Resolution of run-time targets runs only where a read-only sandbox (bubblewrap) is available unless `SYNAPSE_RESOLVE=always`; bubblewrap is a stated requirement of the evaluation and study machines. Four tests in `cmd/synapse/analysis_loop_test.go` drive the real loop with a scripted model.
Package and service state is modelled in `internal/effects/pkgstate.go`, which asks the system's own tools (`apt-get -s`, `dpkg-query`, `apt-cache policy`, `dpkg-deb -f`, `systemctl is-active`/`is-enabled`) what a command would do and derives an inverse command: install to purge (or remove if config remains), remove or purge to a versioned install if a repository still offers that version (otherwise unrecoverable), upgrade to downgrade, start and stop, enable and disable, mask to unmask (and enable), and `service NAME ACTION` mapped to `systemctl`. Purge also captures its conffiles as removals. `undo.Entry` carries `Inverses`; `Apply` runs them after trash and before content restore, with elevated privilege if the original had it, and prints the command if one fails.
- **Does not exist:** the held-out evaluation; modelling of maintainer scripts and service start-up side effects, network mutations, and other package managers (pip, npm, snap and the like), which stay unrecoverable unless plainly read-only; a decision on whether resolution should ever run without a sandbox beyond the `SYNAPSE_RESOLVE=always` override.
- **Depends on:** A1's corpus for evaluation, not for building. **Closes** the package-manager gap by modelling package and service state rather than only asking about it; process, account, and firewall state remain outside the model and always ask.
- **Done when:** it is wired behind the gate without weakening it, and on the held-out corpus it has no more silent losses than the fail-closed list, protects (captures) more of the commands that need it, and asks no more often. A held-out result, not the pilot's, is the bar.
- **Risk retired:** that static analysis over generated shell is intractable in practice. Mitigation if it proves so: narrow the operator set and report the coverage honestly rather than claim generality.

### A3 — Evaluation and write-up 🚧

- **Delivers:** The comparison against three systems and one bound: the current pattern list (L0), a list flipped to fail closed (L1), the effect analysis (ALG) under each gate policy, and a full working-directory snapshot as the trivial upper bound on safety. Metrics fixed in `algorithms.md` before any results existed: silent loss and false-negative reporting kept separate rather than folded into accuracy, **capture coverage** verified by sandboxed execute-and-diff, friction, storage/time overhead, and composition coverage. Two primary comparisons, so a Holm correction.
- **Exists in code:** `cmd/listpilot` runs L0, L1, and ALG over a corpus and writes one record per command per system; `pilot/analyze.py` scores them (silent loss, consent without undo, friction, per shape, with Wilson intervals); `make pilot` re-runs the round-2 pilot after checking the frozen corpus hash. The sandboxed execute-and-diff needed for capture coverage exists (`internal/recoverycheck`, `cmd/recoverycheck`, `make recoverycheck`, output in `pilot/recovery_results.txt`). Rounds 1, 2, 2b, and 3 are recorded in `algorithms.md`, and `make round4` scores the automated development corpus; a held-out round on the frozen analyser is pending. CI (`.github/workflows/ci.yml`) runs `make -C prototype ci` and `tools/claude-hardening/test-guard.sh` on every change. Dependencies for the eventual bootable image are inventoried and hoarded (`../distro/manifest.tsv`, `check.sh`, `hoard.sh`; `hoard/` is git-ignored), on the rule that existing tools are preferred over new code.
- **Does not exist:** a held-out evaluation result; McNemar and Holm computations; recovery-success verification over the whole automated corpus.
- **Done when:** the results chapter can be written without reference to the user study. That independence is the reason this contribution was chosen (D29) and is the whole of the answer to the reviewer's sixth question (D32). **Note:** §3.1 of the manuscript was two pages, which was not proportionate to a primary contribution; it has been extended with corpus sizing, baselines, and statistics, and the depth is still an outstanding deliverable until the results exist.

### V1 — End-to-end validation before the study ⬜

**Added 2026-09-03 (Session 29).** Four manual suites now exist (`manual-tests/`), created as each milestone's final step — and two of them have never been run. Every milestone verifies *itself*; nothing verifies that the assembled system works for a person sitting in front of it. That gap is invisible while building and unrecoverable once a participant is in the room.

- **Goal:** Establish that the whole runtime works end-to-end, by a human, before any of it is pointed at a participant.
- **Delivers:** A completed pass of every suite in `manual-tests/`, with findings recorded — including the ones that come back fine, since "ran it, it worked" is itself the evidence this milestone exists to produce.
- **Why this cannot be folded into the individual milestones:** each suite is scoped to what its own milestone added, deliberately, so none of them exercises a realistic session that crosses features — a task that streams, hits a confirmation, gets undone, and is then referred back to by a follow-up. Interactions between milestones are exactly where a system like this breaks, and no per-milestone suite is looking there.
- **Carries a known constraint, stated plainly:** TUI mode needs a real TTY, so no automated harness and no assistant-run smoke test can substitute for a person here. `m5-tui-mode.md` in particular has never been executed against a real terminal by anyone.
- **Depends on:** the milestones whose suites it runs. Best done once M7 exists, so a validation pass also confirms the telemetry the study depends on is actually being written.
- **Done when:** all four suites have been run by a human, findings are recorded, and anything found is either fixed or documented as a known limitation with a reason.
- **Risk retired:** That the system works milestone-by-milestone but not as a whole — the failure mode that only appears when features meet, and the one most likely to surface first in front of a participant.
